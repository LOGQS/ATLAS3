## Source Resolution
- Artifact/evidence/claim/observation/validation/critique content carried by blocks; this file defines higher-level identity+lifecycle where needed.
- Claim tracking is opt-in structured semantics, not an obligation to turn every sentence into a claim.
- Evidence links carry relation/confidence/provenance/applicability; balanced/conflicting evidence remains unresolved unless one side is stronger.
- Provenance derived from canonical graph of blocks/versions/runs/capability calls/ledger entries, not a parallel provenance store.
- Artifact materialization/export/external representation are projections of durable artifact identity, not the identity itself.

## 1. Chosen Model `artifact.chosen-model`
One entity layer for produced outputs (`Artifact`); one for first-class factual assertions (`Claim`); one substrate for support records (`Evidence` + `Citation` + `Observation` + `Validation` + `Critique`, all blocks per File 08); one derived query surface for provenance.
- significant produced outputs become `Artifact` entities (durable, versioned, materializable, validated, reviewable, citable, exportable). May be one inline object/one file/many files/composed bundle/dynamic product through a surface. Each `ArtifactVersion` is an `Artifact`-kind `Block` per [`block.kind-catalogue`, File 08 §3.1]; entity record adds stable cross-version identity.
- load-bearing assertions become `Claim` entities (durable, identifiable, status-tracked, evidence-linked, supersedable). The `Claim` block kind is a canonical extension to File 08 §3.1 catalogue declared here.
- support flows through `Evidence`/`Citation`/`Observation`/`Validation`/`Critique` blocks (canonical per File 08) + `EvidenceLink` typed-edge metadata declared here.
- causal chain back from any block/edge/version/artifact/claim to producing run/capability/route/intent thread/conversation/ledger entries is a queryable projection — `Provenance` — over existing substrates. No parallel provenance store.
No parallel artifact/claim/evidence registry, no parallel observation pool, no parallel provenance database. Every entity participates in unified `Block` pool [`block.chosen-model`, File 08 §1] + unified Capability Registry [`capability.chosen-model`, File 05 §1]; entity identity sits over those as a thin record layer where strictly required.
`Artifact` supersedes earlier vocabulary ("deliverable", "produced output", "generated file as entity", "work product", "drafts as named outputs", "artifact registry record"). `Claim` supersedes ("assertion", "factual statement entity", "knowledge claim", "grounded fact", "agent answer as record"). `Evidence`/`Citation`/`Observation`/`Validation`/`Critique` retain File 08 names. `Provenance` supersedes ("lineage record", "audit chain", "origin trace", "derivation history record"). "artifact" remains informal synonym for an `Artifact`-kind block when entity layer not load-bearing. Model elaborates [`core.artifact`, File 01 §4.3], [`core.evidence`, File 01 §4.4], [`core.evidence-provenance`, File 01 §7.12]; honors [`run.output-semantics`, File 04 §24] listing of artifact versions/claims/evidence links/validation reports among run outputs.

## 3. `Artifact` `artifact.artifact`
### 3.1 Definition
Durable, identifiable, versionable user-visible product persisting across edits/supersessions/validations/reviews while one+ `Artifact`-kind blocks carry content per version. Need not be a single file; may be inline object/one file/multiple files/composed bundle/generated report/dynamic product through sandbox or surface/non-visual reusable object. File materialization is one appearance shape, not identity. An `Artifact`: has stable `artifact_id` (survives version changes, edits, retitling, scope promotion, review-state changes); carries typed `ArtifactKind` (§4) from closed catalogue + `Custom { namespace, name }`; has default/latest version pointer for non-branch-specific reads while active surfaces resolve effective version through active `ContextVersion`; accumulates ordered version chain via `supersedes` closure from selected version block; has producing context — `producing_run_id`, `producing_task_id`, `producing_intent_thread_id`, `producing_conversation_id`, `producing_workspace_id` — captured at first-version commit; carries declared `MaterializationPolicy` + per-version `materialized_paths` (§10); carries review+validation policy defaults (effective review/lifecycle/validation derived per artifact version + per `ContextVersion` §5); is `scope`-bound [`block.block-scope`, File 08 §11] (cross-scope via `promotes_scope_of`/`scope_projection_of` edges [`block.canonical-edge-kinds`, File 08 §5.2]).
NOT: a `Block` (block = version content carrier; artifact = cross-version identity; trivial single-version artifact still has entity record, cost one row); a workspace file (files are one materialization shape per `MaterializationPolicy: InWorkspace`; identity doesn't require disk + may span multiple/no files); a transcript entry (transcripts may reference as children of `MessageAssistant` but identity independent); a UI element (same artifact rendered in conversation card/inspector pane/gallery thumbnail/comparison board/artifact viewer without changing it); a stored projection (entity record is source of truth for identity + cross-version metadata; materialized paths/retrieval indices/surface projections derived).
### 3.2 Required Fields
- `artifact_id` — globally stable; assigned at first version commit; never reused/reassigned/mutated
- `artifact_kind` — typed `ArtifactKind` (§4); declared at creation; immutable
- `title` — short user-visible; editable (edits create new sibling artifact-version block reflecting new title; denormalized title updates atomically with new version)
- `description` — short user-visible (distinct from per-version block-level description [`block.block-description`, File 08 §10]); summarizes artifact across versions
- `current_version_block_id` — default/latest `block_id` for non-branch-specific reads; branch-aware surfaces resolve current version through active `ContextVersion`
- `producing_run_id` — `run_id` of first-version commit; null when created outside a run (manual import, inspector apply outside run)
- `producing_task_id` — `task_id` of owning task; null otherwise
- `producing_intent_thread_id` — `intent_thread_id` of producing run's primary intent thread; null when committed outside conversation
- `producing_conversation_id` — `conversation_id`; null otherwise
- `producing_workspace_id` — workspace id when materialized into workspace; null when materialization `None`/external
- `materialization_policy` — closed enum (§10); declared at creation; mutable only through `artifact.update_materialization_policy`
- `scope` — broadest visibility scope [`block.block-scope`, File 08 §11]; declared at creation; mutable only through `artifact.promote_scope` (creates typed promotion record `promotes_scope_of` [`block.canonical-edge-kinds`, File 08 §5.2] rather than mutating original)
- `tags` — optional typed tags (`agent-invokable-output`, `user-published`, `validated-required`, `archival`, plus user-extensible)
- `created_at` — full-granularity first-version-commit timestamp; immutable
- `last_version_committed_at` — denormalized latest version commit; atomic with each version commit
- `entity_schema_version` — version of entity record shape, so Storage spec can normalize earlier shapes
`current_version_block_id` is a default/latest projection pointer updated through `artifact.commit_version`; branch-specific currentness lives in version graph projection; every pointer update is a typed event (§20) + ledgered [`run.execution-ledger`, File 04 §23.1]. Other fields immutable or carry own mutation capability.
### 3.3 Boundary
Entity record defines cross-version identity + review/lifecycle/materialization metadata; version content owned by `Artifact`-kind block [`block.kind-catalogue`, File 08 §3.1]; version chain in block graph; ledger records policy decision + capability execution producing each version commit; File 11 records which version active in each `ContextVersion`. Wire-stable through `entity_schema_version`; no migration framework required now; when external records persist, normalization-on-load applies.

## 4. `ArtifactKind` `artifact.artifact-kind`
### 4.1 Closed Canonical Catalogue
**Textual/structured documents:** `Document` (markdown/plain text/structured rich-text/prose report); `Note` (short note/memo distinct from full document; minimal entity layer); `Report` (structured report: text+charts+citations, typically composed over child blocks); `Lesson` (Teacher-surface lesson: sections/examples/exercises); `Curriculum` (Teacher-surface ordered lesson sequence with prerequisites + progress affordances); `Quiz` (assessment: prompts/answer keys/grading policy/feedback rules); `ExerciseSet` (practice tasks with expected outputs/solution guidance); `FlashcardSet` (spaced-repetition/study-card collection: fronts/backs/tags/optional media); `Rubric` (evaluation rubric: criteria/levels/scoring rules/feedback guidance).
**Code/patches:** `CodePatch` (structured patch over files; diff content + target paths); `Macro` (recorded GUI/web action sequence replayable via surface's macro executor).
**Data/tables:** `Dataset` (structured tabular/columnar data; may reference external storage for large); `Chart` (generated chart/plot/visualization; inline data + renderer hint); `Table` (structured tabular inline; small-row count distinguishes from `Dataset`).
**Media:** `Image`; `Audio`; `Video`; `ScreenshotSeries` (ordered screenshots + optional annotations; typically GUI Control/Web output).
**Web/browser:** `BrowserExtract` (structured extract from web pages; text+structured sections+citations); `WebDocument` (self-contained HTML/CSS/JS document to keep/embed/share).
**Notebooks/computational:** `Notebook` (notebook-style ordered cells: SQL/transform/chart/code/text/AI); `Diagram` (structured: Mermaid/Tldraw/hand-drawn/rendered — architecture/flowchart/whiteboard); `InstructionFragment` (reusable instruction-source content authored by user/agent; persisted for cross-conversation reuse).
**Workflow/reuse:** `WorkflowTemplate` (reusable workflow declaration, future Workflows spec); `Adapter` (registered adapter capability authored by user/agent [`capability.adapter-capabilities`, File 05 §17.4]); `Validator` (registered validation rule authored by user/agent; typically pairs with QC subsystem).
**Composed:** `ArtifactBundle` (`Composed`-content artifact whose children are themselves artifacts, e.g. project export = code+report+chart; for bundle export/gallery/reuse).
**Extension:** `Custom { namespace, name }` (specialized kind registered by subsystem/surface/plugin/user-defined extension via proposal-first registration [`capability.runtime-mutation`, File 05 §16.2]; `namespace` matches sourcing taxonomy [`capability.capability-source`, File 05 §9.1]; `name` is kind id within namespace).
Closed catalogue canonical for cross-cutting reasoning; `Custom` canonical for specialization; every artifact belongs to exactly one — no unparseable kind.
### 4.2 Kind Composition Rules
- `ArtifactBundle` always `Composed`; version block resolves to `Composed` block [`block.block-content`, File 08 §4] whose children are other artifact-version blocks
- `Dataset` exceeding inline-size threshold [`block.inline-size-threshold`, File 08 §4.2] MUST use `External`; small may use `Inline`
- `Image`/`Audio`/`Video`/`ScreenshotSeries` MUST use `External`; inline payloads for these are Explicit Rejection (§21)
- `CodePatch` may use `Inline` for small patches; large default `External` + diff format hint in metadata
- `Macro` uses `Inline` for macro DSL regardless of size (inspected+edited as structured records)
- `WorkflowTemplate`/`Adapter`/`Validator`/`InstructionFragment` typically `Inline` for inspectability; `External` only when payload genuinely exceeds practical inline storage
- `Custom` inherits composition rules from kind's registration declaration
Enforced at version-commit time by artifact commit validator.
### 4.3 Custom Extension
Registered via capability call (proposal-first [`capability.runtime-mutation`, File 05 §16.2]). Declares: `allowed_content_variants` (which `BlockContent` variants permitted: `Inline`/`External`/`Composed`); `default_materialization_policy`; `default_review_state`; `default_validation_required` (whether validation runs by default before leaving `Draft`); `description`; `surface_renderer_hint` (typed: interactive-sandbox runtime tag / type-specific-renderer name / `None`); `default_edges` (canonical edges [`block.canonical-edge-kinds`, File 08 §5.2] artifacts of this kind typically participate in). Persist in registry [`capability.registered-capability`, File 05 §10] under same registered-state envelope + same source-trust narrowing [`policy.source-approval-flow`, File 06 §9]. Cannot violate canonical composition rules; structurally invalid declaration rejected.
### 4.4 Boundary
Catalogue defines categories the system reasons about; doesn't define rendering/storage/retrieval. UI/storage/retrieval consume; don't extend (only registered Custom extension does).

## 5. Artifact Lifecycle and States `artifact.artifact-lifecycle-states`
### 5.1 `ArtifactLifecycle` `artifact.artifact-lifecycle`
Runtime view-state of an artifact version within a particular `ContextVersion`; effective lifecycle = projection of version selected by that context. Closed states:
- `Draft` — has ≥1 committed version but not accepted as ready; surface marks in-progress; retrieval may deprioritize
- `Active` — current version is accepted/current output; default when review doesn't gate or first version committed with `auto_accept_first_version: true`
- `Validated` — current version has ≥1 `Validation` linked via `validated_by` whose `ValidationOutcome` is `Passed` (§14); when multiple checks required, all required must pass
- `Superseded` — version superseded by sibling through `supersedes`; prior remains in pool, addressable through version chain
- `Archived` — preserved but moved out of default surface views; remains inspectable/retrievable/exportable; not in primary palette/panel by default
- `Discarded` — current version explicitly discarded by user/policy; entity record remains for audit; discarded version remains in pool unless hard-deleted
### 5.2 `ReviewState` `artifact.review-state`
- `Unreviewed` — default for new versions; marked pending review
- `AcceptedByUser` — user explicitly accepted via `artifact.set_review_state` or equivalent UI
- `AcceptedByAgent` — agent (typically reviewer subagent) accepted; weaker than user acceptance; does NOT lift typed-confirmation on downstream actions
- `Rejected` — explicitly rejected; remains in pool but not current unless restored
- `NeedsRevision` — explicitly marked requiring further work; agent may produce a new superseding version
### 5.3 `ValidationState`
- `NotValidated` — no validation run for this version
- `PendingValidation` — validation requested + in progress; `Validation` block not yet committed
- `Passed` — ≥1 `Validation` via `validated_by` carries `ValidationOutcome: Passed`, no required validation `Failed`
- `Failed` — ≥1 required `Validation` carries `ValidationOutcome: Failed`
- `NeedsReview` — most recent `Validation` carries `ValidationOutcome: Inconclusive` or a model-mediated validator declined
### 5.4 Per-Version vs Per-Entity Derivation `artifact.per-version-vs-per-entity-derivation`
`ArtifactLifecycle`/`ReviewState`/`ValidationState` are derived per-`ContextVersion` from version-graph action log + `validated_by` edges on each version, NEVER stored on entity record (same artifact may be `Active` in one version + `Superseded` in another without entity-record mutation). Storage may cache derived state in a materialized view [`block.what-is-computed`, File 08 §13.2] for O(1) reads, but rebuildable from source action log. Entity's denormalized `current_version_block_id` is only default/latest pointer; branch-aware surfaces read active version from version graph projection.
### 5.5 Lifecycle Transition Rules
- new artifact, first version committed → `Draft` (or `Active` if `auto_accept_first_version: true`)
- `artifact.set_review_state(AcceptedByUser)` → per-version review state transitions; if no validation required, lifecycle `Active`; if required + passes, `Validated`
- `Validation` with `Passed` commits + links `validated_by` → if review state `AcceptedByUser`/`AcceptedByAgent`, lifecycle `Validated`
- `current_version_block_id` updates to new sibling (via `artifact.commit_version`) → prior version lifecycle `Superseded`
- `artifact.archive` → `Archived`
- `artifact.discard` → `Discarded`; version remains until hard-deleted
- `artifact.restore` → returns to appropriate prior state (`Active`/`Validated`/`Draft`) per action log
No time-based transition permitted; no auto-archive-after-N-days at this layer (File 01 constraint). Retention policies may invoke `archive` as explicit operation driven by own logic; entity layer enforces no implicit decay.
### 5.6 Boundary
Lifecycle/review/validation are view-state concerns owned by version graph + entity record's transition log; this file defines state set/derivation rules/transition rules; version-graph spec owns action log + materialized view tracking state per version.

## 6. `ArtifactVersion` `artifact.artifact-version`
### 6.1 Definition
Durable per-version snapshot; every version is an `Artifact`-kind block [`block.kind-catalogue`, File 08 §3.1] carrying content [`block.block-content`, File 08 §4] + per-block fields [`block.block`, File 08 §2.2]. Entity layer adds a per-version metadata record where version requires fields the block doesn't carry (validation report reference, materialization paths, derivation summary). NOT: a separate block kind from canonical `Artifact` (every version is `Artifact`-kind block); mutable (immutable like every block; changes commit new sibling via `supersedes`); decoupled from content (version IS the block; record points but doesn't duplicate).
### 6.2 Required Fields
(in addition to canonical block fields [`block.block`, File 08 §2.2]):
- `version_id` — same value as version-block's `block_id`
- `artifact_id` — owning entity's `artifact_id`
- `version_number` — monotonically increasing integer per artifact; assigned at commit; never reused
- `parent_version_id` — prior version's `version_id` (target of `supersedes`); null for first version
- `derivation_summary` — short structured NL description of what changed from parent; emitted by producer at commit time, fixed thereafter; null for first version
- `produced_by_run_id` — `run_id`; null only for inspector-applied versions committed outside a run
- `produced_by_node_id` — DAG node id [`run.event-stream`, File 04 §23.2 envelope]; null when production not DAG-structured
- `produced_by_capability_id` — capability id [`capability.id`, File 05 §13.1] that committed version-block (e.g. `file.create`, `file.edit`, `data.notebook.export`, `teacher.lesson.compose`)
- `materialized_paths` — list of paths where content materialized (empty when `MaterializationPolicy: None`)
- `validation_report_id` — `block_id` of most recent linked `Validation`; null until first validation
- `metadata` — typed extension map for kind-specific fields (chart axis config, dataset schema, macro replay parameters); declared per artifact kind
Record fixed at commit; changes commit a new version per §5.5 `current_version_block_id` update flow.
### 6.3 Version Creation `artifact.version-creation`
New `ArtifactVersion` created when one of these commits a new `Artifact`-kind block:
- `artifact.create` — first version; assigns `artifact_id`, `version_number = 1`, `parent_version_id = null`
- `artifact.commit_version` — subsequent; takes new content (Inline/External/Composed), artifact_id, optional derivation summary, optional new title; commits new `Artifact`-kind block, sets `parent_version_id` to prior current, advances `version_number`, updates `current_version_block_id`
- `file.edit`/`file.create` on a path mapping to existing `Artifact: InWorkspace` materialization — file-management subsystem [File 08 file-block contract + future Coder surface spec] commits sibling `Artifact`-kind block as new version; entity record points at new
- `artifact.merge` — new version composed over 2+ existing versions (best-of-N selection / explicit merges); `parent_version_id` set to one parent (principal); additional parents linked through `derives_from` edges [`block.canonical-edge-kinds`, File 08 §5.2]
Version commit boundaries match [`block.commit-boundary-set`, File 08 §7.6] — `accepted assistant turn`, `capability completion`, `inspector apply`, `workflow node complete`, `import`, `consolidation`, `manual draft commit`, or a subsystem-internal boundary the capability declares.
### 6.4 Boundary
Version creation = capability concern; version content = block concern; cross-version chronology = version-graph concern. This file specifies metadata record + creation rules; future Storage spec realizes persistence; File 11 realizes chronology.

## 7. Artifact Materialization `artifact.artifact-materialization`
### 7.1 Definition
`Materialization` = process by which an artifact version's content becomes addressable on local filesystem or external storage. Separate from identity: artifacts have identity whether materialized or not.
### 7.2 `MaterializationPolicy`
Declared per artifact at creation; closed enum:
- `InWorkspace` — content written to a workspace path computed from `(workspace_id, artifact_id, artifact_kind, version_id)` per future Workspaces+Materialization spec (canonical default: `<workspace>/.atlas/artifacts/<artifact_id>/<version_id>/` with kind-typed leaf filename). Default for `Document`/`CodePatch`/`Notebook`/`Image`/`Audio`/`Video`/`Chart` whose containing scope is workspace or narrower.
- `ExternalRef` — content lives in external storage (cloud bucket, content-addressed external store, MCP-server-hosted resource); version-block uses `BlockContent::External` with storage_ref; materialization = binding external reference; no local file written by default; user may opt to cache locally (cache state per-installation, doesn't change identity).
- `None` — no materialization beyond version-block itself; used for `Note`/`InstructionFragment`/`Validator`/`Adapter` consumed inline; version-block's `BlockContent::Inline` payload is the artifact.
`MaterializationPolicy` is part of entity record; changing requires `artifact.update_materialization_policy` + creates audit-visible event (§20); changes apply to new versions, existing versions retain original policy.
### 7.3 Materialization Mechanics
**InWorkspace:** materialization at same boundary version-block commits (atomically); live-partial-write capabilities [`run.streaming-partial-execution`, File 04 §12] stage file under temp path during streaming + atomic-rename at version-commit boundary (if streaming run cancelled, staged file deleted before commit, no `ArtifactVersion` created); `materialized_paths` records resolved paths (multi-file artifacts like a `Notebook` with auxiliary assets list every path); subsequent commits materialize to new paths (from new `version_id`); prior version's paths remain on disk by default (subject to retention), entity points at new paths.
**ExternalRef:** version-block's `BlockContent::External { storage_ref, size_bytes, content_type, external_content_hash }` carries binding; no local file at commit by default; user may invoke `artifact.materialize_locally` to fetch local cache; `materialized_paths` empty unless cached.
**None:** no materialization step; `materialized_paths` empty; version-block carries full content inline (or composed structure).
### 7.4 Materialized Paths Provenance `artifact.materialized-paths-provenance`
A `materialized_paths` entry carries: `workspace_id`; `relative_path` (canonical, relative to workspace root); `resolved_absolute_path` (optional runtime projection for local display, not canonical identity); `is_principal` (true for single primary file — user's default-open target; false for auxiliary); `content_role` (typed: `Primary`, `Asset`, `Sidecar`, `Companion`; surfaces render with structure not flat list); `materialized_at`; `content_hash` (SHA-256 of file content at materialization; freshness checking against version-block's `content_hash` [`block.content-hash`, File 08 §4.5]; mismatch indicates external modification, handled per [`block.streaming-commit-boundary`, File 08 §7] disk→block sync loop). Workspace-root relinking explicit: moving workspace dir + updating root re-resolves all relative paths; individual files moved/deleted outside ATLAS → system reports unresolved materializations + offers relink/re-materialize, doesn't pretend to track arbitrary filesystem moves.
### 7.5 Disk→Entity Sync `artifact.disk-entity-sync`
External modifications detected by filesystem watcher [`block.streaming-commit-boundary`, File 08 §7]/file-management contract. When external edit detected: new sibling `Artifact`-kind block committed as new version [`block.block`, File 08 §2.2 producer typed `UserMessage` when user-driven, or `Subsystem { subsystem_id: filesystem_watcher, reason: "external_edit" }` when not directly attributable]; `current_version_block_id` updates atomically; `ArtifactExternallyEdited` event emits (§20); new version's `derivation_summary` auto-populated identifying file system as source.
### 7.6 Boundary
Workspace-tree materialization mechanics owned by future Workspaces+Materialization spec + file-management subsystem [`block.streaming-commit-boundary`, File 08 §7]. This file specifies policy enum, path-on-version metadata, disk→entity sync contract. Implementation (path templates, hash algorithms beyond SHA-256, materialization atomicity primitives, watcher backends) belong there.

## 8. Artifact Tombstones `artifact.artifact-tombstones`
### 8.1 Hard Delete
Follows [`block.hard-delete`, File 08 §6.6] for underlying `Artifact`-kind block. Entity-record consequences:
- `artifact.hard_delete_version(version_id)` is `UserApproval`-tier with `permission_floor: Denied` + policy template requiring denied-override via typed confirmation; discarded/only-version state may change preview text + warnings, never lowers floor
- version-block hard-deleted [`block.hard-delete`, File 08 §6.6] (composition-materialization preserves composed parents; tombstone retains identity)
- `ArtifactVersion` metadata record transitions to tombstone shape; row retained
- if deleted version was `current_version_block_id`, entity transitions to most recent non-deleted version; if none remain, entity becomes orphaned + marked for explicit user resolution (rename, hard-delete entity, or commit fresh version)
- `artifact.hard_delete_entity(artifact_id)` separate capability with `permission_floor: Denied` requiring typed-confirmation; tombstones every version + entity record
### 8.2 Tombstone Fields `artifact.tombstone-fields`
Version tombstone retains: `version_id`; `artifact_id`; `version_number`; `parent_version_id` (lineage chains continue resolving); `produced_by_run_id`/`produced_by_node_id`/`produced_by_capability_id`; `deleted_at`; `deleted_by` (user/agent/automation/subsystem); `deletion_reason` (typed: `UserRequested`, `RetentionPolicy`, `CredentialExpungement`, `SourceUnavailable`, `MaintenanceCleanup`, plus `Custom { code, description }`); `safe_description` (version's `description` [`block.block-description`, File 08 §10] at deletion, retained for inspection; sensitive content redacted per `default_sensitivity`). Entity tombstone retains same set of entity-record fields at deletion, content fields redacted to safe descriptions.
### 8.3 Lineage Preservation
Provenance queries (§15) continue resolving tombstoned versions: `provenance.lineage(target)` returns chain incl tombstoned, each tombstoned link as typed `Tombstoned` placeholder; `provenance.contributing_runs(target)` resolves producing runs of every version incl tombstoned; `provenance.replay_trace(target)` returns ledger entries incl tombstoned (content references resolving to redacted-description placeholders). Hard delete is canonical mechanism for user storage-reclamation, credential expungement, right-to-erasure [`core.non-destructive-by-default`, File 01 §7.13]; never automatic. Tombstone retention is safe default; explicit policy-governed pruning of tombstones is itself a typed-confirmation user operation.

## 9. `Claim` `artifact.claim`
### 9.1 Definition
Typed, identified factual assertion the system/agent has made or proposes to make; makes load-bearing assertions inspectable/supersedable/explicitly evidence-tied. For source-dependent or load-bearing assertions, not forcing every task into a neat evidence chain (web research, knowledge-heavy reports, validations, policy decisions, reusable factual outputs benefit most). Ordinary conversational text remains message content unless explicit publication or opt-in extraction promotes it. A `Claim` block is a canonical extension to [`block.kind-catalogue`, File 08 §3.1] declared here:
- block kind: `Claim` (registered as canonical baseline, NOT `Custom` namespaced; catalogue evolves through canonical-spec updates [`block.explicit-rejections`, File 08 §15])
- `allowed_content_variants`: `Inline` (canonical: claim text + structured metadata) or `Composed` (over sub-claims for compound assertions)
- `default_sensitivity`: `Public`; overridden to `Sensitive` when claim originates from user-private context per producer's `data_sensitivity` [`capability.permission-policy-fields`, File 05 §3.5]
- `transcript_anchorable`: false (may be referenced from transcripts but don't anchor transcript messages)
- `permitted_parent_kinds`: `Any` (typically `MessageAssistant`, `MessageUser`, or `WorkflowNode`)
- `permitted_child_kinds`: `Claim`, `SourceExcerpt`, `Evidence`, `Citation`, `Observation` (when `Composed`)
- `default_edges`: `cites`, `references`, `responds_to`, `supersedes`
NOT: a fact (claim = assertion something is the case; whether supported is separate via evidence linking); a conversation message (a `MessageAssistant` may contain asserting text; only becomes a `Claim` when published via `claim.publish` or auto-extracted under settings opt-in); a memory entry (`Memory` blocks [File 08 §3.1] may consolidate claims into long-term knowledge; memory mechanics File 14); a knowledge-base entry (File 12 knowledge entries may reference claims through `cites`/`references` but a claim is not by default a knowledge entry).
### 9.2 Required Fields
(in addition to canonical block fields [`block.block`, File 08 §2.2]):
- `claim_id` — globally stable; same value as block's `block_id`
- `claim_text` — assertion text (UTF-8); canonical content stored `Inline { text }`
- `claim_kind` — typed `ClaimKind` (§9.3)
- `confidence_class` — typed `ClaimConfidenceClass` (§9.5); declared by producer
- `confidence_score` — optional float [0.0, 1.0]; declared when meaningful; for ranking, never policy
- `scope` — broadest visibility scope [`block.block-scope`, File 08 §11]
- `anchor` — optional typed `ClaimAnchor` (§9.6) pointing to source block + optional span
- `claim_schema_version` — version of claim-block extension shape
Effective `ClaimStatus`, withdrawal, supersession, explicit override reason are projection/action-log facts, NOT mutable claim-block fields. Claim block carries immutable assertion content; lifecycle interpretation derived from evidence links + status records.
### 9.3 `ClaimKind`
Closed canonical + `Custom { namespace, name }`: `Factual` (asserts empirically the case — "build passes on commit abc", "file has 1234 lines"); `Causal` ("removing this guard caused the test failure"); `Conditional` ("if X then Y", "works on macOS only"); `Recommendation` ("we should switch to library X"); `Prediction` ("migration will take ~10 minutes"); `Definition` ("by `widget` we mean an instance of the Widget class"); `Identity` ("commit a + commit b have same effect", "file X unrelated to file Y"); `Summary` (longer body of evidence summarizes to a given claim); `Negation` (something is not the case); `Custom { namespace, name }`.
### 9.4 `ClaimStatus` `artifact.claim-status`
Closed canonical: `Candidate` (newly created, no evidence evaluated; default for first publication); `Supported` (≥1 `Supports`/`Corroborates` link active above configured threshold + no stronger refuting active); `Contradicted` (≥1 `Refutes` link active with confidence strictly greater than strongest supporting); `Unresolved` (both supporting + refuting active with comparable confidence; explicit user resolution required); `Superseded` (replaced by newer claim through supersession projection); `Withdrawn` (explicitly retracted by author/user through withdrawal record).
Status derived from evidence-link set when not explicitly overridden. Derivation: 1. withdrawal record exists → `Withdrawn`. 2. supersession projection record exists → `Superseded`. 3. compute support/refute aggregation per §11.4: any `Refutes` link with confidence strictly greater than max(supporting confidence), treating absent support as below all confidence classes → `Contradicted`; any active `Supports`/`Corroborates` above `claim.evidence_threshold` setting + no refuting of comparable confidence → `Supported`; both supporting + refuting with comparable confidence → `Unresolved`; no active links of meaningful confidence → `Candidate`. 4. explicit status override record from `claim.update_status` overrides derived value until superseded/withdrawn; override reason + actor recorded in policy ledger.
### 9.5 `ClaimConfidenceClass`
Canonical policy-grade confidence enum (from cosight five-level + graphify three-level, harmonized): `DirectlyObserved` (system directly observed — file read, tool output, postcondition validation; highest policy-grade; no further support for routine use); `VerifiedExternal` (supported by external authoritative evidence — cited paper, official docs page, passing test; evidence link must reference external source); `Inferred` (derived by reasoning from other supported claims; evidence link must reference premises); `Plausible` (reasonable conclusion from available context but not rigorous; appropriate for ordinary conversational answers); `Speculative` (hypothesis/guess; surfaces render with explicit speculative marking); `Disputed` (asserted with awareness of significant contradicting evidence; explicit acknowledgment of disagreement). `confidence_class` is primary policy-grade signal (typed-confirmation requirements, automation gating, retrieval ranking weights, validation pipeline routing read from it); optional `confidence_score` float supplements for ranking/comparison but never sole policy input.
### 9.6 `ClaimAnchor`
When claim originates from content within a source block (typically `MessageAssistant`), `anchor` captures: `source_block_id`; `source_span` (optional typed `SourceSpan` §12.3 grammar — character/line/byte range or composed-child index); `anchor_kind` (typed: `Authored` published from producer-written text, `Extracted` auto-extracted from existing text, `Annotated` attached as commentary to existing content, `Derived` summarizes/derives from source). Anchor lets surfaces highlight source span + lets retrieval index claim against source location.
### 9.7 Claim Lifecycle
Claim block immutable per File 08; observable content changes commit new sibling via `supersedes`; status changes are projection records: editing `claim_text`/`claim_kind`/`confidence_class` → new sibling claim block via `claim.publish` with `supersedes` edge; updating `status` through derivation → no new block, computed on read; explicit `status` override (user marks `Unresolved`) → emits `ClaimStatusOverridden` + stores override record with reason; explicit `claim.withdraw` → commits withdrawal record + emits `ClaimWithdrawn` (claim block unchanged but every projection treats it withdrawn). Withdrawn claim remains addressable for provenance but excluded from retrieval/surface display/evidence-link computation by default.
### 9.8 Boundary
Claims are blocks; identity/content/immutability follow File 08. This file adds canonical `Claim` kind, `ClaimStatus` derivation, `ClaimConfidenceClass` policy-grade enum, anchor reference contract. Retrieval/ranking/surface presentation/memory consolidation are downstream.

## 10. Claim Extraction `artifact.claim-extraction`
### 10.1 Explicit Publication
`claim.publish(claim_text, claim_kind, confidence_class, anchor?, scope?, evidence_links?)` is canonical capability. Declares: dynamic permission tier from scope/sensitivity/downstream use (routine conversation/task/workspace usually `WorkspaceWrite`; global/reusable/external-publication/automation-gating/policy/security/medical/legal/financial/high-impact/user-configured sensitive escalate to `UserApproval` or stronger); `replay_class: deterministic_replayable`; `output_block_kinds`: `[Claim]`; `touched_resources`: meta-resource over claim entity pool; `concurrency`: `SelfParallel` (independent claim publications parallel-safe). Publication commits new `Claim`-kind block per [`block.commit-boundary-set`, File 08 §7.6] + creates entity-record row.
### 10.2 Automatic Extraction
Opt-in per scope (default off), task-specific. Strongest for web research, source-dependent reports, knowledge-base work, validation output; not a default requirement. When enabled: designated extractor model runs post-commit on accepted `MessageAssistant` blocks within configured scope; candidate claims identified against configured extraction model-request template (registry-managed per [`policy.agent-exposure-policy-settings`, File 06 §16.4] pattern), each candidate a tuple `(claim_text, claim_kind, confidence_class, source_span)`; each committed as `Claim` block via same `claim.publish`, derived status initially `Candidate`, extracted source-span as anchor; extracted claims default `Sensitive` until user review (regardless of source block sensitivity); `claim.review` UI surfaces for explicit accept/reject. Settings (§19): `claim.auto_extraction.enabled` per scope (default false); `claim.auto_extraction.model_id`; `claim.auto_extraction.model_request_template_id`; `claim.auto_extraction.minimum_confidence_class` (discard candidates below); `claim.auto_extraction.review_required` (true → extracted wait in `Candidate` until explicit review; false → proceed to derived status immediately). Always emits per-extraction `ClaimAutoExtracted` events with extractor model identity, model-request template id, source block reference, extracted candidate.
### 10.3 Boundary
Extraction produces `Claim` blocks through normal pipeline; extractor model selection/template registration/confidence-threshold tuning are settings concerns; retrieval+memory may consume extracted claims [Files 12,14].

## 11. `Evidence` `artifact.evidence`
### 11.1 The `Evidence` Block Kind
Canonical per [`block.kind-catalogue`, File 08 §3.1]: "structured evidence record supporting a claim, output, or action; carries citation references + the typed claim it supports". File 09 specifies content shape + typed-edge metadata. Content is structured `Inline` carrying: `evidence_kind` (typed: `DirectObservation` — itself an `Observation` block or wraps one; `CitedSource` — a `Citation`/`SourceExcerpt` block or wraps one; `ToolResult` — captured tool result referenced by `witnesses` edge to a `ToolResult` block; `ValidationOutcome` — a `Validation` block; `DerivedReasoning` — chain of reasoning blocks producer captured); `summary` (short structured summary of what evidence asserts + why supports claim); `originating_run_id`; `originating_capability_id`. An `Evidence` block MUST reference ≥1 supporting block via `cites`/`witnesses`/registered evidence-relation edges (§11.3); evidence block with no supporting references is Explicit Rejection (§21) — [`block.kind-composition-rules`, File 08 §3.3] already established this.
### 11.2 `EvidenceLink`
Typed metadata attached to a directed edge between a `Claim` (or other supported target) and a supporting block (`Evidence`/`SourceExcerpt`/`Citation`/`Observation`/`Validation`/any prior block captured as evidence). Edge is one of [`block.canonical-edge-kinds`, File 08 §5.2] (`cites`, `witnesses`, `validated_by`) or registered extension edge (§11.3). Carries on edge metadata [`block.block-edge-block-graph`, File 08 §5.1 edge `metadata` field]: `relation` (typed `EvidenceRelation` §11.3); `confidence_class` (typed `EvidenceConfidenceClass` §11.4, independent of claim's own confidence); `confidence_score` (optional float [0.0, 1.0]); `applies_to_span` (optional `SourceSpan` — which portion of source block evidence specifically supports); `captured_at`; `captured_by_run_id`; `captured_by_capability_id`; `notes` (optional free-text rationale).
### 11.3 `EvidenceRelation`
Closed canonical + `Custom { namespace, name }`: `Supports` (source supports target claim/artifact); `WeakSupports` (suggestive but not conclusive); `Refutes` (contradicts target); `Contextualizes` (provides relevant context without supporting/refuting); `Corroborates` (independently confirms what another source already supports); `Summarizes` (summary of target's underlying material); `Derives` (target derived/transformed/computed/inferred from source); `Witnesses` (the observation that triggered the target; for capability postconditions + stale-state revalidation [`run.call-pipeline`, File 04 §8.2]); `IllustratesByExample` (illustrates target through concrete example). Extension relations use `Custom { namespace, name }`, registered proposal-first [`capability.runtime-mutation`, File 05 §16.2]; an extension relation declares own confidence-aggregation semantics + containment under canonical relations.
### 11.4 `EvidenceConfidenceClass`
Reuses `ClaimConfidenceClass` enum (§9.5) but applies to strength of supporting relation rather than assertion's grounding: `DirectlyObserved` (grounded in directly observed event captured by system); `VerifiedExternal` (references external authoritative source system captured); `Inferred` (justified by reasoning over other linked evidence); `Plausible` (reasonable but not rigorous); `Speculative` (hypothesis); `Disputed` (offered with awareness of contradicting evidence). Optional `confidence_score` provides numerical ranking within class.
### 11.5 Evidence Set Closure
`EvidenceSet` of a claim/artifact = set of blocks reachable from target following `cites`/`witnesses`/`validated_by`/registered evidence-relation edges. Rules: direct closure (every block linked by an `EvidenceLink` from target is in set); transitive closure (every block linked from any block in set is in set only when that edge's relation declares `transitive: true`; canonical defaults: `Supports`/`Corroborates`/`Derives`/`Witnesses` transitive; `Refutes`/`Contextualizes`/`WeakSupports`/`Summarizes`/`IllustratesByExample` not; extensions declare own); bounded by configurable max depth (default 4) + max cardinality (default 100); when bounds exceeded, set reported with `truncated: true` + user may request expansion. Compaction policies MUST preserve evidence-set closure for any claim/artifact at `Supported`/`Validated` state by default (File 13 implements); removing an evidence link is explicit capability operation; compaction NEVER silently severs evidence chains.
### 11.6 Boundary
Evidence blocks are blocks; evidence links are edges; closure mechanics are graph queries over existing canonical block-graph. This file specifies relation enum, confidence class enum, closure rules; future Storage spec + File 12 implement fast-query indexes.

## 12. `Citation` `artifact.citation`
### 12.1 The `Citation` Block Kind
Canonical per [`block.kind-catalogue`, File 08 §3.1]: "structured reference to an external source (URL, document section, file range, prior block id, MCP resource); durable lookup key for provenance". Content: `reference_kind` (typed `CitationReferenceKind` §12.2); `reference_value` (canonical reference value for the kind — URL string, document handle, file path, prior block id, MCP resource URI); `source_span` (optional typed `SourceSpan` §12.3 narrowing to a portion); `captured_at` (freshness context); `captured_by_run_id`; `captured_by_capability_id`; `retrieval_strategy` (typed: `DirectFetch` fetched directly, `CachedFetch` returned from local cache, `SearchResult` retrieved through search service, `UserAttached` user provided manually, `AgentInferred` agent inferred without retrieval); `display_metadata` (optional typed map: title/author/published date/language/other surface-rendering fields). A URL-only citation is a durable reference, not durable source content; evidence-bearing/high-impact use must link to captured support content (`SourceExcerpt`, `Observation`, `BrowserExtract` artifact version, equivalent block).
### 12.2 `CitationReferenceKind`
Closed canonical + `Custom { namespace, name }`: `Url` (stable URL); `DocumentBlockSpan` (reference to a block within a document in the block pool; `reference_value` = `block_id` + optional span); `FileRange` (range within a workspace file; `reference_value` = `(file_path, range_kind, range_value)` where `range_kind` ∈ `LineRange`/`ByteRange`/`CharacterRange`); `PriorBlock` (any block by `block_id`); `McpResource` (`(server_id, resource_uri)`); `KnowledgeEntry` (a `Memory`-kind block or future knowledge-base entry by stable id); `Repository` (code repo commit/path: `repo_url`, `commit_hash`, optional `path`); `ExternalDoiUrn` (DOI/URN/ISBN/other stable scholarly identifier); `ProvenanceRecord` (ledger entry by `(run_id, ledger_entry_id)` for self-referential provenance).
### 12.3 `SourceSpan` Grammar
Typed discriminated value: `CharacterRange { start: usize, end: usize }` (half-open Unicode-character range); `ByteRange { start: usize, end: usize }` (half-open byte range); `LineRange { start_line: usize, end_line: usize, start_column: Option<usize>, end_column: Option<usize> }`; `PageRange { start_page: usize, end_page: usize }` (PDFs, books); `TimeRange { start_seconds: f64, end_seconds: f64 }` (audio/video); `DomSelector { selector: String, occurrence_index: Option<usize> }` (CSS selector against HTML); `XPath { xpath: String }` (against XML/HTML); `Composed { children: Vec<SourceSpan> }` (multiple non-contiguous regions). Canonical-form; surfaces+retrieval consume typed shape, not parsing strings.
### 12.4 Capture Mechanics
Citations commit at boundary their producing capability declares. Canonical citation-producing capabilities: `web.fetch`/`web.search`/`web.extract_document`/`data.extract_*` (produce `Url` + `DocumentBlockSpan`); `file.read`/`file.search`/`file.grep` (produce `FileRange`); `memory.recall`/`knowledge.search`/`knowledge.read` (produce `KnowledgeEntry`); `mcp.<server>.<tool>` fetching resources (produce `McpResource`); `citation.capture` (explicit any-kind capture). `citation.capture` may also commit a `SourceExcerpt` when a selected span/retrieved fragment is promoted to durable evidence. Every committed citation/excerpt flows through standard pipeline [`run.call-pipeline`, File 04 §8.2] + recorded in ledger [`run.execution-ledger`, File 04 §23.1].
### 12.5 Boundary
Citations are blocks; identity/immutability/content hash/graph participation follow File 08. This file specifies typed reference-kind catalogue + source-span grammar; surface-rendering (citation card layout, hover previews, click-to-open) owned by UI specs.

## 13. `Observation` `artifact.observation`
### 13.1 The `Observation` Block Kind
Canonical per [`block.kind-catalogue`, File 08 §3.1]: "structured observation of the world (file content snapshot, accessibility tree snapshot, screenshot reference, status query result, browser DOM extract) committed for replay + policy revalidation". Content: `observation_kind` (typed `ObservationKind` §13.2); `payload_reference` (small inline payloads inline; large — screenshots, accessibility trees, DOM extracts — `External` referencing external content store); `captured_at` (full-granularity); `captured_by_run_id`; `captured_by_capability_id`; `capture_context` (typed map: active scope context at capture — `run_id`, `step_id`, `node_id`, `worktree_id`, `backend_id`); `staleness_fingerprint` (typed `StalenessFingerprint` §13.3 identifying what observation depended on; runtime checks before any mutation declaring observation as precondition [`run.call-pipeline`, File 04 §8.2 stale-state revalidation]); `observation_subject` (typed map identifying observed entity — file path for file snapshots, window handle for accessibility trees, URL for DOM extracts).
### 13.2 `ObservationKind`
Closed canonical + `Custom { namespace, name }`: `FileSnapshot` (content snapshot at a path; payload incl content hash, mtime, byte length); `AccessibilityTreeSnapshot` (captured accessibility tree from desktop app per GUI Control surface; payload incl role-based filtered tree); `Screenshot` (pixel-data; payload references external image blob; metadata incl scale factor, capture region, optional OCR text); `BrowserDom` (captured DOM extract; payload incl URL, captured HTML, optional viewport metadata); `NetworkResponseSnapshot` (captured HTTP response: status/headers/body; for replayable web automation); `DatabaseQueryResult` (captured result set; payload incl query, result schema, data); `TerminalOutput` (captured terminal session: command, stdout/stderr stream, exit code); `ProcessState` (running processes, ports listening, etc.); `EnvironmentSnapshot` (env vars, cwd, shell version, OS version); `RepositoryState` (git: branch, commit, working-tree status, staged changes); `WorkspaceSnapshot` (open files, materialized artifacts, active settings); `Custom { namespace, name }`.
### 13.3 `StalenessFingerprint`
Typed value capability commits with observation so future calls revalidate currency: `ContentHash { hash: String }` (SHA-256 or registered alternative of observed content); `Mtime { mtime_unix_seconds: f64 }` (POSIX mtime); `MtimeAndHash { mtime_unix_seconds: f64, hash: String }` (both, for robustness); `VersionId { version_id: BlockId }` (observation-of-block; block_id whose content observation captures); `AccessibilityTreeHash { tree_hash: String }`; `DomSignature { url: String, signature: String }` (hash over DOM structure — typically tag tree without text); `EtagAndLastModified { etag: Option<String>, last_modified: Option<String> }` (HTTP cache validators); `GitCommit { commit_hash: String, branch: String }`; `Composite { fingerprints: Vec<StalenessFingerprint> }` (all must match for currency); `Custom { namespace, name, value }` (currency check requires registered evaluator). Runtime checks against current state when a capability declares observation as precondition [`run.call-pipeline`, File 04 §8.2 `stale_state_revalidation`]; mismatch → typed `StateChangedSinceObservation` error in-band.
### 13.4 Replay Use
Observations participate in replay [`run.ledger-events-commits`, File 04 §23 + File 10]: a `snapshot_replayable` capability whose original execution depended on an observation requires same observation (or re-captured equivalent) at replay; `staleness_fingerprint` + `content_hash` [`block.content-hash`, File 08 §4.5] enable replay-time equality checks.
### 13.5 Boundary
Observations are blocks; content carriage = File 08. This file specifies kind catalogue, staleness-fingerprint contract, replay use. Surface/subsystem-specific production rules (GUI Control three-tier perception, Web fetch tiers) owned by those specs; committed observations conform to canonical contract here.

## 14. `Validation` and `Critique` `artifact.validation-critique`
### 14.1 The Block Kinds
`Validation` canonical per [`block.kind-catalogue`, File 08 §3.1]: "structured validation result (postcondition check, type check, lint result, evaluator score); referenced from runs + completion-verification hook surface [`run.termination`, File 04 §22]". `Critique` canonical: "structured critique/review record (critic agent's review, code-review comment, QC note); semantically distinct from Validation because critiques are evaluative judgments not pass/fail checks".
`Validation` content: `validation_kind` (typed: `Postcondition`, `TypeCheck`, `Lint`, `Test`, `EvaluatorScore`, `SchemaValidation`, `CitationCheck`, `FactualityCheck`, `ConsistencyCheck`, `SafetyCheck`, `Custom { namespace, name }`); `outcome` (typed `ValidationOutcome`: `Passed`, `Failed`, `Inconclusive`); `validated_target_id` (`block_id` / `artifact_id` + version reference / `claim_id`); `validator_kind` (typed: `Deterministic`, `ModelMediated`, `UserManual`); `validator_reference` (for `Deterministic`: validator capability id; `ModelMediated`: validator model id + policy model-request template id; `UserManual`: user id); `failure_details` (when `Failed`: rule violated, expected value, actual value); `inconclusive_reason` (when `Inconclusive`); `latency_ms`; `evidence_links` (optional list of `EvidenceLink` references to supporting blocks e.g. test output block validation depended on).
`Critique` content: `critique_kind` (typed: `CodeReview`, `EditorialReview`, `PeerReview`, `DesignReview`, `Custom { namespace, name }`); `target_id` (`block_id`/entity id of critiqued target); `summary`; `findings` (structured list: each severity/location reference/description/optional suggested resolution); `critic_kind` (typed: `User`, `Agent`, `Subagent`, `External`); `critic_reference` (actor identifier); `recommended_action` (optional typed: `AcceptAsIs`, `RevisionRecommended`, `RevisionRequired`, `RejectAndRestart`).
### 14.2 `ValidationState` Derivation `artifact.validation-state-derivation`
`ValidationState` of an artifact version (§5.3), a claim, or any target with `validated_by` edge derived from linked `Validation` blocks: 1. Collect all `Validation` blocks linked from target by `validated_by`. 2. Filter to validations whose `validator_kind` + applicable settings considered required for target's kind (a `Validator`-kind artifact may require both `SchemaValidation` + `TypeCheck`). 3. Aggregate: any required validation with `outcome: Failed` → `ValidationState::Failed`; all required with `outcome: Passed` → `ValidationState::Passed`; any required with `outcome: Inconclusive` + no failures → `ValidationState::NeedsReview`; missing required validations → `ValidationState::PendingValidation`; no validations linked → `ValidationState::NotValidated`. Recomputed on every read; caching is storage optimization, derivation rules are contract.
### 14.3 Hook Surface Integration
[`run.termination`, File 04 §22] completion-verification hook surface produces `Validation` blocks: a deterministic check (postcondition validator) registered through [`run.hook-integration`, File 04 §23.3] commits `Validation` with `validator_kind: Deterministic`, `validator_reference` = validator capability id, `outcome` = check result; a model-mediated check commits `validator_kind: ModelMediated`, `validator_reference` = model id + policy model-request template id, `outcome` = model verdict; a user-applied validation commits `validator_kind: UserManual`. `validation.run(target_id, validation_kind?)` is canonical capability; tier from validator capability + touched resources: pure read validators producing only `Validation`/`Evidence` blocks are `ReadOnly`; validators executing code/mutating files/using credentials/publishing externally/changing sandbox state inherit appropriate write/approval tier.
### 14.4 Critique vs Validation
`Validation` produces pass/fail/inconclusive against well-defined checks; `Critique` produces evaluative findings that may recommend but don't gate state transitions. Load-bearing: artifact `ValidationState` derives only from `Validation` blocks (`Critique` doesn't contribute); automation depending on validation outcome reads validation state not critique findings; critiques surface in inspectors/comparison boards/review panels as advisory. A critique may produce a validation (recommending validator be run); validator outcome counts for state.
### 14.5 Boundary
Validation+critique are block-level records; this file specifies content, validation-state derivation, hook-surface integration. Surface/subsystem-specific validators (Coder type checkers, Data Processor data-validation framework, Teacher quiz graders) register through canonical mechanism + produce canonical block shapes.

## 15. `Provenance` `artifact.provenance`
### 15.1 Definition
Derived view over unified block graph (File 08), version graph (File 11), execution ledger [`run.execution-ledger`, File 04 §23.1], capability registry (File 05), entity records (this file). Answer to "what produced this artifact?", "which evidence supports this claim?", "what runs touched this block?", "what is the derivation chain of this version?". NOT: a stored entity (computed on read); a parallel ledger (execution ledger is durable source-of-truth for run-level facts; provenance projects over it); a per-block field (blocks have producer/origin_run_id/source_attribution per File 08; provenance is transitive closure over those + graph edges + entity records); an audit log (audit logs are downstream consumers; canonical layer is the query).
### 15.2 Provenance Closure Rules
- Block-level closure: from a `block_id`, follow `parent_block_id` (causal lineage), `contains` (via `children_block_ids` resolution, composition lineage), `derives_from` (derivation lineage), `supersedes` (edit lineage). Each step yields next ancestor/component.
- Edge-level closure: from `block_id`/entity, follow `cites`, `witnesses`, `validated_by`, `consolidates`, `responds_to`, `references`, `conditioned_on`, registered extension edges to assemble evidence + dependency network.
- Run-level closure: every block's `producer` + `origin_run_id` resolve to a producing run; every run has a `RunIntent`, a producing route, a producing intent thread (or `parent_run_id` for child runs); closure resolves causal chain back to originating user request/automation/external event.
- Capability-level closure: every run's ledger entries reference resolved `(capability_id, capability_version)` [`capability.invocation-record`, File 05 §11]; closure resolves to declarations + registered entries.
- Entity-level closure: artifact+claim entities reference producing run + contributing capabilities directly; closure resolves to producing intent thread/conversation/task/workspace.
Bounded in depth + cardinality per §19 settings.
### 15.3 Canonical Query Surface
- `provenance.query_lineage(target_id, max_depth?, edge_filter?)` — typed lineage tree (parent-axis closure); result: ordered list of `(block_id_or_entity_id, kind, relation, distance)` tuples + `truncated: bool` when bounds hit
- `provenance.query_evidence_set(claim_or_artifact_id, max_depth?, relation_filter?, confidence_floor?)` — evidence-set closure per §11.5; result: ordered list of `(supporting_block_id, EvidenceRelation, confidence_class, confidence_score, captured_at)` tuples
- `provenance.query_contributing_runs(target_id)` — set of `run_id`s that produced/edited/validated/critiqued target across full lineage
- `provenance.query_contributing_capabilities(target_id, distinct_versions?)` — set of `(capability_id, capability_version)` invoked across lineage; `distinct_versions: true` distinguishes versions, otherwise collapses to ids
- `provenance.query_replay_trace(target_id)` — ordered set of execution-ledger entries that produced+modified target, for replay/forensic reconstruction
- `provenance.query_derivation_chain(artifact_id_or_version_id)` — for artifacts returns version chain (`parent_version_id` closure) + `derives_from` graph closure; typed DAG of `(version_id, derivation_summary, produced_by_run_id, produced_by_capability_id)` nodes
- `provenance.contradiction_check(claim_id)` — over claim's `EvidenceLink` set, returns any `Refutes`-relation supporting blocks whose confidence exceeds strongest `Supports`, separately reports equal-confidence conflicts as unresolved; used by QC subsystem + `claim.update_status` automatic derivation (§9.4)
- `provenance.query_artifact_versions(artifact_id, include_tombstones?)` — ordered version chain, incl tombstones when requested
Each query declares `permission_tier: ReadOnly`, `concurrency: ConcurrencySafe`, `replay_class: deterministic_replayable` (target state at query time determines result; replay records snapshot id).
### 15.4 Determinism and Reconstruction
Deterministic given same registry/version-graph/block-pool/ledger snapshots; two queries with same target + same snapshots return byte-identical results (load-bearing for replay/audit/reproducibility). Caching is storage optimization; substrates are source-of-truth; cache invalidation event-driven (new block/edge/version commits or ledger entry recorded → any cached query result whose closure includes affected substrate invalidated).
### 15.5 Cross-Workspace and Cross-Installation Provenance
When an artifact/claim/supporting block imported from another workspace/installation (future Sync, Import, Export, Data Portability spec), import operation commits an `Import` producer record on every imported block [`block.block`, File 08 §2.2]; provenance queries on imported blocks resolve to import record; further closure into originating installation's run+capability history requires future Sync spec's cross-installation mapping table.
### 15.6 Boundary
Query surface over existing substrates; this file specifies closure rules, canonical query set, determinism contract, cross-installation boundary. Implementation (graph traversal algorithms, caching layers, index structures) belong to future Storage spec + File 12.

## 17. Cross-Surface Interoperability `artifact.cross-surface-interoperability`
### 17.1 Single Entity Pool
One artifact entity pool, one claim entity pool, one evidence-link edge set, one block pool [`block.cross-surface-interoperability`, File 08 §12]. Every surface reads/writes through canonical capability set.
### 17.2 Per-Surface Projections `artifact.per-surface-projections`
Each surface projects entity pool through surface-specific filters:
- Coder: `CodePatch`, `Document` (markdown), `Notebook` (when surface-relevant), file-system view of materialized artifacts; inspector shows artifact lifecycle + review state
- Web: `BrowserExtract`, `WebDocument`, `Image` (page screenshots), `Citation` (cited sources), Research Canvas projection of evidence-link graphs
- Data Processor: `Dataset`, `Chart`, `Notebook`, `Table`, data-lineage projection of `derives_from` edges
- Teacher: `Lesson`, `Curriculum`, `Quiz`, `ExerciseSet`, `FlashcardSet`, `Rubric`, custom Teacher kinds for specialized pedagogy + learner-progress projections
- GUI Control: `Macro`, `ScreenshotSeries`, `Observation` (UI tree snapshots), action-replay projections
- System Agent: change records as artifact-like outputs with rollback projections (future System Agent spec declares specific kinds)
- Memory (substrate-service): `Memory`-kind blocks [`block.kind-catalogue`, File 08 §3.1] + knowledge-base projection over claims+citations
- conversation transcript: filters for transcript-anchorable kinds + resolves artifact references to inline cards/sidecar panes
- inspector lens [`surface.inspector-lens`, File 07 §12.4]: every entity in pool, filtered by user-chosen axes (kind, status, scope, source, validation state, review state, lifecycle state)
Filter is a surface concern; entities + content remain in unified pool unchanged (an artifact produced by Coder but referenced from Memory is visible in both).
### 17.3 Cross-Surface Composition
An artifact may compose content from multiple surfaces. A research report (`Document`) may compose: text sections (conclusions); `Citation` children (web sources from Web surface); `Chart` children (Data Processor charts); `Observation` children (files inspected by Coder); `Evidence` children with `Supports`/`Refutes` evidence-link metadata. Composition is a single composed artifact version block whose children are constituent blocks, each at appropriate scope. Renders correctly in any surface supporting the constituent kinds; surfaces not supporting some child kinds render as typed placeholders ("[unsupported kind: …]") + link to inspector lens [`block.cross-surface-composition`, File 08 §12.3].
### 17.4 Cross-Conversation Reference
Artifacts at `workspace` scope (or broader) addressable from any conversation in same workspace; reference uses canonical capability path (conversation references by `artifact_id`; surface resolves to current version's block + renders); identity independent of any conversation.
### 17.5 Boundary
Cross-surface interoperability is a property of the unified pool; this file establishes pool's invariants; later per-surface specs declare how each surface projects/filters/composes; no surface may introduce a private artifact pool, private claim pool, or private evidence-graph.

## 18. Persistence Contract `artifact.persistence-contract`
### 18.1 What Is Durably Stored
- artifact entity pool — every entity record (§3.2) survives process restart, conversation archive, version-graph operations until explicit `artifact.hard_delete_entity`
- claim entity pool — every `Claim` block (+ block-level fields per File 08) survives until explicit hard delete; content in block, derived status recomputed
- artifact version metadata records (§6.2) — durable, survive restart, removed only on hard-delete tombstoning (retains tombstone row)
- `EvidenceLink` edge metadata — durable as part of block-graph edge set [`block.what-is-durably-stored`, File 08 §13.1]
- `Validation` + `Critique` blocks — durable per File 08
- file-system materializations of `InWorkspace` artifacts — durable on disk per workspace-materialization contract
- entity-related events recorded in ledger — every artifact-version commit, review-state change, claim publication, evidence-link commit produces a ledger entry
### 18.2 What Is Computed
- `ArtifactLifecycle`/`ReviewState`/`ValidationState` per `ContextVersion` — derived from version-graph action log + `validated_by` edges, rebuilt on demand
- `ClaimStatus` when not explicitly overridden — derived from evidence-link set (§9.4)
- `EvidenceSet` closure — computed on demand from block-graph edges (§11.5)
- Provenance query results — computed on demand (§15)
- Materialized paths' current freshness — computed by comparing version-block's content hash to file's current SHA-256
### 18.3 Reconstruction Across Restart
On restart: artifact entity pool reloads; artifact-version metadata records reload; block pool re-emerges [`block.reconstruction-across-restart`, File 08 §13.3]; evidence-link edges reload as part of edge set; lifecycle/status/evidence-set/provenance derivations rebuild on first read. In-flight artifact versions whose producing run was orphaned at restart follow [`run.cancellation`, File 04 §17.3] orphan rules: if capability declared `partial_output_meaningful: true` + provided resume handler, version may be recovered as partial-orphan version-block [`block.partial-block-orphans`, File 08 §7.3]; otherwise staged file discarded + no version commits.
### 18.4 Reconstruction Across Retry, Edit, Reroute, Branch
Per [`run.retry-reroute-branch`, File 04 §19], retry/edit/reroute/branch produce new runs linked to prior. Artifact entity pool + version chain shared across these: a retried run may commit a new version superseding prior; prior version's block remains; version chain branches in version graph. Run-scoped evidence-link edges (evidence-links a run produced to support its claims) do NOT transfer across retry/edit/reroute/branch by default — new run is fresh + produces own evidence. Workspace-scoped + broader-scoped evidence-links DO transfer per scope rules [`block.cross-scope-references`, File 08 §11.3; `policy.lease-primitive`, File 06 §11.3].
### 18.5 Cross-Conversation and Cross-Workspace
Artifacts + claims at `workspace` scope visible across all conversations in workspace; provenance queries return references to runs+conversations spanning workspace lifetime. Cross-workspace reference requires future Sync, Import, Export, Data Portability spec; canonical contract: artifact identity portable through import mechanism, import operation producing `Import` producer record per File 08.
### 18.6 Boundary
Persistence is storage layer's responsibility; this file specifies what storage must persist (entity-record field sets, version metadata records, evidence-link edge metadata) + reconstruct (derived states, closures, provenance results). Storage schema/replication/sync/import-export owned by future Storage and Persistence + Sync, Import, Export, and Data Portability specs.

## 21. Explicit Rejections `artifact.explicit-rejections`
- a parallel artifact registry or parallel claim registry separate from the block pool — one block pool (File 08); artifacts are entities over `Artifact`-kind blocks; claims are `Claim`-kind blocks; no second pool
- a separate evidence storage layer outside the block-graph edge set — evidence through `Evidence` blocks + edge-typed `EvidenceLink` metadata; parallel evidence database corrupts unified graph
- mutable artifact content carried on the entity record — content in version-block per File 08; record carries metadata never content
- mutable artifact lifecycle/review/validation state stored on entity record — derived per-`ContextVersion`; storing on entity row forces re-writes on every transition + breaks replay determinism
- claims as anonymous text fragments — every `Claim` has stable `claim_id`, explicit confidence class, status derived/overridden through projection records; free-floating claim-like text in `MessageAssistant` is not a `Claim`
- evidence chains without typed relations — every link carries an `EvidenceRelation` (canonical/registered extension); untyped `cites` edges purporting to support a claim rejected
- closing the `EvidenceRelation` set to support/refute only — closed set includes `Contextualizes`, `Corroborates`, `Summarizes`, `Derives`, `Witnesses`, `IllustratesByExample`; too-narrow set forces misclassification
- a single numerical confidence score as the only policy signal — `ConfidenceClass` is policy-grade enum; numerical scores for ranking only; policy never reads float in isolation
- observations without staleness fingerprints when the observation backs a mutation — capabilities whose mutation depends on a prior observation must consume `staleness_fingerprint` + revalidate [`run.call-pipeline`, File 04 §8.2]; observations with no fingerprint valid as evidence but cannot back mutations
- silent claim-status changes caused by committed substrate changes — a `ClaimStatusChanged` event emits with derivation reason; pure read recomputation is not an event source
- silent evidence-link removal without a recorded event — every removal emits `EvidenceLinkDetached`; compaction never silently removes evidence-link edges
- automatic claim extraction enabled by default — opt-in per scope, default off, explicit enablement required
- treating provenance as a stored entity — derived query surface; storing results as durable rows creates parallel ledger
- hardcoded provenance query results not derived from canonical substrates — every query returns results derived from blocks/edges/versions/runs/ledger entries; fabricated provenance invalid
- artifact versions that mutate the prior version-block in place — versions are sibling blocks linked by `supersedes`; in-place mutation rejected at block layer + re-rejected here
- artifact identity tied to a specific materialization path — path is per-version metadata; renaming materialized file doesn't change identity only current path
- artifact lifecycle transitions driven by time rather than explicit actions — time-based forbidden (File 01); retention policies invoke explicit `archive` driven by own logic
- time-based citation freshness as a correctness condition — currency based on fingerprints/validators/explicit refresh/consuming-workflow requirements; retention timing is storage policy only
- `Critique` blocks contributing to `ValidationState` derivation — critiques advisory; only `Validation` blocks contribute
- claim-publish capability lifting `permission_floor: Denied` claims (none currently exist canonically) without typed-confirmation — floor enforcement [`policy.permission-floor-typed-confirmation`, File 06 §7] applies; no entity capability bypasses floor
- hard-delete floors that weaken for discarded/only-version artifacts — those states may change warnings + typed-confirmation text, not the denied floor
- silent automatic claim status promotion to `Supported` without meeting configured `claim.evidence_threshold` — derivation deterministic; settings define threshold; surfaces never override without explicit override record
- contradiction detection that suppresses the contradiction silently — `ContradictionDetected` emits when stronger refuting evidence committed; equal-confidence conflicts resolve to `Unresolved` + emit status-change event
- entity capabilities operating outside the canonical event bus — every transition emits appropriate canonical event; no private out-of-band notification channel
- claim entities anchored to `MessageUser` blocks the user did not author — anchors must reference actual originating block; misattribution invalid
- materializing `InWorkspace` artifacts outside the workspace root — paths constrained to workspace per file-management security boundary
- preserving any earlier name for the same primitive as a parallel system — `Artifact` (entity) supersedes "deliverable record"/"produced output entity"/"work product registry"; `Claim` supersedes "assertion record"/"knowledge claim"/"agent answer entity"; `Provenance` (derived view) supersedes "lineage record"/"audit chain table"/"origin trace store"; `EvidenceLink` supersedes "support edge type"/"citation relation column"; none survive as parallel primitives
- treating `Artifact` and `Memory` as same primitive — memory entries are `Memory`-kind blocks per File 08; Memory subsystem owns salience/decay/recall/consolidation; artifacts are entity-level identifiable produced outputs; may compose (memory entry may cite an artifact) but distinct
- treating `Claim` and `Memory` as same primitive — a memory entry may consolidate claims into long-term knowledge but a claim has own identity/status/confidence; collapsing removes claim-level status tracking
- treating `Claim` and `MessageAssistant` as same primitive — most assistant utterances are not load-bearing claims; explicit publication required
- treating `Evidence` and `Citation` as same primitive — citations are typed source references; evidence is the structured assertion the source supports a claim; compose but distinct
- treating `Observation` and `Citation` as same primitive — observations are first-party captures; citations reference external sources; compose (a citation may reference an observation) but distinct

## 22. Consequences for Later Specs `artifact.consequences-for-later-specs`
- Execution ledger/event stream/hooks spec MUST record entity-relevant events through canonical envelope, link ledger rows to `artifact_id`/`version_id`/`claim_id`/`evidence_link_edge_id` where applicable, not duplicate entity content (rows reference entities never carry content)
- Version graph/commits/projections spec MUST store per-version action logs driving `ArtifactLifecycle`/`ReviewState`/`ValidationState` derivation (§5,§14.2); per-version diffs must include artifact-version commits, evidence-link edge commits, review-state changes alongside block lifecycle+pin changes; materialized view supports derivation deterministically
- Retrieval/indexing/knowledge-base spec MUST treat `Claim`/`Evidence`/`SourceExcerpt`/`Citation`/`Observation` blocks as first-class retrieval targets; claim retrieval surfaces confidence class+status; evidence retrieval surfaces relation type; knowledge-base entries may cite claims+artifacts through canonical edges
- Context assembly/compaction spec MUST preserve evidence-set closure for `Supported`+`Validated` claims+artifacts by default (§11.5); compaction must invoke explicit block-lifecycle operations on supporting blocks rather than silently severing chains; per-policy rules belong to compaction spec but must respect canonical preservation requirement here
- Memory spec MUST treat memory entries consolidating claims as `consolidates`-edge-linked to source claim blocks; memory promotion preserves claim identity+confidence class
- Model strategy/profiles/selection spec MUST allow per-claim-confidence-class model selection (low-confidence may use cheaper model, high-confidence requires user's primary model)
- Provider layer/rate limits/usage accounting spec MUST record per-call provider/model attribution provenance consumes through `provenance.query_replay_trace`
- World model/state-awareness spec MUST treat artifacts/claims/observations as part of world state; available-capability set filters entity capabilities based on entity catalogue (e.g. `artifact.commit_version` requires artifact entity to exist)
- Perception/observation pipelines spec MUST produce `Observation` blocks conforming to §13 (kind, payload, staleness fingerprint) + route through canonical `observation.commit` path
- Storage/persistence spec MUST store entity-record field sets, version metadata records, evidence-link edge metadata, materialized-paths records, tombstone rows per §18; rebuild derived state (lifecycle, status, evidence-set closure) deterministically from source action log+graph
- Sync/import/export/data portability spec MUST preserve artifact identity, claim identity, evidence-link relations, provenance chains across export+import; imported entities receive `Import` producer records [`block.block`, File 08 §2.2] + continue participating in provenance through future cross-installation mapping table
- Security/credentials/trust boundaries spec MUST treat `Secret`-sensitivity citations/observations/evidence with same redaction discipline [`block.sensitivity`, File 08 §9] establishes for `Secret` blocks; raw secrets in observations redacted at commit
- Sandbox/process control/isolation spec MUST commit `Observation` blocks (§13) for sandboxed-process snapshots capability runs depend on for revalidation [`run.call-pipeline`, File 04 §8.2]
- Workspaces/materialization spec MUST implement `InWorkspace` materialization path-resolution algorithm + disk→entity sync loop (§7.3,§7.5)
- Work surface contract spec + per-surface specs (Coder/Web/Data Processor/Teacher/GUI Control/System Agent) MUST declare which `ArtifactKind`s + `ObservationKind`s they primarily produce + register any `Custom` extension kinds through canonical mechanism; their `SubsystemSurfaceSpec` declarations [`surface.subsystem-surface-spec`, File 07 §5] must include relevant artifact-producing + observation-committing capabilities
- Automation/triggers spec MUST use artifact+claim entities as automation triggers (e.g. "when a new `Validation`-failed artifact commits, run X") + produce artifacts+claims as outputs through canonical capabilities
- Workflows/templates/reuse spec MUST treat `WorkflowTemplate` artifacts as canonical workflow-template store; workflow node outputs warranting durable identity become artifact versions; per-step evidence becomes `Evidence` blocks linked to workflow's output claim/artifact
- Extension/plugin system spec MUST allow plugin-registered `Custom` artifact kinds + `Custom` observation kinds through proposal-first registration; registered kinds participate same way as built-in
- MCP/external integrations spec MUST route MCP-sourced citations+observations through canonical `citation.capture` + `observation.commit` paths; MCP-server-hosted artifacts use `ExternalRef` materialization with `McpResource` reference kind
- UI shell/layout/presentation/interaction models spec + UI customization/widgets/theming spec MUST render artifacts/claims/evidence/citations/observations/validations/critiques/provenance results through canonical data contracts; no UI surface invents a parallel entity shape
- Quality control/validation spec MUST register validators as `Validator`-kind artifacts (or built-in capabilities), produce `Validation` blocks per §14, integrate with [`run.termination`, File 04 §22] completion-verification hook surface
- Evaluation/benchmarking spec MUST consume artifact/claim/evidence data as evaluation targets + grounds; factuality benchmarks consume claims+evidence sets
- Telemetry/logging/observability spec MUST consume entity-relevant events; analytics over artifact-creation rates, claim-status distributions, evidence-link-confidence distributions, provenance-query latency are first-class
- Runtime infrastructure/lifecycle spec MUST orchestrate startup-time registration of canonical artifact kinds, `Claim` block-kind extension, canonical evidence relations, canonical citation reference kinds, canonical observation kinds, canonical entity capabilities
- Packaging/platform/distribution spec MUST ship built-in declarations for every canonical entity capability + canonical artifact kinds + observation kinds + evidence relations + citation reference kinds as `Builtin` source in every install
