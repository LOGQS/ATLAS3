# Context Assembly and Compaction

## Status
Canonical.

## Scope
Defines: context assembly for every model-bound invocation (routing, execution, validation, child runs, programmatic model steps, completion checks); structured model request as assembly parts grouped into semantic regions; per-part authority/sensitivity/source attribution/instruction-boundary handling; `ContextPolicy` + router context policy behavior; budget management, overflow reporting, duplicate detection, oversize input handling; token counting as provider/model-capability contract; logical cache-marker candidate production; compaction as write-side counterpart to read-only assembly; continuity summaries, virtual paging, context pressure signaling, events, persistence, settings, explicit rejections.
Does NOT define: block schema/kinds/lifecycle/commit validation [File 08]; artifact/evidence/claim/citation/provenance identity [File 09]; ledger row schema/event dispatch/hook execution [File 10]; version graph schema/`ContextOp` vocabulary/materialized-view reconstruction/commit mechanics [File 11]; retrieval algorithms/indexing backends/entity extraction/knowledge governance [File 12]; capability declaration schema/policy/approval/leases/tool-surface composition [Files 05-07]; routing decision semantics/`RunIntent` [File 03]; execution lifecycle/run status/cancellation/recovery [File 04]; provider tokenizers/wire formats/cache-control syntax/model selection/rate limits/usage accounting; storage schema/sync/UI layout/exact settings precedence.

## Source Resolution
- Context assembly is per-iteration READ over canonical state; does NOT mutate blocks/tasks/memory/routing state.
- Region-based + part-based: regions provide ordering+budgets; each part carries own source/authority/scope/sensitivity/lifecycle facts.
- Compaction creates explicit durable outputs/lifecycle operations through existing block/version systems; not hidden model-request loss.
- Retrieval, virtual paging, recall use canonical indexes + lifecycle filters, not separate archive stores.
- Rendered model request MUST preserve instruction boundaries, source attribution, provider-native callable declarations without collapsing all content into one governing-instruction blob.

## 1. Chosen Model `context.chosen-model`
Two cooperating services. `ContextAssemblyService` is READ-ONLY: turns active runtime state into structured model request for a specific invocation; reads blocks, materialized views, retrieval outputs, tool-surface snapshots, instruction sources, memory outputs, world-state snapshots, settings, provider/model descriptors; NEVER mutates blocks/lifecycle/indexes/versions. `CompactionService` is WRITE-SIDE: reduces active context by committing versioned operations through block+version graph systems; may drop/recover/mask/group/consolidate, but does NOT hard-delete source content and does NOT bypass version history. Services communicate through durable state + typed pressure signals. Every model-bound invocation uses `ContextAssemblyService`; no separate instruction assembler, router request assembler, per-surface private request builder, or ad-hoc concatenation path.

## 2. Model Request `context.model-request`
### 2.1 Definition
Complete provider-bound input for one invocation. May contain: model-request text content, provider-native callable declarations, provider parameters, references to externalized content, logical cache-marker candidates, diagnostic notices. NOT equivalent to instruction text (callable declarations travel outside text; provider parameters aren't text content; many parts aren't instructions).
### 2.2 Assembly Parts
Sequence of `AssemblyPart` records. Each MUST carry: `part_id`, `region`, `content_kind`, `source_ref`, `authority_class`, `sensitivity`, `inclusion_reason`, budget estimate/count, lifecycle visibility used during selection, omission/redaction/externalization metadata when applicable. `source_ref` points to durable source when one exists: block, ledger entry, route record, capability declaration, provider descriptor, settings snapshot, file source, retrieval result, or synthetic runtime record.
### 2.3 Authority Classes `context.authority-classes`
Authority is per part. Classes: `governing_instruction`, `user_instruction`, `trusted_runtime_fact`, `untrusted_source_data`, `provider_native_callable_declaration`, `diagnostic_notice`. Regions declare default authority but it's only fallback (web-fetched tool result in history stays `untrusted_source_data`; user-authored instruction source stays `user_instruction`; callable declaration stays `provider_native_callable_declaration`). Instruction-boundary markers render at authority transitions between adjacent parts, not merely region boundaries. External descriptions/retrieval snippets/tool outputs/user files marked as data unless source explicitly grants instruction authority.
### 2.4 Sensitivity
Every part carries sensitivity resolved from source+policy. Governs: whether part may be included for target model/provider; cached; logged/snapshotted/displayed; whether redaction/summary/reference-only/omission required. Assembly MUST fail safely when policy cannot decide whether a sensitive part may be included.

## 3. Semantic Regions `context.semantic-regions`
Structural buckets for budgeting+ordering; NOT authority boundaries/storage tables/frontend panes. Canonical set:
- `GoverningInstructions` - Atlas runtime instructions, policy notices, non-user governing constraints
- `InstructionSources` - user/workspace/project/plugin/profile instruction sources
- `CallableDeclarations` - primary tool schemas + callable declarations
- `RuntimeState` - route/run/task/world-state/capability-state/policy-state facts
- `CurrentInput` - triggering message, event, selected content, directly attached inputs
- `ConversationHistory` - active materialized conversation blocks + continuity summaries
- `RetrievedContext` - retrieval results, knowledge entries, memory outputs, source excerpts selected for this invocation
- `DiagnosticNotices` - budget warnings, omission notices, denial notices, assembly diagnostics for the model
- `ReservedOutput` - reserved capacity for model response, not rendered content
Profiles may add custom regions; they still emit ordinary assembly parts + obey same authority/sensitivity/budget/traceability rules. Region order is policy-selected; default should preserve cache-stable+semantically stable prefixes when useful; alternate orderings valid when recorded in assembly snapshot + checked against provider/model constraints.

## 4. Context Policies `context.context-policies`
`ContextPolicy` = fidelity+selection policy for an invocation. Families: `Full` (all eligible active context that fits); `Summarised` (prefer summaries/descriptions/source excerpts over raw history); `Minimal` (only required invocation frame + directly relevant state); `Router` (assemble routing frame for File 03); `Custom` (user/plugin/workspace/subsystem policy from same primitives). Configurable through settings+profiles; may differ by invocation kind, model profile, conversation, workspace, subsystem, surface, capability family, automation, user override. Policies choose inclusion/ordering/budget allocation/summarization preference/retrieval scope/duplicate handling/cache-marker preference/overflow behavior; do NOT change source authority, sensitivity policy, capability approval rules, or routing semantics.

## 5. Router Context Assembly `context.router-context-assembly`
File 03 defines routing semantics + `RunIntent`; this file defines how the router-invocation model request is assembled. Router context policy MUST include full current triggering input unless input cannot be carried directly; then assembly MUST externalize/reference full input + include enough visible structure for router to understand. Current user request MUST NOT be replaced by a summary as normal path. Router policies MAY include: active intent-thread+task state; previous route records/decisions/reasoning summaries; router-generated intent summaries for prior user messages; continuity summaries; selected recent/pinned/attached/referenced blocks; capability/surface/model/provider/approval-state summaries; workspace instruction files+instruction sources when policy grants relevance to routing; retrieval results when agentic router profile explicitly requests them. Cheapness achieved by policy design/summaries/provider caching/prechecks/retrieval/optional agentic inspection, NOT by pretending conversation length is irrelevant. Router summaries are distinct from continuity summaries (router summaries optimize future routing; continuity summaries preserve work-line continuity for downstream calls; a router policy may consume continuity summaries but they're not the same object). Router context policies are user-configurable: compact routing, summary-rich routing, recent-history routing, pinned/reference routing, ambiguity-expanded routing, agentic inspect-and-route, custom. All MUST produce durable route records per File 03.

## 6. Assembly Algorithm `context.assembly-algorithm`
Each invocation: 1. Resolve invocation kind, target model/profile, provider capabilities, active settings, policy snapshots. 2. Resolve semantic region set, region order, budget allocation, default authority classes. 3. Gather candidate sources from instructions, current input, materialized conversation state, task/run state, tool surface, retrieval, memory, world state, policy state, diagnostics. 4. Convert candidates into assembly parts with source references, authority, sensitivity, lifecycle visibility, inclusion reason, estimated budget cost. 5. Apply sensitivity/policy/capability gates. 6. Count/estimate request size through token-counting contract. 7. Fit request under target budget via active policy's priority+overflow rules. 8. Externalize/omit/summarize/reference oversize content per policy. 9. Produce logical cache-marker candidates when target model/provider supports them. 10. Emit `AssemblyOutput` + record snapshot reference required for replay+audit. Assembly is deterministic for same durable inputs, settings snapshot, provider/model descriptor, policy snapshot.

## 7. Current Input and Oversize Handling `context.current-input-oversize-handling`
Current input has special protection (user's immediate request). Retention priority: 1. minimal governing Atlas instructions required for safe operation; 2. current triggering input; 3. direct attachments/selected sources referenced by current input; 4. active task/run state needed to answer current input; 5. optional instruction sources, retrieval, memory, history, diagnostics. When current input too large to carry directly, assembly MUST preserve access to full input by externalizing as referenced source/searchable file/source block/equivalent durable object. Rendered request should include most useful directly visible representation per policy (structural outline, top-and-bottom excerpts, extracted explicit instruction, source map). Rejection allowed ONLY when system cannot safely externalize/reference/inspect input. Attachments follow same principle: large attachments become referenced/searchable/readable sources, not silent omissions; model receives enough metadata to know what exists, how to request more, what wasn't directly included.

## 8. Duplicate and Overlap Handling `context.duplicate-overlap-handling`
Before dispatch/assembly, system MAY detect when pending input duplicates content already in active context. Detection may use: exact content identity, normalized text identity, source identity, large substring overlap, structured selection identity, semantic similarity (when deterministic checks insufficient + policy justifies cost). Resolution choices MUST preserve user intent: include as reference to existing context; drop duplicated span while preserving new instruction; include anyway; edit before sending; apply configured default with visible notice + undo. Decision recorded with triggering input. Duplicate handling MUST NOT mutate prior blocks, hide user's new instruction, or bypass routing/ledger records. Timing-based auto-continue may be offered as UI convenience, but correctness MUST NOT depend on elapsed time.

## 9. Budget and Overflow `context.budget-overflow`
Context window is shared budget across all rendered parts + reserved output. `BudgetReport` MUST describe: target model/profile + provider capability snapshot; total budget, reserved output budget, rendered input budget; per-region allocation+usage; omitted/redacted/summarized/externalized/overflowed parts; policy decisions that materially affected inclusion; token-counting accuracy class; cache-marker candidate summary; cache impact of fitting+reordering decisions — a `cache_impact` classification (`none`, `preserved_prefix`, `changed_tool_surface_only`, `changed_instruction_or_region_order`, `full_cache_break_likely`) per §11, aligned with tool-surface `auto_shrink_record` classification [`surface.auto-shrink-non-destructive`, File 07 §8.3]. Overflow is non-destructive: assembly reports pressure; does NOT compact/delete/mutate/silently discard durable content. Budget values, warning thresholds, region floors/ceilings, reserved-output strategy, overflow behavior are settings/profile concerns.

## 10. Token Counting `context.token-counting`
Provider/model capability consumed by assembly. Model descriptor MUST expose enough to determine: context window/equivalent request-size limit; tokenizer identity/counting identity; whether exact provider-native counting available; whether compatible local estimator available; which request parts count toward which limits; whether callable declarations/cached prefixes/images/files/multimodal payloads have special accounting rules. Assembly may use exact counting, compatible local counting, or conservative estimation; chosen accuracy class recorded in `BudgetReport`. Token counts MUST NOT be stored as unqualified block fields; any reusable count is keyed by content identity, content version/hash, tokenizer/counting identity; counts for pending uncommitted input use content hashes/snapshot references instead of block ids. Provider-specific tokenizer libraries, endpoint names, model-family exceptions belong to provider/model specs.

## 11. Cache Marker Candidates `context.cache-marker-candidates`
Assembly may produce logical cache-marker candidates (sees full structure + stable prefixes). A candidate records: candidate boundary, covered assembly parts, source stability basis, sensitivity eligibility, provider/model capability snapshot used, policy that requested the marker. Provider adapters decide whether/how candidates become provider-native cache controls; assembly does NOT define provider syntax, minimum lengths, retention duration, billing behavior, cache APIs. Cache preservation is strong default preference when not harming correctness, but not absolute; users/profiles may choose orderings/inclusion policies reducing cache efficiency. Assembly should preserve stable ordering + cacheable prefixes when fitting under budget; fitting within context budget WINS over cache preservation, but resulting `cache_impact` MUST be recorded on `BudgetReport` (§9) + `AssemblySnapshot` (§19) using closed classification `none`/`preserved_prefix`/`changed_tool_surface_only`/`changed_instruction_or_region_order`/`full_cache_break_likely`. System should surface consequence when a fitting decision/policy meaningfully harms caching. Sensitive/secret content is cache-ineligible unless policy explicitly allows caching at appropriate sensitivity level.

## 12. Compaction `context.compaction`
Reduces active context by committing versioned operations. NOT model-request trimming, hidden deletion, or assembly side effect. Families: `DescriptionDriven` (select+compact using block descriptions, structure, source metadata); `FullSummarisation` (summaries over larger spans when raw content can't stay active); `IncrementalSummarisation` (update existing continuity summaries as new spans age out); `VirtualPaging` (drop active visibility while preserving searchable recall through standard retrieval path); `SimpleTruncation` (remove lowest-priority active visibility only when policy explicitly allows); `Custom` (user/workspace/plugin/subsystem policy from same operations). May use model steps, deterministic selectors, retrieval, block descriptions, validators; any model-generated summary MUST preserve source links + sensitivity constraints. Operations MUST be revision-safe: a pass declares the view revision it read + fails or rebases safely if view changed before commit.

## 13. Virtual Paging `context.virtual-paging`
A compaction policy, not a separate archive store. `context.archive` applies `Drop` to target blocks (removes from active assembly); `context.recall` applies `Recover` (restores to active assembly). Because dropped blocks excluded from default active retrieval, a VirtualPaging policy configures its conversation namespace/retrieval profile to include `Active`, `Recovered`, `Dropped` lifecycle states for recall/search by that policy. Retrieval results MUST surface lifecycle metadata so agent can distinguish archived from active material. No new lifecycle state, no parallel retrieval mechanism, no private archive database.

## 14. Continuity Summaries `context.continuity-summaries`
Preserve semantic continuity when raw blocks leave active context. Should preserve: user's goal+wording where materially important; decisions+rationale; constraints/assumptions/open questions; pending tasks+commitments; important evidence+source references; what was omitted/summarized/externalized. Continuity summaries are durable blocks linked to compacted source blocks; may be superseded incrementally; included by policy like any other context source; subject to authority/sensitivity/budget rules.

## 15. Context Pressure `context.context-pressure`
Typed coordination boundary between execution, tool surfaces, retrieval, provider handling, compaction. Causes: assembly overflow, provider rejection, budget warning, tool-surface saturation, retrieval result expansion, user/automation request for compaction. Context layer responds through policy: request tool-surface shrink, run compaction, externalize large inputs, ask user, or report no safe reduction exists. Execution coordinates retries+cancellation; does NOT own compaction choices. Time-based triggers are optional user-configured conveniences, not correctness mechanisms, not defaults; event-driven + state-driven triggers preferred.

## 16. Instruction Sources and Workspace Files `context.instruction-sources-workspace-files`
Instruction sources from user settings, workspace files, project files, plugin metadata, committed `InstructionSource` blocks, runtime policy. `ATLAS.md` is default workspace instruction-file name; name/lookup order/enablement/inclusion policy are settings. When a resolved workspace instruction file active, it participates in `InstructionSources` with `user_instruction` or other policy-resolved authority, source attribution, sensitivity metadata, budget governance. File 12 may index the same file as knowledge for retrieval+provenance; indexing does NOT by itself grant instruction authority; instruction inclusion decided by this file's policy.

## 17. Tool-Surface Coordination `context.tool-surface-coordination`
Callable declarations consume context budget. File 07 owns surface composition+loading; this file owns how resolved surface enters model request, how much budget it consumes, how context pressure reported back to tool-surface layer. Under pressure, assembly may request shrinkage/deferred loading/borrowable-catalog reduction/reference-only descriptions per File 07. Tool-surface shrinkage MUST NOT remove a callable the execution contract requires unless policy explicitly permits reroute/pause/failure.

## 18. Capabilities `context.capabilities`
Context assembly+compaction expose capabilities through canonical Capability Registry. Families should cover: inspecting current budget report + assembled structure; dry-running assembly for pending input; listing omitted/redacted/externalized/overflowed sources; triggering compaction under active policy; masking/dropping/recovering/pinning/protecting/archiving/recalling context sources; changing context policy/compaction policy through settings-governed paths. Exact declarations, permission tiers, touched-resource expressions, preview behavior, leases, approval rules [Files 05,06]. Write-like context capabilities MUST declare touched resources + revision preconditions.

## 19. Events, Ledger, and Snapshots
Context events are `Custom { namespace, name, payload }` extensions registered through File 10 unless a later File 10 revision promotes a cross-cutting kind. Expected families: assembly completed; budget warning; context pressure observed; duplicate/overlap detected; compaction started/completed/failed/low-yield; continuity summary updated; context source externalized/omitted/redacted/dropped/recovered/recalled; cache-marker candidates produced; router context assembled. Durable records MUST reference `AssemblySnapshot`s rather than storing raw model-request dumps by default. An `AssemblySnapshot` records/references enough to reconstruct what was sent without re-querying any live source: included assembly parts; omitted+redacted parts with reasons; token counts used for fitting; token-count source identity (the `TokenSource` + tokenizer identity per File 17); retrieval hits or immutable references to retrieval result set used; memory outputs used; tool-surface snapshot consumed [`surface.required-outputs`, File 07 §2.3]; settings snapshot; model/provider descriptor snapshot (provider/model descriptor identity); world/runtime-state snapshot [File 18]; ephemeral facts that were included; policy snapshot, budget report, sensitivity-safe hashes, rendered content references where retention policy allows.
Replay determinism `context.assembly-replay-snapshot`: For replay/audit/deterministic reconstruction, context assembly consumes recorded `AssemblySnapshot`. Replay MUST NOT re-derive inclusion/omission/ranking/token counts/memory outputs/retrieval results/tool-surface contents/runtime-world facts from live mutable sources. Live assembly may consult current services (retrieval, memory, world model, token-counting endpoints); historical replay uses recorded snapshot + immutable source references only. Mutable/ephemeral/non-reproducible live input reconstructable at replay only because captured in `AssemblySnapshot` or referenced through durable snapshot. Transient streaming + UI inspection are NOT source of truth; ledger, block graph, version graph, referenced `AssemblySnapshot`s are.

## 20. Persistence and Settings `context.persistence-settings`
Durable: context+compaction policy selections; continuity summary blocks; compaction commits; source externalization records; assembly snapshot references required for replay/audit/debugging; duplicate-handling decisions tied to triggering input. Computed: rendered model requests; token counts+estimates; budget reports; overflow lists; cache-marker candidates; provider-adapter-specific request forms. Settings MUST cover: context policy by invocation kind; router context policy; region order+region budget allocation; current-input+attachment overflow behavior; duplicate detection+resolution defaults; token-counting strategy; cache-marker candidate behavior; compaction policy+triggers; virtual paging lifecycle-filter behavior; instruction-file lookup/enablement/inclusion; sensitivity handling+snapshot retention; whether time-based convenience triggers enabled. Settings use File 15's model: durable global/workspace/conversation scopes, active profile context+profile layers, plus non-durable invocation overlays for run/automation/evaluation/per-call overrides. Subsystem/surface/capability-family variation represented by namespaced setting keys+constraints, not by inventing additional durable scopes.

## 21. Explicit Rejections `context.explicit-rejections`
- mutating blocks/indexes/lifecycle state/versions during assembly
- treating compaction as hidden model-request trimming
- treating overflow as permission to silently drop user content
- replacing current user request with a summary as normal routing path
- maintaining separate router/instruction/surface/validator request builders
- assigning authority only at region level
- treating external tool descriptions/retrieval snippets/web content as instructions
- hardcoding tokenizer libraries/provider endpoints/context limits/cache retention durations/ratio defaults/numeric thresholds in this spec
- storing token counts as unqualified block fields
- making provider cache behavior part of canonical assembly semantics
- requiring fixed region order solely for cache efficiency
- creating a virtual-paging archive store or lifecycle state
- using time-based triggers as correctness conditions
- making duplicate detection mutate prior blocks
- bypassing File 05-07 capability+policy contracts for context operations
- bypassing File 10/11 records for compaction/snapshots/durable context history
- treating `ATLAS.md` or any workspace file as hidden model-request text without source attribution + policy control

## 22. Consequences for Later Specs `context.consequences-for-later-specs`
- memory specs MUST expose memory outputs as assembly sources with authority/sensitivity/budget/provenance metadata
- settings specs MUST define exact scope precedence for context, router-context, compaction, instruction-file, duplicate-detection, cache-candidate settings
- model strategy+provider specs MUST expose request-size, tokenizer/counting, cache, callable-declaration, multimodal accounting capabilities without leaking provider specifics into this file
- storage specs MUST persist assembly snapshot references, continuity summaries, compaction commits, externalized source records without creating parallel context tables
- UI specs MUST present context inspection, duplicate handling, overflow, compaction history, source externalization as projections over records defined here
- surface specs MUST declare default context+compaction policies without creating private model-request assembly paths
- automation+workflow specs MUST reuse same assembly/compaction/pressure/snapshot contracts
- evaluation specs SHOULD measure context correctness, continuity preservation, duplicate handling, overflow recovery, cache effectiveness, compaction quality
