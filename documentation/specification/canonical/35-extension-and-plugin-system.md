# Extension and Plugin System

## Status

Canonical. This file defines the `Plugin`, the `PluginManifest`, the contribution-point taxonomy, the `PluginRegistry`, and the install/trust/lifecycle contracts by which a cohesive bundle of contributions is packaged, reviewed, registered into the system's one canonical registries, enabled, updated, and removed. It realizes the extensibility planes `core.extension-planes` (File 01 §6.14) names and the extension-integrity invariant `core.extension-integrity` (File 01 §7.10) requires; it owns the plugin packaging and the contribution-point registration/lifecycle that `capability.lifecycle` (File 05 §16), `policy.source-approval-flow` (File 06 §9), `surface.consequences-for-later-specs` (File 07 §20), `ledger.hook-registration-discovery` (File 10 §8), `settings.consequences-for-later-specs` (File 15 §21), `security.trust-model` (File 22 §9.9), `worksurface.registry` (File 25 §10.5), `controlrail.registry` (File 26 §14.3), and `workflow.consequences-for-later-specs` (File 34 §21) declare and delegate to this file. It is the third post-surface spec: horizontal and surface-neutral, the way `worksurface.work-surface` (File 25), `controlrail.chosen-model` (File 26), `automation.chosen-model` (File 33), and `workflow.chosen-model` (File 34) are. Later canonical files may refine it, but may not contradict it.

## Scope

This file defines:

- the `Plugin` — a durable, identified, versioned, installable bundle of contributions that adds capabilities, instructions, surfaces, integrations, automations, and configuration to the system without altering its source, by declaring contributions that register through the one canonical registries; the cohesive packaging unit `core.extension-integrity` (File 01 §7.10) names
- the `PluginManifest` — the typed declaration a plugin carries: identity and compatibility, the contribution set (each contribution typed by its kind), typed dependencies, the permission manifest, the trust hint, the entry module and its declared capabilities, and profile affinity
- the **contribution-point taxonomy** — the catalogue of what a plugin may contribute, organized by the six extension planes (`core.extension-planes`, File 01 §6.14), and for each kind the owning file, the canonical registry it lands in, and the registration path it uses
- the **permission manifest and declared effect envelope** — the bundle-level upper bound over all contribution effects that the source-approval review surfaces, and the rule that it may not understate the contributions it bundles
- **trust, integrity, and source approval for a bundle** — how a plugin's trust class is established and verified (delegated to `security.trust-model`, File 22 §9), how integrity binds an approval to the installed content, and how the proposal-first source-approval flow (`policy.source-approval-flow`, File 06 §9) gates a plugin at the bundle granularity
- **plugin code backends and isolation** — that a plugin's executable contributions run through the existing backend descriptors (`capability.backend-binding-lifecycle`, File 05 §10.4) and the one `Sandbox` contract (`sandbox.contract`, File 23 §3), with no new sandbox
- the `PluginRegistry` — the catalogue of installed plugins, their lifecycle and trust state, and the contribution-attribution index that records runtime source plus plugin bundle ownership so a bundle activates, disables, quarantines, and uninstalls atomically; not a parallel store of the contributions themselves
- the **install, update, enable/disable, quarantine, and uninstall lifecycle** — discovery, validation, source approval, installation, activation-and-registration, the device-local install state, atomic update with re-review on envelope expansion, reversible disable, safety quarantine, and uninstall with orphan-preserving cleanup
- **discovery and distribution** — the install sources (built-in-bundled, local directory, packaged archive, registry URL), the replaceable discovery surface and normalized candidate/effect summary, agent-suggested-never-auto-installed discovery, opt-in-default-off updating, the self-contained export/import bundle over the `PortablePackage`, and the ship-with per-profile plugins as the worked examples
- the **agent/user boundary, custom tools, and AI-assisted customization** — that the agent registers scoped custom tools and proposes reuse units but never installs a plugin, that AI-assisted customization uses the same paths as manual customization, the custom-tool-to-plugin promotion path, and the no-silent-creation and no-self-install guards
- the `plugin.*` capability surface, the events, the persistence/locality/portability split, the settings dimensions, the explicit rejections, and the consequences for later specs

This file honors File 22's six-class set; a plugin carries a `declared_trust_hint`, File 22 computes `effective_trust` from provenance, the install-time capability-manifest review, and integrity verification, and File 06 narrows tiers against it. The zero-monetary-spend signing reality (`unit15` D15.D.1) is realized exactly as `security.trust-model` (File 22 §9.4) fixes it: no code-signing certificate is assumed; ship-with plugins inherit the application's installation trust, user-authored plugins are `User`, third-party packaged or sideloaded plugins are `Sideloaded` or `Community`, and signature verification is the declared evidence path that may establish `Verified`.
- **Who may install, and the agent boundary.** `systems/17-agent-self-modification.md` draws the line by *who initiated the installation*: agent → custom tool (scoped, via `tools.register_custom`); user → plugin (global, versioned, via the install pipeline). `codex_recommendations.md` §9.4 chooses “controlled extension generation” over both unrestricted self-editing and zero self-modification. - **A bundle that can do anything, or the no-override invariant.** A plugin bundles executable contributions, so it could in principle reach for security-critical state. `core.extension-planes` (File 01 §6.14) is explicit: “extensions must not be able to override security-critical system state (environment variables controlling paths, linkers, or interpreters; credential storage; policy kernels).” This file enforces that structurally: a plugin's executable contributions run through the Wasm restricted host or the one `Sandbox` (§8); a plugin's settings contributions cannot replace a `Core` definition or register outside their namespace (`settings.setting-definition`, File 15 §3.4); a plugin's policy contributions are narrowing-only (`policy.source-approval-flow`, File 06 §9; `ledger.hook-registration-discovery`, File 10 §8.3); and no lease, trust override, or contribution may pierce a `permission_floor` (`policy.permission-floor`, File 06 §7).

## 1. Chosen Model

Anchor: `plugin.chosen-model`

### 1.1 Definition

A `Plugin` is a durable, identified, versioned, installable bundle of contributions. Its `PluginManifest` (§4) declares a set of typed contributions — capabilities, instructions and knowledge, surfaces and panels, integrations and hooks, automations and workflows, settings and presets — and each contribution registers into its own canonical registry through the same path a built-in contribution uses. Direct plugin-owned contributions carry `Plugin` runtime source; bundled integrations carry the runtime source of the connected integration plus plugin bundle ownership. A plugin adds to what the system can do without altering the system's source code, its schema, or its execution model.

A plugin is not a subsystem, not a work surface, not a control rail, and not a separate execution architecture (`core.extension-integrity`, File 01 §7.10). It owns no runtime, no private store, and no parallel registry. It is the cohesive packaging unit through which the system's extensibility planes (`core.extension-planes`, File 01 §6.14) are populated by contributions the user reviews and the registries already accept.

The `PluginRegistry` (§9) is the one catalogue of installed plugins. It holds each plugin's identity, version, lifecycle state, trust and integrity state, and the contribution-attribution index that ties registered contributions and bundled integration references back to the plugin that owns them. It is the bundle-lifecycle layer over the existing registries, never a second copy of the contributions.

### 1.2 Purpose

The system's reach is bounded by what it can do, what it knows, where it can act, and how it is configured. Extension is how that reach grows: a developer-oriented user wants engineering tools, code-review skills, and a git-graph panel; a researcher wants citation tools, a literature-review workflow, and an academic persona; an integrator wants a connector to an external service. Each is a coherent set of contributions across several planes that belong together, install together, are reviewed together, and are removed together. The plugin is that coherent set, packaged once and registered through the one substrate so it composes with everything else.

The reframe is load-bearing: a plugin is **not** a second application embedded in the first, and it is **not** a privileged path that bypasses review. It is a reviewed bundle whose contributions are ordinary registrations — a capability is a `CapabilityDeclaration`, a skill is an `InstructionFragment`, a workflow is a `WorkflowTemplate`, a surface is a `SurfaceContract`, a setting is a `SettingDefinition` — each carrying enough source and bundle ownership metadata for the system, the user, and the audit trail to know where it came from. Because the registries already exist, the cost of the contribution after the first is flat (`core.extension-planes`, File 01 §6.14).

### 1.3 Rule

- There is one `Plugin` primitive, one `PluginManifest` contract, one `PluginRegistry`, and one contribution-point taxonomy. No subsystem, surface, or plugin introduces a parallel plugin registry, a parallel contribution store, a private plugin runtime, or a contribution path that bypasses the one canonical registries.
- A plugin contributes by declaration: every contribution registers into its owning registry through the same path a built-in uses (`core.extension-planes`, File 01 §6.14), carrying either direct `Plugin` runtime source or runtime-source plus plugin bundle ownership, with trust state attached to the relevant source. A plugin owns no execution; its executable contributions run through the existing backend descriptors and the one `Sandbox` (§8).
- A plugin is reviewed before its contributions become invocable. Installing, updating, enabling, disabling, and uninstalling a plugin pass the proposal-first source-approval flow (`policy.source-approval-flow`, File 06 §9) and trust establishment (`security.trust-model`, File 22 §9); registration completes only when the flow completes (§7).
- A plugin's contributions register and unregister atomically with the bundle, tracked by the contribution-attribution index (§9). Disabling a plugin flips its enabled flag so its contributions stop being invocable while its registry entries, files, and settings are retained; uninstalling removes its files and orphans its settings values non-destructively (`settings.setting-definition`, File 15 §3.4).
- A plugin is never installed, enabled, or updated silently, and never by the agent. The agent discovers and suggests; the user installs (§12). AI-assisted customization uses the same paths as manual customization (`core.extension-integrity`, File 01 §7.10).

### 1.4 Boundary

This file owns the plugin bundle, its manifest, the contribution-point taxonomy, the permission manifest, the bundle-granularity trust/integrity/approval binding, the plugin registry and attribution index, the install/update/lifecycle, discovery and distribution, the agent/user boundary and promotion path, and the `plugin.*` capability surface. It does not own the per-contribution registries, the policy engine, the trust model, the sandbox, the MCP protocol, the application installer, storage, or sync — those are realized through their owning files.

## 3. The `Plugin` Primitive and the Bundle Contract

Anchor: `plugin.plugin`

### 3.1 Definition

A `Plugin` is the durable object binding a `PluginManifest` (the declaration of what the bundle contributes) to a set of bundled artifacts (the contribution payloads) and a registry record (the installed-bundle lifecycle state). The manifest is the contract; the artifacts are the implementation behind it; the registry record is the live state.

### 3.2 The Field Set

A `Plugin` carries:

- `plugin_id` — stable identity; a globally unique slug; display name; optional description, author, license, and homepage. The identity survives updates and re-installation; contributions, attribution, and the source label reference it.
- `version` — the plugin's semantic version; the unit of update, compatibility, and integrity (§7.4, §10.3).
- `compatibility` — the minimum (and optional maximum) application version the plugin requires, and the canonical-specification or schema version its contributions target, so an incompatible plugin is catalogued as unavailable rather than registered into a contract it does not satisfy (mirroring File 05 §9.4's platform-as-availability rule).
- `manifest` — the `PluginManifest` (§4): the typed contribution set, the permission manifest, the entry module, the trust hint, and the profile affinity.
- `source` — the install source and provenance (§11.1): built-in-bundled, user-authored-local, packaged-archive, or registry-published, with the trust hint the source confers.
- `bundled_artifacts` — the contribution payloads the manifest references (executable modules, schema files, skill and knowledge documents, workflow bodies, panel components, persona and preset definitions, instruction sources), resolved relative to the installed bundle and addressed by content hash for integrity (§7.4).
- `registry_record` — the live `PluginRegistry` state (§9.2): installed version, lifecycle state, enabled state per scope, trust and integrity state, the contribution-attribution index, and diagnostics. Registry state lives on the record, never on the manifest.

### 3.3 Rule

- A `Plugin` carries exactly the fields above; the manifest is the immutable-for-the-version contract, the bundled artifacts are the referenced payloads, and the registry record is the mutable installed-bundle state.
- A plugin's identity is stable across updates; a new version produces a new manifest and integrity record and supersedes the prior version's registry record (§10.3), mirroring `capability.registered-capability` (File 05 §10.2).
- A plugin owns no execution and no private store: its contributions are registrations in the one registries, and its registry record references them through the attribution index rather than duplicating them.

### 3.4 Boundary

File 05 owns the capability declaration and registered-capability state a plugin's capability contributions become; File 20 owns the physical storage of the installed bundle and its blob store; File 22 owns the trust and integrity state; this file owns the bundle object that binds them. The owning files own each contribution kind.

## 4. The `PluginManifest` and Contribution Declarations

Anchor: `plugin.manifest`

### 4.1 Definition

The `PluginManifest` is a plugin's typed, source-authored, immutable-for-the-version declaration of what it contributes and what it requires. It is the surface the source-approval flow reviews, the validator checks, and the lifecycle service registers. It is a contract, not a physical file format; the serialization (a manifest document and a bundle directory or archive) is the storage and Packaging specs' realization, and the bundled-workflow and bundled-knowledge declarations the owning files fixed are referenced, not re-specified.

### 4.2 The Manifest Field Set

A `PluginManifest` carries:

- **Identity and compatibility** — `plugin_id`, `version`, display name, description, author, license, homepage, and `compatibility` (§3.2). These drive discovery, presentation, update, and incompatibility diagnostics.
- **The contribution set** — a list of typed `Contribution` declarations (§4.3), each naming its `ContributionKind` (§5), its owning-registry-typed declaration, its bundled-artifact reference, and its per-contribution metadata. The contribution set is the body of the manifest.
- **Dependencies** — typed required and optional dependencies on plugins, built-in capabilities, MCP servers, provider profiles, runtime prerequisites, or sidecar prerequisites. Dependency version policy reuses File 34 §3.4's `Pinned`, `CurrentActive`, and `LatestCompatible` vocabulary rather than minting plugin-specific policy terms.
- **The permission manifest** — the `PluginPermissionManifest` (§6): the bundle-level declared effect envelope (required permission tiers and floors, touched-resource classes, filesystem paths, network targets, required builtin capabilities, backend kinds, and whether the bundle registers policy inspectors, hooks, or settings).
- **The entry module** — an optional startup contribution: a sandboxed module run on activation with a declared, reviewed capability list, used to bind, initialize, or probe manifest-declared contributions when that work cannot be represented as static data. An entry module is a Wasm contribution under §8; it has no privileged access beyond its declared, approved capabilities and may not introduce undeclared contributions, capabilities, hooks, instructions, resources, backends, or data-egress paths.
- **The trust hint** — the source-asserted trust class (`security.trust-model`, File 22 §9.3); one input the user weighs, never the determinant (§7).
- **Profile affinity** — the profiles for which the plugin is recommended and the per-profile default bundles (§11.4) it delivers; an advisory recommendation, not an enablement.

### 4.3 The `Contribution` Declaration

A `Contribution` is one typed entry in the manifest's contribution set. Each declares:

- `contribution_kind` — the closed-canonical kind (§5) plus `Custom { namespace, name }`; it determines the owning registry and registration path.
- the **owning-registry-typed declaration** — the contribution's payload in the shape the owning registry admits (a `CapabilityDeclaration` for a capability, a `SurfaceContract` for a surface, a `SettingDefinition` for a setting, a `WorkflowTemplate` reference for a workflow, an `InstructionFragment` for a skill, a hook subscription declaration for a hook, and so on). This file does not redefine those shapes; it requires the contribution carry the shape its owning file fixes.
- `bundled_artifact_ref` — the content-addressed reference to the contribution's payload within the bundle (an executable module, a schema, a document, a body), where the kind requires one.
- `contribution_id` — the contribution's own stable identity within the bundle, used for attribution (§9), dependency analysis (§9.4), and per-contribution diagnostics.
- per-kind metadata the owning registry requires (a capability's permission tier, a panel's default slot, a knowledge entry's tags and scope, a workflow's category and agent-invocability).

### 4.4 Composition Downward

A plugin's contribution set may itself include references that compose: a plugin may bundle an MCP server reference (whose tools register through the MCP path as `McpServer`-source capabilities), may bundle a surface (whose own `SubsystemSurfaceSpec` declares capabilities, panels, and instruction sources), and may bundle a workflow that references a sub-workflow or a skill the same plugin contributes. This is the “tiers compose downward” rule of `unit12` D12.7 realized as bundle composition: a plugin is the outer bundle, and its contributions may be smaller registrable units. A contribution may not, through this composition, escape its kind's owning registry or its source-approval review; a bundled MCP server reference is still gated, a bundled surface is still validated by `worksurface.registry` (File 25 §10.3), and a bundled custom node kind is still registered through `workflow.workflow` (File 34 §3.4).

Bundled integration contributions carry two attribution facts. The runtime source is the source class and source instance of the thing that actually executes or connects (`McpServer`, `Api`, `Plugin`, `UserDefined`, or another canonical source). Bundle ownership is the contributing plugin id and version. Policy, approval, trust, and egress evaluate the runtime source; disable, uninstall, dependency impact, and bundle diagnostics evaluate bundle ownership.

### 4.5 Validation

A `PluginManifest` is validated before the plugin is installed or enabled. The validator rejects a manifest that is malformed: a duplicate or namespace-violating `plugin_id`, a contribution whose owning-registry declaration is invalid (reusing each owning registry's validator — `capability.capability-registry` File 05 §12.3, `worksurface.registry` File 25 §10.3, and the rest), a contribution whose bundled-artifact reference is unresolved, a permission manifest that understates the contributions' derived effects (§6), an entry module that requests undeclared capabilities or attempts to widen the declared envelope, a required dependency that is missing or incompatible, or a contribution that reaches for a private substrate the no-private-architecture invariant forbids (§5.4). A required contribution whose owning registry rejects it blocks installation; an optional contribution whose reference or dependency is unresolved enters an `Unavailable` diagnostic state, never a silent substitution (mirroring `workflow.library`, File 34 §9.4). Validation runs at install and at every update.

### 4.6 Rule

- A `PluginManifest` declares identity, a typed contribution set, typed dependencies, the permission manifest, the entry module, the trust hint, and profile affinity; it is the immutable-for-the-version contract the review and registration consume.
- Each `Contribution` carries its owning-registry-typed declaration, its bundled-artifact reference where required, and its identity; this file does not redefine the owning shapes.
- A manifest validates before install and update; understated effect envelopes, invalid contributions, unresolved required references, and private-substrate reaches block; unresolved optional references enter an `Unavailable` state, never a silent substitution.

### 4.7 Boundary

Each owning file owns the declaration shape of the contribution it admits; File 06 owns the review the manifest feeds; File 22 owns the trust hint's evaluation. This section owns the manifest contract, the contribution-declaration shape, the composition-downward rule, and the manifest validator.

## 5. The Contribution-Point Taxonomy

Anchor: `plugin.contribution-points`

### 5.1 Definition

The contribution-point taxonomy is the catalogue of what a plugin may contribute. It is organized by the six extension planes (`core.extension-planes`, File 01 §6.14), and for each kind it names the owning file, the canonical registry the contribution lands in, and the registration path it uses. `ContributionKind` is closed-canonical with the `Custom { namespace, name }` extension. The taxonomy is the structural realization of the flat-marginal-cost rule: because every kind maps to an existing registry, contributing one more thing costs no new architecture.

### 5.2 The Catalogue by Plane

- **Capabilities plane.** Direct `Capability` contributions are `CapabilityDeclaration`s admitted to the Capability Registry under the `Plugin` source (`capability.capability-source`, File 05 §9.1; `capability.runtime-mutation`, File 05 §16.2). `CustomNodeKind` contributions register through `workflow.workflow` (File 34 §3.4). `Provider` contributions are `ModelProfile`/`ProviderProfile` declarations admitted to the model and provider registries (`model.model-profile`, File 16 §4; `provider.provider-adapter`, File 17 §3) behind their typed contracts. Provider contributions may add provider metadata, adapters, model catalogues, tokenizer bindings, profiles, or offering projections only through Files 16 and 17; they do not create a private model-call path and must preserve vault-backed credentials, data-boundary requirements, health state, rate limits, usage accounting, pricing snapshots, model-selection records, and provider events.
- **Instructions and knowledge plane.** `Skill` (instruction-fragment) contributions are `InstructionFragment` units participating in the one `TemplateLibrary` (`workflow.template-family`, File 34 §7) and loaded with their declared authority class (`context.instruction-sources-workspace-files`, File 13 §16). `KnowledgeEntry` contributions register through the knowledge layer carrying `source = PluginBundled` (`retrieval.*`, File 12). `InstructionSource` contributions (an `ATLAS.md`-family fragment a plugin attaches) participate in the instruction-file hierarchy (`workspace.instruction-files`, File 24 §9). `Persona` contributions are style/instruction presets applied as instruction sources under their declared authority class (`context.instruction-sources-workspace-files`, File 13 §16). Plugin-contributed prompts, skills, personas, tool descriptions, and instruction sources never become hidden governing instructions merely because they came from a plugin; they render through File 13's authority-class and instruction-boundary rules, with governing authority only when granted by an explicit trusted path.
- **Surfaces plane.** `Surface` contributions are `SurfaceContract`s registered through `subsystems.register` (`worksurface.registry`, File 25 §10.2). `Panel`/`Widget`/`View` contributions are `PanelKind`/widget declarations the surface or UI customization layer admits (`worksurface.state-declaration`, File 25 §5; File 38). `Rail` contributions register through the one `RailRegistry` (`controlrail.registry`, File 26 §14); `Command` (slash-command) contributions register through the command rail (File 26 §8). `ViewPreset` contributions register through the preset library (`worksurface.views-presets`, File 25 §7). `Theme` contributions register through the UI customization theming layer (File 38).
- **Integrations plane.** `McpServerRef` contributions register an external MCP server through the MCP path (File 36) as `McpServer`-source capabilities. `ExternalApiDefinition` contributions register a declarative user-defined HTTP integration as `Api`-source capabilities (`capability.capability-source`, File 05 §9.1); each endpoint typically lowers to File 05's outbound `HttpEndpoint` backend with auth by vault reference, egress governance, and declared network targets. A capability that uses `HttpEndpoint` directly is governed the same way. A plugin-hosted local service is not an `ExternalApiDefinition`; it is plugin code (`Shell`/`ManagedProcess` or `ServiceMethod`) and any localhost `HttpEndpoint` that calls it is only the invocation bridge. `Hook` contributions register through `ledger.hook-registration-discovery` (File 10 §8.3) and carry File 10's existing subscription fields: `hook_category`, `authority_class`, fail-direction, blocking status, `event_kinds`, I/O schema, and `timeout_ms`; File 10's plugin-source authority and fail-direction defaults still apply. `CustomEventKind` contributions register through the `Custom` event extension (`ledger.event-stream`, File 10 §5) and declare namespace, event name, payload schema, sensitivity class, retention/audit behavior, stream-vs-ledger eligibility, redaction behavior, and versioning policy. `Sensor` contributions register through the perception sensor extension (`perception.*`, File 19) — for example a grounding backend — and inherit their modality-specific consent gates unconditionally; plugin source approval, trust class, or install approval never grants camera, audio, screen, wake-word, or equivalent capture consent.
- **Automation plane.** `Workflow`, `Template`, and `Macro` contributions register into the one `TemplateLibrary` through the `[[plugin.workflows]]` manifest and the proposal-first path (`workflow.library`, File 34 §9.3). `Automation` and `Trigger` contributions register through the one scheduler and trigger rail (`automation.*`, File 33), as templates until accepted. `CustomTriggerKind` contributions register a new trigger kind through that rail's `Custom` extension, declaring their owning registry, registration path, and the validation it applies exactly as a `Custom` node kind does (`workflow.workflow`, File 34 §3.4).
- **Configuration plane.** `SettingDefinition` contributions register with `source: Plugin` (`settings.setting-definition`, File 15 §3.2). `ProfileDefaultBundle` contributions deliver a profile's per-profile defaults on selection, accepted as the exact bundle version presented (§11.4). A bundle's settings values seed File 15's profile-layer defaults (`settings.profiles`, File 15 §7), never explicit user rows; its non-settings presets — memory presets, view presets, watch templates, and curriculum templates — seed their owning substrates' profile-layer defaults through those substrates' own paths, never as settings rows.

### 5.3 Rule

- `ContributionKind` is closed-canonical-plus-`Custom`; every kind maps to exactly one owning file, one canonical registry, and one registration path. A plugin contributes by declaring contributions of these kinds, never by editing a central file or injecting model-request instructions in place of a registration (`capability.explicit-rejections`, File 05 §19's model-request-only-extension rejection).
- A `Custom` contribution kind is a registered extension over an existing registry, never a new registry or runtime; it declares its owning registry, registration path, and the validation its target applies, exactly as a `Custom` node kind does (`workflow.workflow`, File 34 §3.4).
- Every directly plugin-owned contribution carries the `Plugin` runtime source and trust. A bundled integration contribution carries both runtime source and bundle ownership (§4.4, §9.3). Once registered, source and ownership surface as metadata, and the contribution is otherwise indistinguishable from a built-in of the same kind (`capability.sourcing-equivalence`, File 05 §9.3).
- Canonical id collisions are handled by each owning registry's source namespacing and collision rules. User-facing aliases, shortcuts, command-palette entries, panel placements, and default UI placements from plugins are override proposals resolved through settings and the owning surface or rail registry (File 26 for commands and shortcuts), never by plugin load order; source and bundle attribution remain visible.

### 5.4 The No-Private-Architecture Invariant for Plugins

A plugin owns only its contributions' payloads and declared defaults. It must reuse, never privately reimplement, every shared substrate primitive through its canonical contract — the same closed list `worksurface.no-private-architecture` (File 25 §12.2) fixes for surfaces: blocks, capabilities, policy, tool surfaces, execution, world model, version graph, context assembly, settings, memory/retrieval/knowledge, routing, artifacts/evidence, workspaces, storage, sync, security/trust, sandbox, providers, ledger/events, and service-layer ownership. A plugin that reaches for a private store, a parallel registry, a private execution path, or security-critical state (`core.extension-planes`, File 01 §6.14) cannot register; the manifest validator (§4.5) and the owning registries' validators enforce this structurally.

### 5.5 Boundary

Each owning file owns its contribution kind's declaration, registry, and registration; File 01 §6.14 fixes the extension planes; File 25 §12.2 fixes the reuse list. This section owns the taxonomy that maps each kind to its owner and the plugin-level no-private-architecture invariant.

## 6. The Permission Manifest and Declared Effect Envelope

Anchor: `plugin.permission-manifest`

### 6.1 Definition

The `PluginPermissionManifest` is the bundle-level declared effect envelope: the upper bound over the effects of all the plugin's contributions, derived from each contribution's declared metadata. It is what the install-time review surfaces (`security.trust-model`, File 22 §9.5; `policy.source-approval-flow`, File 06 §9) so the user grants or withholds the bundle's reach as a whole, in addition to the per-contribution gating policy applies per call.

### 6.2 The Envelope

The permission manifest declares, as the honest union over the contribution set: the required permission tiers and floors; the touched-resource classes (`capability.touched-resources`, File 05 §6); the required filesystem path patterns; the required network targets (composed with egress governance, `security.egress-governance`, File 22 §11); the required builtin capabilities the plugin's contributions invoke; the declared dependencies (§4.2); the backend kinds that appear (`capability.backend-binding-lifecycle`, File 05 §10.4); the executable artifact classes and resource limits; the side-effect, replay, and data-egress classes; the sandbox and isolation requirements (`sandbox.contract`, File 23 §3); and whether the bundle registers policy inspectors, hooks, settings, instruction sources, sensors, provider integrations, or source-level rules (the policy-extension summary `policy.source-approval-flow`, File 06 §9.3 already names). The envelope is the plugin counterpart of a workflow's `declared_effect_envelope` (`workflow.workflow`, File 34 §3.2).

For update review, the canonical envelope diff is the change set over this envelope. It includes at least: new executable artifacts; changed executable-artifact hashes; backend-kind changes; broader capability scope; broader touched resources; new or changed hooks; new instruction contributions; new or broader sensor capture; new or changed provider or model-call paths; new data-egress paths; new or changed credential requirements; new dependencies; higher permission floors; broader sandbox or network requirements; and source-approval-relevant trust, provenance, or integrity changes. A same-envelope update is one whose diff contains none of these expansions and whose source and integrity verification still pass.

### 6.3 No Understatement

Validation recomputes the envelope from the contributions and rejects a manifest whose declared envelope understates the actual effects (§4.5), exactly as `workflow.validation` (File 34 §12.1) rejects an understated workflow envelope. The declared envelope feeds the source-approval review, the install preview, the dependency-impact projection (§9.4), the update re-review trigger (§10.3), and the import diagnostics (§11.5). A contribution may not register an effect outside the envelope the user approved; an attempt is a typed registration failure, not a silent widening.

### 6.4 Rule

- The permission manifest is the honest union of the contributions' declared effects; validation rejects understatement; the envelope is what the bundle-level review surfaces.
- The envelope composes per-contribution metadata; it does not replace per-call policy — every contribution call is still gated by `policy.effective-tier-resolution` (File 06 §4), and a `permission_floor` (`policy.permission-floor`, File 06 §7) is never pierced by an approved bundle envelope, a lease, or a trust override.
- Expanding the envelope on update triggers re-review (§10.3); a contribution effect outside the approved envelope is a typed failure.

### 6.5 Boundary

File 05 owns the per-contribution touched-resource and tier declarations the envelope unions; File 06 owns the review the envelope feeds and the per-call gating; File 22 owns the trust class that narrows it. This section owns the bundle-level envelope and the no-understatement rule.

## 7. Trust, Integrity, and Source Approval

Anchor: `plugin.trust-integrity-approval`

### 7.1 The Bundle-Granularity Review

When a plugin installs or updates, the proposal-first source-approval flow (`policy.source-approval-flow`, File 06 §9) runs at the bundle granularity: the policy layer constructs a `SourceRegistrationProposal` (`policy.source-approval-flow`, File 06 §9.3) of kind `Plugin`, populated from the manifest — the source identity (id, version, install path or registry URL, declared author, declared trust hint), the declared contributions with their tiers/floors/touched-resources/replay-classes, the computed permission manifest and source-risk summary, the registered-entry trust state, the backend-kind summary, and the policy-extension summary. The user accepts declared defaults, customizes per contribution or per source, denies outright, defers source-level policy, or cancels — the same user options `policy.source-approval-flow` (File 06 §9.4) fixes. Closing or dismissing the flow is `CancelRegistration`; the runtime never registers an invocable plugin whose review the user did not complete (`policy.source-approval-flow`, File 06 §9.7; `security.trust-model`, File 22 §9.5).

### 7.2 Trust Establishment

A plugin's trust class is established by `security.trust-model` (File 22 §9): by provenance plus the install-time capability-manifest review, by evidence-based verification where authorship evidence exists, and by signature verification as the declared path to `Verified` (File 22 §9.4). The manifest's declared trust hint is one input, never the determinant. Trust is installation-local: an imported or synced plugin's trust record is provenance and evidence only and does not activate the plugin or raise its effective trust without local approval and integrity verification (`security.trust-model`, File 22 §9.7). The zero-monetary-spend reality is honored: ship-with plugins inherit the application's installation trust; user-authored plugins are `User`; third-party packaged or sideloaded plugins are `Sideloaded` or `Community`; and trust narrowing (`policy.trust-mapping-defaults`, File 06 §9.6) raises effective tiers for lower-trust sources by default.

### 7.3 Integrity Binding

Installation binds the approval to a `SourceIntegrityRecord` (`security.trust-model`, File 22 §9.6): the canonical-encoding hash over the manifest, the contribution ids and versions, and the bundled-artifact hashes, plus the source version, provenance, and approval decision. A later content mismatch is a tamper signal that re-gates the plugin and downgrades its trust until re-reviewed; a `Verified` or bundled plugin whose content fails integrity is treated as tampered. The hash is computed over a declared `CanonicalEncoding` (`core.canonical-hash`, File 01 §7.14), never physical storage bytes; this file defines no new canonical hash and inherits File 22's `SourceIntegrityRecord` hash and File 21's `PackageManifest` bundle-integrity hash.

### 7.4 Update and Revocation

A plugin update creates a new version and a new integrity record; it never silently rewrites the approved record (`security.trust-model`, File 22 §9.6). Compatibility, re-review, and trust requirements resolve from the new record, the prior approval, the canonical envelope diff (§6.2), and File 06 policy (§10.3). Revoking a plugin's trust disables or quarantines its contributions and records the revocation in the audit overlay (`ledger.hash-chained-audit-log`, File 10 §16.4); the records the plugin produced are preserved (`core.non-destructive-by-default`, File 01 §7.13). A trust downgrade staleness-revalidates the plugin's leases (`policy.mid-execution-policy-re-evaluation`, File 06 §10.2).

### 7.5 Rule

- A plugin's contributions become invocable only after the bundle-granularity source-approval flow completes; closing the flow is `CancelRegistration`, never silent registration.
- A plugin's trust class is established by File 22 from provenance, review, and integrity; the declared hint is one input; imported trust is inert until local approval.
- Installation binds the approval to a content-integrity record over a canonical encoding; a content mismatch re-gates and downgrades; an update creates a new integrity record and re-reviews on envelope expansion; revocation disables contributions and preserves produced records.

### 7.6 Boundary

File 06 owns the source-approval flow's user options, resolution, and persistence; File 22 owns the trust classes, establishment, verification, integrity, and revocation; File 10 owns the audit overlay. This section owns how a plugin presents to that flow at the bundle granularity and how integrity binds an approval to the installed bundle.

## 8. Plugin Code Backends and Isolation

Anchor: `plugin.code-backends`

### 8.1 Backends Are Reused, Not Reinvented

A plugin's executable contributions — tool handlers, the entry module, dynamic service handlers, and executable panel components — run through the existing backend descriptors (`capability.backend-binding-lifecycle`, File 05 §10.4): a `Wasm` module resolved against the loaded Wasm module registry, a `Shell` subprocess confined by the sandbox, a `ServiceMethod` resolved against the dynamic service registry, or an outbound `HttpEndpoint` whose auth comes from the vault by reference. The default and recommended plugin code backend is `Wasm`, compiled and cached and sandboxed through the wasmtime restricted host with no filesystem, network, or environment access; a Wasm contribution is eligible for constrained execution after install-time review only when every host import, resource limit, and host interaction is enumerated, mediated, and revocable through the sandbox and capability surface. A `Shell`-backed contribution is not sandboxed by language and carries a higher tier and a confined `ManagedProcess` (File 23 §5) on every call. `Wasm` restricted-host and `Shell` backends have no ambient outbound network; external API declarations and governed `HttpEndpoint` calls are the sanctioned outbound paths. This file introduces no new sandbox; it consumes File 23.

### 8.2 The Dynamic Service Backend

A plugin whose contribution needs a backend service handler (rather than a closure or a static service) registers it through the dynamic service registry (the `register`/`unregister`/`dispatch`/`list` contract File 42 §9 owns), so a plugin-loaded handler is resolvable like a static one and is torn down on unload. A `ServiceMethod`-backed capability contribution binds to that dynamic registration; its lifecycle follows the plugin's (§10). This realizes the plugin-loaded-capability dynamic-service backend `capability.backend-binding-lifecycle` (File 05 §10.4) names.

### 8.3 Isolation and the No-Override Invariant

A plugin's executable contributions run least-privilege: a Wasm contribution at the restricted host's zero-authority baseline, a Shell contribution at the sandbox tier its trust and declared effects require (`sandbox.isolation-tiers`, File 23 §4). No plugin contribution, of any backend, may override security-critical state — environment variables controlling paths, linkers, or interpreters; credential storage; or the policy kernel (`core.extension-planes`, File 01 §6.14) — and the environment-allowlist enforcement (File 23 §5) and the secret boundary (`secret.backend-boundary`, File 22 §4) make that reach unavailable by construction. A plugin contribution that declares a closure backend declares `replay_class: not_replayable` (`capability.backend-binding-lifecycle`, File 05 §10.4); a crashed plugin process is reaped and retried with backoff by the runtime lifecycle, never left orphaned (`run.cancellation`, File 04 §17.3; File 42).

Shell, script, local-service, and endpoint-binding contributions must not accept or compose command strings containing inline secret values. Credentials are supplied only through vault references resolved by sandbox `EnvPolicy`, stdin, restricted temporary credential files cleaned up after use, or native credential-store integration. Pre-dispatch validation rejects detected inline secrets with a typed error before process launch; terminal-output redaction remains defense-in-depth.

### 8.4 Rule

- A plugin's executable contributions run through the existing backend descriptors and the one `Sandbox`; `Wasm` is the default constrained backend, not an inherent safety grant; `Shell` carries a higher tier and a confined process; no new sandbox is introduced.
- A plugin's backend service handlers register through the dynamic service registry and are torn down on unload.
- No plugin contribution may override security-critical state or exceed the sandbox tier its trust and declared effects require; least-privilege is the default; crashed plugin processes are reaped, not orphaned.

### 8.5 Boundary

File 05 owns the backend descriptors and the dynamic-service binding; File 23 owns the sandbox, isolation tiers, and process control; File 22 owns the secret boundary; File 42 owns the reaper. This section owns the rule that plugin code reuses them and overrides nothing.

## 9. The `PluginRegistry`, Contribution Attribution, and Dependency Impact

Anchor: `plugin.registry`

### 9.1 Definition

The `PluginRegistry` is the one catalogue of installed plugins. It admits an installed plugin, pairs it with mutable registry state, and exposes lookup, enumeration, enable/disable, the lifecycle operations (§10), and the registration-mutation event stream. There is no parallel plugin store and no per-plane plugin catalogue; the contributions themselves live in their owning registries, and this registry tracks the bundles and their attribution. A bundled connector the registry catalogues — an `McpServerRef` or `ExternalApiDefinition` — is reviewed and registered through its own integration path (File 36; `capability.capability-source`, File 05 §9.1) under the bundle-granularity source approval (§7.1); the registry records only its bundle attribution and runs no second connector review.

### 9.2 The Installed-Plugin Record

An installed plugin's registry record carries: the installed `plugin_id` and `version`; the `lifecycle_state` (`Installing`, `AwaitingReview`, `Installed`, `Activating`, `Active`, `Disabled`, `Updating`, `Quarantined`, `Uninstalling`, `Failed`); the `enabled` state, scoped global, workspace, or conversation (`capability.lifecycle`, File 05 §16.3's scoped-enable discipline); the `trust_state` and `integrity_state` (§7); the `source` and provenance (§11.1); the **contribution-attribution index** — the set of registry entries and bundled integration references (capability ids, surface ids, rail ids, setting keys, hook subscription ids, workflow ids, knowledge-entry ids, `McpServerRef`s, `ExternalApiDefinition`s) this plugin owns, each cross-referencing the owning registry's entry or integration reference; and diagnostics (last load result, failed-contribution reasons, last integrity-verification result). Registry state mutates without changing the manifest; a new version supersedes the prior record.

### 9.3 Attribution Records Runtime Source and Bundle Ownership

The attribution index is not a duplicate of the contributions. It is an authoritative registration-time projection over each owning registry's source and bundle facts. For directly plugin-owned contributions, the runtime source is `Plugin { plugin_id, plugin_version }`. For bundled integrations, the runtime source remains the actual executing or connected source (`McpServer`, `Api`, or equivalent), and the registered entry carries `contributing_bundle: { plugin_id, plugin_version }` (File 05 §10.1) or the equivalent back-reference in its owning registry. The lifecycle service uses bundle ownership to register, disable, quarantine, and unregister a bundle's contributions atomically. Policy, approval, trust, and egress use the runtime source.

Lazy bundled integrations are attributed before their tools materialize. The attribution index records the bundled integration reference (`McpServerRef`, `ExternalApiDefinition`, or equivalent) from the manifest, then reconciles dynamically discovered capabilities under that reference as they appear. Uninstalling or disabling a plugin tears down the integration reference and cascades to currently registered and future capabilities under it; it does not depend on the remote integration being online during uninstall or rebuild.

### 9.4 Dependency Impact

The `PluginRegistry` exposes a dependency-impact projection derived from declared dependencies, contribution attribution, and the references other units hold to a plugin's contributions: workflows, automations, rails, surfaces, view presets, and other plugins that depend on a capability, skill, node kind, provider profile, integration, or surface a plugin contributes. The projection is computed from canonical references, not stored as a separate database (the same posture `workflow.library`, File 34 §9.5 takes). Required missing or incompatible dependencies fail activation or park the plugin in `AwaitingReview`; optional missing dependencies make only the dependent contribution `Unavailable`. Disabling, uninstalling, downgrading, revoking, or quarantining a plugin produces typed diagnostics listing the affected dependents; a dangerous removal requires typed-confirmation, creates `Unavailable` references with recovery actions, or parks affected dependents until the user repairs or accepts the change — never a silent break and never a silent deletion (`worksurface.registry`, File 25 §10.4's missing-reference discipline).

### 9.5 Rule

- There is one `PluginRegistry`; it catalogues installed bundles and their lifecycle, trust, and attribution state; it never duplicates the contributions, which live in their owning registries.
- Contribution attribution records runtime source and bundle ownership; it lets a bundle register, disable, quarantine, and unregister atomically while policy still evaluates the source that actually executes.
- Dependency impact is surfaced through a projection over declared dependencies and references; weakening a plugin's contributions is never silent and never silently deletes a dependent.

### 9.6 Boundary

Each owning registry owns its entries, runtime source, and bundle-ownership back-references; File 20 owns the registry's physical persistence and projection rebuild. This section owns the installed-plugin record, the attribution index, and the dependency-impact projection.

## 10. Install, Update, Enable/Disable, and Uninstall

Anchor: `plugin.lifecycle`

### 10.1 Install and Activation

A plugin is installed and activated in deterministic steps:

1. **Acquire** the bundle from its install source (§11.1) into the user-writable plugin directory under the data root (`storage.physical-layout-locality`, File 20 §8.3 places it).
2. **Validate** the manifest and every contribution (§4.5).
3. **Review** through the bundle-granularity source-approval flow (§7.1) and **establish trust and integrity** (§7.2, §7.3).
4. **Stage** each manifest-declared contribution for its owning registry, recording provisional contribution attribution (§9.3). Registration is a capability call through the one pipeline and policy (`capability.runtime-mutation`, File 05 §16.2); it is not a privileged side door.
5. **Run the entry module** (if any) under its declared, approved capabilities (§8.1), bounded by a configurable activation timeout. The entry module may bind, initialize, or probe staged contributions but may not widen the declared envelope.
6. **Validate the staged projection** against the declared envelope (§6), then **commit** the registrations, **mark active**, and **emit** `PluginActivated` (§14).

A required contribution that fails to register, an entry-module timeout or crash, or an attempt to widen the envelope rolls back staged registrations, records a typed failure, and leaves the plugin `Failed` or `AwaitingReview`; it leaves no partial activation. An optional contribution that fails enters an `Unavailable` state with diagnostics. Activation is reconstructed at startup phase 3 (File 42; `capability.startup-registration`, File 05 §16.1 phase 3): installed plugins re-register their contributions, availability is re-evaluated, and a `Sideloaded` plugin not previously confirmed re-prompts for permission.

### 10.2 Enable and Disable

`enabled` is registry state, not a manifest field. Disabling a plugin flips its enabled flag so its contributions stop accepting new calls and are no longer surfaced while their registry entries stay catalogued (retained but not invocable), preserves the bundle's files and its settings values, and is reversible: re-enabling flips the flag back and the contributions are invocable again. Disable, like enable, is scoped — a plugin may be globally enabled but disabled within a workspace or conversation (`capability.lifecycle`, File 05 §16.3). Ordinary disable lets already-running calls complete under the recorded plugin version and produce ledger outcomes. Quarantine is the safety response to integrity, source-approval, sandbox, policy, or runtime behavior violations: it stops new calls and may cancel active calls through File 04's cooperative run-cancellation path with a typed reason, never by silent mid-effect abort. Disable is also the intermediate step of an update (old contributions disabled, new registered, then the old unregistered atomically; `capability.lifecycle`, File 05 §16.3).

### 10.3 Update

An update replaces an installed plugin with a new version. The new manifest validates, source and integrity verification run, and a new integrity record is created (§7.4). Re-review is required when the canonical envelope diff (§6.2) expands risk, when source or integrity verification fails, or when the user's update policy does not explicitly allow an unattended same-envelope update for that plugin/source. A same-envelope update may proceed unattended only when settings permit, source and integrity verification pass, and the envelope diff is empty; executable content changes still require that explicit same-envelope update policy, otherwise the update parks for review. The contributions swap atomically from the caller's perspective: in-flight calls against the prior version complete under the prior contract; new calls use the new contract. Updates are opt-in and default-off (§11.3); no plugin updates silently from the network.

### 10.4 Uninstall

Uninstalling a plugin stops new calls, unregisters all its contributions (atomically, via the attribution index), tears down bundled integration references including not-yet-materialized capabilities (§9.3), removes the bundle's executable files, and cleans up non-destructively: the plugin's settings values orphan rather than delete (hidden, inspectable, exportable, reclaimable if the plugin returns with a compatible definition; `settings.setting-definition`, File 15 §3.4); durable data the plugin's contributions produced (knowledge entries, workflow definitions, committed artifacts) is preserved by default and removed only on the user's explicit, itemized choice (the “also remove the N entries / M workflows this plugin added” confirmation); and historical references to the plugin's contributions remain resolvable through their recorded versions for replay (`worksurface.registry`, File 25 §10.4). In-flight calls complete under the recorded plugin version unless quarantine-triggered cancellation is required. Uninstall retains a non-executable tombstone containing plugin id, version, manifest hash, contribution ids, source provenance, integrity record, install/remove actors, removal time, and removal reason; sensitive manifest fields may be redacted only if identity, integrity, and contribution references remain reconstructable. Uninstall is a `UserApproval` operation escalating to typed-confirmation when dependents would break (§9.4).

### 10.5 Who May Drive the Lifecycle

Install, update, enable, disable, and uninstall are user-initiated capability invocations (§13) gated by policy. The agent may discover and suggest (§12.2) but may not install, update, or enable a plugin; registration capabilities are not privileged side doors and the agent cannot self-promote (`capability.runtime-mutation`, File 05 §16.2). A plugin's own lifecycle never registers or enables another plugin silently. Policy and safety systems may suspend contributions or move an installed plugin to `Quarantined` when its declared contract is violated; quarantine is reversible through explicit review and never deletes the plugin or produced records.

### 10.6 Rule

- Install acquires, validates, reviews-and-trusts, stages registrations, runs the entry module under approved capabilities, validates the staged projection, commits atomically with attribution, and reconstructs at startup; a required-contribution failure leaves no partial activation.
- Disable stops new calls and preserves files and settings reversibly; quarantine may cancel active work through typed cooperative cancellation; update validates, re-integrity-records, re-reviews on envelope expansion or failed verification, and swaps contributions atomically; uninstall unregisters atomically, removes executable files, retains a tombstone, orphans settings non-destructively, and preserves produced data by default.
- Install, update, enable, disable, and uninstall are user-only and policy-gated; the agent suggests but never drives the lifecycle.

### 10.7 Boundary

File 05 owns the registration mechanism and scoped-enable discipline; File 06 owns the gating; File 15 owns orphaned-value handling; File 20 owns the directory placement and reconstruction; File 42 owns startup-phase orchestration and the crash reaper. This section owns the bundle lifecycle and the user-only rule.

## 11. Discovery, Distribution, and the Ship-With Bundles

Anchor: `plugin.distribution`

### 11.1 Install Sources

A plugin is installed from one of a closed-canonical set of sources, each conferring a default trust hint (§7.2) and recorded as provenance: `BuiltinBundled` — shipped with the application and copied into the user-writable plugin directory on first run; `LocalDirectory` — a plugin draft or unpacked bundle on the user's disk (the destination of the promotion path, §12.4); `PackagedArchive` — a self-contained bundle file the user explicitly obtained and chose to install; `RegistryPublished` — resolved by id against a configured discovery registry. The source is a `Plugin`-source provenance fact (`capability.capability-source`, File 05 §9.1), not a trust grant; trust is established per §7. Normal installation creates an immutable, hash-bound installed snapshot. Editing a local source directory creates a candidate update that must pass the normal validation, source-approval, and integrity path. Live mutable development mode is a separate explicit setting, visibly marked as development-only.

### 11.2 The Discovery Surface

The discovery surface is a replaceable implementation behind a typed contract: given a query and a kind filter, it returns candidate plugins (and bundled-integration candidates) with a normalized candidate/effect summary. The summary includes identity, description, source provenance, trust hint, author, install reference, compatibility, integrity status where known, the §6 permission envelope, required approvals, dependencies, sandbox/backend classes, credential requirements, data-egress summary, package size, and lazy-population behavior. The same summary feeds discovery, install review, update review, and plugin management UI. There is no Atlas-hosted marketplace requirement; the discovery registry may be community-maintained, organization-hosted, or local, and a deployment with no registry configured still installs from local and packaged sources. Concrete registry endpoints, marketplace economics, and store mechanics are implementation and File 43's; this file owns that discovery is a typed, replaceable surface and that it never installs.

### 11.3 Agent-Suggested, Never Auto-Installed; Opt-In Updates

The agent reaches the discovery surface through a `ReadOnly`, agent-invocable capability (§13) and may suggest a plugin or a bundled integration that fits the work; every install passes the same user-gated install pipeline as a manual install (§10.1), and the agent cannot auto-install (`unit12` D12.7 realized; `capability.runtime-mutation`, File 05 §16.2). Updates are opt-in and default-off: a plugin updates only on the user's explicit action or under an explicit per-plugin/per-source update policy, never silently from the network by default. The update check, trusted-update-source allowlist, source/integrity verification requirements, and same-envelope unattended-update policy are settings (§16).

### 11.4 The Ship-With and Per-Profile Bundles

The application ships a set of per-profile plugins as the worked examples: each bundles the tools, skills, knowledge entries, workflows, personas, view presets, and panels for one user profile, and is the packaging mechanism that delivers the per-profile defaults earlier layers defer to “where do these live.” The installer image carries them (File 43); on first run, they are copied into the user-writable plugin directory and registered, lazily where disk budget warrants (only the active profile's plugin eagerly, others on activation). Seeding is idempotent and tombstone-aware: a user-uninstalled ship-with plugin is not silently re-seeded on app update; the system may offer to re-add it, but never auto-resurrects it. Selecting a profile at onboarding activates the corresponding plugin and accepts its `ProfileDefaultBundle` for the exact bundle version presented. `ProfileDefaultBundle` settings values seed File 15 profile-layer defaults, never explicit rows; later bundle updates may re-seed only the profile layer and never override explicit user rows. Later bundle updates require source-approval review before new or changed executable contributions become enabled (the same exact-bundle-version acceptance `workflow.library`, File 34 §9.3 fixes for profile-bundled workflows). A ship-with plugin is a plugin like any other; the registry distinguishes it only by `BuiltinBundled` source and the application's installation trust.

### 11.5 Export and Import

A plugin exports and imports as a self-contained bundle over the `PortablePackage` (`portability.export-bundle`, File 21 §10): the export carries the manifest, the bundled artifacts (by content hash), and the referenced contributions, with no raw secret (credential references are vault references, `security.secret-vault`, File 22 §5; §15). Importing re-validates the manifest, re-resolves references, passes source approval and integrity verification locally (imported trust is inert, §7.2), and produces an installed-but-disabled or draft plugin with typed `UnresolvedReference` diagnostics when a required reference cannot resolve, never a silent substitution (`workflow.library`, File 34 §9.4). The packaged-archive form (§11.1) is one export's serialization.

### 11.6 Rule

- Install sources are the closed set built-in-bundled / local-directory / packaged-archive / registry-published; the source is provenance, not trust.
- Discovery is a typed, replaceable surface with one normalized candidate/effect summary; it never installs; the agent suggests, the user installs; updates are opt-in and default-off with no silent network update.
- The ship-with per-profile plugins are the worked examples, copied and registered idempotently, accepted at the exact bundle version, tombstone-aware on app update, and distinguished only by source and installation trust; a plugin exports and imports as a `PortablePackage` with no raw secret, re-approved locally on import.

### 11.7 Boundary

File 21 owns the portable bundle and the import pipeline; File 22 owns the local re-approval and integrity; File 43 owns the installer image and the discovery-registry endpoints; File 37 and File 38 own the plugin browser and marketplace presentation. This section owns the install sources, the discovery contract, the agent-suggested-never-auto-installed rule, and the ship-with bundle treatment.

## 12. The Agent/User Boundary, Custom Tools, and AI-Assisted Customization

Anchor: `plugin.self-extension`

### 12.1 The Boundary

The line between an agent-created extension and a user-installed plugin is who initiated it, and it is load-bearing: the agent extends itself through scoped, owning-file-governed contributions; the user installs bundles. The agent may register a custom tool (a `UserDefined`-source capability with a `Wasm` or `Shell` backend, scoped to conversation, workspace, or global, through `tools.register_custom` at `UserApproval`; `capability.capability-source` File 05 §9.1, `capability.runtime-mutation` File 05 §16.2), may propose a skill, workflow, automation, or knowledge entry through its owning graduation path (`workflow.creation-and-graduation` File 34 §11; `automation.creation-and-graduation` File 33 §15; the knowledge proposal path), and may generate controlled extensions — workflow templates, custom tools in sandboxes, adapters, validators, and extraction schemas (the `codex_recommendations.md` §9.4 target). The agent may not install a plugin, write the application's source, change the schema, share code across conversations without approval, or register any contribution silently. These are security guarantees, not implementation details; relaxing one requires an explicit user setting with a warning.

### 12.2 AI-Assisted Customization

AI-assisted customization uses the same paths as manual customization (`core.extension-integrity`, File 01 §7.10). An agent that proposes a capability, skill, workflow, surface, or setting passes the same validation, the same proposal-first source-approval (`policy.source-approval-flow`, File 06 §9), and the same no-silent-creation rule a manual contribution does; an agent that suggests a plugin from the discovery surface produces a suggestion the user installs, never an install. There is no agent-only registration API and no agent-only contribution store; the agent reaches every extension plane through the same registries, gated by policy.

### 12.3 No Silent Creation

A contribution is never created, registered, or enabled silently. The agent's custom-tool registration is `UserApproval` on first use; its skill, workflow, automation, and knowledge proposals are reviewed before they become active; and its discovery suggestions never auto-install. Bounds on agent self-authoring — a maximum number of active agent-created contributions, a default approval posture — are settings, not hardcoded limits (`settings.settings-over-constants`, File 15 §13). This is the plugin counterpart of `workflow.creation-and-graduation` (File 34 §11.2) and `automation.creation-and-graduation` (File 33 §15.2).

### 12.4 The Custom-Tool-to-Plugin Promotion Path

A custom tool (or a coherent set of agent- or user-created contributions) that proves useful is promoted to a plugin through a user-driven path: the user selects the contributions, supplies plugin metadata, and the system generates a plugin draft in the user-writable plugin-draft directory — a complete bundle with a manifest populated from the contributions' declarations and the contribution payloads — which the user may edit and then install locally (the `LocalDirectory` source, §11.1) or package into a portable bundle for sharing (§11.5). On install, the original custom-tool registration is archived (hidden, not deleted) so there is one active registration, and the plugin's version takes precedence; the promotion is non-destructive and reversible — a plugin contribution may be demoted back to a custom tool for editing, extracting its backend payload into a fresh custom-tool registration without republishing the plugin. The promotion's install step is user-gated like any plugin install (§10.5); a draft is not an installed plugin until the user installs it. A promotion preserves provenance (the producing contributions and a derivation summary), and a graduated contribution carries the promotion forgery guard already fixed for reuse units — a contribution with no real registered or ledgered substance cannot be crystallized into a bundle (`workflow.creation-and-graduation`, File 34 §11.4).

### 12.5 Rule

- The agent extends itself through scoped, owning-file-governed contributions and proposals; the user installs plugins; the agent suggests but never installs, never writes the application's source, never changes the schema, and never registers silently.
- AI-assisted customization uses the same registries, validation, and approval as manual customization; there is no agent-only API or store; self-authoring bounds are settings.
- A custom tool or contribution set is promoted to a plugin through a user-driven, non-destructive, reversible path that archives the original on install and preserves provenance and the promotion forgery guard.

### 12.6 Boundary

File 05 owns the custom-tool (`UserDefined`-source) registration and the runtime-mutation gate; File 34 owns the reuse-unit graduation and the promotion forgery guard; File 06 owns the source-approval the promotion's install passes; File 37 and File 38 own the custom-tool panel and the promotion wizard. This section owns the agent/user boundary, the AI-assisted-customization governance, and the promotion path as a bundle-producing operation.

## 13. The `plugin.*` Capability Surface

Anchor: `plugin.capability-surface`

### 13.1 Closed Canonical Capabilities

The plugin layer exposes its operations as built-in capabilities declared per `capability.declaration` (File 05 §3), flowing through the standard call pipeline (`run.call-pipeline`, File 04 §8.2) and policy (File 06). These discharge the `extensions.install` and `extensions.search_registry` ids `capability.settings` (File 05 §18.1) names:

- `plugin.install(source_ref)` — install and activate a plugin from an install source (§10.1); `UserApproval`, escalating to typed-confirmation by trust and declared envelope; passes source approval.
- `plugin.update(plugin_id)` — update an installed plugin (§10.3); `UserApproval`, re-reviewing on envelope expansion, failed source/integrity verification, or absent same-envelope update authorization.
- `plugin.enable(plugin_id, scope)` / `plugin.disable(plugin_id, scope)` — scoped enablement transitions (§10.2); registry/settings writes.
- `plugin.uninstall(plugin_id, options)` — unregister, remove executable files, retain a tombstone, and clean up (§10.4); `UserApproval`, escalating to typed-confirmation when dependents break or data is itemized for removal.
- `plugin.list(filter)` / `plugin.get(plugin_id)` / `plugin.inspect(plugin_id)` — read the installed catalogue, a plugin, and its contributions, attribution, trust, and diagnostics; `ReadOnly`, `ConcurrencySafe`.
- `plugin.search_registry(query, kind)` / `plugin.suggest_install(context)` — query the discovery surface and normalized candidate/effect summaries (§11.2, §11.3); `ReadOnly`, agent-invocable; never installs.
- `plugin.export(plugin_id)` / `plugin.import(package)` — self-contained export and import (§11.5); import passes source approval and local integrity verification.
- `plugin.promote_contributions(selection, metadata)` / `plugin.extract_to_custom(plugin_id, contribution_id)` — the user-driven promotion to a plugin draft and the demotion to a custom tool (§12.4); `UserApproval`; the install of a draft is a `plugin.install`.

### 13.2 Rule

- The plugin capabilities are built-in declarations under the one registry, carrying the touched-resource and tier metadata their effects warrant; install, update, uninstall, enable/disable, import, and promotion are tier-gated and user-only; list, inspect, search, and suggest are `ReadOnly` and the search/suggest pair is agent-invocable but never installs.
- An agent invokes these capabilities like any other, subject to policy and the no-self-install rule (§10.5, §12.1); there is no privileged plugin-installation side door.

### 13.3 Boundary

File 05 owns the declaration and registry; File 06 owns the policy gating; File 36 (MCP and External Integrations) owns the MCP-server install a bundled reference triggers. This section declares the canonical plugin capability set.

## 14. Events

Anchor: `plugin.events`

### 14.1 Rule

- Plugin lifecycle and registry facts use the `Custom { namespace: "plugin", name, payload }` extension (`ledger.event-stream`, File 10 §5). The canonical plugin namespace includes: `PluginInstalled`, `PluginAwaitingReview`, `PluginActivated`, `PluginActivationFailed`, `PluginEnabledChanged`, `PluginUpdated`, `PluginDisabled`, `PluginQuarantined`, `PluginQuarantineLifted`, `PluginUninstalled`, `PluginContributionRegistered`, `PluginContributionUnregistered`, `PluginContributionUnavailable`, `PluginTrustChanged`, `PluginIntegrityVerified`, `PluginIntegrityViolated`, `PluginDependencyImpactComputed`, `PluginPromotionProposed`, and `PluginDiscoverySuggested`. `PluginEnabledChanged` records a scoped enable-or-disable flag flip (§10.2) that leaves the bundle installed and its lifecycle state unchanged, while `PluginDisabled` records the bundle's transition into the `Disabled` lifecycle state (§9.2); `PluginActivationFailed` records a rolled-back activation (§10.1) and `PluginQuarantineLifted` the reversal of a quarantine after explicit review (§10.5).
- A plugin's *contribution* events remain the owning registries' events (`CapabilityRegistered`, surface/rail/setting/hook registration events, `WorkflowCreated`, and the rest), carrying runtime source and plugin bundle ownership where applicable; this section declares the bundle-lifecycle events, not duplicates of the contribution events. Security-relevant plugin operations (install, trust change, integrity violation, revocation, quarantine) record into the device-local hash-chained audit overlay (`ledger.hash-chained-audit-log`, File 10 §16.4) and default to `Sensitive`.

### 14.2 Boundary

File 10 owns the event envelope, the `Custom` extension, the audit overlay, and the sensitivity rules; the owning registries own the contribution events. This section declares the plugin lifecycle event vocabulary.

## 15. Persistence, Locality, and Portability

Anchor: `plugin.persistence`

### 15.1 What Is Durable, Device-Local, and Portable

- **Durable and (where its owner syncs) syncable:** a plugin's bundled durable contributions — knowledge entries, workflow and template definitions, settings *definitions* — are versioned substrate owned by their files (Files 12, 34, 15) and follow each owner's locality; most sync so a user's contributed knowledge and workflows follow them.
- **Device-local:** the plugin *install and enablement state* — which plugins are installed on this device, their enabled state per scope, trust and integrity records, and trust overrides — is device-local and does not sync, the same installation-local discipline `security.trust-model` (File 22 §9.7) fixes for trust and `automation.persistence` (File 33 §18) fixes for arming state. A plugin is installed per device; installing it on another device is a fresh local install-and-approve. The contribution-attribution index and the discovery cache are device-local projections, rebuilt on demand; their loss is a rebuild, never a loss of a definition or history.
- **Portable:** a plugin's importable bundle (manifest, bundled artifacts, referenced contributions) is part of the `PortablePackage` (`portability.export-bundle`, File 21 §10), re-resolved and re-approved locally on import (§11.5).

Install, enablement, lifecycle, and update-policy state are never part of the integrity hash (§7.3) or the portable bundle (§11.5); only the manifest, contribution ids and versions, bundled-artifact hashes, and referenced portable contribution payloads are.

### 15.2 Security

A plugin bundle, export, or sync stream contains no raw secret: a credential a plugin's contribution needs is a vault reference (`security.secret-vault`, File 22 §5), never inline; raw secrets never sync, export, or materialize (`portability.sensitivity-egress`, File 21 §12). A plugin's executable contributions and the integrity record reconstruct deterministically from the durable bundle; every hash a plugin relies on is computed over a declared `CanonicalEncoding` (`core.canonical-hash`, File 01 §7.14), and this file defines no new canonical hash, inheriting File 22's integrity hash and File 21's bundle hash.

### 15.3 Rule

- A plugin's bundled durable contributions follow their owning substrate's locality; the install and enablement state is device-local and rebuilt; the importable bundle is portable and re-approved on import.
- No raw secret is part of a plugin bundle, export, or sync; credentials are vault references; hashes are over a declared canonical encoding.

### 15.4 Boundary

Files 20 and 21 own storage, locality, sync, and the portable bundle; File 22 owns the vault and integrity cryptography; the owning files own each contribution's locality. This section owns the install-state-device-local versus contribution-durable split for plugins.

## 16. Settings

Anchor: `plugin.settings`

Plugin behavior is configurable through `settings.setting-definition` (File 15), with agent exposure governed by `policy.agent-exposure-policy-settings` (File 06 §16.4). At minimum, settings must support:

- the install-source policy: whether registry, packaged-archive, and sideloaded installs are permitted, and the trusted-source allowlist (default empty) and per-source trust defaults;
- the update policy: auto-update enablement (default off), the trusted update-source allowlist, source/integrity verification requirements, whether same-envelope unattended updates are allowed per plugin or source, and whether an envelope-expanding update requires fresh review;
- the activation policy: entry-module activation timeout, activation retry posture, and whether local-directory development mode is enabled;
- the runtime-registration enablement for the agent — whether the agent may invoke the discovery-and-suggest capabilities and the custom-tool registration path (off, ask-each-time, allowlist, allow), composed with `capability.settings` (File 05 §18.1), never duplicated;
- the source-approval risk thresholds and the trust-mapping overrides per source class, composed with `policy.settings-resolution-for-policy` (File 06 §16);
- the agent self-authoring bounds (maximum active agent-created contributions, default approval posture) and the no-silent-creation posture;
- the per-plugin enable/disable scope and the per-plugin and per-contribution policy overrides resolved by File 06;
- the discovery ranking inputs and result caps, and the discovery-registry configuration;
- the lazy-population policy for ship-with bundles and the per-profile activation behavior.
- the tombstone and re-seeding policy for ship-with bundles, including whether removed built-in plugins may be proposed for re-add.

Settings define intended variation; they must not become hidden hardcoded branches (`settings.settings-over-constants`, File 15 §13). Trust thresholds, install-source permissions, update cadence, and self-authoring bounds are settings; concrete values are never canonical.

## 17. Explicit Rejections

Anchor: `plugin.explicit-rejections`

The following shapes are wrong for this layer:

- a parallel plugin registry of contributions, a private plugin runtime or executor, a per-plane plugin tool/rail/surface/setting/hook store, or any contribution path that bypasses the one canonical registries — every plugin contribution enters its owning registry through the same path a built-in uses, carrying runtime source and plugin bundle ownership metadata (`core.extension-planes`, File 01 §6.14; `capability.sourcing-equivalence`, File 05 §9.3);
- a plugin as a subsystem, a work surface, a control rail, or a separate execution architecture — a plugin is a cohesive contribution bundle (`core.extension-integrity`, File 01 §7.10); a surface or rail it contributes registers through that primitive's own registry;
- an "extension" as a backend primitive — extension is a user-facing category; the backend primitive is a plugin bundle plus typed contributions. There is no `DomainExtension`, extension-owned tool/settings/policy store, or extension-specific policy channel.
- the agent installing, updating, or enabling a plugin, or any plugin install that completes without user review — install is user-only and source-approval-gated; the agent suggests, never installs (`capability.runtime-mutation`, File 05 §16.2; `policy.source-approval-flow`, File 06 §9.7);
- a plugin contribution that becomes invocable without passing source approval and trust establishment, or self-declared trust treated as the determinant — trust is established by provenance, review, and integrity (`security.trust-model`, File 22 §9);
- a plugin overriding security-critical state (environment variables controlling paths, linkers, or interpreters; credential storage; the policy kernel), replacing a `Core` setting, registering outside its namespace, or piercing a `permission_floor` (`core.extension-planes`, File 01 §6.14; `settings.setting-definition`, File 15 §3.4; `policy.permission-floor`, File 06 §7);
- a plugin permission manifest that understates its contributions' effects, or a contribution registering an effect outside the approved envelope (§6.3);
- prose-only or model-request-only extension — adding agent behavior by injecting instructions without registering a typed contribution (`capability.explicit-rejections`, File 05 §19);
- a plugin's executable contribution escaping the Wasm restricted host or the one `Sandbox`, or a new sandbox introduced for plugin code (`sandbox.consequences-for-later-specs`, File 23 §21);
- plugin source approval, trust class, or install approval satisfying camera, audio, screen, wake-word, or equivalent sensor consent; sensor consent remains modality-specific and owning-policy-governed;
- silent install, enablement, update, mutation, or contribution registration; silent deletion of a dependent on disable or uninstall; or silent substitution of an unresolved imported reference (§9.4, §11.5);
- a raw secret in a plugin bundle, export, sync, manifest command, or shell/script command line — credentials are vault references or mediated secret inputs (`security.secret-vault`, File 22 §5);
- plugin install or enablement state synced as authority, or imported trust activating a plugin without local approval (`security.trust-model`, File 22 §9.7);
- a parallel `plugins`/`extensions` source-of-truth table for the contributions — the installed-plugin record and attribution index are the bundle-lifecycle layer over the one registries, recording runtime source and bundle ownership without duplicating contribution storage (§9.3);
- hardcoding install sources, update cadence, trust thresholds, ranking weights, or self-authoring bounds outside settings (§16).

## 18. Consequences for Later Specs

Anchor: `plugin.consequences-for-later-specs`

- The **MCP and External Integrations** spec owns the MCP protocol, transport, standalone-server registration, discovery, trust, and remote-capability metadata; a plugin that bundles an `McpServerRef` registers it through that path as `McpServer`-source capabilities with plugin bundle ownership, and a standalone MCP server the user adds directly is an `McpServer`-source integration, not a plugin. That spec must introduce no parallel plugin packaging and must honor the bundle-granularity source approval, lazy integration attribution, and runtime-source-versus-bundle-ownership split this file fixes.
- The **UI Shell** and **UI Customization** specs render the plugin browser, the install-and-permission review, the contribution inspector, the discovery and marketplace surfaces, the custom-tool panel and the promotion wizard, and the placement of plugin-contributed panels, widgets, and themes; they consume the data contracts (§9, §11, §13) and must not make the presentation the install or trust truth. The theming and widget contribution kinds (§5.2) register through the UI Customization layer's own registries.
- The **Quality Control and Validation** and **Evaluation and Benchmarking** specs own the validators a plugin contributes (registering blocking hooks, `ledger.hook-registration-discovery` File 10 §8.3) and the reliability evaluation a plugin's contributions feed; they must integrate through the hook, validation, and evaluation substrates, not a parallel plugin-validation pipeline.
- The **Telemetry, Logging, and Observability** spec consumes the plugin lifecycle events and the contribution-attribution projection; it must introduce no parallel plugin-state store and must honor the `Sensitive` default and audit-overlay routing of security-relevant plugin operations (§14).
- The **Runtime Infrastructure and Lifecycle** spec orchestrates plugin loading at startup (the registration and reconstruction of installed plugins in the startup phase order), the device-local rebuild of the attribution index and discovery cache, the dynamic-service registration backing plugin-loaded handlers, and the reaping of crashed plugin processes; it must place no parallel plugin runtime and persist no install state across sync.
- The **Packaging, Platform, and Distribution** spec owns the application binary's installer, auto-updater, release channels, code-signing certificate acquisition, sidecar inventory, and the bundling of the ship-with plugins into the installer image; this file owns the plugin's own packaging, its first-run copy and registration, the plugin install/update lifecycle, and the plugin discovery and distribution contract. The packaging layer (File 43) distributes the application and seeds the ship-with bundles into the image; File 35 installs, registers, updates, and removes plugins.
- The **per-surface specs** (Files 27–32) and the horizontal specs (Files 25, 26, 33, 34) own each contribution kind's registry and per-contribution registration; a plugin contributes instances of their primitives through their registries under the correct runtime source and plugin bundle ownership, and they must treat a plugin-sourced contribution identically to a built-in of the same kind, distinguished only by source, trust, bundle ownership, and default enablement.
