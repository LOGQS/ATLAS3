# Data Processor Surface

## Status

Canonical. This file defines the `Data Processor` work surface — the specialized environment for transforming, converting, extracting, analyzing, validating, and visualizing structured and unstructured data. It is the third per-surface specification: it fills the `SurfaceContract` that `worksurface.surface-contract` (File 25 §4) delegates to each per-surface spec, and declares the data-specific workflows, panels, capabilities, and policies the Data Processor surface contributes over the shared substrate. It owns user-facing data workflows and specialized views; it owns no private architecture. It composes blocks, artifacts and evidence, capabilities, execution, the version graph, retrieval, context, the world model, perception, the sandbox, workspaces, security, providers, and every other substrate through the same contracts every surface uses. Later canonical files may refine it, but may not contradict it.

## Scope

This file defines:

- the `Data Processor` `WorkSurface` and its `SurfaceContract` (`worksurface.work-surface`, File 25 §3, `worksurface.surface-contract` (File 25 §4)): identity, declared panels and selection kinds, the `SubsystemSurfaceSpec` and contributed capabilities, view presets and inspectors, and default context, model, execution, sandbox, and workspace policies
- the **artifactized-data-lab reframe**: a data result is a durable, lineage-tracked, validatable `Dataset`, `Table`, `Chart`, or `Notebook` `Artifact` revision (`artifact.artifact-kind`, File 09 §4), not a one-shot file conversion accompanied by transcript prose; scripting is an extension path, not the default primitive, and the default is typed transform, query, extraction, and chart capabilities over a replaceable in-process analytical engine
- the datasets-and-tables contract: the `Table` and `Dataset` artifact kinds, the small-inline-versus-large-external split, schema inference, the analytical-engine query capability over file-resident data, multi-file joins and federation, and the durable, citable, lineage-bearing outcome of every data operation
- the structured-extraction contract: `data.extract` and the document, table, entity, and domain-specific extraction capabilities, their chunking, multi-pass, cross-chunk-context, few-shot-schema, and streaming sub-modes, source grounding back to character spans through `Citation`, the replaceable document-parser and optical-character-recognition implementations behind the capability, and the borrow of the shared retrieval substrate
- transformation, format conversion, and data pipelines: the transform, join, concatenate, schema-map, and format-conversion capabilities, and the data pipeline as a `surface_runtime` / programmatic-execution structure over the one shared execution and DAG model and a `WorkflowTemplate` artifact when reused — never a private pipeline engine or table
- notebooks: the `Notebook` artifact as a composed block of typed cells, cell execution as run execution, cell output as blocks, notebook export, and the notebook-versus-pipeline duality as two presentations of one execution graph
- data profiling and data validation: the profiling capability and the `DataProfile` it produces as an `Observation` and a cached projection, and the schema-validation framework producing `Validation` blocks of the `SchemaValidation` kind
- visualization: the chart, dashboard, map, and graph-visualization capabilities producing `Chart` artifacts with renderer hints rendered through the shared artifact runtime
- media-as-data: optical-character recognition, audio transcription, video transcoding and extraction, non-generative image processing, and batch operations, and the boundary between processing media as data (owned here) and generating new media (borrowed)
- the data rails: slash and custom commands, the notebook and pipeline keybinding contexts, the palette and quick-open, data mentions, and the data-source change monitor — bound to capabilities through the control-rail layer (File 26)
- memory integration for remembered transformation preferences and style templates, cross-surface composition, the data world-model and perception integration, and the data capability, event, and settings surface

Resolution rule: this file realizes the Data Processor surface by filling File 25's `SurfaceContract` and declaring data-specific workflows; it re-owns no substrate. Every substrate's semantics stay with its owning file. Where the source material describes a data mechanism the canon has already settled horizontally — the block and artifact model, the version graph, the execution and DAG model, retrieval and extraction-into-indexing, the sandbox, the workspace mirror, the evidence and citation model — this file consumes the settled contract and adds only the data-specific presentation and workflow. The implementation groundings the sources lock — an in-process analytical SQL engine, a dataframe library, document and table parsers, an optical-character-recognition engine, a media toolchain, a charting and dashboard library, a notebook runtime, a Python/Wasm execution runtime, and a node-graph canvas widget — are named in the sources for grounding but are kept out of the canonical body as replaceable implementations behind the surface's capabilities and panels, per the project rule against provider- and library-specific detail in canonical specs.

Resolved tensions:

- **Data engine: scripts versus spreadsheet-only versus an artifactized data lab.** One-shot converter tools, spreadsheet-style work, and script-only handoff each cover part of data work but fail as the primary model: they under-specify provenance, schema introspection, validation state, replay, and artifact identity. This file adopts the artifactized data-lab (§1, §6): a data result is a durable, lineage-tracked, validatable `Artifact` revision, consistent with `artifact.chosen-model` (File 09 §1) and `block.chosen-model` (File 08 §1), exactly as `coder.chosen-model` (File 27 §1) made a code change an artifact revision and `web.chosen-model` (File 28 §1) made gathered web content durable evidence. Scripting remains an extension path, not the identity layer.
- **Tables, notebooks, lineage, and profiles as private tables versus shared substrate.** The specbase proposes a `TableBlock` block kind and parallel `data_notebooks`, `data_notebook_cells`, `data_lineage`, and `data_profiles` tables (`unit11b-data-processor.md` D11.DP.7/D11.DP.9/D11.DP.10, `unit12-infrastructure.md` D12.1). `CONSTRAINTS.md` §12 establishes the block-first rule — "if a feature seems to need a new SQL table for durable conversation data, reframe it as a `block_type`" — and the canon has already settled these: `artifact.per-surface-projections` (File 09 §17.2) states the Data Processor surface presents "`Dataset`, `Chart`, `Notebook`, `Table`, plus the data-lineage projection of `derives_from` edges," `version.explicit-rejections` (File 11 §23) forbids parallel history stores, and the prior per-surface specs deleted exactly these shapes (`coder.explicit-rejections` (File 27 §22) deleted `file_checkpoints`; `web.explicit-rejections` (File 28 §22) deleted the parallel research-session tables). This file resolves toward the substrate (§6, §10, §11): `Table` and `Dataset` are artifact kinds, a `Notebook` is a composed-block artifact whose cells are child blocks, lineage is `derives_from` edges queried through `provenance.query_derivation_chain` (File 09 §15.3), and a `DataProfile` is an `Observation` and a cached projection. No private data table is introduced.
- **The data pipeline as a private engine versus the one shared execution-graph model.** `run.execution-structure` (File 04 §5) and `run.programmatic-execution` (File 04 §14) already own the one execution and DAG model, and `worksurface.no-private-architecture` (File 25 §12) forbids a private execution model. This file resolves toward the shared model (§9): a data pipeline is a `surface_runtime` / programmatic-execution structure over the one run model with a data node library, a reusable pipeline is a `WorkflowTemplate` artifact, per-node output caches are rebuildable projections keyed by full execution identity, and the canvas is a UI projection over execution and the version graph. The notebook view and the pipeline view are two presentations of one execution graph.
- **Compute over data: launch a separate coder sandbox versus programmatic execution in place.** The specbase routes complex transforms to "launch Coder." `unit11b-data-processor.md` D11.DP.15-B replaces that with programmatic tool calling, and `unit04-routing-agents-prompt.md` D4.7 names the Data Processor a primary consumer of `code.execute_with_tools`. This file resolves toward programmatic execution in place (§9.5, §15.4): custom transforms, formula evaluation, and notebook code cells run as confined execution under a data `SandboxProfile` (`sandbox.contract`, File 23 §3) through `run.programmatic-execution` (File 04 §14), keeping the work and its outputs in the Data Processor surface; the coder code-execution capability remains borrowable for heavy scripting.
- **Per-profile workflows as autonomy modes versus view presets.** The specbase proposes ten per-profile "view presets" (researcher, data analyst, office worker, and so on) with quick actions and emphasized tools (`unit11b-data-processor.md` D11.DP.3). `worksurface.no-autonomy-field` (File 25 §13) and the participation-level deletion fix that presets are presentation only; `ui/15-3-and-15-4-...` states explicitly that presets are "not autonomy modes, not rule-based, not prompt-injecting." This file resolves the per-profile workflows to `ViewPreset`s and settings/profile customization seeds (§16); they carry no autonomy field, and the surface ships a small baseline of presets with the broader per-profile set as user-customizable seeds.
- **Media: a media surface owning generation versus media-as-data here and generation borrowed.** This file resolves toward processing media **as data** here and treating generation as borrowed or a future surface (§14): optical-character recognition, transcription, transcoding, frame and audio extraction, deterministic or non-generative image manipulation, and batch operations are owned by the Data Processor; generative image and media creation is the borrowable `image.*` family and a future Media Studio surface, never a primary Data Processor capability.
- **Engines and libraries: name the implementation versus a replaceable contract.** The sources lock specific engines (an analytical SQL engine, a dataframe library, document and table parsers, an optical-character-recognition engine, a media toolchain, a charting library, a notebook/Python runtime, and a node-graph canvas). The canonical choice is provider- and library-neutral behavior: implementations are replaceable behind the surface's capabilities and panels, while `core.local-extensibility` (File 01 §7.10) owns the extension invariant.

## 1. Chosen Model

Anchor: `data.chosen-model`

ATLAS3 has one `Data Processor` `WorkSurface`. It is the specialized environment for working with data — ingesting, converting, extracting, querying, transforming, joining, validating, profiling, analyzing, and visualizing structured and unstructured data — and it is one instance of the `WorkSurface` primitive `worksurface.work-surface` (File 25 §3) defines, classified `Data Processor` by `core.current-major-area-classification` (File 01 §5.4).

The Data Processor surface owns user-facing data workflows and specialized data views; it owns no private architecture (`worksurface.no-private-architecture`, File 25 §12). It is declared by one `SurfaceContract` (§3) registered in the `SurfaceRegistry` (`worksurface.registry`, File 25 §10), and it composes the shared substrate — blocks, artifacts and evidence, capabilities, capability policy, tool surfaces, execution, the world model, perception, the version graph, retrieval, workspaces, context assembly, memory, routing, storage, sync, security, the sandbox, providers, and the ledger — through each one's canonical contract.

The load-bearing model of the Data Processor surface is the **artifactized-data-lab reframe**: a data result is a durable, identified, versioned, lineage-tracked, validatable `Artifact` — a `Dataset`, `Table`, `Chart`, or `Notebook` — not a one-shot file conversion accompanied by transcript prose, and not a file silently dropped on disk. Three consequences follow:

- **A data result is a durable, lineage-bearing artifact, not transient prose.** A table or dataset is a `Table` or `Dataset` `Artifact` revision (`artifact.artifact-kind`, File 09 §4); a chart is a `Chart` artifact; an exploration is a `Notebook` artifact composed of cells. Each carries provenance — the producing run, capability, inputs, and parameters (`artifact.provenance`, File 09 §15) — and each derived result is linked to its upstream inputs by the `derives_from` edge (`block.canonical-edge-kinds`, File 08 §5.2) so that every chart and every derived dataset is traceable to the datasets and transforms that produced it. Artifact- and evidence-grade data content is never stored only as an assistant message (§23).
- **The default primitive is a typed, lineage-tracked operation over an analytical engine, not a script.** The default way to work with data is through the surface's typed transform, query, extraction, validation, profiling, and chart capabilities over a replaceable in-process analytical engine, each recording lineage and producing artifacts. Scripting — programmatic execution of code over data — is an extension path for the cases typed operations do not cover (`run.programmatic-execution`, File 04 §14, §9.5), not the default, and it runs confined and lineage-recorded like any other operation.
- **Pipelines, notebooks, profiles, and lineage are projections over the shared substrate, not private stores.** A pipeline is an execution structure over the one run model and a `WorkflowTemplate` artifact when reused (§9); a notebook is a composed-block artifact whose cells are child blocks (§10); a profile is an `Observation` and a cached projection (§11); lineage is the `derives_from` graph queried through `provenance.query_derivation_chain` (File 09 §15.3, §6.3). The pipeline canvas, the notebook view, the lineage tree, and the dataset card are projections over blocks, artifacts, the version graph, and provenance — never parallel data tables.

`Data Processor` is the canonical surface name; the `surface_id` is `data_processor` and equals the subsystem id (`capability.capability-source`, File 05 §9.1, `worksurface.work-surface` (File 25 §3.3)), the value `routing.run-intent` (File 03 §4.3)'s `primary_surface` resolves to for data work, the prefix of its settings namespace (`surface.data_processor.*`) and its instruction-file qualifier (`ATLAS.data_processor.md`). Earlier vocabulary that named the same surface — "data-processor domain", "data lab", "analyst mode", "pipeline builder" — is source vocabulary only and does not survive as canonical terminology or a parallel primitive; "data lab" survives as the informal name of the reframe. The anchor namespace for this file is `data.*`, deliberately distinct from File 07's `surface.*` (tool surfaces), File 25's `worksurface.*`, File 26's `controlrail.*`, File 27's `coder.*`, and File 28's `web.*`; the capability families `data.*` are capability ids in the one registry, not anchors, disambiguated by context exactly as `web.*` is in File 28.

### 1.1 Boundary

This file defines what the Data Processor surface is and what it declares and contributes. It does not define how the `SurfaceContract` is registered or composed (File 25), how its tool surface composes (File 07), how its live state is held (File 18), how a dataset materializes (File 24), how confined transforms run (File 23), how its history is versioned (File 11), how its content is indexed (File 12), or how its views render (the UI specs).

## 2. Boundaries with Adjacent Layers

Anchor: `data.boundaries`

### 2.1 With File 25 (Work Surface Contract)

This file fills the `SurfaceContract` `worksurface.surface-contract` (File 25 §4) defines: identity (§3), state and panels (§4), the `SubsystemSurfaceSpec` and contributed capabilities (§5), views and presets (§16), and default context/model/execution/sandbox/workspace policies (§15). It obeys the no-private-architecture invariant (`worksurface.no-private-architecture`, File 25 §12), the static-versus-live split (`worksurface.state-declaration`, File 25 §5 — this file declares the shape, File 18 holds the values), the hint-not-fence rule (`worksurface.actions-declaration`, File 25 §6.3), and the deletion of autonomy/participation/interaction-shape fields (`worksurface.no-autonomy-field`, File 25 §13). The Data Processor surface registers as a `Subsystem`-class source through the proposal-first path (`worksurface.registry`, File 25 §10).

### 2.2 With Files 08 and 09 (Blocks, Artifacts, Claims, Evidence, Provenance)

The boundary is sharp and load-bearing, because the Data Processor surface's outputs are durable data artifacts. Data flows as `Block`s through the one pool (`block.cross-surface-interoperability`, File 08 §12). A table or dataset is a `Table` or `Dataset` `Artifact` revision (`artifact.artifact-kind`, File 09 §4) — `Table` inline for small tabular data, `Dataset` `External` for large data referencing the content-addressed blob store (`block.block-content`, File 08 §4, `artifact.artifact-kind` (File 09 §4.2)); a chart is a `Chart` artifact; a notebook is a `Notebook` composed-block artifact (§10); a profile is an `Observation` (§11); a schema check is a `Validation` block of the `SchemaValidation` kind (`artifact.validation-critique`, File 09 §14.1). A derived result links to its inputs by `derives_from` and to its supersessions by `supersedes` (`block.canonical-edge-kinds`, File 08 §5.2, `version.sibling-block-versioning-over-block-pool` (File 11 §12)); extracted facts cite their source through `Citation` and `SourceSpan` (`artifact.citation`, File 09 §12), and load-bearing findings are `Claim`s with `Evidence` (`artifact.claim` (File 09 §9), `artifact.evidence` (File 09 §11)). The surface introduces no `TableBlock` kind, no parallel artifact store, and no private claim, evidence, or observation pool (§23).

### 2.3 With File 11 (Version Graph)

Notebook, dataset, table, chart, and pipeline history are projections over the one version graph (`version.consequences-for-later-specs`, File 11 §24); a transform produces a sibling `Artifact`-kind block linked by `supersedes`, and reverting a dataset or a notebook cell is a forward `ContextEdit` swapping the active sibling or a backward switch to a version where the historical sibling was active (`version.version-switching`, File 11 §8), exactly as `coder.file-history` (File 27 §8) projects coder history. The surface introduces no parallel checkpoint, lineage, notebook, profile, or pipeline-config store (`version.explicit-rejections`, File 11 §23).

### 2.4 With File 04 (Execution and Run Model)

Data runs use the shared run lifecycle, ledger, cancellation, budgets, parallelism, programmatic execution, child runs, and DAG execution structure (`run.consequences-for-later-specs`, File 04 §29); a data pipeline is a `surface_runtime` execution structure (`run.execution-entry`, File 04 §4, `run.execution-structure` (File 04 §5)) over the one model, a batch operation is parallel capability execution (`run.parallelism`, File 04 §15), a custom transform or notebook code cell is programmatic execution (`run.programmatic-execution`, File 04 §14), and a deep analysis is a child-run structure (`run.child-runs-multi-agent-work`, File 04 §16). The surface owns no private executor, scheduler, or DAG engine. The deterministic completion floor (`run.termination`, File 04 §22) applies: a data run whose contract required a produced artifact cannot complete on prose alone.

### 2.5 With File 12 (Retrieval) and File 13 (Context Assembly)

The Data Processor surface owns data-extraction semantics — what entities, schemas, columns, and lineage a document or dataset yields (`retrieval.source-records`, File 12 §4.2 names "data-processing surfaces/subsystems may extract dataset, column, schema, and lineage entities"; `retrieval.ingestion` (File 12 §14.3) delegates document-extraction entity choice to the producing surface) — and consumes File 12's shared index, query, namespace, chunking, embedding, hybrid-search, and entity-relationship-projection contract; it introduces no private index, knowledge, or graph substrate (`retrieval.explicit-rejections`, File 12 §21). It assembles every model request through the one `ContextAssemblyService` (`context.chosen-model`, File 13 §1): a large query result, dataset, or extracted document is referenced rather than flooded into context (`context.current-input-oversize-handling`, File 13 §7), untrusted ingested or fetched content enters as `untrusted_source_data` (`context.authority-classes`, File 13 §2.3), and the `ATLAS.data_processor.md` contribution is an `InstructionSources` part (`context.instruction-sources-workspace-files`, File 13 §16). It builds no private model-request path (`context.consequences-for-later-specs`, File 13 §22).

### 2.6 With File 23 (Sandbox) and File 24 (Workspaces)

The surface runs all confined execution — the analytical engine over file-resident data, custom transforms, formula evaluation, notebook code cells, and media toolchains — through the one `Sandbox` contract (`sandbox.consequences-for-later-specs`, File 23 §21), declaring data `SandboxProfile`s (`sandbox.contract`, File 23 §3) and extending the base contract only with its data-runtime capability surface; it redefines no lifecycle, filesystem, network, resource, or kill semantics, and opens no private sandbox (§15.4). Its views render over a bound `Workspace` (`workspace.conversation-binding`, File 24 §7); datasets, charts, notebooks, and reports materialize through the disk↔substrate mirror and File 23's filesystem boundary (`workspace.materialization`, File 24 §10), external edits to materialized data files enter through the disk→substrate sync loop (`workspace.disk-sync-loop`, File 24 §12), and mounted external data sources use File 24's mounting and ingestion (`workspace.mounted-projects`, File 24 §14). The surface owns no workspace identity, disk-history store, or parallel materialization path (`workspace.explicit-rejections`, File 24 §23).

### 2.7 With Files 05, 06, 07 (Capabilities, Policy, Tool Surfaces) and File 16 (Model Strategy)

Data capabilities are `Capability` declarations in the one registry (`capability.chosen-model`, File 05 §1) with `source: Subsystem { subsystem_id: data_processor }`; data-specialized presentations of shared capabilities use adapter capabilities (`capability.adapter-capabilities`, File 05 §17.4). Approval flows through the one policy layer (`policy.chosen-model`, File 06 §1); the surface contributes a data approval posture and references the egress, untrusted-content, and credential rules but evaluates no policy itself. Its tool surface composes through `surface.visibility-composition-resolution-algorithm` (File 07 §9). It declares a default data-and-vision-capable `ModelProfile` and per-role preferences, including the vision route for table-from-image and document extraction (`model.model-profile`, File 16 §4), and implements no private model selection (`model.consequences-for-later-specs`, File 16 §16).

### 2.8 With File 18 (World Model) and File 19 (Perception)

The surface self-registers its panels and contributes the world entities its work produces — `Dataset`, `Table`, `Notebook`, `Pipeline`, `Connection`, and `QueryResult` entities (`world.world-entity`, File 18 §4) — and is never screen-scraped to learn its own state (`world.observation-state-update`, File 18 §8.1, `perception.tiered-sensing` (File 19 §5.4)). It declares the sensors it exposes — the filesystem sensor for data files, and the screen/visual sensor for table-from-image and scanned-document extraction (`perception.sensor`, File 19 §4.3) — and consumes their structured output, owning no private capture pipeline (`perception.explicit-rejections`, File 19 §18). It produces `DatabaseQueryResult`, `FileSnapshot`, and data-profile observations through the canonical `observation.commit` path (`artifact.observation`, File 09 §13). It is structured-data-first (`core.world-model`, File 01 §6.7): it reads a document's structure before grounding over a rendered page, and a screenshot only when pixels are required.

### 2.9 With File 22 (Security, Credentials, and Trust)

File 22 owns the `SecretVault` (`security.secret-vault`, File 22 §5), the credential lifecycle (`security.credentials`, File 22 §6), the untrusted-content structural rule (`security.untrusted-content`, File 22 §12), and the egress-governance tiers (`security.egress-governance`, File 22 §11). This file consumes all of them: database and API credentials are vault-held `SecretRef`s (§22.3), ingested files and fetched documents and untrusted database content carry no capability or policy authority (§8.6), outbound database, API, and fetch connections are egress-governed (§22.3), and a profile, sample, or extracted value that contains a secret or personally-identifiable value is redacted at capture and never materialized raw (`secret.backend-boundary`, File 22 §4). The surface introduces no private secret store, trust authority, or egress path.

### 2.10 With Files 26, 03, 04 (Control Rails, Routing, and Future Automation)

The surface's control affordances are capabilities reachable through the rails (`controlrail.consequences-for-later-specs`, File 26 §21); it registers surface-scoped keybinding contexts and custom commands and owns no private rail. A data-source change monitor — a watch on a file, folder, query result, or feed — is a `Trigger`-rail entry (`controlrail.chosen-model`, File 26 §1, the `Trigger` rail kind) whose firing produces a `RunIntent` (`routing.trigger-kinds-routing`, File 03 §2.1); the deep scheduling and non-interactive-execution mechanics belong to the future Automation and Triggers spec, and this file frames the data monitor as one consumer (§17.4). ## 6. The Artifactized-Data Contract

Anchor: `data.artifactized-data`

### 6.1 Definition

The artifactized-data contract is the set of rules by which the Data Processor surface produces data results: a data result is a durable, versioned, lineage-tracked, validatable `Artifact` revision, produced by typed capabilities over a replaceable analytical engine, recorded as a citable block linked to its inputs by `derives_from`, never as transcript prose or an untracked file.

### 6.2 Data Result as Artifact Revision

A table or dataset the surface produces is a `Table` or `Dataset` `Artifact` whose content is the source of truth (`artifact.artifact-version`, File 09 §6, `block.kind-catalogue` (File 08 §3.1)); a chart is a `Chart` artifact; a notebook is a `Notebook` composed-block artifact (§10). A transform, query, extraction, or conversion creates a new artifact version — a sibling `Artifact`-kind block linked by `supersedes` when it revises an existing artifact, or a fresh artifact when it produces a new one — committed through the canonical version-creation path (`artifact.version-creation`, File 09 §6.3) and materialized through the workspace mirror where the artifact's `MaterializationPolicy` is `InWorkspace` (`artifact.artifact-materialization`, File 09 §7, `workspace.materialization` (File 24 §10)). A data result therefore carries validation state (§12), profiling state (§11), lineage (§6.3), and provenance (`artifact.provenance`, File 09 §15) — it is never only transcript prose, and artifact-grade data is never stored only as an assistant message (§23). A data operation that produces only a transient preview commits no artifact; the durable artifact commits at the operation's commit point with atomic, partial-safe materialization for streamed content (`run.streaming-partial-execution`, File 04 §12, `block.live-partial-write-capabilities` (File 08 §7.5)).

### 6.3 Lineage Is the `derives_from` Graph

Every derived data result records its lineage as `derives_from` edges (`block.canonical-edge-kinds`, File 08 §5.2) from the produced artifact version to its input artifacts and source blocks, with the transformation summary — the operation, its parameters, and the input and output schemas — carried on the edge metadata, and the producing run and capability recorded in the ledger (`run.execution-ledger`, File 04 §23.1). "What produced this chart, and from which datasets and transforms" is answered by `provenance.query_derivation_chain` (`artifact.provenance`, File 09 §15.3); the `lineage` panel (§4.2) renders that derivation chain, and a reproducibility report is an export over the derivation chain, the version graph, and the ledger. The surface introduces no `data_lineage` table and no private lineage event store (§23); lineage is the canonical derivation graph, exactly as `artifact.per-surface-projections` (File 09 §17.2) states the Data Processor surface presents "the data-lineage projection of `derives_from` edges."

### 6.4 Tables versus Datasets and Lazy Data

A small tabular result is a `Table` artifact with `Inline` content; a large result is a `Dataset` artifact with `External` content referencing the content-addressed blob store or a materialized data file (`block.block-content`, File 08 §4, `artifact.artifact-kind` (File 09 §4.2), `storage.blob-store` (File 20 §6)). The inline-versus-external decision uses the canonical inline-size threshold (`block.inline-size-threshold`, File 08 §4.2). A dataset too large to load whole is accessed through a lazy window: the durable artifact references the data file or blob, and the runtime resolves a bounded window or an analytical-engine relation over it for display and computation. That runtime relation — an open analytical-engine relation over a file — is device-local computed state, never a durable fact (§21); the durable artifact is the file or blob the relation reads. A query result over a dataset is itself a `Table` or `Dataset` artifact plus a `DatabaseQueryResult` observation (§7).

### 6.5 Boundary

This section defines the artifactized-data contract. File 08 owns the block, content variants, and content hash; File 09 owns the artifact, kinds, materialization, and provenance; File 11 owns the version commit; File 20 owns the blob store; File 24 owns the disk mirror. ## 7. Datasets, Tables, and the Analytical Engine

Anchor: `data.datasets-tables-engine`

### 7.1 Definition

The analytical-engine contract is the set of rules by which the Data Processor surface reads, queries, profiles, and transforms tabular and columnar data: an in-process analytical engine queries file-resident data directly, schema is inferred on read, every result is a lineage-bearing `Table`/`Dataset` artifact plus a `DatabaseQueryResult` observation, and the engine itself is a replaceable implementation behind the query capability.

### 7.2 The Query Capability

The data query capability (`data.query`) issues a query against one or more data sources and returns a result table. The canonical capability has a `dialect` or `query_language` parameter defaulting to `SQL`; adapter-specific variants such as `data.query.sql` or `data.query.dataframe` register only when a backend needs a distinct declaration. Its sources are canonical source classes plus registered source adapters: workspace files, workbook sheets, established database/API/remote-source connections, committed artifact tables or datasets, and execution-local in-memory relations backed by prior artifacts or observations. Source adapters declare touched resources, credential use, egress, sensitivity, snapshot/replay behavior, and produced artifact or observation kinds through the capability registry; they never create connector-private data stores. The engine queries common tabular and columnar file formats directly without a prior import step, supports querying many files through a glob, joins across files and connections, and infers schema on read; the specific engine and query dialect are capability-declaration and implementation concerns kept out of the body. A query is `ConcurrencySafe` for read-only sources, so independent queries run in parallel (`run.parallelism`, File 04 §15). A query against an external database or API resolves its credential as a vault-held `SecretRef` at the point of use and checks the destination against egress policy (§22.3).

An in-memory relation is an execution-local handle, not durable identity. It may feed later operations in the same execution unit, but it cannot cross a run boundary, turn boundary, export boundary, or user-visible artifact boundary unless materialized as a `Table`/`Dataset` artifact or committed as an `Observation`. Replay consumes the recorded artifact or observation, never a stale live relation handle.

### 7.3 Schema, Profiling, and Cleaning

Reading a dataset infers and records its schema — column names, inferred types, and nullability — as part of the dataset artifact's metadata and the analytical relation. Profiling (§11) is the canonical first operation on a new dataset. Cleaning operations — deduplication, type coercion, null handling, and outlier detection — are transforms (§9) producing lineage-bearing artifact revisions; their operation, parameters, input schema, output schema, producing run, and capability identity are reachable through the `derives_from` edge, ledger, and provenance record so the cleaning is reproducible and reviewable. A remembered cleaning preference is applied through Memory (§19) without becoming hidden behavior.

### 7.4 Pivots, Aggregations, and Multi-File Operations

Pivot, rollup, group-and-aggregate, join, concatenate, and merge operations are transforms over one or more input datasets producing a new `Table`/`Dataset` artifact linked by `derives_from` to its inputs. A join or concatenate across multiple files or sheets is a single capability invocation declaring its inputs, join keys, and join kind; the result is one lineage-bearing artifact. These operations run through the analytical engine or the dataframe runtime as the capability declares; both are replaceable implementations.

### 7.5 Streaming and Large Files

A file too large to load whole is read through a streaming or windowed-scan capability that yields bounded table chunks rather than buffering the whole file — a streaming parse of a large structured-text file, a column-projected filtered scan of a large columnar file, or a tail of a growing log file producing structured records. Chunks are typed streaming results or staged relations by default, not automatically committed blocks. Accepted chunks, retained windows, or final outputs commit as `Table`/`Dataset` artifacts, `Observation` blocks, or `SourceExcerpt` blocks according to the user's requested retention and the capability's output contract. The durable artifact references the source file or blob; the streaming relation is device-local computed state. Live tail/feed/monitor windows are transient unless deliberately retained, and retention is sensitivity-aware and configurable. Long-running scans stream progress as data activity events (§22.2) and run under a finite, configurable, killable wall-clock guard that is a safety guard around an operation with no completion signal, never a correctness condition (`sandbox.resource-limits`, File 23 §9.3); a fixed delay is never the readiness mechanism (§23).

### 7.6 Result Outcome and Oversize Handling

Every analytical operation produces a durable outcome when the user or run contract asks for a result: a `Table`/`Dataset` artifact, a `DatabaseQueryResult` observation, and the `derives_from` lineage (§6.3). A live database/API query result records the query text or query-template id, normalized parameters, redaction-safe source and connection identity, source fingerprint or revision when available, result schema, row count, sampling or window information, and transaction or isolation metadata when available. Replay uses the captured observation or artifact; refreshing against the live source is a new capability invocation subject to policy, egress, credentials, and stale-state checks. A large result is referenced rather than flooded into the model request: context assembly renders a schema, a sample window, and a reference, and the model requests more through the table window (`context.current-input-oversize-handling`, File 13 §7); the surface never returns an artifact-grade result as transcript prose alone (§23).

### 7.7 Database and API Writeback

Read-only query is the default. Mutating database, API, or remote-source operations are distinct write-capable capability modes or adapter capabilities, not implicit side effects of `data.query`. A writeback declares `access: write` or `read_write`, exact touched-resource expressions, preview mode when possible, transaction or rollback semantics when available, affected rows/resources, idempotency, reversibility class, postconditions, and expected artifact or observation outputs. If a backend cannot preview or bound the write, policy escalates rather than silently proceeding. Destructive or irreversible writes require the typed-confirmation and approval posture File 06 resolves for that proposal.

### 7.8 Boundary

This section owns the analytical-engine and dataset workflow. File 09 owns the `Table`/`Dataset` artifact kinds and the `DatabaseQueryResult` observation; File 20 owns the blob store; File 22 owns the credential and egress boundary; File 13 owns the oversize handling. The in-process analytical engine, the dataframe library, and the streaming parsers are replaceable implementations behind the surface's capabilities.

## 8. Structured Extraction

Anchor: `data.extraction`

### 8.1 Definition

The structured-extraction contract is the set of rules by which the Data Processor surface turns unstructured and semi-structured content — documents, scanned images, web pages, and free text — into structured, schema-conforming, source-grounded data. Extraction is a capability with typed sub-modes; its document parsers and optical-character-recognition engine are replaceable implementations behind the capability; every extracted fact is grounded to its source, and ungroundable output is flagged rather than asserted.

### 8.2 The Extraction Capability and Its Sub-Modes

The extraction capability (`data.extract` and its document, table, entity, and domain-specific variants) takes a source — a file, text, a fetched page, or a prior block — a target schema, optional few-shot examples, and a configuration, and returns structured output conforming to the schema. Its acquisition and structuring strategies are capability sub-modes within one capability, not separate model-facing calls (`capability.capability`, File 05 §2.3): the document path parses a document into typed content (text, tables, images, equations) through a replaceable parser; the schema-driven path constrains model-mediated extraction to the target schema with few-shot examples; the table path detects and lifts tables from documents, images, or pages; the entity path extracts named entities and relationships. The canonical contract this file fixes is the durable, grounded outcome (§8.4), the schema conformance, and a typed error when extraction fails; chunking, multi-pass policy, cross-chunk context, streaming, and grounding detail are configuration the capability resolves internally.

### 8.3 Chunking, Multi-Pass, Cross-Chunk Context, and Streaming

For long sources, extraction chunks the source respecting semantic boundaries so each model call receives coherent text, optionally includes trailing context from the prior chunk so entities spanning a boundary are not missed, optionally runs multiple passes and merges non-overlapping results to improve recall at a higher cost, and may stream extracted records as they complete (`run.streaming-partial-execution`, File 04 §12). These are configuration with sane defaults overridable per task and by setting; the multi-pass policy maps to the extraction sub-agent's thoroughness (`run.child-runs-multi-agent-work`, File 04 §16, §9.6) without hardcoding a pass count. The specific chunking and merging algorithms are a capability-declaration concern.

### 8.4 Source Grounding

Every extracted fact is grounded to its source: extraction records, for each extracted value, a typed `SourceSpan` within the source content where the value was found, captured as a `Citation` (`artifact.citation`, File 09 §12, `SourceSpan` per §12.3). Data grounding must support the relevant modality: text span, byte or line range, page range, page region or bounding box, table cell or cell range, structured-node selector, image region, audio/video time range, and composed spans where applicable. Grounding is the quality signal: a value that cannot be grounded to a span in the source is flagged as ungrounded and surfaced for review or excluded rather than asserted as fact, because an ungroundable extraction is likely fabricated. A grounded extraction backing a load-bearing assertion is a `Claim` with `Evidence` linking to the source excerpt and the `Citation` (`artifact.claim` (File 09 §9), `artifact.evidence` (File 09 §11)); a captured source span is committed as a `SourceExcerpt` block (`retrieval.chunking-excerpts`, File 12 §5.2) so the extracted material survives the source changing. The structured result is a `Table`/`Dataset`/`Document` artifact carrying the grounded values and their citations; URL and reference fields in the schema ground to captured anchors, never invented references.

### 8.5 Documents, Optical-Character Recognition, and Tables-from-Images

A document is parsed through a replaceable parser registry into typed content; an Office-style document is converted to a parseable form first; a scanned document or image is read through optical-character recognition; a table embedded in a document, an image, or a rendered page is detected and lifted into a `Table`/`Dataset` artifact. Table-from-image and scanned-document extraction is structured-data-first: the surface reads a document's machine-readable structure when present, grounds over a rendered page through the visual sensor and optical-character recognition when structure is absent, and uses a screenshot only when pixels are required (`perception.tiered-sensing`, File 19 §5, §20.3). Optical-character-recognition and table-from-image output is a derived observation linked to the raw source or capture, carries confidence where the processor provides it, and routes low-confidence or ambiguous fields through validation or review rather than silently treating them as facts. The optical-character-recognition engine, the document parsers, and the table-detection model are replaceable implementations behind the capability; the surface consumes the visual sensor's structured output and owns no capture pipeline (`perception.consequences-for-later-specs`, File 19 §19).

### 8.6 Untrusted Content and Borrowed Retrieval

All ingested files, fetched documents, parsed content, and content returned by a database or API are `untrusted_source_data` (`context.authority-classes`, File 13 §2.3) and carry no capability or policy authority by their own text (`security.untrusted-content`, File 22 §12.2): an instruction found inside an extracted document — including a document bearing a familiar instruction-file name — reaches the runtime as data the user or policy still gates, never as a command. This is the surface's non-negotiable default. Extraction borrows the shared retrieval substrate (`retrieval.consequences-for-later-specs`, File 12 §22): it consults the local knowledge base before the web where the workflow prefers it, uses the shared hybrid retrieval to find entities and reference data, and commits extracted entities and relationships into the shared entity-relationship projection (`retrieval.source-records`, File 12 §4.2) — a knowledge graph over the extracted data — rather than a private graph store. A repeated schema extraction may be promoted to a reusable extractor through the canonical capability, sandbox, policy, validation, and ledger path (§9.4); a generated extractor never becomes hidden script execution outside the registry, policy layer, sandbox, and ledger.

### 8.7 Boundary

This section owns the data-extraction workflow and its grounding contract. File 09 owns the claim, evidence, citation, source-excerpt, and `SourceSpan` contracts; File 12 owns the retrieval index, the chunking, and the entity-relationship projection; File 13 owns the authority class; File 19 owns the visual sensor and capture; File 22 owns the untrusted-content rule. The document parsers, the optical-character-recognition engine, the table-detection model, and the structured-extraction algorithm are replaceable implementations behind the surface's capabilities.

## 9. Transformation, Format Conversion, and Pipelines

Anchor: `data.transformation-pipelines`

### 9.1 Definition

The transformation-and-pipeline contract is the set of rules by which the Data Processor surface transforms and converts data and composes multi-step data workflows: a transform is a typed, lineage-bearing capability producing an artifact revision, a format conversion is a transform, and a pipeline is a `surface_runtime` / execution structure over the one shared execution and DAG model — a reusable pipeline being a `WorkflowTemplate` artifact — never a private pipeline engine or configuration table.

### 9.2 Transforms, Format Conversion, and Schema Mapping

A transform — filter, map, aggregate, pivot, join, concatenate, reshape, clean, or schema-map — is a capability invocation over one or more input artifacts producing a new `Table`/`Dataset` artifact linked by `derives_from` (§6.3). A format conversion across data interchange formats (and across document formats, §8.5) is a transform whose output is a converted artifact, with schema inference and optional schema validation before and after. A schema map is a transform that maps source fields to target fields — by name, by explicit mapping, by type-coerced or computed mapping — with a live preview of the transformed result; the `schema_map` panel (§4.2) presents it. Every transform records enough lineage to explain and replay the derivation: capability id and version, parameters, input and output artifact versions, validation records, and execution/cache identity are reachable from the `derives_from` edge through the ledger and provenance records. A transform whose result the user rejects reshapes the pending buffer before commit (`version.pending-operations-buffer`, File 11 §6).

### 9.3 The Data Pipeline as an Execution Structure

A data pipeline is a multi-step data workflow expressed as a graph of nodes — data sources, parse and extraction nodes, transform and validate nodes, and output nodes — over the one shared execution and DAG model (`run.execution-structure`, File 04 §5, `run.programmatic-execution` (File 04 §14)). Each node is a capability invocation; the pipeline's structure is a run's execution graph, executed through the shared executor with topological scheduling, parallel layers, and the shared node-output cache as a rebuildable projection. A node cache key includes every input that can change the output: input artifact/version ids or content hashes, upstream node output identities, capability id and version, parameters, schema version, parser/engine/model identity where relevant, model-selection record for model-mediated nodes, settings/profile inputs that affect output, declared environment and sandbox inputs, and output-kind schema. Content hash alone is insufficient. The data node library — the data source, parse, transform, validate, and output node kinds — is the surface's contribution to the shared node-kind catalogue, registered as `Custom` node kinds through the proposal-first mechanism; the pipeline canvas (§4.2 `pipeline`) is a UI projection over that node library, the shared execution-graph canvas with a data-focused node library, never a separate canvas. The surface introduces no private pipeline executor, no `dag_configs`/`dag_presets` tables, and no parallel scheduler (§23); pipeline execution, scheduling, and parallelism are File 04's.

### 9.4 Reusable Pipelines and Generated Operations

A pipeline the user wants to reuse is a `WorkflowTemplate` artifact (`artifact.artifact-kind`, File 09 §4, `run.automation-reuse` (File 04 §26)) carrying the pipeline structure, its parameters, and its required capability scope; a pipeline saved as a template, parameterized, and re-run is the Workflows-and-Reuse path the future Workflows spec owns, not a private pipeline store. A generated transform or extraction operation — code or a query the agent produces to perform a transformation — that proves useful may be promoted to a reusable operation or capability artifact through the same capability, sandbox, policy, validation, and ledger path; it never becomes hidden execution outside the registry, policy layer, sandbox, and ledger.

### 9.5 Custom Transforms and Programmatic Execution

A transformation the typed capabilities do not cover runs as programmatic execution (`run.programmatic-execution`, File 04 §14): the agent chains capability calls deterministically — iterating over rows, files, or records, transforming, and aggregating in one execution unit — or executes code over the data, with each inner call passing through the full pipeline, approval, and ledger. Code over data runs confined under a data `SandboxProfile` (§15.4); formula evaluation runs in a restricted, confined evaluator. A formula or transform runtime that exposes unmediated filesystem, network, process, environment, native-code, or foreign-function escape paths cannot qualify as merely runtime-confined; it must run at the isolation tier File 23 requires or be rejected. This is the canonical compute-over-data path; the prior "launch Coder for complex transforms" framing is superseded (§23), and the coder code-execution capability remains borrowable for scripting that genuinely belongs in the Coder surface.

### 9.6 Parallel and Multi-Agent Data Work

Batch operations over many files or records run as parallel capability execution (`run.parallelism`, File 04 §15) bounded by the shared concurrency cap; a deep analysis or a large extraction runs as a child-run structure (`run.child-runs-multi-agent-work`, File 04 §16) — representatively a perspective-guided or staged analysis with per-stage outputs and source-quality filtering, mirroring the web research structure (`web.research`, File 28 §9). The surface declares the data sub-agent kinds it can spawn (`worksurface.runtime-execution-declaration`, File 25 §9.2) — representatively a data extractor, a data cleaner, and a data visualizer — each running under the data surface defaults as a child run, returning through the canonical child-run output contracts (`run.merge`, File 04 §16.4), never mutating the coordinator's state directly. A three-mode depth control (quick, standard, deep) is a research/analysis-workflow parameter and an advisory budget (`run.budgets-limits`, File 04 §21), not an autonomy mode and not a phase machine (§23).

### 9.7 Boundary

This section owns the data transformation and pipeline workflow. File 04 owns the run, the execution structure, programmatic execution, parallelism, child runs, and the DAG executor; File 09 owns the `WorkflowTemplate` artifact and the lineage edges; File 11 owns the version commit and the pending buffer; File 23 confines the code execution; the future Workflows and Automation specs own reusable-pipeline and scheduling mechanics. The dataframe library and the node-graph canvas are replaceable implementations.

## 10. Notebooks

Anchor: `data.notebooks`

### 10.1 Definition

A notebook is the Data Processor surface's cell-based exploration document: a `Notebook` `Artifact` that is a composed block whose ordered children are typed cells, each cell's output a block, executed through the shared run model, versioned through the version graph, and exported through the canonical artifact export. The surface introduces no `data_notebooks` or `data_notebook_cells` tables.

### 10.2 The Notebook as a Composed-Block Artifact

A `Notebook` is an `Artifact` of kind `Notebook` (`artifact.artifact-kind`, File 09 §4) whose version is a `Composed` block (`block.block-content`, File 08 §4) whose ordered `children_block_ids` are the notebook's cells. A cell is a typed child block — a query cell, a transform cell, a chart cell, a model-prompt cell, a text cell, or a code cell — carrying its source content; a cell's output is a separate block (a `Table`, `Chart`, `Document`, or text block) linked to the cell. Inserting, deleting, reordering, or editing a cell edits the composed notebook block, creating a new sibling notebook version linked by `supersedes` (`block.edit-semantics`, File 08 §6.2, `version.sibling-block-versioning-over-block-pool` (File 11 §12)); the cells themselves are immutable blocks. Notebook history, cell-output history, and revert are projections over the version graph (§2.3), exactly as `coder.file-history` (File 27 §8) projects coder history; the surface introduces no per-cell snapshot store (§23).

### 10.3 Cell Execution

Running a cell is a run over the shared execution model: a query cell runs the analytical query capability (§7), a transform cell runs a transform (§9.2), a chart cell runs a visualization capability (§13), a model-prompt cell runs a model step over the cell's input data, a code cell runs programmatic execution confined under a data `SandboxProfile` (§9.5, §15.4), and a text cell is non-executing prose. Each cell's output commits as a block linked to the cell; cell outputs feed subsequent cells through the cell graph, which is a data pipeline execution structure (§9.3) — a notebook and a pipeline are two presentations of the same execution graph, and the surface offers conversion between them. A cell execution records its input cell version, referenced artifact or dataset versions, parameters, environment descriptor, sandbox profile, capability identity, and produced outputs. Editing or replacing a cell marks dependent outputs stale until re-executed or explicitly accepted as historical. Long-running cells stream progress as data activity events (§22.2). A cell execution that depends on prior data revalidates currency before mutating (`run.call-pipeline`, File 04 §8.2).

### 10.4 Notebook Export

A notebook exports to a self-contained document or an interchange notebook format through the canonical artifact export (`artifact.export`, File 09 §16.1, `artifact.preview_export`): the export walks the notebook's cells and their outputs and renders them, materialized through the workspace mirror or an external destination. Interchange formats are lossy unless the export is a `PortablePackage` or artifact bundle that carries Atlas metadata, lineage, observations, and version identities. Export passes through egress governance and sensitivity filtering on any share or external write (`security.egress-governance`, File 22 §11, §21.4); no unredacted secret or personally-identifiable value is written to an exported notebook. The export formats are a capability concern; the export is an artifact projection, never a private write path.

### 10.5 Boundary

This section owns the notebook workflow. File 08 owns the composed block and the cell children; File 09 owns the `Notebook` artifact kind and the export; File 11 owns the version graph the notebook history projects; File 04 owns the cell execution; File 23 confines code cells; File 24 owns the materialization. The notebook runtime is a replaceable implementation behind the panel.

## 11. Data Profiling

Anchor: `data.profiling`

### 11.1 Definition

Data profiling is the Data Processor surface's "describe this dataset" operation: a profiling capability produces a `DataProfile` — row and column counts, per-column type, null and unique counts, statistics, distributions, representative aggregate summaries, detected correlations, and detected schema and quality issues — committed as an `Observation` and cached as a rebuildable projection, rendered as a dataset card. Raw samples, rare values, top values, and free-text examples are gated, bucketed, or redacted by sensitivity policy. The surface introduces no `data_profiles` table.

### 11.2 The Profile as Observation and Projection

The profiling capability (`data.profile`) reads a dataset and produces a `DataProfile`. The profile is committed as an `Observation` block (`artifact.observation`, File 09 §13 — a data-profile `ObservationKind`) capturing the dataset state it describes, with a staleness fingerprint over the dataset's content so a stale profile is detected and recomputed; a profile the user keeps remains an observation rendered as a dataset-card projection, while a report or shareable profile export is a `Document`/`Report` artifact linked to that observation. A cached profile is a rebuildable projection keyed by the dataset content hash plus the profiling configuration (`core.projection`, File 01 §6.11); its loss is a recomputation, never data loss. Profiling is the canonical first operation on a new dataset. Profiles persist aggregate summaries by default; personally-identifiable values are redacted at capture, and `Secret` values are never persisted in the profile (§5.5, `secret.backend-boundary` (File 22 §4)). Sampled or model-derived profile statistics record the sample frame, method, seed or window where applicable, source version, model-selection and provider-call attribution, and any pricing or tokenizer identity/snapshot that affected accounting or replay at the time of use; replay uses those recorded facts rather than assuming every value can be recalculated from live provider state.

### 11.3 Boundary

This section owns the data-profiling workflow. File 09 owns the `Observation` kind and the staleness fingerprint; File 01 owns the projection rebuild rule; File 22 owns the redaction. The profiling implementation is a replaceable implementation behind the capability.

## 12. Data Validation and Quality

Anchor: `data.validation`

### 12.1 Definition

Data validation is the Data Processor surface's workflow for checking a dataset against a schema and quality rules: a validation capability produces a `Validation` block of the `SchemaValidation` kind carrying pass/fail per rule and sensitivity-filtered failing-row evidence, the dataset's `ValidationState` derives from its linked validations, and validation integrates with the shared completion-verification and quality-control hook surface.

### 12.2 Schema and Constraint Validation

The validation capability (`data.validate.schema` and its variants) checks a dataset against a declared schema and a set of constraints — column type, range, pattern, uniqueness, null, and cross-column rules — and commits a `Validation` block of kind `SchemaValidation` (`artifact.validation-critique`, File 09 §14.1) linked to the validated dataset version by the `validated_by` edge (`artifact.validation-state-derivation`, File 09 §14.2). The validation block carries the outcome per rule, row locators and counts for failures, and redacted failing-row samples where policy allows. Secret values and raw personally-identifiable data are not duplicated into validation blocks; the block stores the rule id, row locator, count, and a redacted placeholder while the full row remains only in the source artifact when policy permits. The dataset's `ValidationState` derives from its required validations (`artifact.validation-critique`, File 09 §14.2). The schema format is a capability concern; the validation produces the canonical block shape. Validation integrates with the completion-verification hook surface (`run.termination`, File 04 §22) and the quality-control hooks (`ledger.hook`, File 10 §7) — a data run whose contract required a validated result does not complete on prose alone — and the surface owns no parallel validation pipeline (`artifact.consequences-for-later-specs`, File 09 §22). Personally-identifiable-data detection is a validation and capture concern: detecting personally-identifiable or secret values in a dataset is a validation check feeding the redaction and sensitivity classification (§5.5, `security.untrusted-content` (File 22 §12)).

### 12.3 Boundary

This section owns the data-validation workflow. File 09 owns the `Validation`/`SchemaValidation` contract and the validation-state derivation; File 04 §22 owns the completion floor; File 10 owns the hook surface; the future Quality-Control spec registers data validators through the canonical mechanism. The validation framework is a replaceable implementation behind the capability.

### 13.2 The Chart Artifact and Chart Specification

A chart is a `Chart` `Artifact` (`artifact.artifact-kind`, File 09 §4) whose content is a chart specification — the chart kind, the data binding, and the presentation configuration — plus a renderer hint, linked by `derives_from` to the dataset or query result it visualizes (§6.3). Automatic chart-kind recommendation from a dataset's profile (§11) is a capability that proposes a chart specification the user may accept or edit.

## 14. Media-as-Data

Anchor: `data.media`

### 14.1 Definition

Media-as-data is the Data Processor surface's workflow for processing images, audio, and video as data: optical-character recognition, transcription, transcoding, frame and audio extraction, deterministic media transforms, non-generative image processing, and batch operations produce data and media artifacts with provenance. Generative media creation is not a Data Processor primary; it is the borrowable image-and-media capability family and a future Media Studio surface.

### 14.2 Processing Media as Data

The Data Processor surface owns media processing that turns media into data or other formats: optical-character recognition turns a scanned image into text or a table (§8.5); audio transcription turns audio into text or a timed transcript; video operations trim, transcode, extract frames as images, extract audio, and handle subtitles; non-generative image processing applies filters, resizes, crops, composes, removes backgrounds, and organizes images by content, date, or location; batch operations rename, resize, compress, and convert many files in parallel (§9.6). Each media operation produces a durable artifact — a text or `Document` artifact (transcription, extracted text), an `Image`/`Audio`/`Video` artifact (a processed media file), or a `Table`/`Dataset` artifact (extracted structured data) — with provenance and lineage (§6.3). The boundary is firm: the Data Processor transforms and extracts media as data; it borrows generation in place when a workflow needs an illustrative output, and never re-owns generation. When a borrowed model produces media, the resulting artifact records provenance and prompt lineage under the owning generative capability's contract.

### 14.4 Boundary

This section owns the media-as-data workflow and the generation boundary. ## 15. Context, Model, Execution, Sandbox, and Workspace Policy

Anchor: `data.policy-declaration`

### 15.1 Definition

The Data Processor surface declares its default context, compaction, model, execution, budget, sandbox, and workspace policies by reference (`worksurface.context-model-declaration` (File 25 §8), `worksurface.runtime-execution-declaration` (File 25 §9)). It names which policies it defaults to; the policy mechanics stay with their owning files, and every default is overridable through the settings cascade (`settings.scopes-profile-contexts-overlays`, File 15 §5.2).

### 15.2 Default Context and Compaction Policy

The Data Processor surface declares a default data-aware `ContextPolicy` and `CompactionPolicy` from the canonical families (`context.context-policies`, File 13 §4, `context.compaction` (File 13 §12)): the context policy assembles dataset schemas, profiles, samples, and query results as `RetrievedContext` and references large datasets and documents rather than flooding context with full data (`context.current-input-oversize-handling`, File 13 §7, `context.virtual-paging` (File 13 §13)), marks ingested and fetched content `untrusted_source_data` (§8.6), and protects the current input and the active dataset; the compaction policy preserves the lineage, evidence, and validation chains of accepted datasets and reports (`artifact.evidence` (File 09 §11.5), `context.continuity-summaries` (File 13 §14)) and pages out large captured data to references. Every model request assembles through the one `ContextAssemblyService`; the surface creates no private model-request path.

### 15.3 Default Model Profile

The Data Processor surface declares a default data-and-vision-capable `ModelProfile` and per-role preferences (`model.model-profile`, File 16 §4): the profile prefers a model with provider-native tool calling and structured-output support for extraction and schema-conforming output, prefers a vision-capable route where table-from-image, scanned-document, or rendered-page extraction is needed (§8.5), and prefers a lower-cost route for classification, query reformulation, and routine extraction. Per-role preferences distinguish the responder, the extractor, the cleaner, the validator, the analysis-stage roles, and the chart-recommendation role. Data sensitivity is analyzed over the input before model selection (`model.model-workload-requirements`, File 16 §5.3), so a `Sensitive` dataset selects a model satisfying the data-boundary requirement. The surface implements no private model-selection logic; selection stays the Model Strategy layer's, and the user may override the profile per scope.

### 15.4 Default Sandbox Profiles

The Data Processor surface declares its default `SandboxProfile`s (`sandbox.contract`, File 23 §3): an analytical-engine-and-transform profile confining the analytical engine and dataframe transforms to the operating-system-confined isolation tier, the workspace filesystem region plus the data sources the operation declares, no network by default (widened only by explicit opt-in through egress policy for a declared database or API source), and a bounded memory and process budget for large-data operations; a code-cell profile confining notebook code cells, custom transforms, and formula evaluation, with a stricter filesystem and no-network default; and a media profile confining the media toolchain to the workspace filesystem with a bounded resource and time guard. The environment allowlist governs both direct environment variables and variables discovered from workspace environment files; values enter through the environment policy or `SecretRef` resolution, not automatic raw injection (`process.spawning`, File 23 §5.3). Untrusted ingested or downloaded content is treated as carrying no authority (§8.6) and, where executed or rendered, runs at the isolation tier its trust class requires (`sandbox.isolation-tiers`, File 23 §4.3). A runtime that exposes unmediated filesystem, network, process, environment, native-code, or foreign-function escape paths must run at the stronger isolation tier File 23 requires or be rejected. The surface extends the base contract only with its data-runtime capability surface; it redefines no enforcement or kill semantics and opens no private sandbox.

### 15.5 Default Execution Preset and the Plan Capability

The Data Processor surface declares a default execution preset — the surface-runtime structure its data runs start from (`run.execution-entry`, File 04 §4) — as a model-and-tool agent loop over the shared run lifecycle: read and profile the data, propose and apply transforms or extractions, query and visualize, validate, and iterate until completion, pause, or user intervention. A pipeline or a deep analysis runs as the data execution structure (§9.3) or a child-run structure (§9.6) over the same semantics. Planning is the optional shared `plan` capability (`run.task-promotion-task-updates`, File 04 §18): the agent may call it to produce an editable `Plan` block when a data task's complexity warrants it. There is no planning phase, no planner-versus-executor model split, no phase state machine, and no per-surface "analysis mode enabled" toggle; the `plan` capability is a normal block-producing tool any surface may use, and plan blocks live in the version tree (§23). Completion evidence is data-specific: transforms commit artifact revisions and lineage, validations commit `Validation` blocks, extraction commits grounded structured output, profiling commits an `Observation`, and query work commits or stages a result. Prose-only completion is valid only for explanation-only runs. The surface declares default run budgets as advisory ceilings overridable per scope, never hidden hard limits (`run.budgets-limits`, File 04 §21), and declares the data sub-agent kinds it spawns (§9.6).

### 15.6 Instruction-File Qualifier and Contribution

The Data Processor surface declares its instruction-file qualifier — the `ATLAS.data_processor.md` variant of the `ATLAS.md` hierarchy (`workspace.instruction-files`, File 24 §9.2) — and its model-request instruction contribution: the surface's identity, the data-environment facts, the untrusted-data discipline, and the data guidance, assembled by context assembly into the `InstructionSources` region with the correct authority class (`context.instruction-sources-workspace-files`, File 13 §16). The surface's instruction contribution is one attributed assembly part among many, never a private prompt the surface owns. Instructions found inside ingested data, fetched documents, or database content are untrusted data with no instruction authority, regardless of any familiar instruction-file name they bear (§8.6); only the workspace `ATLAS.md`/`ATLAS.data_processor.md` hierarchy carries instruction authority, resolved through File 24.

### 15.7 Workspace Relationship

The Data Processor surface's views render over the bound `Workspace` (`workspace.conversation-binding`, File 24 §7); its datasets, converted files, charts, notebooks, reports, and media outputs materialize through the disk↔substrate mirror and File 23's filesystem boundary (§6.2); its per-surface working convention is a `data/` subdirectory (representatively `datasets/`, `outputs/`, and `notebooks/`) projected against the workspace mirror (`workspace.materialization`, File 24 §10). Workspace `.atlas/` may contain data settings, command definitions, and redaction-safe database-connection declarations or bindings; actual credentials, connection secrets, and absolute source paths are device-local and vault-held (§22.3) and never sync or export. The surface owns no workspace identity, disk-history store, or parallel materialization path.

### 15.8 Boundary

This section declares the data defaults by reference. File 13 owns context and compaction; File 16 owns the model profile and selection; File 04 owns the run, the execution structure, the `plan` capability, and budgets; File 23 owns the sandbox; File 22 owns the egress and credential boundary; File 24 owns the workspace and instruction files; File 15 owns the settings resolution.

The per-profile workflows the source material proposes (researcher, data analyst, office worker, developer/log-analysis, student, creative, solopreneur, casual, power user, educator) are presentation and customization seeds — quick-action sets, emphasized capabilities, and default panel layouts — saved as view presets and settings/profile records (`settings.profiles`, File 15 §7), never autonomy or participation modes (§23): switching from the office preset to the analyst preset opens more panels and surfaces more capabilities; it does not change how autonomous the agent is, which model is selected, the context policy, the execution entry, the budget, the sandbox profile, or the approval posture. Selecting a richer preset is progressive disclosure, never a mode change. The user may save custom presets and override the default per scope.

### 16.3 The Activity Feed and Inspectors

The Data Processor surface presents an activity feed — the conversational execution display of the data run — that renders the run's progress through the shared execution-presentation contracts (`run.presentation`, File 04 §25): ingestion, extraction, transform, query, and visualization steps (with data results shown as table previews and charts shown inline), batched approval requests (§5.5), pipeline-node and child-run activity (§9, collapsible), programmatic-execution inner calls, and streaming progress for long operations (§7.5). The feed is a projection over the ledger and event stream, not a private log. The surface declares default inspectors (context, schema, lineage, and validation inspection) as inspector-panel projections over substrate state.

### 16.4 Customization, Morphing, and the Shell

The Data Processor surface declares a customization policy (`worksurface.views-presets`, File 25 §7.4) describing which kinds of customization it permits — panel rearrangement, the notebook-and-pipeline split, custom panel registration, and widget placement — resolved by the UI customization layer; the surface owns what kinds are allowed, not the concrete placement mechanics. Surface morphing — projecting the data panels and active view preset when the Data Processor surface becomes the active presentation surface — is a UI projection driven by the `SurfaceContract`, the live `SurfaceState`, and the routing decision (`worksurface.views-presets`, File 25 §7.3); it changes presentation, not the work model. Conversation is an always-available control rail and an expand/collapse view, never forced to occupy the primary pane during data work (`worksurface.activation-shell`, File 25 §11.3); a data conversation may move between conversation-first and a data-surface focus over time without changing the work model.

### 16.5 Boundary

This section declares the data view presets and customization policy. ### 17.4 The Data-Source Change Monitor

Change detection is event-first where the source emits change signals (a file-system change event) and otherwise a configurable polling cadence that is a flagged fallback, never a correctness condition (`perception.triggers`, File 19 §8.2); change detection diffs the source's captured state against its prior captured state using a content fingerprint and the version-graph history of its observations. The deep scheduling, eligibility, and non-interactive-execution mechanics belong to the future Automation and Triggers spec; this file frames the data monitor as a `Trigger` consumer.

## 21. Persistence, Locality, and Portability

Anchor: `data.persistence-locality`

### 21.1 Definition

The Data Processor surface's durable state persists as substrate families through the one storage contract, splits by locality the way a workspace's does, and moves cross-installation through the canonical portability mechanisms. The surface introduces no private durable store.

### 21.2 What Persists and Where

The surface's durable state — its registered `SurfaceContract` versions, its registered `Custom` kinds, its scoped enable state and settings, its registered monitors and reusable pipeline templates, and the blocks, artifacts, versions, datasets, notebooks, charts, extraction records, source excerpts, citations, validations, lineage edges, and observations its work produces — persists as substrate families and content-addressed blobs through the storage contract (`storage.durable-substrate`, File 20 §3, `storage.consequences` (File 20 §18)); large datasets, converted files, and media blobs resolve from the content-addressed blob store (`storage.blob-store`, File 20 §6). The surface's live state — active panels, focus, selection, the materialized presentation, open analytical-engine relations, lazy dataset windows, cached profiles, full-execution-identity node-output caches, and database connection handles — is computed and rebuilt from self-registration and the version-graph projection, never a durable fact (`worksurface.persistence-locality`, File 25 §16.1); its loss is a rebuild, never data loss. Data indexes, embedding shards, the entity-relationship projection, and profile and node-output caches are rebuildable projections over the durable artifacts and observations (`retrieval.indexing-pipeline`, File 12 §12.3, `core.projection` (File 01 §6.11)).

### 21.3 Locality

The Data Processor surface's identity splits by locality the way a workspace's does (`worksurface.persistence-locality`, File 25 §16.2, `workspace.locality` (File 24 §4)): the surface's logical declaration, the datasets, charts, notebooks, reports, validations, lineage, and pipeline-template definitions sync, while device-bound runtime state — open analytical-engine relations, database connection handles and their credentials, node-output caches, profile caches, and absolute source paths — is device-local and rebuilds or re-establishes per device and never syncs. A monitor or a pipeline that depends on a local data source, a database connection, or a credential syncs as a definition, not as an active local binding; activation on another device revalidates the source, the connection, the credential, and the egress policy. `Connection` world facts are device-local by default (`portability.what-replicates`, File 21 §11). Vault-held database and API credentials never sync as raw material (§22.3).

### 21.4 Portability

The surface's durable data state rides the syncable substrate and the `PortablePackage` for cross-device and cross-installation movement (`portability.consequences`, File 21 §18); a dataset, its lineage, its validations, and the charts and notebooks derived from it export losslessly with the captured support content required to reproduce them — source excerpts, captured observations, artifact versions, and the content-addressed blobs they reference — unless policy or sensitivity filtering omits them with typed provenance gaps. Derived indexes, the entity-relationship projection, profile caches, node-output caches, and analytical-engine relations are rebuilt on receive rather than transported (excluded from export as rebuildable, `CONSTRAINTS.md` §14 realized through `portability.what-replicates` (File 21 §5.3)). The surface may declare a lossy convenience export (a rendered chart image, a flat data file, a rendered report), but it passes through egress governance, audit recording, and sensitivity filtering (§22.3) and uses no private export path. The surface persists no unredacted secret, raw credential, or personally-identifiable value in any materialized, exported, or synced state, and exposes no absolute host directory layout to the model by default (`secret.backend-boundary`, File 22 §4). Every hash the surface relies on — a dataset content hash, a blob address, a profile cache key, an extraction-identity cache key, an export-bundle hash — is computed over a declared `CanonicalEncoding`, never physical bytes (`core.canonical-hash`, File 01 §7.14); the surface defines no new canonical hash.

### 21.5 Boundary

This section declares the data persistence and locality classification. File 20 owns the storage substrate, the blob store, and rebuild orchestration; File 21 owns replication and the package; File 22 owns the secret and egress boundaries; File 24 owns the workspace locality split; File 11 and File 12 own the version-graph and index projections.

## 23. Explicit Rejections

Anchor: `data.explicit-rejections`

The following are architecturally invalid for the Data Processor surface and for any later spec that extends it:

- **A data result stored only as transcript prose, or a file silently dropped on disk without an artifact** — a data result is a durable, lineage-bearing `Dataset`/`Table`/`Chart`/`Notebook` `Artifact` revision; storing artifact-grade data only as an assistant message is message inflation (`artifact.consequences-for-later-specs`, File 09 §22) and is rejected (§6.2).
- **A `TableBlock` block kind or a parallel artifact store for data** — tabular data is the `Table` and `Dataset` artifact kinds over the one block pool; lazy and engine-resident data is external content plus a device-local runtime relation, not a new durable block kind (§6.4; `block.explicit-rejections`, File 08 §15, `artifact.explicit-rejections` (File 09 §21)).
- **Parallel `data_notebooks`, `data_notebook_cells`, `data_lineage`, `data_profiles`, `dag_configs`, or `dag_presets` tables** — a notebook is a composed-block artifact whose cells are child blocks, lineage is the `derives_from` graph queried through provenance, a profile is an `Observation` and a cached projection, and a reusable pipeline is a `WorkflowTemplate` artifact (§6.3, §10, §11, §9.4; `version.explicit-rejections`, File 11 §23, `retrieval.explicit-rejections` (File 12 §21)). If a feature seems to need a new durable data table, it is reframed as a block, artifact, observation, edge, or projection under the canonical registries (`CONSTRAINTS.md` §12 realized).
- **A private pipeline executor, DAG engine, scheduler, or pipeline canvas** — a data pipeline is a `surface_runtime` / programmatic-execution structure over the one shared execution and DAG model with a data node library, and the pipeline canvas is a UI projection over that shared canvas (§9.3; `run.consequences-for-later-specs`, File 04 §29, `worksurface.no-private-architecture` (File 25 §12)).
- **A private data-index, knowledge, or graph store** — data extraction commits entities and relationships into the shared retrieval and entity-relationship projection; the surface owns extraction semantics, not a parallel retrieval or graph substrate (§8.6; `retrieval.explicit-rejections`, File 12 §21).
- **Extraction without source grounding, or invented references** — every extracted fact grounds to a `SourceSpan` captured as a `Citation`, ungroundable output is flagged or excluded rather than asserted, and URL or reference fields ground to captured anchors (§8.4; `artifact.citation`, File 09 §12).
- **A private model-request assembly path or private model-selection logic** — every data model request assembles through the one `ContextAssemblyService` with ingested and fetched content marked untrusted, and the surface declares a default `ModelProfile` (including the vision route) without implementing selection (§15.2, §15.3; `context.consequences-for-later-specs`, File 13 §22, `model.consequences-for-later-specs` (File 16 §16)).
- **Authority granted by ingested or fetched data** — an instruction inside an ingested file, a fetched document, a database value, or a familiar-named instruction file in data holds no capability or policy authority; all ingested and fetched content is `untrusted_source_data` (§8.6; `security.untrusted-content`, File 22 §12).
- **A data autonomy, participation, interaction-shape, persona, or analysis-mode field** — at any layer, in any form; data autonomy is capability permission tiers, leases, and approval posture plus user direction, progressive disclosure is which panels and view preset are open, the per-profile workflows and the notebook/pipeline distinction are presentations, and the three-mode depth control is a workflow parameter, not a phase machine (§15.5, §16.2; `worksurface.no-autonomy-field`, File 25 §13). There is no planner-versus-executor split, no two-phase machinery, and no `Drive`/`Supervise`/`Collaborate`/`Delegate` dial.
- **A private sandbox, process spawner, or analytical-engine confinement path** — all confined data execution runs through the one `Sandbox` contract under a data `SandboxProfile`; custom transforms, formula evaluation, and notebook code cells are programmatic execution confined through File 23, and the prior "launch Coder for complex transforms" framing is superseded by in-place programmatic execution (§9.5, §15.4; `sandbox.explicit-rejections`, File 23 §20).
- **Generative media creation as a Data Processor primary** — the surface processes media as data (optical-character recognition, transcription, transcode, extraction, deterministic media transforms, non-generative image processing, batch); generative image and media creation is the borrowable `image.*` family and a future Media Studio surface, reached by borrow or reroute, never re-owned (§14.3).
- **Database, API, or remote-source writes hidden inside read-only query** — read-only query is the default; writeback is a distinct write-capable mode or adapter capability with preview, policy evaluation, resource expressions, transaction or rollback semantics where available, postconditions, and typed confirmation for destructive or irreversible effects (§7.7).
- **A view preset that silently changes backend policy** — applying a data view preset (minimal, default, notebook, pipeline, analyst, or a per-profile seed) changes presentation only and never silently changes model selection, context policy, execution entry, budget, sandbox profile, or approval posture (§16.2; `worksurface.views-presets`, File 25 §7.2).
- **Plaintext or app-encrypted database/API credentials** — data credentials are vault-held `SecretRef`s with only redaction-safe metadata persisted; no credential value enters the durable substrate, the ledger, the model context, an export, or a sync stream (§22.3; `secret.backend-boundary`, File 22 §4, `security.secret-vault` (File 22 §5)).
- **Materializing or exporting an unredacted secret, raw credential, or personally-identifiable value, or exposing absolute host paths to the model by default** — profiles, samples, query results, extracted values, and exports are redaction-filtered and sensitivity-governed, and model-facing content uses dataset ids, schemas, and workspace-relative paths (§5.5, §11.2, §21.4; `secret.backend-boundary`, File 22 §4).
- **Time-based or polling data behavior as a correctness condition** — dataset freshness, file-change capture, and re-profiling are event-first with flagged polling fallback only where a source emits no change events; the only permitted timer is a finite, configurable, killable wall-clock safety guard on a long-running operation with no completion signal, and a fixed delay is never the readiness mechanism (§7.5, §17.4; `world.explicit-rejections`, File 18 §16, `sandbox.explicit-rejections` (File 23 §20)).
- **Naming a specific analytical engine, dataframe library, document parser, optical-character-recognition engine, media toolchain, charting library, notebook runtime, or canvas widget as the canonical semantics** — these are replaceable implementations behind the surface's capabilities and panels; the canonical contract is the behavior, never the library (Source Resolution; `core.local-extensibility`, File 01 §7.10).

## 24. Consequences for Later Specs

Anchor: `data.consequences-for-later-specs`

Later specs must follow these rules:

- The other **per-surface specs** (Teacher, GUI Control, System Agent) declare their own `SurfaceContract`s to File 25's shape, the same way this file does for Data Processor; they may borrow the Data Processor's extraction, query, profiling, transform, validation, and visualization capabilities (§18.2) but introduce no private data mechanism. The Data Processor borrows web extraction, coder code-execution, and image generation in place, never by silent surface change.
- The **Automation and Triggers** spec owns the deep mechanics of the data-source change monitors this file frames as `Trigger`-rail entries (§17.4): scheduling, eligibility, enablement, change-detection cadence, and non-interactive-execution safety for a data monitor, confined to the narrowest data sandbox profile and pinning the Data Processor surface and its policies at save time the way routing does; it introduces no parallel data execution path.
- The **Workflows, Templates, and Reuse** spec treats reusable data pipelines (§9.4), the data default workflows (§17.3), and custom commands (§17.2) as reusable workflow and command definitions over `WorkflowTemplate` artifacts, and treats a successful data run as a promotable workflow; data workflow outputs that warrant durable identity become artifact versions through the canonical mechanism.
- The **Extension and Plugin System** and **MCP and External Integrations** specs may contribute data capabilities, analytical engines, document and table parsers, extraction adapters, chart and dashboard renderers, database connectors, and data-tool integrations through the proposal-first registration and source-approval path; a plugin-contributed data capability, engine, parser, or connector participates in the one registry, policy layer, sandbox, egress governance, and ledger exactly as a built-in does, and a connector-supplied source is egress- and trust-governed.
- The **UI Shell, Layout, Presentation, and Interaction Models** and **UI Customization, Widgets, and Theming** specs render the data panels — the table and dataset views, the chart and dashboard renderers, the notebook view, the pipeline and lineage canvases, the profile dataset card, the query and schema-map editors, the activity feed, the command palette, the keybinding contexts, and the view presets — over the data and behavior contracts this file fixes; charts and tables render through the shared interactive artifact runtime and the type-specific table renderer; presentation may vary freely, the work model cannot. - The **Quality Control and Validation** spec registers data validators (schema validation, data-quality checks, personally-identifiable-data detection, extraction-grounding and citation checks, and reproducibility checks) producing `Validation`/`Critique`/`Observation` blocks and integrating through the completion-verification hook surface and the event and capability hooks, not a separate pipeline; it consumes the data validation-state derivation (§12).
- The **Telemetry, Logging, and Observability** spec consumes the data events and the per-call attribution this file and File 10 emit; it renders the data run inspector from the version graph, ledger, lineage graph, and observation handles, never by re-running a query, re-extracting a document, or re-executing a transform for a historical view.

- The **Evaluation and Benchmarking** spec verifies the data round-trips — ingest-to-dataset-artifact, query-to-table-with-observation, extract-to-grounded-structured-output, transform-to-lineage-edge, notebook-cell-execution, pipeline-as-execution-structure, profile-as-observation, schema-validation-gate, the chart-as-artifact, and the lossless dataset-and-lineage export round-trip — replaying over recorded observations and immutable references, not a live query or engine, and verifying that no instruction in untrusted data escalated authority and that no recorded result re-queried a live source.
