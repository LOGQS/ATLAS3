# MCP and External Integrations

## Status

Canonical. This file defines the `Connector` primitive, the `ConnectorRegistry`, the Model Context Protocol (MCP) realization in both roles (Atlas as client and Atlas as server), the external-HTTP-API integration path, the inbound webhook/external-event transport, the connection lifecycle and reconnect machinery, and the remote-capability metadata contracts by which an external tool provider's operations, resources, and prompts are discovered, trusted, registered into the one Capability Registry, surfaced, executed, and removed. It realizes the external-tool-provider boundary `capability.capability-source` (File 05 §9.1), `policy.source-approval-flow` (File 06 §9), `surface.mcp-plugin-tool-integration` (File 07 §15), `provider.boundaries-with-adjacent-layers` (File 17 §2.7), `security.trust-model` (File 22 §9), `ledger.app-event-catalogue` (File 10 §4), `controlrail.external-protocol-rail` (File 26 §12), `automation.event-and-webhook-triggers` (File 33 §5), `workflow.consequences-for-later-specs` (File 34 §21), and `plugin.consequences-for-later-specs` (File 35 §18) declare and delegate to this file. It is the fourth post-surface spec: horizontal and surface-neutral, the way `worksurface.work-surface` (File 25), `controlrail.chosen-model` (File 26), `automation.chosen-model` (File 33), `workflow.chosen-model` (File 34), and `plugin.chosen-model` (File 35) are. It realizes the `core.stack-commitments` (File 01 §9) commitment to MCP as the external extension and integration protocol. Later canonical files may refine it, but may not contradict it.

## Scope

This file defines:

- the `Connector` — the durable, identified, versioned binding of one configured external integration (an MCP server, an external-HTTP-API definition, an inbound webhook receiver, or a richer registered protocol adapter) to its transport configuration, credential references, trust state, declared effect envelope, and connection lifecycle; the unifying primitive `codex_recommendations.md` §7.5 names `ConnectorRegistry`, realized so that simple HTTP-defined connectors and richer protocol adapters both contribute capabilities the same way
- the `ConnectorRegistry` — the one catalogue of configured connectors, their connection lifecycle and trust state, and the contribution-attribution index that ties registered remote capabilities, resources, and prompts back to the connector that produced them; the bundle-lifecycle layer over File 05's `McpServer`/`Api` source instances, not a parallel store of the contributions
- the **MCP client role** — consuming external MCP servers: declarative server configuration with `vault:<key>` substitution, the `tools/list`/`resources/list`/`resources/templates/list`/`prompts/list` query, schema translation from remote descriptors into `CapabilityDeclaration`s under the `mcp.<connector_slug>.<remote_tool_name>` identity and the `McpProxy` backend, deferred/lazy schema loading for large registries, and the `mcp.<connector_slug>.<tool>` namespace
- **MCP transport** — the transport-agnostic `McpSession` contract, the closed `McpTransportKind` catalogue (`Stdio`, `Http`, `Sse`, `StreamableHttp`, `WebSocket`, `NativeMessaging`, plus `Custom`), request/response pairing, server-pushed notification routing, progress streaming, and protocol-version negotiation localized to the session layer
- the **connection lifecycle, health, and reconnect** — spawn-on-demand, connection pooling, identity preservation across reconnect, the typed `ConnectionState` machine, the typed `IntegrationError` classification and transport-level retry with backoff and idempotency, the circuit-breaker recovery, and the no-clock-poll discipline
- **MCP resources and prompts** — resource and resource-template bridging into the one retrieval contract and external-content blocks, prompt discovery/render/import through File 13 instruction-authority rules, and the policy-gated server-initiated sampling path
- the **MCP server role** — exposing the externally-exposed Capability subset, resources, and prompts to external MCP clients over the same protocol implementation; the listener, scoped external-client credentials, per-client exposure allowlists, the localhost-default-remote-opt-in posture, and the external-MCP-client `Invoker`
- the **external-HTTP-API connector** — the declarative `Api`-source definition, the `api.<service_name>.<endpoint_id>` identity and the `HttpEndpoint` backend, auth kinds, request schemas, response capture, non-JSON and streaming body formats, pagination, the load pipeline and hot reload, connector-scoped rate limiting, and the HTTPS/no-remote-definition-fetch security posture
- **discovery and suggestion** — the `mcp.search`/`connector.search`/`connector.suggest` capability surface over a replaceable discovery registry, deferred-loading discovery, and the agent-suggests-never-connects rule
- **inbound webhooks and external-event transport** — `WebhookReceiver` connectors with receiver endpoint bindings, signature/bearer/basic authentication, freshness and idempotency, the localhost-default-remote-opt-in posture, and the handoff of an authenticated delivery to File 33's `Webhook` trigger
- **remote node kinds and cross-spec contributions** — a connector's remote operations registered as `Custom` workflow node kinds and as retrieval adapters, gated by source approval
- the **trust, credential, and egress posture** for every external integration; the `mcp.*`/`connector.*`/`integration.*` capability surface; the events; the persistence/locality/portability split; the settings dimensions; the explicit rejections; and the consequences for later specs

This file does not define:

- the `CapabilityDeclaration` field set, the Capability Registry, capability identity/versioning, the runtime-mutation registration mechanism, or the `McpProxy`/`HttpEndpoint` backend descriptors — `capability.declaration` (File 05 §3), `capability.capability-registry` (File 05 §12), `capability.backend-binding-lifecycle` (File 05 §10.4), and `capability.lifecycle` (File 05 §16) own those; a connector's remote operations are declarations admitted to that one registry under the `McpServer`, `Api`, or custom connector source (`capability.capability-source`, File 05 §9.1)

- the trust classes, trust establishment and verification, integrity verification, the secret vault internals, encryption, egress-governance policy semantics, or the untrusted-content structural rule — File 22 owns those; this file specifies how a connector is classified, credentialed, governed, and treated as untrusted through them

- the storage substrate, the on-disk config layout, the sync transport, the conflict pipeline, or the portable-bundle format — Files 20 and 21 own those; this file specifies what is durable, device-local, and portable
- the application installer, the auto-updater, the Chrome-extension publishing and native-messaging-host registration, or sidecar bundling — the Packaging, Platform, and Distribution spec (File 43) owns those; this file owns the connector-definition lifecycle and the MCP/webhook protocol surfaces, not the binary distribution
- UI rendering — the MCP/connector manager, the discovery browser, the resource panel, the OAuth consent surface, the connection inspector — File 37 and File 38 own those; this file specifies the data and resolution contracts they consume

Resolved tensions:

- **A parallel MCP/connector concept stack, or capabilities over the one substrate.** `unit11` CT.3 and the external ecosystems frame MCP as a distinct subsystem with its own tool list, lifecycle, and policy hooks; `codex_recommendations.md` §11.5 is decisive — “MCP exposure and ingestion should sit on top of the capability contract system … first-class capabilities and artifacts, not a parallel concept stack” — and `capability.sourcing-equivalence` (File 05 §9.3) forbids a parallel “MCP tool list.” This file adopts that posture absolutely. A connector's remote operations are `CapabilityDeclaration`s in the one Capability Registry under the `McpServer`, `Api`, or custom connector source; webhook receivers contribute trigger sources, not callable operations; resources are retrieval sources and external-content blocks; prompts are source-authored templates rendered/imported through File 13. The one net-new durable object is the `ConnectorRegistry` — the catalogue of configured integrations, their connection lifecycle and trust state, and the contribution-attribution index — the bundle-lifecycle layer over the existing registries, exactly the posture `plugin.registry` (File 35 §9), `automation.persistence` (File 33 §18), and `workflow.identity-versioning-source` (File 34 §8.1) took.
- **Three separate integration paths, or one `Connector` abstraction.** The sources present MCP, declarative HTTP APIs, webhooks, and ad-hoc connectors as unrelated mechanisms with near-identical lifecycle, trust, credential, and registry machinery. `codex_recommendations.md` §7.5 chose the `ConnectorRegistry` “where simple HTTP-defined connectors and richer protocol adapters both appear as capabilities,” rejecting both bare-HTTP-TOML-as-primary and connector-specific ad-hoc plugins. This file adopts one `Connector` primitive with a closed-canonical-plus-`Custom` `ConnectorKind` (`McpServer`, `ExternalApi`, `WebhookReceiver`, `Custom { protocol_adapter_id }`): an MCP server is a connector of kind `McpServer`; a declarative HTTP definition is a connector of kind `ExternalApi`; an inbound receiver is a connector of kind `WebhookReceiver`; richer protocol adapters register as `Custom`. One lifecycle, one trust path, one credential path, one registry, distinguished by kind. The three-tier extensibility insight (`unit12` D12.7) survives as the `File 35`↔`File 36` boundary: a raw MCP server is a connector, a plugin is a bundle that may *carry* a connector reference, a surface is a File 25 contribution.
- **MCP client-only, or both roles.** `infrastructure/mcp.md` and `atlas3-core/Context.md` are explicit: Atlas speaks MCP “in both directions,” and exposing Atlas itself as an MCP server is “the structurally TOS-safe integration path.” This file adopts both roles over one protocol implementation: the client role consumes external servers as connectors; the server role exposes the externally-exposed Capability subset, resources, and prompts to external MCP clients over the same `McpSession` and the File 26 External-Protocol rail. One protocol, two roles, one transport-agnostic session layer (`infrastructure/mcp.md`: “protocol upgrades only touch the session layer”).
- **Three trust levels, or the canonical six.** `unit12` D12.9 and `unit11` CT.3/CT.14 propose `McpTrustLevel { Verified, Community, Sideloaded }` (and the plugin `TrustLevel { Verified, Community, Unverified }`). `security.trust-model` (File 22 §9.2) already fixes the closed six-class set `System` / `Verified` / `User` / `Community` / `Unverified` / `Sideloaded`. This file honors File 22's set; a connector carries a `declared_trust_hint`, File 22 computes `effective_trust` from provenance, install-time review, and integrity, and File 06 narrows tiers against it. The unit's per-tier downgrade effects (one-tier / two-tier / first-use) are the realization of `policy.trust-mapping-defaults` (File 06 §9.6) applied to connector sources, not a parallel trust ladder.
- **Transport-retry and health reinvented, or the File 17 shape reused.** A connection to an MCP server or HTTP service needs the same transport-level retry, error classification, health-state, and circuit-breaker machinery `provider.transport-level-retry-backoff` (File 17 §11), `provider.provider-error-classification` (File 17 §10), and `provider.provider-health` (File 17 §12) define for model providers, but File 17 is explicitly “for model/inference providers, not tool providers.” This file reuses the *typed shapes* — the `ErrorClassification` advice (`retryable`, `rate_limited`, `retry_after_ms`, `recovery_advice`, `severity`), the backoff strategies, the event-driven health-state machine, and the no-scheduled-health-ping rule — as the cross-cutting transport-retry contract, instantiated for connector connections with connector-scoped identity, never File 17's provider registry, provider scopes, or model-call accounting.
- **External APIs as a separate file, or a connector kind.** `infrastructure/external-apis.md` and `infrastructure/mcp.md` are sibling files; `unit12` D12.15's plugin-reconciliation rule keeps them distinct paths. This file keeps the *declarative form* distinct (an `ExternalApi` connector is authored declaratively; an `McpServer` connector speaks a protocol) while unifying the *primitive*: both are `Connector`s with one lifecycle, trust path, credential path, registry, and rate-limit model. The reconciliation rule (`unit12` D12.15: declarative-TOML for a single endpoint, plugin for a bundle, MCP for a service that already speaks it) is preserved as guidance on connector-kind selection, not as three architectures.

## 1. Chosen Model

Anchor: `integration.chosen-model`

### 1.1 Definition

A `Connector` is a durable, identified, versioned binding of one configured external integration to its transport configuration, credential references, trust state, declared effect envelope, and connection lifecycle. A connector's kind is closed-canonical-plus-`Custom`:

- `McpServer` — an external Model Context Protocol server (a local binary or a remote endpoint) whose tools, resources, and prompts Atlas consumes
- `ExternalApi` — a user-authored declarative HTTP integration whose endpoints become callable operations
- `WebhookReceiver` — an inbound receiver binding whose contribution is a trigger source and whose effect envelope is inbound-only
- `Custom { protocol_adapter_id }` — a richer registered protocol adapter (a non-MCP, non-plain-HTTP external service) that contributes operations through the same registries

A connector contributes by registration, never by a parallel store. Its remote operations are `CapabilityDeclaration`s admitted to the one Capability Registry (`capability.capability-source`, File 05 §9.1): an `McpServer` connector's tools register under the `mcp.<connector_slug>.<remote_tool_name>` identity (`capability.id`, File 05 §13.1) with the `McpProxy { connector_id, remote_tool_name }` backend (`capability.backend-binding-lifecycle`, File 05 §10.4) and the `McpServer { connector_id, server_uuid, server_version }` source; an `ExternalApi` connector's endpoints register under the `api.<service_name>.<endpoint_id>` identity with the `HttpEndpoint { url_template, method, auth_ref }` backend and the `Api { api_name, api_definition_path }` source; a `WebhookReceiver` connector contributes an authenticated trigger source and no callable operations. A connector's resources are retrieval sources and external-content blocks (File 12); its prompts are source-authored prompt templates whose rendering/import follows File 13. MCP, external APIs, webhooks, prompts, and resources are first-class capabilities and artifacts over the one substrate, not a parallel concept stack (`codex_recommendations.md` §11.5).

The `ConnectorRegistry` (§3) is the one catalogue of configured connectors. It holds each connector's identity, kind, version, transport configuration, lifecycle and connection state, trust and credential state, and the contribution-attribution index that ties registered remote capabilities, resources, and prompts back to the connector that produced them. It is the connection-lifecycle layer over File 05's `McpServer`/`Api` source instances, never a second copy of the contributions.

### 1.2 Purpose

The system's reach extends past what it ships with through external services: an MCP server the user runs, a private company REST API, a third-party SaaS connector, an inbound webhook from an external system. Each is an external boundary across which operations, resources, prompts, and events must cross — discovered, trusted, credentialed, registered, surfaced, executed, governed, and removed — without the rest of the runtime learning a second way to do any of those things. The connector is that boundary made into a typed, reviewed, lifecycle-managed object, so that an external operation composes with everything else exactly as a built-in does.

The reframe is load-bearing: an external integration is **not** a parallel subsystem with its own tool list, its own approval path, its own execution loop, or its own event bus. MCP is a transport-and-protocol layer; an external API is a declarative-binding layer; a connector is the configured instance of either. Their operations enter the one registry, pass the one policy, surface through the one `ToolSurface`, execute through the one call pipeline, emit through the one event bus, and are governed by the one trust, secret, and egress model. Because the registries already exist, the cost of integrating service N+1 is flat (`core.extension-planes`, File 01 §6.14).

### 1.3 Rule

- There is one `Connector` primitive, one `ConnectorRegistry`, one MCP protocol implementation serving both roles, and one connector-lifecycle path. No subsystem, surface, plugin, receiver, or connector introduces a parallel external-tool list, a parallel connector store, a private external-integration runtime, or a registration path that bypasses the one canonical registries (`capability.sourcing-equivalence`, File 05 §9.3).
- A connector's remote operations register as `CapabilityDeclaration`s through `capability.runtime-mutation` (File 05 §16.2), its resources as retrieval sources (File 12), its prompts as source-authored prompt templates (File 13), and its webhook receivers as trigger-source contributions; a connector owns no execution and no private registry, and its remote calls run through the one `run.call-pipeline` (File 04 §8.2) and policy (File 06).
- A connector becomes active only after the proposal-first source-approval flow (`policy.source-approval-flow`, File 06 §9) and trust establishment (`security.trust-model`, File 22 §9) complete; connection is a user-only capability invocation. The agent discovers and *suggests* a connector but never connects, installs, enables, or externally exposes one (`capability.runtime-mutation`, File 05 §16.2).
- A connector's outbound calls are governed by egress policy (`security.egress-governance`, File 22 §11); a connector's inbound content (tool results, API responses, resource content, prompt text, webhook payloads) is untrusted content that holds no authority (`security.untrusted-content`, File 22 §12); a connector's credentials are vault references (`security.secret-vault`, File 22 §5), never inline.
- A connector's transport, connection lifecycle, and reconnect are event-driven and never clock-polled; identity is preserved across reconnect so the same registered capabilities re-resolve to the same entries.

### 1.4 Boundary

This file owns the connector, the connector registry, the MCP protocol realization in both roles, the transport and session layer, the connection lifecycle and reconnect, the remote metadata and bridging, the external-API connector, discovery, the inbound webhook transport, the remote-node-kind contribution path, and the `mcp.*`/`connector.*`/`integration.*` capability surface. It does not own the Capability Registry, the policy engine, the tool-surface composition, the trust model, the secret vault, the egress semantics, the event bus, the sandbox, the plugin bundle, the trigger object, the workflow body, the retrieval normalization, storage, sync, or the application installer — those are realized through their owning files.

## 3. The `Connector` and the `ConnectorRegistry`

Anchor: `integration.connector`

### 3.1 The `Connector` Field Set

A `Connector` carries:

- `connector_id` — stable identity; a registry-assigned globally unique slug, separate from the mutable display name, optional description, author, and homepage. The identity survives rename, reconnection, and version change; registered capabilities, attribution, and source labels reference it. For an `McpServer` connector, remote tools register under the stable slug while `server_uuid` remains provenance and collision evidence (`capability.id`, File 05 §13.1).
- `kind` — the closed-canonical-plus-`Custom` `ConnectorKind` (§1.1): `McpServer`, `ExternalApi`, `WebhookReceiver`, or `Custom { protocol_adapter_id }`.
- `version` — the connector's version, advanced when its definition or the remote server's advertised version changes; the unit of integrity and re-review (§9).
- `transport_config` — the typed transport configuration: for `McpServer`, the `McpTransportKind` (§6) plus its parameters (a command, arguments, and environment overlay for `Stdio`; a URL and headers for the network transports); for `ExternalApi`, the base URL, the auth kind, and the endpoint set (§11); for `WebhookReceiver`, the receiver path, binding posture, auth kind, freshness/idempotency declaration, and trigger-source handoff (§13); for `Custom`, the adapter's declared configuration. Secret-bearing values are `vault:<key>` references, never literals (§15).
- `credential_refs` — the vault references the connector resolves at the point of use (`security.secret-vault`, File 22 §5); a connector may hold multiple named accounts where the service supports them (§15).
- `declared_effect_envelope` — the honest upper bound over the connector's effects: the permission tiers and floors of its operations, the touched-resource classes, the network targets, the data-egress classes, the backend kinds, and whether the connector registers hooks, resources, resource templates, prompts, trigger sources, sampling, or node kinds. The envelope feeds the source-approval review (§9) and the import diagnostics (§17), and is the connector counterpart of a plugin's `PluginPermissionManifest` (`plugin.permission-manifest`, File 35 §6).
- `trust_state` — the `{ declared_trust_hint, registry_trust_override, effective_trust }` triple (`security.trust-model`, File 22 §9.3), computed by File 22, consumed by File 06; trust state lives on the registry record, never on the declarative definition.
- `install_source` — the provenance: bundled with the application, bundled with a plugin (carrying the `plugin_id`), resolved from a configured discovery registry, or user-declared in the connector's local definition. Provenance is a fact, not a trust grant (§9).
- `registry_record` — the live `ConnectorRegistry` state (§3.3): the connection state, the enabled state per scope, the contribution-attribution index, the descriptor cache, and diagnostics.

A connector definition is immutable for its `(connector_id, version)`; a new version supersedes the prior registry record, mirroring `capability.registered-capability` (File 05 §10.2).

### 3.2 Purpose

A connector exists so that the heterogeneous facts about one external integration — where it is, how to reach it, who authored it, how much it is trusted, what it may affect, which credentials it needs, what it currently contributes, and whether it is reachable right now — live in one inspectable object with one lifecycle, rather than scattered across a config file, a credential store, a tool list, and an ad-hoc connection handle. One object lets the source-approval review, the trust narrowing, the credential resolution, the egress governance, the reconnect machinery, and the uninstall cleanup all key on the same identity.

### 3.3 The `ConnectorRegistry`

The `ConnectorRegistry` is the one catalogue of configured connectors. It admits a configured connector, pairs it with mutable registry state, and exposes lookup, enumeration, enable/disable, the lifecycle operations (§5), and the registration-mutation event stream. There is no parallel connector store and no per-kind connector catalogue; the remote capabilities, resources, and prompts live in their owning registries, and this registry tracks the connectors and their attribution.

A connector's registry record carries: the `connector_id`, `kind`, and `version`; the `lifecycle_state` (`Configured`, `AwaitingReview`, `Approved`, `Connecting`, `Connected`, `Degraded`, `Disabled`, `Quarantined`, `Removing`, `Failed`); the `connection_state` (§7); the `enabled` state scoped global, workspace, or conversation (`capability.lifecycle`, File 05 §16.3); the `trust_state` and any integrity state (§9); the **contribution-attribution index** — the set of registered capability ids, resource source ids, prompt fragment ids, hook subscription ids, and node-kind ids this connector owns, each cross-referencing the owning registry's entry; the **descriptor cache** — the device-local cached remote tool/resource/prompt descriptors with their provenance and freshness (§7.3); and diagnostics (last connection result, failed-tool reasons, last refresh result). For a bundled connector reference the runtime source is `McpServer`/`Api` and the registry entry carries `contributing_bundle: { plugin_id, plugin_version }` (`capability.registered-capability`, File 05 §10.1); policy, approval, trust, and egress evaluate the runtime source, while disable, removal, and dependency impact evaluate bundle ownership (`plugin.registry`, File 35 §9.3). Registry state mutates without changing the connector definition; a new version supersedes the prior record. The attribution index and the descriptor cache are device-local projections rebuilt on reconnect; their loss is a rebuild, never a loss of a definition (`core.projection`, File 01 §6.11).

### 3.4 Rule

- A `Connector` carries identity, kind, version, transport config, credential references, declared effect envelope, trust state, install source, and a registry record; the definition is immutable-for-the-version and the registry record is the mutable connection-lifecycle state.
- There is one `ConnectorRegistry`; it catalogues configured connectors and their lifecycle, trust, attribution, and descriptor-cache state; it never duplicates the contributions, which live in their owning registries.
- A connector contributes by registration under the `McpServer`/`Api`/`WebhookReceiver`/`Custom`-adapter source; the attribution index records runtime source and, for bundled references, bundle ownership, so a connector registers, disables, and removes its contributions atomically while policy evaluates the source that actually executes.

### 3.5 The `ConnectorContract`

A connector of any kind exposes a typed `ConnectorContract` the registry and the source-approval review consume, realizing the `codex_recommendations.md` §7.5 `ConnectorRegistry` target so that simple HTTP-defined connectors and richer protocol adapters describe themselves the same way. The contract declares: the **auth model** (the auth kind and the vault credential namespace, §15); the **capability contracts** (the operations the connector contributes, each resolving to a `CapabilityDeclaration` with its tier, touched resources, and replay class); the **rate-limit model** (the connector-scoped rate-limit windows, §11.5); the **schema versioning** (how a remote descriptor's version is tracked so a changed remote schema is a versioned change, not a silent mutation); the **cache policy** (the descriptor-cache TTL and invalidation triggers, §7.3); the **resource classes** (the touched-resource classes and any registered extension class the connector's operations declare, `capability.extension-resource-classes`, File 05 §6.3); and the **sync strategy** (which of the connector's facts are device-local versus portable, §17). For an `McpServer` connector the contract is derived at connect time from the server's advertised capabilities and annotations (§5); for an `ExternalApi` connector it is read from the declarative definition (§11); for a `WebhookReceiver` connector it declares an empty capability-operation set and one trigger-source contribution with an inbound-only effect envelope; for a `Custom` adapter it is the adapter's declared contract. The contract is the one shape the discovery summary, the install review, and the connection inspector consume.

A `Custom { protocol_adapter_id }` connector is valid only when its adapter has a source-approved `ConnectorAdapterDeclaration`: adapter identity, version, source, supported transports, auth model, contribution mapping, descriptor-versioning strategy, cache policy, lifecycle hooks, error classification, touched-resource mapping, credential requirements, replay strategy, and source-approval metadata. A custom adapter contributes through the same registries and cannot create private tool, resource, prompt, or trigger stores.

### 3.6 Boundary

File 05 owns the capability declaration and registered-capability state a connector's operations become; File 22 owns the trust and integrity state; File 12 and File 13 own the resource and prompt forms; this file owns the connector object that binds them and the registry that catalogues them.

## 4. MCP — Atlas as Client

Anchor: `integration.mcp-client`

### 4.1 Definition

In the client role, Atlas consumes one or more external MCP servers, each configured as an `McpServer` connector. A configured server is declared in a device-local declarative form (the storage realization is `~/.atlas/mcp-servers.toml`, with the in-app MCP manager writing the same typed configuration) carrying the server name, the `McpTransportKind` and its parameters, and the environment overlay; secret-bearing values are `vault:<key>` references resolved at the point of use, never at configuration-load time, and a literal secret found where a reference belongs is detected and refused with a typed diagnostic (`security.secret-detection-redaction`, File 22 §7; `settings.secret-boundary`, File 15 §10).

### 4.2 Tool, Resource, and Prompt Registration

When a server connects (§5), Atlas queries its advertised `tools`, `resources`, and `prompts` and registers them:

- each remote **tool** registers as a `CapabilityDeclaration` under the `mcp.<connector_slug>.<remote_tool_name>` identity (`capability.id`, File 05 §13.1) with the `McpProxy { connector_id, remote_tool_name }` backend (`capability.backend-binding-lifecycle`, File 05 §10.4) and the `McpServer { connector_id, server_uuid, server_version }` source (`capability.capability-source`, File 05 §9.1). The remote tool's input schema is translated from its advertised form into the capability's `input_schema` (§4.3). The registered tool is otherwise indistinguishable from a built-in of the same kind; source surfaces only as metadata (`capability.sourcing-equivalence`, File 05 §9.3).
- each remote **resource** registers as a retrieval source and is bridgeable into an external-content block; reading its content is an explicit `resources/read` capability call, never a hidden side effect (§8; File 12). Parameterized resource templates register as retrieval-source templates and instantiate through the same explicit read path.
- each remote **prompt** registers as an inspectable source-authored prompt template; rendering or importing it into model-request assembly is an explicit policy-governed action whose authority is assigned by File 13 and source approval (§8; File 13).

There is no parallel “MCP tool list,” “MCP resource list,” or “MCP prompt list”; remote contributions enter the one Capability Registry, the one retrieval contract, and the one instruction-fragment library, with the connector source as metadata.

### 4.3 Schema Translation

A remote MCP descriptor is translated into the canonical declaration form at registration: the remote tool's name and description into the capability's display fields; the remote input schema into the capability's `input_schema` (`capability.input-schema`, File 05 §4.1) with the minor normalization a foreign schema dialect requires; and the remote tool's annotations into declared metadata. The closed MCP `ToolAnnotations` — `readOnlyHint`, `destructiveHint`, `idempotentHint` — map onto the canonical declaration: `readOnlyHint` informs a `ReadOnly` default tier and an `InternalAnalysis` capability class; `destructiveHint` informs an `ActionExternal` class and a non-`reversible` `reversibility_class`; `idempotentHint` informs the `idempotent` flag. The annotations are advisory inputs to the declared defaults, never a source of authority; trust narrowing and the floor still apply, and a remote tool that under-declares its effects is governed by its trust class and the egress and untrusted-content rules regardless. Translation is deterministic given the same remote descriptor and is recorded with the descriptor's provenance and version so replay re-derives nothing from the live server (§7.3, §16).

Remote names, descriptions, schemas, resource descriptions, prompt descriptions, discovery summaries, and API endpoint summaries are external source-authored metadata. They carry source attribution, configurable length limits, and File 13 authority-class boundaries whenever rendered into model-request text. Provider-native callable declaration wrappers may use `provider_native_callable_declaration`; the source-authored text inside or adjacent to those wrappers remains untrusted source data. Filtering prompt-injection phrases is not a correctness mechanism; architectural boundaries are.

Every proposed connector invocation binds to the resolved capability version and descriptor snapshot at proposal time. Approval requests, retries, workflow node executions, automations, and in-flight calls execute against that snapshot. A later server-pushed descriptor change affects future proposals only; if the old descriptor can no longer execute safely, the call fails with a typed stale-descriptor result rather than silently upgrading.

### 4.4 Deferred and Lazy Schema Loading

An MCP server with a large tool registry need not register every full schema eagerly. The connector supports deferred loading: at connect, the connector caches the compact descriptor (name, family, short description, declared tier, annotations, and `tool_count`) for each remote tool and registers the capability with that compact metadata; the full input schema is fetched on first borrow or first invocation and cached for the connection's lifetime. The agent sees a category-level description (a connector and its tool count and summary) and materializes the full schemas it needs through the discovery capabilities (§12) and the surface-borrow path (`surface.late-loading-runtime-discovery`, File 07 §7). Deferred loading trades a round trip for model-request-budget savings; it is default-off and opt-in per connector through the `defer_loading` flag in the connector configuration. This is the transport-side realization of the surface-side deferred-loading behavior `surface.loading-semantics` (File 07 §4.6) and `surface.mcp-plugin-tool-integration` (File 07 §15.4) already fix: File 07 places MCP-sourced capabilities in `Borrowable` and composes the surface; File 36 fetches the schema on demand.

### 4.5 Rule

- An external MCP server is an `McpServer` connector; its tools register as `mcp.<connector_slug>.<tool>` capabilities with the `McpProxy` backend and `McpServer` source, its resources as retrieval sources, and its prompts as source-authored prompt templates, through the one registries.
- Remote descriptors are translated deterministically into the canonical declaration form; `ToolAnnotations` inform declared defaults but never grant authority; translation is recorded with descriptor provenance and version for replay.
- Large registries support deferred loading (compact metadata at connect, full schema on demand), default-off and opt-in per connector, realizing the surface-side deferred-loading behavior File 07 fixes.

### 4.6 Boundary

File 05 owns the declaration, identity, backend, and registration mechanism; File 07 owns the surface placement and the borrow path; File 12 and File 13 own the resource and prompt forms; this file owns the protocol query, the schema translation, and the deferred-loading transport.

## 5. MCP Connection Establishment and Server Lifecycle

Anchor: `integration.mcp-lifecycle`

### 5.1 Spawn-on-Demand and Connection

A configured and approved `McpServer` connector connects on demand: a `Stdio` server's process is spawned the first time one of its tools is invoked, confined as a `ManagedProcess` (File 23 §5) with the environment denylist (§15.3); a network server (`Http`, `Sse`, `StreamableHttp`, `WebSocket`) is connection-pooled and the connection is opened on first use. On connection the connector performs the protocol handshake and version negotiation (§6), queries the advertised tools, resources, resource templates, and prompts, and registers them (§4.2). A `Stdio` connection may stay alive across calls, but is bounded by settings-driven idle reaping and/or concurrent-process caps and is reaped on shutdown; a network connection is pooled and idle-managed. A reaped `Stdio` server is spawned again on the next explicit call if the connector remains enabled and policy allows. The connect, register, and per-server tool-count facts emit through the events of §16.

### 5.2 Refresh and Server-Pushed Changes

A connector re-queries its advertised contributions on explicit refresh (the `mcp.refresh` capability, §16) and on a server-pushed tool-list-changed notification: an MCP server may notify that its tool set changed, and the connector re-queries and reconciles the registered capabilities, registering new ones, updating changed ones (as version increments, `capability.lifecycle`, File 05 §16.4), and transitioning removed ones to unavailable. Each refresh computes the connector envelope diff (§9.1). Non-expanding changes may reconcile under the approved connector policy; expanded contributions register as `unavailable_pending_source_review` until source approval accepts them. Already-approved contributions continue operating only where policy permits partial approval. Server-pushed progress notifications during a tool call surface as progress events the live UI and the run consume; a server-pushed notification is data, not authority, and never escalates a capability's tier. Refresh is event-driven; the runtime does not poll the server for contribution changes on a schedule.

### 5.3 Disconnect, Reconnect, and Identity Preservation

On disconnect — a crashed `Stdio` process, a dropped network connection, an explicit disable — the connector marks its registered capabilities `availability_status: unavailable_handler` (`capability.registered-capability`, File 05 §10) and its `connection_state` accordingly; the surface renders them `Unavailable` (`surface.degradation-graceful-absence`, File 07 §17.4). Reconnection preserves identity: the same `mcp.<connector_slug>.<tool>` ids re-resolve to the same registered entries and the `resolved_backend_binding` is re-bound without changing identity, so saved automations, workflows, and shortcuts that reference the connector's capabilities survive a reconnection (`surface.mcp-plugin-tool-integration`, File 07 §15.2). A crashed or idle-reaped `Stdio` server is re-spawned on the next tool call; a dropped network server reconnects per the recovery machinery (§7).

### 5.4 Removal

Disconnecting a connector entirely unregisters all its contributions atomically through the attribution index, tears down its session and pooled connections, and cleans up non-destructively: the connector's settings values orphan rather than delete (`settings.setting-definition`, File 15 §3.4); durable data its operations produced (knowledge entries, committed artifacts, ledgered invocations) is preserved (`core.non-destructive-by-default`, File 01 §7.13); and historical references to the connector's capabilities remain resolvable through their recorded versions for replay. Removal retains a non-executable tombstone with the connector identity, version, source provenance, and removal reason. Before `connector.remove`, `connector.disable`, or a quarantine that unregisters contributions, the runtime previews affected capabilities, borrow grants, leases, automations, workflows, shortcuts, hook subscriptions, retrieval adapters, prompt fragments, exposed MCP-server entries, and trigger sources. Broken references resolve to typed unavailable states, never silent absence. Disable is the reversible intermediate that unregisters the contributions but preserves the definition, credentials, and settings; re-enable re-registers and reconnects. Quarantine is the safety response to integrity, trust, sandbox, or runtime-behavior violations: it stops new calls and may cancel or kill connector-owned active units through File 04's killability contract, never by silent mid-effect abort, and is reversible through explicit review.

### 5.5 Who May Drive the Lifecycle

Configuring, connecting, enabling, disabling, and removing a connector are user-initiated capability invocations (§16) gated by policy. Refresh is a registry mutation allowed only for an already-reviewed connector or explicit user action, and envelope expansion parks new contributions for review. The agent discovers and *suggests* a connector (§12) but may not connect, enable, configure, or expose one; connection capabilities are not privileged side doors and the agent cannot self-promote (`capability.runtime-mutation`, File 05 §16.2). Policy and safety systems may quarantine a connector when its declared contract is violated; quarantine never deletes the connector or its produced records.

### 5.6 Rule

- A connector connects on demand, handshakes and negotiates version, queries and registers its contributions, and stays alive (`Stdio`) or pools (network); refresh and server-pushed changes re-query and reconcile event-first, never clock-polled.
- Reconnection preserves identity so the same capability ids re-resolve to the same entries; removal unregisters atomically, orphans settings non-destructively, preserves produced data, and retains a tombstone; disable is reversible and quarantine is the safety response.
- Configure, connect, enable, disable, refresh, and remove are user-only and policy-gated; the agent suggests but never drives the lifecycle.

### 5.7 Boundary

File 23 owns the spawned-process sandbox and the reaper; File 05 owns the registration and availability mechanics; File 07 owns the surface degradation; File 42 owns the startup-phase orchestration. This section owns the connection lifecycle and the user-only rule.

## 6. MCP Transport and the `McpSession`

Anchor: `integration.mcp-session`

### 6.1 The Transport-Agnostic Session

One transport-agnostic `McpSession` handles request/response pairing, server-pushed notification routing, progress delivery, and error mapping for every MCP connection in both roles. Transport-specific bindings implement a small typed transport contract — send a message, receive a message, close — and the session logic sits above it, so protocol-version upgrades touch only the session layer and never the transports (`infrastructure/mcp.md`). The session normalizes a transport's native event vocabulary into the canonical message and notification forms before they leave the session boundary, the same way `provider.streaming` (File 17 §9) normalizes provider chunks.

### 6.2 The Transport Catalogue

The `McpTransportKind` set is closed-canonical-plus-`Custom`:

- `Stdio` — a spawned local subprocess speaking the protocol over standard input and output; the default for local servers; confined as a `ManagedProcess` (File 23 §5). The session filters protocol-invalid lines (a blank or non-message line on stdin is dropped rather than allowed to fault the parser).
- `Http` and `Sse` — request/response and server-sent-events over HTTP for networked servers.
- `StreamableHttp` — the streamable-HTTP transport for networked servers that stream; on a stream failure the connection re-establishes as an isolated session rather than corrupting the existing one.
- `WebSocket` — bidirectional streaming for clients and servers that prefer it.
- `NativeMessaging` — the browser-extension native-messaging channel by which the Atlas Chrome extension and the backend exchange messages (the external browser backend, `atlas3-core/TODO.md` §8.0/§21); the extension is published separately and registers a native-messaging host (File 43). This transport is valid only when authenticated, local, session-bound, and peer-identity checked before dispatch.
- `Custom { transport_id }` — a registered transport for a protocol variant outside the canonical set, registered through the same source-approval path.

### 6.3 Network Posture and Authentication

A network MCP connection's authentication is a bearer token, OAuth credential, or equivalent credential resolved from the vault (§15); the credential is a `vault:<key>` reference, never inline. A `Stdio` connection inherits the user's process identity and needs no token. Network transports default to localhost; reaching a remote endpoint is an explicit opt-in plus the egress-destination governance (`security.egress-governance`, File 22 §11.4). `NativeMessaging` accepts messages only from the authenticated local peer whose identity is bound to the connector's integrity record (§9.4); an unauthenticated, non-local, unrecognized, or changed peer is rejected before session dispatch. A connector that uses the impersonation or proxy facilities of the outbound HTTP stack does so under the same egress governance; a connection-level proxy configuration never bypasses the destination policy.

### 6.4 Rule

- One transport-agnostic `McpSession` pairs requests to responses, routes notifications, and delivers progress for both roles; protocol-version negotiation lives in the session layer so upgrades never touch transports.
- The `McpTransportKind` set is the closed `Stdio`/`Http`/`Sse`/`StreamableHttp`/`WebSocket`/`NativeMessaging` plus `Custom`; each transport implements the small send/receive/close contract; the session normalizes native vocabularies before they leave the boundary.
- A network connection authenticates with a vault-held credential, defaults to localhost, and reaches a remote endpoint only through explicit opt-in and egress governance; `NativeMessaging` additionally requires authenticated-local peer identity validation.

### 6.5 Boundary

File 23 owns the `ManagedProcess` a `Stdio` transport spawns; File 22 owns the egress governance a network transport passes; File 43 owns the native-messaging-host registration; File 42 owns the transport implementation. This section owns the session contract and the transport catalogue.

## 7. Connection Health, Reconnect, and Transport Retry

Anchor: `integration.connection-recovery`

This section defines connector reconnect and transport retry for tool servers, reusing the File 17 typed shapes as the cross-cutting transport-retry contract (§2.2) and obeying the no-clock-poll discipline (`provider.provider-health`, File 17 §12.4; `automation.*`, File 33).

### 7.1 The `ConnectionState` Machine

Every connector connection carries a typed `connection_state`:

- `Disconnected` — no active connection; the next call connects on demand
- `Connecting` — the handshake and contribution query are in progress
- `Connected` — recent calls have succeeded; the connector's capabilities are `Available`
- `Degraded { since, contributing_failures }` — recent failures observed but the connection is still attempted with logging
- `Unavailable { reason, retry_after }` — calls are disqualified by default; the connector's capabilities are `Unavailable`; an explicit user-directed retry may attempt a connection
- `Failed { reason }` — a non-transient failure (authentication rejected, protocol-version incompatible, configuration invalid); surfaced for user repair, not retried as-is

Transitions are event-driven: a successful call returns the state to `Connected`; consecutive transient failures increment the contributing counter and cross configured thresholds into `Degraded` then `Unavailable`; a non-transient failure transitions to `Failed`; an explicit user reset returns to `Disconnected`.

### 7.2 Error Classification and Transport Retry

A connector transport failure is classified into a typed `IntegrationError` carrying an `ErrorClassification` of the shape File 17 §10.2 defines — `retryable`, `rate_limited`, `retry_after_ms`, `recovery_advice`, and `severity` — and the retry loop consults that classification, never raw transport strings. Transport-level retry against the same connector obeys: the `retryable` field is authoritative; a provider-suggested `retry_after_ms` is honored; absent one, the next delay is computed by a typed backoff strategy (exponential backoff with cap and jitter, fixed, or decorrelated jitter); the per-error-class retry cap is a setting; every retry wait is an individually killable execution unit with a finite ceiling; and a `Fatal` classification is never converted to `Transient`. A retried call uses an `idempotency_key` where the operation supports it so a retry does not duplicate an external effect, and a non-idempotent connector operation (`idempotent: false`) is not silently retried after a partial effect.

### 7.3 Circuit Breaking and the Descriptor Cache

A connector that fails repeatedly opens a circuit breaker — `Closed` → `Open { until }` → `HalfOpen` — so a persistently failing server is not retried on every call. Recovery is primarily triggered by source-recovery signals, connection-lifecycle events, or explicit user reset; a configurable minimum cooldown remains as a killable safety guardrail against flapping and is never a correctness condition. The breaker's thresholds and cooldown are settings, not constants. The device-local descriptor cache (§3.3) holds the connector's last-known tools, resources, resource templates, and prompts with their provenance and version under the connector's cache policy (§3.5). TTL expiry marks cached descriptors stale and may require explicit refresh or refresh-on-next-use, but never schedules background polling. A disconnected connector's cached descriptors keep its capabilities inspectable (rendered `Unavailable`) but not invocable; the cache is a projection rebuilt on reconnect, never a source of truth for whether the server is reachable.

### 7.4 Server-Initiated Sampling

An MCP server may request that Atlas perform a model completion on its behalf (sampling). A sampling request is a policy-gated, non-recursive model step: it resolves a model through the File 17 adapter under the active provider allowlist, data-sensitivity, and model settings; it records a `ModelSelectionRecord`, usage/accounting, connector identity, and outbound result egress; it honors the connector's trust class (a `Community`/`Unverified` connector's sampling requires explicit user permission); it does not emit a nested `ToolCallProposed`, cannot call tools, and cannot recursively request approval; and its prompt content is untrusted content that holds no authority. The connector supplies workload requirements, never a provider/model identity. Sampling output returned to the connector is outbound data to that connector and passes egress/sensitivity policy. Sampling is opt-in per connector and off by default.

Other server-initiated MCP requests are explicit policy-governed request classes with no authority by default. Exposing workspace roots, filesystem roots, conversation resources, or user elicitation to an MCP server requires source approval and per-request policy where appropriate. Roots are scoped references, not raw filesystem authority, and must match touched-resource and egress rules. Server-initiated elicitation becomes a File 04 user intervention or File 06 approval/clarification flow, not a direct prompt outside Atlas rails. Any result returned to the connector is outbound egress to that connector.

### 7.5 No Scheduled Health Pings

The runtime does not poll connectors for health on a schedule. Connection health is observed from call outcomes and from server-pushed notifications; an explicit connectivity probe exists only as a user-triggered diagnostic, never as a scheduled ping (`provider.provider-health`, File 17 §12.4). The reconnect attempt is driven by the next call or an explicit user action, not by a clock.

### 7.6 Rule

- Every connection carries the typed `connection_state` machine, transitioning event-first on call outcomes; transport failures are classified into a typed `ErrorClassification` and retried with backoff, idempotency, a finite killable ceiling, and a circuit breaker; a `Fatal` classification is never retried as transient.
- The descriptor cache is a device-local projection under the connector's cache policy, keeping disconnected capabilities inspectable but not invocable, rebuilt on reconnect; server-initiated sampling is a policy-gated, non-recursive, trust-gated, off-by-default model step.
- No connector is health-pinged on a schedule; reconnection is driven by the next call or explicit user action.

### 7.7 Boundary

File 17 owns the typed shapes this section reuses; File 04 owns the cooperative-cancellation and killability the retry waits obey; File 06 owns the policy a sampling step passes; File 42 owns the reaper and the connection-pool implementation. This section owns the connector connection recovery machinery.

## 8. MCP Resources and Prompts

Anchor: `integration.mcp-resources-prompts`

### 8.1 Resources

An MCP server's resources are addressable read-only content (each carrying a server-scoped URI) that registers as an external retrieval source (File 12). A resource is browseable and bridgeable into an external-content block whose external reference is the resource URI; reading the content triggers an explicit `resources/read` capability call at `ReadOnly` tier on demand, never as a hidden side effect of local retrieval (File 12). Resource templates are parameterized retrieval-source templates with input schemas, source attribution, sensitivity metadata, and untrusted-content handling; instantiating one is an explicit read capability call. Resource content is untrusted content (`security.untrusted-content`, File 22 §12) rendered with source attribution, length limits, and instruction-boundary markers at the assembly boundary; it carries no authority by appearing in context. Resource read results normalize into the one retrieval-result contract so context assembly, the UI, and evaluation consume no private resource format (File 12).

### 8.2 Prompts

An MCP server's prompts are reusable source-authored templates that register as inspectable prompt descriptors (File 13). Discovery or inspection does not put the prompt into model context. Rendering or importing a prompt requires explicit user or model action through a policy-governed capability; the rendered text enters model-request assembly through File 13's instruction-authority and instruction-boundary rules and never becomes a governing instruction merely because it came from a connector (`plugin.contribution-points`, File 35 §5.2). Imported prompt fragments record connector id, prompt version, trust class, and import decision. A prompt fragment from a `Community`/`Unverified` connector carries the trust-driven authority limits its source warrants.

### 8.3 Rule

- MCP resources register as external retrieval sources, resource templates register as parameterized retrieval-source templates, both are read on demand through explicit `ReadOnly` calls, normalize into the one retrieval contract, and are untrusted content with no authority.
- MCP prompts register as inspectable source-authored prompt templates; rendering/import is explicit and policy-governed through File 13's authority and boundary rules; a connector prompt never becomes a hidden governing instruction.

### 8.4 Boundary

File 12 owns the retrieval-result normalization and indexing; File 13 owns the instruction-fragment authority and assembly; File 22 owns the untrusted-content rule. This section owns the bridge from MCP resources and prompts into those contracts.

## 9. Trust, Source Approval, and Integrity for Connectors

Anchor: `integration.trust-approval`

### 9.1 The Bundle-Granularity Review

When a connector is configured and first connected (or updated to a new version with an expanded effect envelope), the proposal-first source-approval flow (`policy.source-approval-flow`, File 06 §9) runs at the connector granularity: the policy layer constructs a `SourceRegistrationProposal` of kind `McpServer`, `Api`, `WebhookReceiver`, or the connector's source kind, populated from the connector contract — the source identity (id, version, transport endpoint or command, declared author, declared trust hint), the declared operations with their tiers/floors/touched-resources/replay-classes, the computed effect envelope and risk summary, the registered-entry trust state, the backend-kind summary, the network targets and credential requirements, and whether the connector registers hooks, resources, prompts, trigger sources, or node kinds. The user accepts declared defaults, customizes per operation or per connector, denies outright, defers connector-level policy, or cancels — the same user options `policy.source-approval-flow` (File 06 §9.4) fixes. Closing or dismissing the flow is `CancelRegistration`; the runtime never registers an invocable connector whose review the user did not complete (`policy.source-approval-flow`, File 06 §9.7).

The connector envelope diff is computed once and reused by source approval, refresh reconciliation, and `mcp.refresh`. Shared expansion dimensions follow File 35's vocabulary: new executable artifacts, backend-kind change, broader scope, broader touched resources, new hooks, new egress, new credentials, higher floors, and integrity-provenance change. Connector-specific expansion dimensions are a new remote tool or operation, a broadened annotation that raises a tier or floor, a new network target or destination, or a new node-kind, resource, resource-template, prompt, trigger-source, or sampling contribution. Non-expanding descriptor changes may version and reconcile under the current approval; expanding contributions remain unavailable pending source review.

### 9.2 Trust Establishment and the Six Classes

A connector's trust class is the closed six-class set `security.trust-model` (File 22 §9.2) fixes: `System`, `Verified`, `User`, `Community`, `Unverified`, `Sideloaded`. The connector's `declared_trust_hint` is one input the user weighs, never the determinant; File 22 establishes `effective_trust` from provenance plus the install-time review, evidence-based verification where authorship evidence exists, and signature verification as the declared path to `Verified`. Bundled-with-the-application connectors inherit the application's installation trust; a user-declared standalone server is `Sideloaded` or, where added from a configured registry, `Community`; a connector bundled with a plugin inherits its consideration through the plugin's review (File 35) while keeping the `McpServer`/`Api` runtime source. Trust is installation-local: an imported or synced connector definition's trust is provenance and evidence only and does not activate the connector or raise its effective trust without local approval (`security.trust-model`, File 22 §9.7).

### 9.3 Trust-Driven Tier Narrowing

File 06 narrows a connector operation's effective tier against its `effective_trust` per call (`policy.trust-mapping-defaults`, File 06 §9.6): a `Community`-trust connector's operations at `WorkspaceWrite` or below register with effective tier `UserApproval`; an `Unverified`/`Sideloaded`-trust connector's operations additionally require per-call ask-user on first use until the user upgrades the source's trust. This is the canonical realization of the `unit12` D12.9 one-tier / two-tier / first-use downgrades — they are policy-side narrowing over the six-class set, not a parallel three-class ladder and not a mutation of the declared tier (`capability.trust-source-approval-flow`, File 05 §9.2).

### 9.4 Integrity

Where a connector's definition or content can be integrity-bound — a bundled connector reference, a signed remote server identity, an external-API definition file, or a native-messaging peer identity supplied by the packaging/runtime layer — the approval binds to a `SourceIntegrityRecord` (`security.trust-model`, File 22 §9.6) computed over a declared `CanonicalEncoding` (`core.canonical-hash`, File 01 §7.14), never physical bytes; a later content mismatch or unrecognized peer identity is a tamper signal that re-gates and downgrades the connector until re-reviewed. A connector update creates a new version and a new integrity record and re-reviews on envelope expansion; revoking a connector's trust disables or quarantines its contributions and preserves its produced records. This file defines no new canonical hash; it inherits File 22's `SourceIntegrityRecord` hash.

### 9.5 Rule

- A connector becomes invocable only after the connector-granularity source-approval flow completes; closing the flow is `CancelRegistration`, never silent registration.
- A connector's trust class is the six-class File 22 set; the `unit12` one-tier/two-tier/first-use downgrades are File 06 trust-driven narrowing over that set; imported trust is inert until local approval.
- An integrity-bindable connector's approval binds to a content-integrity record over a canonical encoding; a mismatch re-gates and downgrades; an envelope-expanding update re-reviews; this file introduces no new hash.

### 9.6 Boundary

File 06 owns the source-approval flow and the tier narrowing; File 22 owns the trust classes, establishment, verification, and integrity; File 35 owns a bundled connector's plugin-level review. This section owns how a connector presents to those flows at the connector granularity.

## 10. Atlas as an MCP Server

Anchor: `integration.mcp-server-role`

### 10.1 Definition

In the server role, Atlas exposes a reviewed subset of its own capabilities, resources, and prompts to external MCP clients (an IDE extension, a desktop assistant, another tool) over the same `McpSession` and transport layer (§6). Exposing Atlas as an MCP server is the structurally safe integration path (`atlas3-core/Context.md`): an external client drives Atlas's own reviewed operations rather than scraping or automating a surface. The server role is off by default (the `mcp.server.enabled` setting defaults to `false`).

### 10.2 What Is Exposed

- **Tools** — the externally-exposed Capability subset: a capability is reachable by an external client only if it is tagged `external-exposed` and the source-approval policy permits external exposure (`surface.presentation-in-user-facing-surfaces`, File 07 §12.6); a capability not so tagged is unreachable through the server role regardless of its visibility in other lenses. The exposed set is further constrained by a per-external-client operation-prefix allowlist. User-only lifecycle capabilities are structurally excluded and can never be tagged `external-exposed`.
- **Resources** — read access to selected durable content (conversations, blocks, files, instruction fragments) addressed by a stable URI scheme, gated at `ReadOnly` tier and scoped by a per-external-client allowlist of which conversations are exposed; an external client cannot read across content it has not been granted.
- **Prompts** — a curated set of instruction templates the user has marked exportable, rendered on demand.

### 10.3 Authentication, Posture, and the External-Client Invoker

The server listens on the transport the user selects: `Stdio` for clients that launch Atlas as a subprocess (inheriting process identity, needing no token); `Http`/`Sse`/`WebSocket` for networked clients, bound to localhost by default with remote binding requiring an explicit opt-in and a vault-held external-client credential. Credentials are scoped to exposure profiles; a single-token profile is only the simplest configuration. The operation-prefix allowlist, conversation/resource allowlist, and exposure posture bind to the client credential, not to a server-global grant. Each invocation records client identity, credential id, transport, exposure scope, and conversation/resource scope; revoking one client credential removes exactly that scope without touching others. An external client's invocation is an `Invoker` recorded with its source identity and transport (the External-Protocol rail framing, `controlrail.external-protocol-rail`, File 26 §12); it passes the **same** policy, the same effective-tier resolution, the same approval router, the same `ToolCallProposed` emission, and the same ledger record as an agent or user invocation. The external-client `Invoker` is never "the user" and never satisfies a user-initiation requirement; a user-only capability reached through the server role resolves to denial, not an approval prompt. An external tool call that would mutate state resolves to the same approval the agent's call would face; the security boundary is the tier system, and the server role bypasses none of it (`infrastructure/mcp.md`). An external invocation associated with an active conversation records into that conversation's version tree; an external invocation that supplies arguments for a consequential action resolves to preview, elicitation, or approval before mutation unless a valid lease covers the exact action.

### 10.4 Rule

- The server role exposes only the `external-exposed`-tagged, source-approval-permitted Capability subset (further constrained by per-client operation-prefix allowlists), selected resources under per-client conversation/resource allowlists at `ReadOnly`, and curated exportable prompts; it is off by default.
- A `Stdio` server inherits process identity; a network server binds localhost by default and requires explicit opt-in plus a vault-held external-client credential for remote binding.
- An external client is an `Invoker` that passes the identical policy, approval, and ledger path as any other invoker, but it is never the user and cannot invoke user-only capabilities through approval prompts; the server role bypasses no tier, floor, or approval.

### 10.5 Boundary

File 07 owns the external-exposure lens and the externally-exposed Capability subset; File 06 owns the policy an external call passes; File 26 owns the External-Protocol rail framing; File 22 owns the listener's authentication credential and the localhost-vs-remote egress posture; File 37 and File 38 own the server-management surface. This section owns the server-role exposure and the external-client transport.

## 11. The External-HTTP-API Connector

Anchor: `integration.external-api`

### 11.1 Definition

An `ExternalApi` connector is a user-authored declarative HTTP integration for a service that does not speak MCP. It is the lightweight escape hatch — “I have a REST endpoint, I want the agent to call it, I do not want to write an adapter” — and the reconciliation rule is preserved: use an `ExternalApi` connector for a single endpoint or a small handful with no associated logic, use a plugin (File 35) to bundle endpoints with skills and a persona, and use an `McpServer` connector for a service that already speaks MCP (`unit12` D12.15). The definition is authored in a device-local declarative form (the storage realization is `~/.atlas/apis/<name>.toml`).

### 11.2 The Definition and Identity

An external-API definition declares the integration name, the base URL, display metadata, the auth configuration, and a set of endpoints. Each endpoint registers as a `CapabilityDeclaration` under the `api.<service_name>.<endpoint_id>` identity (`capability.id`, File 05 §13.1) with the `HttpEndpoint { url_template, method, auth_ref }` backend (`capability.backend-binding-lifecycle`, File 05 §10.4) and the `Api { api_name, api_definition_path }` source (`capability.capability-source`, File 05 §9.1). `endpoint_id` is local to the API connector namespace and should not include the service name; renames use File 05 aliases or become remove/add transitions, never silent identity mutation. Each endpoint declares its method, path (with path and query parameters), a request input schema validated against the agent's call before the request is sent, a declared permission tier mapped onto the canonical tier set, and a response-capture specification. A capability that uses the `HttpEndpoint` backend directly (not through an external-API definition) is governed identically.

### 11.3 Authentication

The auth model is the closed set `none`, `bearer`, `basic`, `header`, `query_param`, and `oauth2`. Secret-bearing material is a vault reference (`token_vault_key` / `vault:<key>`), never inline; a literal secret in a definition is refused at load with a typed diagnostic. For `oauth2` the connector handles the client-credentials flow for machine-to-machine access and the user-delegated flow where the user completes the authorization once and the refresh token is stored in the vault, with the short-lived access token refreshed on demand inside the backend (§15). A user-delegated authorization is a File 04/06 user-intervention flow carrying a `state` nonce bound to the initiating connector and pending request; the redirect/callback URI is validated against the connector's declared audience; the returned token binds to that connector id; a callback whose state, connector, or audience does not match the pending request is rejected. The same rule governs `mcp.oauth.completed` (§16.3). Credentials never appear in a ledger entry, an event, an export, a log, or agent context.

### 11.4 Response Capture, Body Formats, and Pagination

A response-capture specification selects which fields of a response become the tool result, keeping results compact and avoiding dumping large bodies into context. Raw response snapshots are retained only when the endpoint or user enables explicit raw capture; they pass secret redaction, sensitivity stamping, size limits, retention policy, and audit rules. The supported response body formats are the closed set `json` (with a JSONPath-dialect capture), `csv` (first row as headers, rows as a table), `ndjson` (per-line capture), `xml` (an XPath-dialect capture), `text` (the full body as the result), and `sse` (a server-sent-events stream with an event-type filter, a maximum-event cap, and a timeout, returning the accumulated typed events as the result; a long-running stream may accumulate into a streaming block in the chat on an explicit opt-in). Pagination is declared per GET endpoint with the closed set `offset`, `cursor`, and `link_header`; a paginated call may transparently loop pages up to a caller-specified maximum and concatenate the items into one result.

### 11.5 Load Pipeline, Hot Reload, and Rate Limiting

External-API definitions load after the secret vault is available: each definition is parsed (a parse error is diagnosed per file and the rest continue), its credential references are resolved against the vault (a missing key marks the integration unauthenticated and registers its credentialed endpoints disabled until the key is added), its endpoints generate capability declarations, and the declarations register, emitting the load event (§16). A hot-reload capability stages, validates, diffs, and commits a new connector version atomically; if validation fails, the last valid registered version remains active and diagnostics surface. On success the diff applies atomically: new versions, unavailable removals, and source-review parking for envelope expansion. A connector's outbound calls are governed by connector-scoped rate limiting that reuses the structural `RateLimitWindow` and admission-control mechanism (`provider.rate-limit-state-header-reconciliation`, File 17 §13) keyed by connector and endpoint identity — not File 17's provider scopes; a connector declares its rate-limit windows in its contract (§3.5). Base URLs must use HTTPS unless the host is localhost or the user opts into plaintext HTTP; Atlas loads only local definition files and does not fetch API definitions from remote URLs (which an attacker could swap).

### 11.6 Rule

- An `ExternalApi` connector is a declarative HTTP integration whose endpoints register as `api.<service_name>.<endpoint_id>` capabilities with local endpoint ids, the `HttpEndpoint` backend, and `Api` source through the one registry; the apis-vs-plugin-vs-MCP reconciliation rule selects the connector kind.
- Auth is the closed `none`/`bearer`/`basic`/`header`/`query_param`/`oauth2` set with vault-only secrets, connector-bound OAuth state/callback validation, and OAuth refresh tokens in the vault; response body formats are the closed `json`/`csv`/`ndjson`/`xml`/`text`/`sse` set; pagination is the closed `offset`/`cursor`/`link_header` set.
- Definitions load after the vault, register through the one pipeline, hot-reload atomically, are connector-scope rate-limited over the shared window mechanism, default to HTTPS, and are never fetched from remote URLs; raw response capture is explicit, redacted, bounded, and sensitivity-stamped.

### 11.7 Boundary

File 05 owns the `HttpEndpoint` backend and the `Api` source; File 22 owns the vault and the egress governance an outbound call passes; File 17 owns the structural rate-limit mechanism this reuses; File 12 owns the result normalization where a response becomes retrieval content. This section owns the external-API connector definition, the load pipeline, and the response/auth/pagination contract.

## 12. Discovery and Suggestion

Anchor: `integration.discovery`

### 12.1 The Discovery Surface

Beyond connectors the user has already configured, the agent and the user reach a discovery surface over a replaceable discovery registry: given a query and a kind filter, it returns candidate MCP servers and connectors with a normalized candidate/effect summary (identity, description, author, trust hint, tool count, install reference, the declared effect envelope, required approvals and credentials, and the connector contract summary). Discovery metadata carries source attribution, registry identity, freshness, and signature/integrity evidence when present, but remains untrusted candidate evidence until source approval verifies the actual connector contract. Trust hints and effect summaries never grant effective trust or approval. The same summary feeds discovery, the connection review, and the connection inspector. There is no Atlas-hosted marketplace requirement; the discovery registry may be community-maintained, organization-hosted, or local, and a deployment with no registry configured still configures connectors from local definitions. The discovery surface is a typed, replaceable implementation behind a contract; concrete registry endpoints and marketplace mechanics are File 43's.

### 12.2 The Discovery Capabilities

The discovery operations are built-in `ReadOnly`, agent-invocable capabilities that flow through the standard pipeline and never connect: `mcp.search` (the MCP-server discovery capability `surface.late-loading-runtime-discovery`, File 07 §7.1 already names, discharged here against an MCP registry), `connector.search` (discovery across MCP and connector candidates by query and kind), and `connector.suggest` (recommending a connector after a failed tool call, taking the failed pattern and error context and returning candidate connectors that would satisfy it). Query payloads sent to a remote discovery registry are outbound egress: failed patterns and error context pass egress policy and are scrubbed of secrets, sensitive arguments, and sensitive paths before leaving, or are matched locally against a cached registry index. A discovery result carries the candidate's trust hint and effect envelope so the user can judge before connecting. The deferred-loading discovery of an already-connected connector's tools (materializing a compact-registered tool's full schema) is the surface-borrow path (`surface.late-loading-runtime-discovery`, File 07 §7).

### 12.3 Agent Suggests, User Connects

The agent reaches the discovery surface and may suggest an MCP server or connector that fits the work; every connection passes the same user-gated source-approval flow as a manual connection (§9), and the agent cannot auto-connect, auto-configure, or auto-enable (`capability.runtime-mutation`, File 05 §16.2; `unit12` D12.7). A connector suggestion is data the user acts on, never an action.

### 12.4 Rule

- Discovery is a typed, replaceable surface returning one normalized candidate/effect summary that feeds discovery, review, and inspection; registry metadata is untrusted candidate evidence; it never connects, and a deployment with no registry still configures local connectors.
- `mcp.search`, `connector.search`, and `connector.suggest` are `ReadOnly`, agent-invocable, never-connecting capabilities; remote discovery queries are egress-governed and scrubbed; `mcp.search` implements the provisional discovery id File 07 names.
- The agent suggests; the user connects through the source-approval flow; the agent never auto-connects.

### 12.5 Boundary

File 07 owns the surface-side deferred-loading and the borrow path; File 06 owns the source-approval flow a connection passes; File 43, File 37, and File 38 own the registry endpoints and the discovery browser. This section owns the discovery contract and the suggest-never-connect rule.

## 13. Inbound Webhooks and External-Event Transport

Anchor: `integration.webhooks`

### 13.1 Definition

The inbound webhook/external-event transport is the receiver side of external integration: an external service calling into Atlas over HTTP. A receiver is a `WebhookReceiver` connector: it has connector identity, source approval, lifecycle state, integrity/trust posture, credential references, removal tombstone, and portability rules, but contributes no callable operations. This file owns the **transport** — the listener, the endpoint binding, the authentication, the freshness and idempotency, and the delivery of an authenticated payload to a trigger — that `automation.event-and-webhook-triggers` (File 33 §5.2) delegates here. File 33 owns the `Webhook` trigger's existence, its routing to a `RunIntent`, and its `fire_id` semantics.

### 13.2 The Receiver

A webhook receiver is a `WebhookReceiver` connector with a device-local declarative binding (the storage realization is `~/.atlas/webhooks/<n>.toml`) carrying the receiver path, the authentication kind, the verifying secret reference, and the signature header where applicable. The receiver runs as a route on the same Atlas HTTP server that hosts the MCP server role and the application's IPC, registered after the IPC layer is available. The authentication kind is the closed set `none`, `hmac_signature`, `bearer`, and `basic`; the verifying secret is a `vault:<key>` reference, never inline and treated as an inbound verifying secret, not an outbound credential. An `hmac_signature` receiver verifies the request signature against the vault-held secret before the binding fires. A receiver binds to localhost by default. `none` is valid only for localhost-bound local/development posture; remote binding requires an explicit opt-in, authentication, and freshness validation.

### 13.3 Authentication, Freshness, and Idempotency

A receiver verifies the inbound request before it fires: the signature, bearer token, or basic credentials authenticate the request; an unauthenticated or signature-failed delivery is recorded and dropped, never fired. The receiver derives a `source_event_id` and a freshness or idempotency signal from the delivery (a provider event id, a signed timestamp plus nonce, a delivery id, or a deterministic content key); duplicate deliveries map to the same identity and are recorded as duplicates, not re-fired, and remote bindings require freshness validation appropriate to their authentication scheme. The inbound payload is untrusted content that carries no authority (`security.untrusted-content`, File 22 §12): it may parameterize the triggered run but can never escalate a capability's scope or auto-approve a gated capability.

### 13.4 Handoff to the Trigger

An authenticated, fresh, de-duplicated delivery becomes the routing-frame trigger context for File 33's `Webhook` trigger with the routing `trigger_kind` `external_event`; File 33 resolves it to a `RunIntent` and the run uses the same run model, policy, and ledger as any other invocation (`automation.event-and-webhook-triggers`, File 33 §5.2). The webhook transport owns getting an authenticated payload to the trigger; the trigger owns what happens next. The endpoint binding and its verifying secret are device-local (§17).

### 13.5 Rule

- The inbound webhook transport is a `WebhookReceiver` connector with a device-local receiver binding on the shared Atlas HTTP server, an empty capability-operation set, one trigger-source contribution, an inbound-only effect envelope, the closed `none`/`hmac_signature`/`bearer`/`basic` authentication set, a vault-held verifying secret, and a localhost-default-remote-opt-in posture.
- `none` authentication is local-only; remote receiver bindings require authentication and freshness validation.
- A receiver authenticates, validates freshness/idempotency (mapping duplicates to one identity, never re-firing), and treats the payload as untrusted content with no authority.
- An authenticated, fresh, de-duplicated delivery hands off to File 33's `Webhook` trigger as `external_event` trigger context; this file owns the transport, File 33 owns the trigger.

### 13.6 Boundary

File 33 owns the `Webhook` trigger, the `fire_id` no-duplicate-fire semantics, and the routing; File 22 owns the signature verification's cryptography and the untrusted-content rule; File 10 owns the bus the receiver's events flow through; File 42 owns the HTTP listener's process. This section owns the `WebhookReceiver` connector and inbound external-event transport.

## 15. Credentials, Egress, and Security Posture

Anchor: `integration.security-posture`

### 15.1 Credentials Are Vault References

Every credential a connector uses — an MCP server's bearer token or OAuth credential, an external-API auth secret, a webhook verifying secret, the Atlas-as-server bearer token — is a `vault:<key>` reference resolved against the vault at the point of use inside the backend and discarded when the call no longer needs it (`security.secret-vault`, File 22 §5; `secret.backend-boundary`, File 22 §4). A credential never appears inline in a connector definition, a ledger entry, an event, an export, a sync stream, a log, or agent context; a literal secret in a declarative definition is detected and refused (`security.secret-detection-redaction`, File 22 §7). A connector may hold multiple named accounts where the service supports them, each credential under its own vault key; OAuth refresh tokens live in the vault and the short-lived access token is refreshed on demand. Credential rotation re-resolves on the next call and never triggers an active health probe (`provider.credentials-accounts-pools`, File 17 §14.4).

### 15.2 Egress Governance and Untrusted Content

Every outbound connector call passes the egress-destination governance (`security.egress-governance`, File 22 §11.4): the destination is matched against the user's allowlist and denylist, and every redirect hop revalidates host, scheme, port, method/body semantics, credential forwarding, and data sensitivity so an allowed destination cannot redirect to a forbidden one. Credentials forward only when the destination remains within the credential's declared audience/scope; widening destination or credential scope fails with a typed egress error. An irreversible connector write and a credential egress carry a `permission_floor: Denied` and the typed-confirmation override (`policy.permission-floor-typed-confirmation`, File 06 §7; `codex_recommendations.md` §17.3); no lease, posture preset, or trust override lifts the floor. Every inbound connector content — a tool result, an API response, a resource, a prompt, a webhook payload, a sampling prompt — is untrusted content that holds no authority and is scrubbed of secret material before it re-enters context (`security.untrusted-content`, File 22 §12; `provider.sensitivity-redaction-secret-boundary`, File 17 §23 for the scrubbing pattern).

Connector credential and account dependencies are tracked by vault key or account id. On `SecretRevoked`, account disconnect, OAuth revocation, or narrowed external-client credential scope, affected connector contributions become unavailable with typed `CredentialRequired` or scope diagnostics; affected automations, workflows, shortcuts, leases, exposed-server entries, and prompt/resource bindings surface the dependency that broke them. Produced records remain intact.

### 15.3 Process Isolation and the Environment Denylist

A spawned `Stdio` MCP server process and any subprocess a connector launches run confined as a `ManagedProcess` (File 23 §5) at the isolation tier the connector's trust and declared effects require. The spawn passes a minimal environment allowlist and a denylist of the security-critical variables that control paths, linkers, or interpreters (the canonical realization of the 31-variable denylist source pattern), so a connector cannot hijack the process through the environment (`core.extension-planes`, File 01 §6.14; File 23 §5). A connector's shell, script, or endpoint binding must not compose command strings containing inline secret values; credentials are supplied only through vault-resolved environment policy, stdin, or restricted temporary files cleaned up after use, and pre-dispatch validation rejects detected inline secrets before launch.

Connector-owned active units are File 04/File 23 cancellation and kill targets: active MCP tool calls, resource reads, sampling requests, external API calls, pagination loops, SSE streams, OAuth handshakes, webhook receiver dispatches, retry waits, and spawned server processes. Connector-level disable or quarantine may categorically cancel or kill connector-owned units according to policy. A remote operation that cannot be force-killed locally is locally abandoned with a typed orphan or unknown-remote-effect outcome.

### 15.4 Rule

- Every connector credential is a vault reference resolved at the point of use and never inline, persisted, exported, synced, or shown to the agent; OAuth refresh tokens live in the vault; rotation re-resolves on the next call without a probe.
- Every outbound connector call passes egress-destination governance with per-hop redirect, method/body, credential-forwarding, and sensitivity revalidation; irreversible connector writes and credential egress carry a `Denied` floor with typed-confirmation; every inbound connector content is untrusted and scrubbed.
- Credential/account revocation disables affected connector contributions and surfaces dependent automations, workflows, shortcuts, leases, exposed-server entries, and resource/prompt bindings with typed diagnostics; produced records remain intact.
- A spawned connector process runs confined with a security-critical-environment denylist; no connector composes inline secrets into a command, and pre-dispatch validation rejects detected inline secrets; connector-owned active units are individually and categorically cancellable/killable through File 04/File 23.

### 15.5 Boundary

File 22 owns the vault, the egress semantics, the untrusted-content rule, and the secret detector; File 23 owns the sandbox, the tiers, and the environment enforcement; File 17 owns the credential-rotation event shape and the scrubbing pattern this reuses. This section owns the connector's application of them.

### 16.2 Rule

- The integration capabilities are built-in declarations under the one registry, carrying the touched-resource and tier metadata their effects warrant; add, connect, enable/disable, remove, and server-role configuration are tier-gated and user-only; refresh is a connector-registry mutation; list, inspect, read-resource, list-resource-template, load-toolset, search, and suggest are `ReadOnly`, and the search/suggest set is agent-invocable but never connects.
- An agent invokes these capabilities like any other, subject to policy and the no-self-connect rule (§5.5, §12.3); there is no privileged connector-connection side door. User-only lifecycle capabilities are excluded from external MCP exposure and cannot be reached by converting an external client into an approval requester.

### 16.3 Events

The canonical namespaces include the MCP facts (`mcp.client.server_started`, `mcp.client.tool_registered`, `mcp.client.server_crashed`, `mcp.status.updated`, `mcp.oauth.completed`, `mcp.server.client_connected`, `mcp.server.tool_invoked`), the external-API facts (`external_api.loaded`, `external_api.call_failed`), the webhook facts (`webhook.received`, `webhook.triggered_agent`, `webhook.signature_failed`), and the connector facts (connection-state transitions, trust changes, refresh results). A connector's *contribution* events remain the owning registries' events (`CapabilityRegistered` and the rest), carrying the runtime source and bundle ownership; this section declares the connector-lifecycle events, not duplicates. Security-relevant connector operations (connection approval, trust change, credential resolution, egress block, signature failure) record into the device-local hash-chained audit overlay (`ledger.hash-chained-audit-log`, File 10 §16.4) and default to `Sensitive`; events that touch credentials never carry raw secret material.

## 17. Persistence, Locality, and Portability

Anchor: `integration.persistence`

### 17.1 What Is Durable, Device-Local, and Portable

- **Durable and device-local:** a connector's declarative definition — its identity, kind, transport configuration, and credential references, including `WebhookReceiver` bindings — is device-local declarative config that does **not** sync (`infrastructure/sync.md`; `infrastructure/external-apis.md`: external-API tool definitions “do not sync”); a connector is configured per device, and configuring it on another device is a fresh local configure-and-approve. The connector's credentials are vault entries (device-local, `security.secret-vault`, File 22 §5).
- **Computed / device-local runtime state:** the connection state, the pooled connections, the descriptor cache, the contribution-attribution index, and the circuit-breaker state are device-local runtime projections reconstructed on connect from the durable definition; their loss is a rebuild, never a loss of a definition or history (`core.projection`, File 01 §6.11). This is the same durable-definition-versus-device-local-runtime split `automation.persistence` (File 33 §18), `workflow.persistence` (File 34 §18), and `plugin.persistence` (File 35 §15) fix.
- **Durable through their owners:** the records a connector's operations produce (knowledge entries, committed artifacts, ledgered invocations) are durable substrate owned by their files and follow each owner's locality.
- **Portable:** a connector's declarative definition may be carried in a `PortablePackage` (`portability.export-bundle`, File 21 §10) with no raw secret (credentials are vault references); importing re-validates the definition, re-resolves references, passes source approval and trust establishment locally (imported trust inert, `security.trust-model`, File 22 §9.7), and produces a configured-but-disconnected connector with typed `UnresolvedReference` diagnostics when a reference cannot resolve, never a silent substitution. A synced or imported record that references a missing connector resolves to an unavailable/inert state and importing never connects or executes connector code (`portability.export-bundle`, File 21 §10).

### 17.2 Replay

A connector operation replays from its recorded `CapabilityInvocation` and ledger entries (`capability.invocation-record`, File 05 §11), not from the live server: the recorded invocation carries the resolved capability id and version, the resolved descriptor snapshot and `server_version`, and the typed result, so replay re-derives nothing from the live connection. A value obtained from a live external endpoint (a `tools/list` result, an OAuth token, a remote response) is recorded with full keying so historical reconstruction never re-queries the endpoint, the tool-server analog of `provider.token-source` (File 17). The live connection state is an explicitly-typed non-replayed gap (device-local), matching the rate-limit-state and arming-state gaps Files 17 and 33 fix.

### 17.3 Rule

- A connector's definition, including `WebhookReceiver` bindings, is device-local declarative config that does not sync; the connection state, descriptor cache, attribution index, and breaker state are device-local projections rebuilt on connect; produced records follow their owners' locality; the importable definition is portable, re-approved on import, imported-trust-inert.
- No raw secret is part of a connector definition, export, or sync; credentials are vault references; a connector operation replays from recorded invocations and descriptor snapshots, never the live endpoint; the live connection state is an explicitly-typed non-replayed gap.

### 17.4 Boundary

Files 20 and 21 own storage, locality, sync, and the portable bundle; File 22 owns the vault and the imported-trust rule; the owning files own each produced record's locality. This section owns the connector definition-device-local-versus-runtime-projection split and the replay contract.

## 18. Settings

Integration behavior is configurable through `settings.setting-definition` (File 15), with agent exposure governed by `policy.agent-exposure-policy-settings` (File 06 §16.4) and secrets held only as vault references (`settings.secret-boundary`, File 15 §10). At minimum, settings support:

Trust thresholds, retry caps, breaker thresholds, rate-limit windows, binding posture, and discovery configuration are settings; concrete values are never canonical.

## 19. Explicit Rejections

Anchor: `integration.explicit-rejections`

The following shapes are wrong for this layer:

- a parallel MCP/connector tool list, a private external-integration runtime or executor, a per-kind connector store, or any contribution path that bypasses the one canonical registries — every connector operation enters its owning registry through the same path a built-in uses, carrying runtime source and (for bundled references) bundle-ownership metadata (`capability.sourcing-equivalence`, File 05 §9.3; `codex_recommendations.md` §11.5);
- a connector as a subsystem, a work surface, a control rail, or a separate execution architecture — a connector is a transport-and-protocol binding whose operations are ordinary capabilities; a surface it might suggest registers through File 25, a rail through File 26;
- the agent connecting, configuring, enabling, or installing a connector, or any connection that completes without user review — connection is user-only and source-approval-gated; the agent suggests, never connects (`capability.runtime-mutation`, File 05 §16.2; `policy.source-approval-flow`, File 06 §9.7);
- an external client satisfying a user-only initiation requirement or driving connector/MCP-server lifecycle through the Atlas-as-MCP-server role — external clients are not the user, and user-only capabilities are not externally exposable;
- a connector's content (tool results, API responses, resource content, prompt text, webhook payloads, sampling prompts) treated as instruction or authority — it is untrusted content rendered inside explicit boundaries that can never widen a lease, lift a floor, lift typed-confirmation, lower sensitivity, raise trust, or authorize egress (`security.untrusted-content`, File 22 §12);
- a parallel trust ladder for MCP servers or connectors — trust is the six-class File 22 set; the one-tier/two-tier/first-use downgrades are File 06 trust-driven narrowing over that set (`policy.trust-mapping-defaults`, File 06 §9.6), not a `Verified`/`Community`/`Sideloaded`-only scheme;
- an inline secret in a connector definition, an MCP entry, a webhook binding, or a command line — credentials are `vault:<key>` references resolved at the point of use (`security.secret-vault`, File 22 §5; `secret.backend-boundary`, File 22 §4);
- an outbound connector call that bypasses the egress-destination policy, or an irreversible connector write or credential egress without the `Denied`-floor-plus-typed-confirmation gate (`security.egress-governance`, File 22 §11);
- a spawned MCP server process that can hijack paths, linkers, or interpreters through the environment, or a connector process outside the one `Sandbox` (`core.extension-planes`, File 01 §6.14; `sandbox.consequences-for-later-specs`, File 23 §21);
- the Atlas-as-MCP-server role bypassing the tier system — an external client is an `Invoker` that passes the identical policy, approval, and ledger path as any other (`infrastructure/mcp.md`; `controlrail.external-protocol-rail`, File 26 §12);
- a server-pushed notification, a sampling request, a remote schema change, or a tool annotation treated as authority — server-pushed facts are data; a changed schema is a version increment; annotations inform declared defaults but never grant a tier;
- a scheduled health ping or a clock-polled reconnect — connection health is observed from call outcomes and server-pushed notifications; reconnection is driven by the next call or explicit user action (`provider.provider-health`, File 17 §12.4);
- silent reconnect that breaks identity — reconnection preserves the `mcp.<connector_slug>.<tool>` ids so saved automations, workflows, and shortcuts survive (`surface.mcp-plugin-tool-integration`, File 07 §15.2);
- a webhook delivery fired without authentication, freshness, and idempotency, or a duplicate delivery re-fired — an unauthenticated or signature-failed delivery is dropped, and duplicates map to one identity (`automation.event-and-webhook-triggers`, File 33 §5.2);
- a remotely bound webhook receiver using `none` authentication, or a webhook receiver lifecycle outside the connector registry — receivers are `WebhookReceiver` connectors and remote bindings require authentication and freshness validation;
- a connector model-call path parallel to File 17 — server-initiated sampling resolves a model through File 17's adapter as a policy-gated, non-recursive, trust-gated step, never a private model-call path;
- a parallel rate limiter, retry loop, or error taxonomy for connectors — they reuse the File 17 typed shapes as the cross-cutting transport-retry contract, keyed by connector identity, never File 17's provider registry or scopes;
- a connector definition or its install/connection state synced as authority, or imported trust activating a connector without local approval (`security.trust-model`, File 22 §9.7);
- a connector operation that replays by re-querying the live endpoint rather than from its recorded invocation and descriptor snapshot (`capability.invocation-record`, File 05 §11);
- raw external responses logged by default, discovery query payloads sent remotely without egress governance, or remote descriptor metadata treated as trusted instructions;
- a connector defining a new canonical hash — integrity binds to File 22's `SourceIntegrityRecord` and File 21's bundle hash over a declared `CanonicalEncoding`, never physical bytes (`core.canonical-hash`, File 01 §7.14);
- splitting MCP, external APIs, and webhook receivers into separate lifecycle architectures — protocol variants share the connector lifecycle, trust, credential, source-approval, egress, replay, and attribution model;
- hardcoding trust thresholds, retry caps, breaker thresholds, rate-limit windows, binding posture, descriptor-cache freshness, `Stdio` caps, or discovery configuration outside settings (`settings.settings-over-constants`, File 15 §13).

## 20. Consequences for Later Specs

Anchor: `integration.consequences-for-later-specs`

- The **per-surface specs** (Files 27–32) that reach external services — the Coder surface's hosted-forge pull-request integration, the Data Processor's `data.api.call`/`data.graphql.query`, the Web surface's connectors, the System Agent's external integrations — consume this file's `Connector`, MCP, and external-API machinery; a hosted-forge connector is an `ExternalApi` or `Custom`-adapter connector contributing `api.*`/`mcp.*` capabilities, while the surface-specific workflow presentation (the pull-request board, the data-pipeline node) stays the surface's. None introduces a private external-integration path.
- The **UI Shell** and **UI Customization** specs render the MCP/connector manager, the discovery browser, the resource panel, the OAuth consent surface, and the connection inspector; they consume the data contracts (§3, §12, §16) and must not make the presentation the connection or trust truth.
- The **Quality Control and Validation** and **Evaluation and Benchmarking** specs verify the connector contracts — that a remote schema change is a version increment, that reconnection preserves identity, that an external call passes egress governance, that an inbound payload holds no authority, that a connector operation replays from recorded snapshots — replaying over recorded invocations and descriptor snapshots, never live connections.
- The **Telemetry, Logging, and Observability** spec consumes the connector lifecycle, connection-state, and call events and the attribution projection; it introduces no parallel connector-state store and honors the `Sensitive` default and audit-overlay routing of security-relevant connector operations (§16.3).
- The **Runtime Infrastructure and Lifecycle** spec orchestrates connector loading at startup (the registration and reconnection of configured connectors in the startup phase order, the webhook receiver registration after the IPC layer, the MCP server listener), the device-local rebuild of the descriptor cache and attribution index, the connection-pool and `Stdio`-process lifecycle and crash reaper, and the no-clock-poll reconnect; it places no parallel connector runtime and persists no connection state across sync.
- The **Packaging, Platform, and Distribution** spec owns the application installer, the auto-updater, the Chrome-extension publishing and native-messaging-host registration, the sidecar inventory (including any bundled standalone MCP servers), and the bundling of ship-with connectors into the image; this file owns the connector-definition lifecycle, the MCP and webhook protocol surfaces, and the connector discovery and distribution contract. The packaging layer distributes the application and seeds ship-with connectors into the image; File 36 configures, connects, refreshes, and removes connectors.
- The horizontal specs **File 33 (Automation)** and **File 34 (Workflows)** consume this file's transport and contribution paths: File 33's `Webhook` trigger consumes this file's authenticated, fresh, de-duplicated inbound transport; File 34's `TemplateLibrary` admits this file's connector-contributed `Custom` node kinds; neither introduces a parallel detection or execution path. **File 35 (Plugins)** bundles an `McpServerRef` that registers through this file's MCP path carrying plugin bundle ownership; a standalone server is an `McpServer`-source connector, not a plugin.

Specific integration contracts will be stated in those files when they are written.
