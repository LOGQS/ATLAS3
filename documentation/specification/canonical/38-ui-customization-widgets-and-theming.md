# UI Customization, Widgets, and Theming

## Status

Canonical. This file defines the customization layer of the presentation: the design-token system and themes, user-saved named compositions and the save/switch/customize flow, the `PresentationContribution` primitive and contribution placement, the localized copy-override records, the realization of the surface `customization_policy`, AI-assisted customization, plugin UI placement, and per-profile UI defaults. It consumes the contracts File 37 declares — the presentation-role model, the composition model, the `RendererRegistry`, `PresentationUnitKind` rendering, built-in `ViewPreset` rendering, the `InteractionModel` lens set, and the semantic-token *discipline* — and realizes the `customization_policy` `worksurface.views-presets` (File 25 §7.4) declares and the widget/theme/view-preset/panel contribution kinds `plugin.contribution-points` (File 35 §5.2) routes here. It is the second UI-layer spec: horizontal, surface-neutral, and medium-neutral, the way File 37 is. Its rules are patterns every frontend can realize; where a pattern has a windowed-desktop realization, that realization is carried in its section's windowed-desktop profile subsection and binds only a session declaring `desktop.windowed` (`ui.frontend-profile`, File 37 §1.3). The default rendering is complete without this file; this file adds customization over it. Later canonical files may refine it, but may not contradict it.

Resolved tensions:

- **A customization subsystem versus a layer over the container and settings.** The sources offer two postures: a dedicated customization store and runtime (the per-tool pane-tree tables, the per-domain layout JSON files), or a thin layer whose every customization is a settings/customization record persisted through the one settings substrate and rendered by File 37's composition model. `worksurface.no-private-architecture` (File 25 §12.2), `ui.renderer-boundary` (File 37 §16.4 — the presentation layer holds no private durable store), and `settings.consequences-for-later-specs` (File 15 §21 — no parallel store or cascade) are decisive. This file adopts the layer posture absolutely: a `SavedComposition`, a contribution placement, a per-contribution configuration, a theme selection, and a per-profile default are all settings/customization records (§3); the net-new primitives this file introduces — `Theme`, `PresentationContribution`, `SavedComposition`, and the `DesignTokenSystem` — are declarations and registries over File 37's composition model, not a parallel persistence path or runtime.
- **Theme as a CSS-file swap versus a typed token override set.** The specbase describes themes as CSS files mapping semantic variables to raw values; the unit synthesis and distribution specs refine this to a typed token set keyed in a perceptually-uniform color space with relative derivation and contrast validation. A canonical UI spec must define provider-invariant contracts rather than copying one renderer library's syntax. This file defines the `DesignTokenSystem` and `Theme` as the provider-invariant *contract* (§4, §5) — three token layers declared per medium, a perceptual-metric encoding for the families that admit one, the override-the-semantic-layer rule, the required-token and conformance-floor validation, and the adding-a-theme-is-one-declaration property — and leaves the concrete color library, file format, and utility-class registration to the renderer implementation, consistent with how File 37 keeps vendor names out of the body.
- **Persona, personality, and participation as a customization dimension.** Nearly every reviewed source still attaches a personality preset, participation level, or persona to a profile or surface. The canon deletes the field at every layer (`core.interaction-shapes`, File 01 §2.2; `core.explicit-rejections`, File 01 §8; `worksurface.no-autonomy-field`, File 25 §13; `controlrail.no-autonomy-field`, File 26 §17; `world.surface-state`, File 18 §5.5; `settings.explicit-rejections`, File 15 §20; `ui.interaction-models`, File 37 §7). This file adopts the deletion and fixes the per-profile consequence (§17): a profile default selects which theme, density, composition, and contributions are presented — the *consequences* the deleted fields once described — and any "personality" a profile carries is a Memory or instruction preset governed by File 14, a starting template the user edits, never a customization-layer mode, dial, autonomy control, or backend field.
- **Widget as a block renderer versus a placeable customization unit.** The sources use "widget" for two distinct things: a block renderer that displays a structured result inline in the transcript (a weather card, a chart) and a placeable ambient unit the user composes into a customizable region (a dashboard tile, a sidebar status panel). This file separates them (§8): the inline block renderer is File 37's `RendererRegistry` rendering a `Block` (`ui.substrate-rendering`, File 37 §9), already canonical; the `PresentationContribution` is the net-new customization primitive — a declared, source-qualified, configurable, data-bound unit a user, plugin, or agent composes into a slot, of which a widget is the windowed-desktop realization (§8.7). A contribution may *render* a block, artifact, or observation projection, but it adds placement, configuration, data/action binding, and lifecycle as a customization unit.
- **AI customization as a special path versus the one capability path.** The charter and the strategic review both insist that manual and AI customization use one layer, and that the agent customizes through the same interface a human does. `core.extension-integrity` (File 01 §7.10 — "AI-assisted customization must use the same system paths as manual customization") and `worksurface.views-presets` (File 25 §7.4 — "AI-assisted surface, view-preset, widget, or layout mutation is a capability flow: inspect, propose a diff or preview, pass policy, commit reversibly, record provenance") are decisive. This file adopts the one-path posture (§14): there is no agent-only customization API and no agent-only customization store; the agent reads the structural projection and proposes through the same `customize.*` capabilities the user invokes, every change is policy-gated and reversible, and natural-language customization resolves through the control rails into those capabilities.
- **Structural understanding versus coordinate reasoning.** The charter (§5) and the world-model spec resolve that the interface is described to the agent structurally and relationally — which surface is active, which roles are bound, what is presented, what contains what, and what is focused, selected, and primary — and that raw pixel coordinates are a weak primary representation. `world.chosen-model` (File 18 §1, structured-data-first) and `core.world-model` (File 01 §6.7, screenshot-driven self-perception is fallback) already fix this for perception. This file adopts the same posture for customization (§13): the agent reasons over the semantic-relational customization projection — the presentation roles, surfaces, presentation units, contributions, slots, and their relationships — never over coordinates as the primary interface.

## 1. Chosen Model

Anchor: `customize.chosen-model`

ATLAS3 has one customization layer. It is how the user, the agent, and plugins shape the presentation: the themes that resolve the visual tokens, the saved compositions that arrange the presentation units, the contributions that compose ambient and actionable units into customizable slots, the localized copy overrides that replace rendered text without changing behavior identity, and the per-profile defaults that seed these customizations. It builds entirely over File 37's rendering layer and the one settings substrate, and it realizes the customization the prior files declare and delegate.

The customization layer does five things and only five things:

- it **resolves the presentation tokens** through the `DesignTokenSystem` (§4) and the active `Theme` (§5), which override the semantic-token layer File 37 requires every renderer to consume
- it **arranges the composition** through `SavedComposition`s (§7) over File 37's `PresentationComposition`, and seeds those arrangements from built-in `ViewPreset`s (File 25) and per-profile defaults (§16)
- it **composes contributions** — the `PresentationContribution` primitive (§8) registered in the `ContributionRegistry` (§9), placed into the customizable slots a surface's `customization_policy` permits (§11), data-bound and action-bound through the governed substrate (§10)
- it **overrides the rendered copy** through the localized copy-override records (§3.4), which supersede the shipped string catalogue for the user's exact locale in File 37's copy resolution (`ui.i18n`, File 37 §15), changing rendered text and no behavior identity
- it **mediates customization** through the one customization flow — manual through direct manipulation and AI-assisted through the same capability path (§14), every change reversible, policy-gated, and recorded

The customization layer owns no business logic and no private durable store. A customization is a settings/customization record (`settings.setting-definition`, File 15 §3; `core.versioned-durable-state`, File 01 §6.10) rendered by File 37's composition model and registries; its loss is a rebuild, never data loss (`core.projection`, File 01 §6.11). Every theme, composition, contribution, placement, and configuration is reversible and resettable (`core.non-destructive-by-default`, File 01 §7.13; the charter's removability rule).

This file introduces the net-new customization primitives the prior files referenced without owning: the `DesignTokenSystem` (§4), the `Theme` and `ThemeRegistry` (§5), the `SavedComposition` (§7), the `PresentationContribution` and `ContributionRegistry` (§8, §9), and the `LocalizedCopyOverride` record family (§3.4). `Theme`, `PresentationContribution`, `SavedComposition`, `LocalizedCopyOverride`, `ContributionRegistry`, `ThemeRegistry`, and `DesignTokenSystem` are new canonical noun-objects.

### 1.1 "Customization," "Contribution," "Theme," and "Composition" Are Disambiguated

Anchor: `customize.disambiguation`

This file fixes the customization-layer meanings of the overloaded words and distinguishes them from adjacent concepts:

- a **`PresentationContribution`** (this file, §8) — a declared, source-qualified, configurable, data-bound unit a user, plugin, or agent composes into a customizable slot, which projects governed data, exposes capabilities as actions, or both, and carries its own structural semantics and trust. It is not a `PresentationUnitKind` (`worksurface.state-declaration`, File 25 §5.3 — a surface-declared work-environment unit kind), not a `Block` (`block.chosen-model`, File 08 — a durable content-bearing unit), not an `Artifact` (File 09), not a `PresentationView` (`ui.presentation-projection`, File 37 §3 — one rendered projection), and not a `PresentationRole` (`ui.shell`, File 37 §4.2 — a role a presentation context binds to its own affordances). A contribution *renders through* a `PresentationView` and *may project* a block, artifact, or observation, but it adds placement, configuration, binding, and lifecycle as a customization unit. A **widget** is its windowed-desktop realization (§8.7).
- a **`Theme`** (this file, §5) — a named override set over a medium's semantic-token layer, with its declared ambient variants. It is not the `RendererRegistry` (File 37 §3.3) and not the semantic-token discipline (File 37 §16.5 — the rule that renderers consume only tokens); it is the system that fills the tokens that discipline requires.
- a **design token** (this file, §4) — a named, themeable presentation value a renderer resolves instead of a literal. This file owns the token system; File 37 owns the discipline; a medium declares which token families its presentation admits (§4.2), realized in the windowed-desktop profile as the visual family set (§4.6).
- a **`SavedComposition`** (this file, §7) — a user-saved named composition of what a presentation context presents. It is not the `PresentationComposition` itself (`ui.layout`, File 37 §5 — the composition model) and not a built-in `ViewPreset` (`worksurface.views-presets`, File 25 §7.2 — a surface-shipped startup presentation seed); it is the user's customized, reversible override that the composition model renders and the settings substrate persists.
- a **`ViewPreset`** (`worksurface.views-presets`, File 25 §7.2) — a surface-declared, named startup presentation seed. File 25 §7 owns the declaration and File 15 owns the saved-preset settings; File 37 renders built-in presets; this file owns only the `SavedComposition` (§7), which may capture a preset as a seed and freely override it.
- a **slot** (this file, §11) — a named, policy-owned insertion point in a presentation composition, declared by the surface's `customization_policy`, declaring what it accepts and from which sources, into which a `PresentationContribution` or a presentation unit may be placed. What a slot binds to is the medium's own (realized in the windowed-desktop profile as its customizable regions, §11.6). A slot is the realization of `worksurface.views-presets` (File 25 §7.4)'s abstract customization classes.
- a **profile** (`settings.profiles`, File 15 §7) — a named local setup that contributes ordered default layers. File 15 owns the profile; this file owns the per-profile UI defaults (§16) it carries and applies.

### 1.2 Boundary

This file defines how the presentation is themed, composed, and extended with contributions, and how customization is made and reversed. It does not define how the runtime is rendered (File 37), what any surface declares (File 25), how live state is held (File 18), how settings resolve (File 15), how plugins install (File 35), or how customizations are stored or synced (Files 20, 21).

## 3. The Customization Substrate and the No-Private-Store Invariant

Anchor: `customize.customization-substrate`

### 3.1 Definition

A customization is any user-, plugin-, or agent-made change to the presentation that the customization layer permits: an active theme, a saved composition, a placed contribution, a per-contribution configuration, a density or information-scale preference, a per-profile UI default. The customization substrate is the rule that every customization is a settings/customization record persisted and resolved through the one settings substrate (File 15) and rendered by File 37's composition model and registries, with no private durable store of its own.

### 3.2 Rule

- Every customization is a settings/customization record (`settings.setting-definition`, File 15 §3; `settings.logical-persistence`, File 15 §17). The customization layer maintains no private durable store, no parallel persistence, and no source-of-truth state; it renders projections (`core.projection`, File 01 §6.11) and persists changes through the settings substrate and the canonical storage contract (`storage.consequences`, File 20 §18). The single permitted device-local cache — the first-presentation token cache (§6) — is a rebuildable projection of the settings-resolved theme, not a source of truth.
- A customization record references the substrate it customizes by canonical identity, never by duplicating it (`worksurface.persistence-locality`, File 25 §16.1): a `surface_id` and `surface_contract_version` where the customization targets a surface, a `unit_kind`, a `PresentationContributionKind` and source-qualified contribution id, a policy-owned slot identifier, a source-qualified theme id, and the scope it applies at. Source-qualified registry identities are structural `{ source_id, local_id }` identities; display names are mutable and need not be unique. A customization that names a missing surface, presentation unit, contribution, or theme becomes an unavailable record with a typed diagnostic and a recovery action; it is never silently deleted or rewritten (`worksurface.registry`, File 25 §10.4).
- Every customization record carries `source_ref` and `provenance_refs`. `source_ref` identifies the user, built-in seed, plugin bundle, profile seed, import, or AI proposal that created or last materially changed the record. `provenance_refs` point to the request or observation, source approval, profile bundle, import plan, ledger event, settings revision, or version that explains why it exists. These are references, not duplicated provenance blobs, and feed the source-agnostic "why is this active?" inspector (§17.1).
- Durable customization writes are revision-safe. A write carries the current customization revision or resolved-state hash for the records it changes; if the base is stale, the write fails with a typed conflict and repair path instead of silently overwriting newer user, plugin, import, or agent changes.
- A customization record may carry a `CustomizationDependency` closure: the themes, contributions, plugins, profiles, connectors, capability declarations, renderer registrations, and surface versions required to apply it. Import, sync, composition resolution, and plugin uninstall use this closure to explain unavailable records and repair options.
- Every customization is reversible, removable, and resettable (`core.non-destructive-by-default`, File 01 §7.13; the charter's removability rule): resetting a composition, theme, contribution, or preference restores the default or profile-default value, and the prior value survives as a version-graph or settings sibling, never a destructive overwrite. The user is never trapped by a customization, whether made manually or by the agent.
- A customization is policy-resolved and scoped through the canonical cascade (`settings.scopes-profile-contexts-overlays`, File 15 §5.2): a customization applies at the `Global`, `Workspace`, or `Conversation` scope, or as a profile-layer default; the customization layer is not a durable settings scope and invents no new scope.
- A customization holds no business logic. The customization layer computes presentation values (placement resolution, token resolution, composition arithmetic) but never the substrate's truth (`ui.renderer-boundary`, File 37 §16.2; `core.invariants`, File 01 §7.7).

### 3.3 Customization Is a Projection

A customized view is a `core.projection` (File 01 §6.11): rebuildable from the customization records plus the substrate, declaring an event-first rebuild trigger (a setting-change event, a composition-switch, a theme-switch, a contribution-placement event), never the source of truth for any durable fact, and recoverable by rebuild on loss. The cost of losing the rendered customization state is a rebuild from the records, never data loss.

### 3.4 The Localized Copy-Override Record Family

- A `LocalizedCopyOverride` is a customization record that replaces the rendered text of one localizable target for one exact locale. A target is a registered presentation descriptor — a label, description, tooltip, placeholder, notification or error message template, or accessibility text — including the localizable display descriptors `capability.display-fields` (File 05 §3.2) declares, whose user-facing projection an override may replace while the declaration's model-facing description stays as declared. Model output, documents, logs, identifiers, provenance facts, formatted user data, and user-owned entity names are not copy targets; an entity's name stays editable through its owning capability.
- The record carries a structural source-qualified target identity — §3.2's `{ source_id, local_id }` discipline extended with the object kind and the overridden field, never a literal or a delimiter-joined string; the exact canonical BCP-47 locale tag it binds, validated as an open tag rather than drawn from a closed persisted set, so an override for one tag never rewrites a related tag; the scope it applies at, structurally present and restricted to `Global` until a revision of this section widens it (`settings.scopes-profile-contexts-overlays`, File 15 §5.1); the validated message template; the message-contract fingerprint, which is the placeholder and argument-name set parsed from the template's own structure, recursing into plural and select arms and derived independently of the shipped default text; and a `safety_class` marking a target whose renderer is baseline-only sensitive (`ui.i18n`, File 37 §15). It carries source and provenance references, revision and base revision with causal identity, sensitivity, locality, and dependency state under §3.2 and §18, like every other customization record.
- A record never copies the shipped default text. A compatible catalogue update flows through to the override unchanged; a catalogue update that changes the message contract, a renamed target, or an uninstalled plugin preserves the record inactive with a typed diagnostic and a successor or repair path, never a silent deletion or rewrite (§3.2).
- An override value is validated at write and never enforced for terminology or style (`ui.i18n`, File 37 §15's provenance boundary): the target resolves or the record is preserved as a typed orphan, the template parses, the required placeholders, placeholder types, plural and select arms, and formatting contracts remain intact, control-character and bidirectional spoofing and injection-bearing markup are rejected, raw secret material is refused (`settings.secret-boundary`, File 15 §10), and an accessibility-required label stays non-empty.
- Reset restores that locale's shipped default by writing a causally descendant unset revision, never by deleting the record (`settings.logical-persistence`, File 15 §17; File 21 §6.3). The copy-management surface shows the shipped default, the effective resolved text, the source attribution and "why is this active?" explanation (§17.1), and a catalogue-only preview, so a confusing customization is always escapable.
- Copy customization is gated by the target's own contract and `safety_class`, not by the slot and placement model (§11): a surface enumerates no copy targets in its `customization_policy` (`worksurface.views-presets`, File 25 §7.4), and an override changes no placement, bound, or authority.
- A source-approved catalogue provider is a reserved resolution layer between the override records and the shipped catalogue, and custom locales and translation packs are a future extension over it. A provider-supplied addition — a new target or a new locale — registers namespaced under the provider identity, so an addition cannot collide with a shipped string; a provider-supplied replacement of a shipped string resolves through explicit, inspectable collision reporting, never plugin or filesystem load order.

### 3.5 Boundary

This section fixes the customization-as-record and no-private-store invariant. File 15 owns the settings model, cascade, and persistence; File 20 owns the physical storage; File 11 owns the version graph that records reversibility; File 37 owns the composition model and registries that render the customization. This file requires every customization to be a record.

## 4. The `DesignTokenSystem`

Anchor: `customize.design-tokens`

### 4.1 Definition

The `DesignTokenSystem` is the layered model of named, themeable presentation values that renderers resolve in place of literals. It fills the semantic-token discipline `ui.renderer-boundary` (File 37 §16.5) fixes (a renderer that resolves a presentation property from a literal rather than from a named token is invalid) and is the substrate every `Theme` (§5) overrides. The three layers and the discipline are the same in every medium; the families of value a medium's presentation admits are the medium's own (§4.2).

### 4.2 The Three Token Layers

The token system has three layers, resolving outward, in every medium:

- **Primitive tokens** — literal values with no semantic meaning, of whatever kinds the medium's presentation admits. Primitives are the raw value set; a renderer never references a primitive directly.
- **Semantic tokens** — intent mapped to primitives, and the layer themes override. A medium declares its own semantic-token families: each family is a role the medium's presentation can vary, named by the role it serves and never by the input or output device that realizes it, so an interaction-state family is named by state (available, engaged, active, unavailable) and never by a gesture. Every medium declares at least the families its active accessibility conformance profile validates (§5.4) and the information-density axis (§5.8). The windowed-desktop medium's declaration is the windowed-desktop profile's (§4.6). A renderer consumes only semantic (and, where declared, component) tokens.
- **Component tokens** (optional) — for complex multi-part presentations, derived from semantic tokens for local roles; they never introduce a literal and always resolve to semantic tokens or primitives.

A medium's semantic-token family set is not a canonical set and has no canonical member: it is that medium's own declaration, registered through the frontend profile its sessions declare (`ui.frontend-profile`, File 37 §1.3), because a family is a role one medium's presentation can vary and no other's. What closes is each declared family's values: a family declares the encoding its values take (§4.3), and a value outside that encoding is invalid at validation (§5.4). A surface or plugin that needs a semantic role its medium's declaration does not carry registers a `Custom` token through the proposal-first mechanism (§9), declaring the family it extends and its default mapping, and never references a literal. A family declared for one medium binds no other, and a renderer that finds no token for a role its own medium does not declare presents without that role rather than falling back to a literal.

### 4.3 The Perceptual-Metric and Derivation Contract

- Where a medium's token values admit a perceptual metric, a token's canonical encoding is in that metric rather than in a device-native encoding. Perceptual uniformity is the load-bearing property: it lets a theme derive a related token by a relative transform of one axis, without recomputing the whole token set, and it makes conformance validation (§5.4) tractable. The visual medium's metric is a perceptually-uniform color space (§4.6).
- A device-native value may appear only as a reference annotation or a primitive; the source of truth for a token whose medium declares a perceptual metric is that metric's encoding. The concrete value library and its renderer encoding are the renderer implementation's; this file fixes the contract that such tokens are perceptually encoded and relatively derivable.

### 4.4 The Token Discipline

- A renderer — built-in, surface-contributed, or plugin-contributed — consumes only semantic and component tokens, never a literal (`ui.renderer-boundary`, File 37 §16.5; `worksurface.no-private-architecture`, File 25 §12.3). A contribution or theme that resolves any presentation property it varies from a literal rather than from a named token is invalid and is rejected at registration (§9, §5.5), and which values a medium's renderers must never resolve from a literal is the medium's own (realized in the windowed-desktop profile as the raw-value prohibition, §4.6).
- A surface or contribution that needs a local variant layers a scoped token overlay (a per-surface or per-contribution token set derived from the semantic layer, §5.6), never a literal and never a fork of the token system. A scoped overlay resolves to the semantic layer so a theme switch propagates without a renderer change.
- Adding a token is a declaration: a new semantic or component token registers with its default mapping and is immediately available to renderers and themes, at flat marginal cost (`core.extension-planes`, File 01 §6.14; the self-registration-into-the-token-system invariant). No central file is edited to add a token.

### 4.5 Boundary

This section owns the token model, the perceptual-metric contract, and the discipline's content. File 37 owns the discipline's enforcement at the renderer boundary; §5 owns the themes that override the semantic layer; the renderer implementation owns the concrete value library and its registration. This file fixes the system the discipline consumes.

### 4.6 Windowed-Desktop Profile

Windowed-desktop profile (`ui.frontend-profile`, File 37 §1.3); binds only a session declaring `desktop.windowed`.

Realizes: §4.2. The primitive kinds this medium's presentation admits are a specific color value, a spacing step, a radius, a shadow, a font family, and a motion duration. Its declared semantic-token families are surface (background and elevation surfaces, borders), text (primary, secondary, tertiary, disabled, inverse), interactive (accent and its hover/active/disabled states, success, danger, warning), feedback (error, success, warning, info, and their backgrounds), component radius and shadow, motion (short, normal, long durations and easing classes), typography (body, heading, and monospace families and sizes), spacing, and the surface-density and information-density axes.

Realizes: §4.3. Colour tokens are defined in a perceptually-uniform cylindrical color space (lightness, chroma, hue, with optional alpha), not in a device-RGB hexadecimal encoding: it lets a theme derive a related token by a relative transform of one axis (a slightly darker surface variant by lowering lightness) without recomputing the whole token set. A hexadecimal or device-RGB value may appear only as a reference annotation or a primitive.

Realizes: §4.4. A renderer, widget, or theme that references a raw color, radius, font, spacing, or motion value is invalid and is rejected at registration.

## 5. The `Theme` and the `ThemeRegistry`

Anchor: `customize.theme`

### 5.1 Definition

A `Theme` is a named, registered override set over the semantic-token layer of the medium it themes, carrying one or more ambient variants. The active theme resolves the semantic tokens every renderer consumes; switching the theme re-resolves the tokens and re-presents, without any renderer change. The `ThemeRegistry` is the one registry of available themes.

### 5.2 The `Theme`

A `Theme` carries: a stable source-qualified theme identity, display name, author, license, version, source metadata, and dependency closure; the ambient variants it provides; and, per variant, a `ThemeTokenSet` mapping the semantic-token names of the medium it themes (§4.2) to values in that medium's declared encoding. A theme overrides the semantic layer only; it never redefines primitives' meaning, never resolves a renderer's property from a literal, and never carries logic, executable content, selector- or rule-based styling authority, remote imports, remote asset references, or undeclared assets. The family names a `ThemeTokenSet` writes durably close at the registered family declaration of the medium it themes (§4.2, `ui.frontend-profile`, File 37 §1.3), never at a canonical family set, and a theme naming a family that declaration does not carry is invalid (§5.4). A theme is a complete declarative override of the medium's semantic layer, not a swap of one family: it sets every family that medium declares (§4.2), in every ambient variant it declares, which is what makes two themes differ structurally rather than in one family's values (realized in the windowed-desktop profile as its structural theme differences, §5.10). A declaration that covers fewer families than the medium declares is not a theme: registration rejects it with a typed diagnostic naming the families it omits (§5.4). There is no partial theme, no selectable incomplete theme, and no inheritance of an undeclared family from the default theme; an incomplete token set exists only as an unregistered draft or preview object (§5.4).

`AmbientVariant` is closed-canonical-plus-`Custom { namespace, name }` (`core.closed-canonical`, File 01 §6.16) with the canonical members `Auto`, `Light`, and `Dark`. A theme declares the ambient variants it provides — the conditions of the presenting environment its values are for — and a medium declares which variants it distinguishes and ignores the rest, so a member a medium does not distinguish constrains nothing there. `Auto` follows the presenting environment: the active variant resolves from settings, and `Auto` resolves from the host's declared ambient preference event-first and re-resolves when that preference changes (`ui.settings`, File 37 §22; the no-time-based-polling rule, `core.event-first-by-default`, File 01 §7.15). Which variants a medium distinguishes is the medium's own (realized in the windowed-desktop profile as its ambient axis, §5.10).

An ambient variant is not the style extension point. Additional variants of appearance are themes, accessibility preferences, or scoped token overlays, never new members of the ambient-variant set; a `Custom` member is registered only where a medium's presenting environment distinguishes an ambient condition the canonical members do not name.

### 5.3 The `ThemeRegistry`

The `ThemeRegistry` is the one registry that holds the available themes (built-in, plugin-contributed, and user-authored), keyed by source-qualified theme identity `{ source_id, local_id }`, and exposes lookup, enumeration, and the active-theme resolution. There is one `ThemeRegistry`; no surface, contribution, or plugin maintains a private theme table. A plugin contributes a theme through the proposal-first source-approval-gated path (`plugin.contribution-points`, File 35 §5.2; `policy.source-approval-flow`, File 06 §9) under the same source taxonomy and trust model as every other contribution (§15). A built-in baseline set of themes ships as worked examples, including at least a default theme, one theme per ambient variant the medium declares, and a maximum-conformance theme (§5.7); the exact shipped catalogue is distribution's, not canonical here (realized in the windowed-desktop profile as its own shipped baseline, §5.10).

### 5.4 Theme Validation

A theme validates before it is registered or selectable through a `ThemeValidationMatrix`: every family the medium declares is present, in each ambient variant the theme declares, and a declaration missing a family is rejected with that family named (§5.2), and no family name outside the medium's declaration appears; each value lies in the valid range of its family's declared encoding; every declared family's values and its asset references are declarative and bounded; executable content, selector- or rule-based styling authority, remote imports, undeclared assets, and literal renderer values are rejected; and the active accessibility conformance profile's floors hold for every token role that profile covers (`ui.accessibility`, File 37 §14.2), the enumerated roles being the profile's own (realized in the windowed-desktop profile as its own conformance obligations, §5.10). A nonconforming or incomplete token set may be held as an unregistered draft or preview object with a typed diagnostic, but it is never registered, never selectable, and never presented as a theme; activation requires the active conformance profile to pass.

### 5.5 Theme Switching and the Default-Theme-Not-Only-Theme Rule

- Theme selection is the `ui.theme` setting resolved through the canonical cascade (`settings.scopes-profile-contexts-overlays`, File 15 §5.2; `settings.types-semantics-constraints`, File 15 §4.2's `ColorToken` semantic). Switching the theme is a settings write; the renderer reads it reactively and re-resolves the tokens, re-presenting without rebuilding what is presented (`ui.settings`, File 37 §22). Theme switching commits no work-model change and never silently changes model selection, context policy, execution, budget, sandbox profile, approval posture, or instruction-source authority.
- The shipped default theme is a default, not the only theme: a medium's presentation language is every family the medium declares (§4.2), token-based and independent of any one family's values, so any theme fills the same tokens and every renderer responds to the change. A theme is a complete swap of the medium's semantic layer, not a per-renderer opt-in (realized in the windowed-desktop profile as its visual language, §5.10).

### 5.6 Per-Surface and Per-Contribution Token Overlays

A surface or a contribution may layer a scoped token overlay — a named token set derived from the active theme's semantic tokens for local roles, one visual example being a surface's editor-background derived from the surface-background token and a contribution's accent derived from the interactive-accent token — applied within the surface or contribution's scope. An overlay resolves to the semantic layer through the relative-derivation rules (§4.3, §4.4), so a theme switch propagates into the overlay without an overlay change. A scoped overlay never introduces a literal, never escapes its scope, and never forks the theme; it is the canonical mechanism for the per-surface presentation identity the per-surface specs may declare.

### 5.7 The Maximum-Conformance and Accessibility Themes

The maximum-conformance theme is a first-class theme, not an afterthought (`ui.accessibility`, File 37 §14.3): it satisfies the strictest conformance profile the medium declares purely by overriding the semantic tokens — no renderer change — and its existence is what proves the discipline holds (realized in the windowed-desktop profile as the high-contrast theme, §5.10). The reduced-motion and information-scale accessibility preferences (`ui.accessibility`, File 37 §14.2) compose with the active theme through the medium's own token axes, not through a separate theme. Accessibility conformance is verified against the active theme, including every ambient variant it declares (`ui.accessibility`, File 37 §14.2).

### 5.8 Named Focus and Trust-State Token Axes

Beyond ambient variants, the token system carries two further token axes a theme and a customization may set without introducing a mode field (`codex_recommendations.md` §10.5 realized):

- **information-density axis** — a token-resolved level on the medium's information-per-unit-of-attention axis, selectable as a preference (§16) and a per-profile default; it is a token axis, not a mode dial (realized in the windowed-desktop profile as its density levels, §5.10).
- **trust-state tokens** — semantic tokens that cue risky actions, low-confidence output, and unverified claims in the medium's own idiom, resolved by the theme so the cue is consistent and themeable. These render the consequences of the policy and provenance layers (Files 06, 09), never a new authority.

A named focus (a command focus, an artifact focus, a teaching focus, a review focus) is a presentation lens realized as which roles are bound, which presentation units and contributions are present and at what prominence, and which density and token overlay apply — a `SavedComposition` plus token state — never a backend autonomy mode (`ui.interaction-models`, File 37 §7; §17).

### 5.9 Boundary

## 6. Theme Persistence, Switching, and the Token Cache

Anchor: `customize.theme-persistence`

### 6.1 Rule

- The active theme and ambient variant are the source-of-truth in the settings substrate (`ui.theme` and the ambient-variant setting), resolved through the canonical cascade and synced as user preferences per their declared locality (`settings.locality-sync-export`, File 15 §18). The customization layer persists the theme selection nowhere else; no frontend-local storage mechanism is a settings store (`settings.explicit-rejections`, File 15 §20).
- Theme switching is event-first: a setting-change event drives re-resolution and re-render (`ui.settings`, File 37 §22; `settings.events-snapshots`, File 15 §14). `Auto` ambient-variant tracking subscribes to the host's declared preference change, never polls.

### 6.2 The First-Presentation Token Cache

A presentation context resolves its token state before it first presents. Where the settings-resolved theme is not yet available at that moment, the renderer maintains one device-local cache of the resolved theme tokens for the active theme and resolves from it, so the first presentation carries the user's theme rather than a default one (realized in the windowed-desktop profile as a synchronous pre-presentation read, §6.4). This cache is the single sanctioned device-local presentation cache and is bounded by these rules:

- it is a **rebuildable projection**, not a source of truth: it holds a copy of the tokens the settings-resolved theme produces, keyed to the active theme identity and version, ambient variant, token-system/schema version, relevant renderer/theme-engine version, active accessibility conformance inputs, profile/default layer identity where it affects tokens, source/contribution identity for plugin themes, and the medium-declared token dependencies and resource availability the resolved values depend on; it is rebuilt whenever any key input changes, and its loss is a re-resolution, never data loss (`core.projection`, File 01 §6.11)
- it fails safe: a cache miss, stale key, failed integrity check, missing source, or validation mismatch causes synchronous token resolution from the settings/customization substrate before it first presents, never reuse of an invalid cache entry
- it holds **no source-of-truth state, no preference, no authority, and no secret**: the theme selection is the settings substrate's, and the cache holds only resolved tokens for the first presentation, never a composition, a contribution, plugin code, raw contribution payloads, or policy state
- it is **device-local and never syncs** (`settings.locality-sync-export`, File 15 §18's `DeviceLocal`; `portability.what-replicates`, File 21 §5.3); a new device re-resolves and re-caches on first run
- the concrete synchronous storage mechanism is the renderer implementation's and File 43's; this file fixes that the first-presentation token cache is a device-local rebuildable projection of the settings-resolved theme

This is the one carve-out from the no-private-store rule (§3.2, `ui.renderer-boundary`, File 37 §16.4), and it is permitted precisely because it is a projection: it owns no fact the substrate does not already own.

### 6.3 Boundary

This section owns the theme-persistence contract and the token-cache exception. File 15 owns the theme setting and its locality; File 43 owns the concrete pre-presentation resolution mechanism; File 21 owns sync. This file fixes that the theme is a setting and the cache is a projection.

## 7. The `SavedComposition` and Composition Customization

Anchor: `customize.saved-layout`

### 7.1 Definition

A `SavedComposition` is a user-saved, named composition over File 37's `PresentationComposition` (`ui.layout`, File 37 §5): which presentation units and contributions a context presents, in which role bindings and slots, their grouping, ordering, primacy and prominence, and the focus shape (realized in the windowed-desktop profile as the layout container, §7.7). It is the user's customized, reversible override over the built-in `ViewPreset`s (File 25) the surface ships and File 37 renders. Composition customization is the save/switch/rename/reset/duplicate/set-default flow over saved compositions.

### 7.2 The Saved-Composition Record

A `SavedComposition` carries: a stable id and display name; the scope it applies at (`Global`, `Workspace`, or `Conversation`, or a profile layer, §18) and the surface or presentation context it customizes; the semantic composition — the presentation units and contributions it presents, with their `PresentationUnitKind`/`PresentationContributionKind`, source-qualified identities, role bindings, slots, grouping, ordering, primacy, `PresentationProminence`, co-presence and minimum-viability constraints, and the focus shape; an optional map from frontend profile id (`ui.frontend-profile`, File 37 §1.3) to a reference to that profile's realization payload for this composition; its source/provenance references, revision, and `CustomizationDependency` closure; and whether it is a built-in seed or a user-authored override. The semantic composition fixes no topology and no geometry: a realization payload is profile-local, is resolved only by a session declaring that profile, joins no part of the record's portable identity, and a session that finds no payload for its own profile realizes the semantic composition alone without loss of correctness (realized in the windowed-desktop profile as the container's arrangement, §7.7). Physical positions and offsets are renderer hints or derived state, never canonical portable identity. A `SavedComposition` is a settings/customization record (§3); it references presentation units, contributions, and surfaces by identity and stores no presented content.

The record's identity is its stable id within the scope it applies at; ordering is internal to it and no ordering holds between records. Its locality is the customization record's, `Syncable` where its owner syncs (§18.1), while a realization payload resolves per device where the payload it references is device-local. Every vocabulary it writes durably closes at its owning file — `PresentationUnitKind` (`worksurface.state-declaration`, File 25 §5.3), `PresentationContributionKind` (§8.4), and `PresentationProminence` (`world.surface-state`, File 18 §5.3) — and a frontend profile id is an open registered identifier, so a new profile widens no closed set. It is retained until the user deletes it, and a reset preserves the prior value as a version-graph or settings sibling rather than overwriting it (§3.2). Its guarantee is bounded honestly: applying it restores the semantic composition exactly, and restores a realization only for a session that declares the profile the payload was written for; for any other session the payload is inert.

### 7.3 The Save/Switch/Customize Flow

- The user arranges the composition through the presentation operations File 37's composition model exposes (`ui.layout`, File 37 §5) and the contribution-placement operations (§12), then saves the current arrangement as a named `SavedComposition` at a chosen scope (capture-current). The user switches between saved compositions and built-in presets, renames, duplicates, resets a composition to its seed or the surface default, and sets a default composition per scope or per profile. Each operation is a `customize.composition.*` capability (§19) and a settings/customization write; none commits a work-model change.
- Applying a `SavedComposition` changes presentation only (`worksurface.views-presets`, File 25 §7.2): it never silently changes model selection, context policy, execution entry, budget, sandbox profile, approval posture, or instruction-source authority. A composition is a presentation arrangement, not an autonomy mode (§17). A saved composition may reference an associated settings/profile bundle, but applying the composition applies those settings only if the user explicitly applies the bundle through the settings path.
- A `SavedComposition` is a seed the user freely overrides: applying it establishes the initial arrangement, after which the user's ongoing arrangement changes, however they are made — presenting a unit, moving a contribution, changing a unit's prominence or the composition's ordering — are tracked as live `SurfaceState` (File 18) and may be re-captured into a new or updated saved composition (realized in the windowed-desktop profile as direct manipulation of the container, §7.7). Switching away and back restores the saved arrangement.

### 7.4 Built-in Presets, User Compositions, and the Seed Rule

- A built-in `ViewPreset` (`worksurface.views-presets`, File 25 §7.2) is a surface-shipped startup seed File 37 renders; a `SavedComposition` is the user's customization over the composition model. The two compose: a user captures a preset as a starting `SavedComposition` and customizes from there, or saves a fresh composition. A preset is a seed, not a contract — every arrangement it makes is reversible (the `ui/15-3-and-15-4` rule realized).
- The frontend ships a default composition per surface and a default conversation-first composition (`ui.layout`, File 37 §5.3); the default rendering is complete without any saved composition. On activation, the resolved composition is the user's saved default for the scope and surface if present, else the surface's default preset, else the conversation-first default — the preset-fallback chain.

### 7.5 Skip-Unavailable Recovery and Responsiveness

- A `SavedComposition` that references a missing presentation unit, contribution, surface, or surface-contract version (a feature not installed, a plugin disabled, a surface unavailable) is restored with the missing element skipped and a typed unavailability diagnostic and recovery action; it is never silently deleted or rewritten (`worksurface.registry`, File 25 §10.4). If no saved composition can be applied, the frontend falls back to the surface default and records a diagnostic (`ui.states`, File 37 §17).
- Applying a `SavedComposition` produces a deterministic `CompositionResolutionReport` carrying the input composition id/revision, target surface or presentation context, the presentation budget and adaptation profile resolved for it, policy version, applied placements, skipped entries, unavailable dependencies, incompatible placements, density-bound rejections, budget adaptations, fallback used, and repair actions. Resolution never rewrites the source composition silently.
- A `SavedComposition` declares its adaptation under a reduced presentation budget. A medium's presentation budget is the finite quantity of simultaneous presentation a context can carry, declared by the frontend profile a session implements as one scalar with a named unit together with the thresholds at which that scalar counts as reduced (`ui.frontend-profile`, File 37 §1.3); every capacity, density bound and adaptation threshold this file expresses is in that unit, and a session declaring no profile declares the scalar and its unit itself. A durable declaration expressed against that budget — a slot's declared capacity and density bound (§11.2), a contribution's minimum viable presentation budget (§8.3) — is therefore either a fraction of the presenting context's budget or a map from frontend profile id to a value in that profile's own unit over a pattern default in that fraction form, the shape §7.2's realization-payload map already takes; a session that finds no value for its own profile applies the pattern default without loss of correctness, and no session reads another profile's number as though it were in its own unit. Under a reduced budget the composition degrades to one primary unit with navigation among the rest (`ui.layout`, File 37 §5.4), a saved arrangement has a defined reduced-budget adaptation, and a constrained-platform frontend is a purpose-built presentation rather than a degraded one (realized in the windowed-desktop profile as narrow-width stacking, §7.7). A composition change is acknowledged before it completes, and the responsiveness budget for it is a declared, tested, settings-carried value with a stated default, never a canonical constant.

### 7.6 Boundary

This section owns the saved-composition record and the customization flow. File 37 owns the composition model and its operations; File 25 owns the `ViewPreset` declaration and the `PresentationUnitKind`; File 18 owns the live `PresentationUnitState`; File 15 owns the persistence and scope. This file owns the user-saved composition over the composition model.

Windowed-desktop profile (`ui.frontend-profile`, File 37 §1.3); binds only a session declaring `desktop.windowed`.

Realizes: §7.1. The composition is the layout container: which panels and widgets are placed in which regions and slots, their split structure and sizes, their visibility, and the focus shape.

Realizes: §7.2. Physical divider positions and pixel offsets are renderer hints or derived state, not canonical portable identity, and they never join the record's portable identity.

## 8. The `PresentationContribution` Primitive and `PresentationContributionKind`

Anchor: `customize.widget`

### 8.1 Definition

A `PresentationContribution` is a declared, source-qualified, configurable, data-bound unit that a user, plugin, or agent composes into a customizable slot: it projects governed data, exposes capabilities as actions, or both, and carries its own structural semantics and trust. A contribution displays live or cached information, summarizes background or runtime state, exposes actions, triggers workflows or commands, navigates into a fuller surface, or reflects scheduled or background processes — an ambient interface to the runtime (the charter's §6 rule). It is the net-new customization primitive this file introduces; a **widget** is its windowed-desktop realization (§8.7).

### 8.2 Purpose

The presentation is bounded by what it surfaces and where. Different users and different work benefit from different available context — a research feed bound to the inspection role, a task-and-blockers summary bound to the conversation role, a workflow-status or scheduled-output unit, a memory-proposal or reminder unit — and a stable contribution layer is how that ambient, actionable context is added without hardcoding it into the frontend, editing core source, or one-off plugin hacks (the charter's §2 rule). The contribution primitive carries that addition while reusing the substrate underneath, so adding a contribution is a declaration and a placement, not a new architecture (`core.local-extensibility`, File 01 §7.8). What separates a contribution from decoration is what it carries, not how it looks: a contribution projects live or cached substrate, capability, automation, or runtime state, or exposes at least one governed action or navigation target, or both; a unit that projects neither is decoration and is not a contribution.

### 8.3 The Contribution Declaration

A `PresentationContribution` is declared by a `PresentationContributionDeclaration` carrying: a stable source-qualified contribution identity and `PresentationContributionKind` (§8.4); localized display name, description, and icon key (`capability.display-fields`, File 05 §3.2's localizable-descriptor discipline, whose symbol form each medium resolves to its own or ignores without loss of correctness); the data sources it binds (§10) and the capabilities it exposes as actions (§10); its typed configuration schema and defaults (§12); its renderer (registered in the `ContributionRegistry`, §9); its placement constraints — the slot classes it fits, the presentation roles it is compatible with, its minimum viable presentation budget expressed as §7.5 requires, and the prominence levels it supports (`world.surface-state`, File 18 §5.3); the structural semantics it exposes (`ui.accessibility`, File 37 §14 — a stable role, accessible label and description, interaction kinds, focus behavior, and state relationships) sufficient for the world model, the rails, and assistive technology; its source and trust state (built-in, plugin-contributed, or user-authored); its `CustomizationDependency` closure; and its default live-versus-cached data behavior (§10). A declaration that omits the required fields or cannot be represented structurally is invalid and rejected at registration (§9); the form its placement constraints take is the medium's own (realized in the windowed-desktop profile as size constraints, §8.7).

### 8.4 `PresentationContributionKind`

`PresentationContributionKind` is closed-canonical-plus-`Custom`. The canonical baseline is a small set of structural archetypes by data-and-behavior role, not a frozen product catalogue:

- `Information` — displays live or cached read-only data projected from substrate or an external source (a status summary, a feed, a metric)
- `Status` — summarizes the live state of a larger process — a run, an automation, a workflow, a connection, a budget — as an ambient indicator (`automation.observability`, File 33 §17; `run.presentation`, File 04 §25)
- `Action` — exposes one or more capability invocations as controls (run-now, enable/disable, a quick command), gated by policy (§10)
- `Navigation` — resolves to opening or revealing a fuller surface, entity, or view through the navigation target contract (`ui.shell`, File 37 §4.4)
- `Composite` — composes child contributions and substrate projections into a unit-scale whole (a grouped set of related indicators, an overview area)
- `EmbeddedRuntime` — renders executable or interactive content inside the confined interactive-artifact runtime (§9.3) — a chart, a canvas, an agent- or plugin-authored mini-interface
- `Custom { namespace, name }` — a surface-, plugin-, or user-registered contribution kind, registered through the proposal-first mechanism (§9), declaring its data contract, renderer, placement constraints, and structural semantics

The concrete contributions the sources name — a weather unit, a latest-research feed, an active-tasks-and-blockers summary, a memory-proposal review, a workflow-status tile, a scheduled-automation-output tile, a recent-artifacts list, a lesson-progress unit, a project-health summary, a context-budget indicator, a usage-and-rate-limit indicator, a sync-status contribution, a whiteboard or node-canvas surface — are built-in or plugin-contributed *instances* of these archetypes registered in the `ContributionRegistry`, not canonical kinds. The baseline archetype set is for cross-cutting reasoning, placement, and policy; it never gatekeeps which concrete contributions may exist (the charter's §13/§14 rule). Adding a canonical archetype is a canonical-spec change; runtime extension uses `Custom`.

### 8.5 Contribution Versus Block, Artifact, Presentation Unit, and Presentation View

A `PresentationContribution` is distinct from the adjacent rendering units (§1.1): a `Block` (File 08) and an `Artifact` (File 09) are durable content units a contribution may *project*; a `PresentationUnitKind` (File 25 §5.3) is a surface-declared work-environment unit a contribution may *render within* or *borrow*; a `PresentationView` (File 37 §3) is the rendered projection a contribution's renderer *produces*. The inline block renderer that displays a structured result in the transcript is File 37's `RendererRegistry` rendering a `Block` (`ui.substrate-rendering`, File 37 §9), already canonical and unchanged; the contribution is the placed, configured, data-bound customization unit that a user composes into a slot and that may itself render such a block. The two are not duplicated: a contribution that displays a block kind reuses File 37's renderer for that kind (realized in the windowed-desktop profile as the inline card renderer, §8.7).

### 8.6 Boundary

This section owns the contribution primitive, its declaration, and the kind archetypes. File 37 owns the rendering the contribution produces; File 25 owns the presentation-unit kinds and the customization policy; File 08/09 own the blocks and artifacts a contribution projects. §9 owns the registry and rendering dispatch; §10 owns the data and action binding.

### 8.7 Windowed-Desktop Profile

Windowed-desktop profile (`ui.frontend-profile`, File 37 §1.3); binds only a session declaring `desktop.windowed`.

Realizes: §8.1. A widget is the windowed-desktop realization of a presentation contribution: a declared, placeable, configurable, data-bound modular UI unit composed into a customizable region — a dashboard tile, a sidebar status panel, an inline card — never a decorative one.

Realizes: §8.3. A widget declaration's placement constraints are the slot kinds and region classes it fits, its minimum and default size, and its supported display modes: inline, side, and fullscreen, where applicable, mirroring `ui.substrate-rendering` (File 37 §9.3).

## 9. The `ContributionRegistry` and Contribution Rendering

Anchor: `customize.widget-registry`

### 9.1 Definition

The `ContributionRegistry` is the one registry that holds the available contribution declarations, keyed by source-qualified contribution identity `{ source_id, local_id }` and `PresentationContributionKind`, and dispatches a contribution to its renderer through File 37's `RendererRegistry`. It is the contribution counterpart of the `ThemeRegistry` (§5.3) and the realization of the widget contribution kind `plugin.contribution-points` (File 35 §5.2) routes here.

### 9.2 Rule

- There is one `ContributionRegistry`. No surface, rail, or plugin maintains a private contribution table. A contribution's renderer registers through the one `RendererRegistry` (`ui.presentation-projection`, File 37 §3.3) — a contribution kind dispatches to its renderer like any substrate kind, with a safe typed placeholder for an unknown or unavailable contribution kind, never a crash and never an empty presentation. A contribution is registered code from a built-in or source-approved contribution; the content it renders keeps its own authority class and sensitivity (`ui.presentation-projection`, File 37 §3.3 — renderer trust and content trust are separate).
- Built-in, surface-contributed, plugin-contributed, and user-authored contributions register through the same proposal-first source-approval-gated path (`capability.runtime-mutation`, File 05 §16.2; `policy.source-approval-flow`, File 06 §9) under the one source taxonomy and trust model (§15), and are treated identically thereafter, distinguished only by source, trust, bundle ownership, and default enablement (`capability.sourcing-equivalence`, File 05 §9.3). A contribution's renderer consumes only the semantic-token layer (§4.4) and receives a resolved presentation environment (the active theme, the prominence it is presented at, scope, resolved tokens, and resolved locale) like any renderer (`ui.presentation-projection`, File 37 §3.3).
- A contribution declaration validates at registration: the required fields are present (§8.3), the renderer is registered, the declared data and action bindings resolve to governed sources (§10), the structural semantics are sufficient (§8.3), and the declared presentation values are tokens, not literals (§4.4). An invalid declaration is rejected with a typed diagnostic; an optional binding that cannot resolve enters an unavailable state, never a silent substitution.
- A disabled or removed contribution's renderer degrades safely: a contribution from a disabled plugin renders the typed placeholder and is not invocable, never a crash; a stale contribution reference resolves to the placeholder until repaired (`ui.states`, File 37 §17).

### 9.3 The Confined Contribution Runtime

An `EmbeddedRuntime` contribution (§8.4), and any contribution that renders executable or interactive content, runs inside the one interactive-artifact runtime (`ui.substrate-rendering`, File 37 §9.3) at a least-authority origin in the one `Sandbox` contract (File 23), inherits File 23's per-runtime CPU, memory, process, network, filesystem, and cleanup limits, and uses the restricted host bridge: the runtime may read and write its own contribution state (with consent, §10.4), emit `Custom { namespace: "contribution.runtime", name, payload }` events, and request its own state be persisted, and has no other access — no network, no other files, no block store, no agent, no secrets — unless the user explicitly grants it (File 22, File 23). Contribution-runtime events carry the contribution instance id, the source-qualified contribution identity, source/plugin identity, and rendered substrate references as envelope cross-references or payload fields; they are sensitivity-defaulted, carry no authority, are never read as instruction, and cannot impersonate system events or trigger security-category hooks (File 10 §8.3; `ui.substrate-rendering`, File 37 §9.3). The runtime-hint registry that selects an executable contribution's runtime backend is the settings-backed, extensible registry File 37 §9.3 names; this file introduces no new sandbox or runtime architecture.

### 9.4 Boundary

This section owns the contribution registry, the rendering dispatch, and the confined-runtime rule. File 37 owns the `RendererRegistry` and the interactive-artifact runtime; File 23 owns the sandbox; File 06 owns the approval the registration passes; File 35 owns the plugin contribution's bundle. This file owns the one contribution registry over them.

## 10. Contribution Data and Action Sources

Anchor: `customize.widget-data-action-sources`

### 10.1 Definition

A contribution's data and action sources are the governed bindings through which it reads state and exposes operations: Atlas-native substrate, workflow and automation output, capabilities and commands, external APIs, user-approved secrets and environment values, and plugin-defined sources (the charter's §7 set). The load-bearing rule is that a contribution's data and action access is governed by the same permission, secret, egress, and extensibility boundaries as the rest of the system; a contribution is never a hidden backdoor around the system boundaries (the charter's §7 rule).

### 10.2 Data Sources

A contribution binds its data through one of the governed sources, event-first:

- **Atlas-native substrate** — a projection of the one block pool (`block.cross-surface-interoperability`, File 08 §12), the entity layer (`artifact.per-surface-projections`, File 09 §17.2), the world model and live state (`world.exposure-consumption`, File 18 §11), the memory substrate (`memory.consequences-for-later-specs`, File 14 §22), the context budget (`context.consequences-for-later-specs`, File 13 §22), the run presentation (`run.presentation`, File 04 §25), or the version graph (File 11). The contribution subscribes to the change events of the facts it reads (`ledger.event-stream`, File 10 §5; `world.state-change-events-reactivity`, File 18 §12) and re-renders event-first; it never polls. A periodic refresh is a flagged, configurable fallback only where a source emits no change events (`ui.presentation-projection`, File 37 §3.2; `core.event-first-by-default`, File 01 §7.15).
- **Workflow and automation output** — the automation observability and consumption contract (`automation.observability`, File 33 §17.3) and the run-history projection; a contribution that surfaces scheduled or background output reads that contract and never becomes the firing or run truth (§2.8).
- **External APIs and connectors** — through the one connector layer (`connector.*`, File 36) under egress governance (`security.egress-governance`, File 22 §11); a contribution makes no out-of-band network request.
- **Secrets and environment values** — by vault reference only (`secret.backend-boundary`, File 22 §4; `settings.secret-boundary`, File 15 §10's `SecretRef`); a raw secret never reaches a contribution's renderer, and a contribution that needs a credential references it by id, the secret resolved on the backend (`infrastructure/configuration.md` realized).
- **Plugin-defined sources** — registered by a plugin through its owning registry (§15), governed identically to a built-in source.

### 10.3 Action Sources

A contribution's action is a presentation of a `Capability` (`capability.capability`, File 05 §2.1): the contribution declares which capabilities it surfaces as controls, and an invocation resolves through the control rail (File 26) and is gated, per call, by `policy.effective-tier-resolution` (File 06 §4). Action availability the contribution presents is advisory; invocation re-resolves capability availability, touched resources, invoker context, policy, leases, source trust, and sandbox constraints before dispatch. A stale action returns a typed unavailable or approval-required result, never a silent execution. A contribution's action that runs an automation resolves to `automation.run_now` (File 33 §19); one that runs a workflow resolves to the `workflow.*` surface (File 34); one that navigates resolves through the navigation target contract (`ui.shell`, File 37 §4.4). A contribution invokes no operation out of band and grants no authority of its own; its available actions are the available-capability list the world model computes for its scope (`world.state-aware-capability-availability`, File 18 §9).

### 10.4 Contribution Persistent State

A contribution that needs durable per-instance state (a display preference, a last-fetched value) persists it as scoped substrate, not a private store: per-contribution configuration is a settings/customization record (§12), and per-instance runtime state requiring persistence uses a scoped, consent-gated storage scope (per contribution instance, per contribution kind, per workspace, or global), the same scoped-artifact-storage discipline the interactive-artifact runtime uses (`ui.substrate-rendering`, File 37 §9.3). Cross-session persistence of an interactive contribution's state requires explicit user consent and is stored as substrate, never a private UI store.

### 10.5 Rule

- A contribution's data and action access goes through the same capability, policy, secret, egress, and sandbox boundaries as every other consumer; a contribution is not a privileged path and not a backdoor (the charter's §7 rule). Every action revalidates at invocation time, even if the contribution previously presented the action as available.
- A contribution binds data event-first and never polls except as a flagged fallback; it presents live and cached data distinctly and shows a typed staleness or unavailability state, never a silent stale value (`ui.streaming-presentation`, File 37 §10; `world.observation-state-update`, File 18 §8.5).
- A contribution renders `Secret`-classified content masked, never raw, and a raw secret never reaches the renderer or any shareable, cached, exported, or synced state (`secret.backend-boundary`, File 22 §4; `ui.presentation-projection`, File 37 §3.2).
- A contribution that renders external, web, connector, model, or tool-returned content treats it as data, never instruction, and carries its authority class and sensitivity (`security.untrusted-content`, File 22 §12; `ui.presentation-projection`, File 37 §3.3).

### 10.6 Boundary

This section owns the contribution data/action binding contract. ## 11. The `CustomizationPolicy` Realization

Anchor: `customize.customization-policy`

### 11.1 Definition

The customization-policy realization is the concrete slot and placement model that fills the `customization_policy` `worksurface.views-presets` (File 25 §7.4) declares. File 25 declares which kinds of customization a surface permits, the maximum extension density or safety bound, and whether user, plugin, or AI placement is allowed per kind; this file owns which insertion points exist and how placement resolves — the slot vocabulary named by role, the placement-compatibility contract, the per-surface customization-freedom variation, and the bound enforcement.

### 11.2 The Slot Model

- A slot is a declared, customizable insertion point in a presentation composition (`ui.layout`, File 37 §5), bound either to a presentation role (`ui.shell`, File 37 §4.2) or to a declared area of a surface's presentation unit. The canonical slot classes are named by the role they serve — control entry, inspection, produced-output access, ambient status, and attention — together with the customizable areas of a surface's declared presentation units and the per-unit extension areas the surface permits. Each slot declares the contribution and unit kinds it accepts, its declared capacity and its density bound expressed as §7.5 requires, and the placement sources it allows (user, plugin, AI). A slot is a policy-owned placement identifier (`worksurface.persistence-locality`, File 25 §16.1), referenced by saved compositions and contribution placements. A slot never removes the reachability its role guarantees: a customization of the control-entry slot leaves control entry reachable regardless of what holds primary focus (`ui.shell`, File 37 §4.2), and what a slot class binds to is the medium's own (realized in the windowed-desktop profile as its customizable regions, §11.6).
- Placement is compatibility-checked: a contribution or presentation unit may be placed in a slot only if the slot accepts its kind, the placement is within the slot's density and safety bound, and the placement source is permitted by the surface's `customization_policy` for that kind. An incompatible placement is rejected with a typed diagnostic; the customization layer never forces an incompatible placement.

### 11.3 Per-Surface Customization-Freedom Variation

Customization freedom varies by surface (the charter's §4.2/§13 rule): a surface's `customization_policy` expresses its freedom as the customization classes it permits, the sources it permits per class, and the bounds it declares per slot, and never as an unmeasured degree. The customization layer enforces the declared policy uniformly: a surface that declares no contribution slots hosts no contributions; a surface that declares a broad slot with a large declared capacity permits broad placement within its bounds. The default presentation is clean and complete without any customization (`core.product-thesis`, File 01 §1; `ui.interaction-models`, File 37 §7.3's progressive-disclosure rule); customization adds depth where the surface permits it.

### 11.4 Who May Place and the Bounds

- The `customization_policy` declares, per customization kind and per slot, whether the user, a plugin, or the agent may place; this file enforces it (§14, §15). A plugin's default placement is a proposal resolved through settings and the policy, never a forced placement (§15). The agent places only through the AI-assisted flow (§14), policy-gated and reversible.
- The maximum extension density or safety bound a surface declares is enforced at placement: a slot's contribution count, the customization density, any per-kind safety bound, and the aggregate concurrent active-contribution-runtime budget are caps the placement check respects, surfaced when reached, never silently exceeded — this file owns that placement rule. Customization density is a computed quantity, not a judgement: it is a slot's occupancy against that slot's declared capacity, and an aggregate density is the occupancy of a scope's slots against their declared capacities. A contribution that is currently presented and running consumes the aggregate runtime budget; one that is not currently presented does not, unless it keeps background work alive under an explicit policy (realized in the windowed-desktop profile as an off-screen frozen widget, §11.6). Bounds are settings, not hardcoded limits (`settings.settings-over-constants`, File 15 §13).

### 11.5 Boundary

This section owns the slot and placement realization. File 25 owns the `customization_policy` declaration and the per-surface variation it permits; File 37 owns the roles and the composition the slots sit in; File 18 owns the live placement state. This file realizes the policy as slots and placement.

### 11.6 Windowed-Desktop Profile

Windowed-desktop profile (`ui.frontend-profile`, File 37 §1.3); binds only a session declaring `desktop.windowed`.

Realizes: §11.2. The canonical slot classes bind to the customizable shell regions — the inspector dock, the artifact navigator, the command rail, and the status and notification regions — together with the customizable areas of a surface's declared panels and the per-panel extension regions the surface permits. A slot's capacity and density bounds are expressed as its size and density bounds in the viewport's own units.

## 12. Contribution Placement, Configuration, and Per-Instance State

Anchor: `customize.widget-placement`

### 12.1 Definition

A contribution placement is a `ContributionInstance` — a placed, configured occurrence of a contribution kind in a slot. Placement, per-instance configuration, multi-instance behavior, and the instance lifecycle are this section's.

### 12.2 The Contribution Instance

A `ContributionInstance` carries: a stable instance id, the source-qualified contribution id and `PresentationContributionKind`, the slot and scope it is placed at, its `PresentationProminence` and the share of the slot's declared capacity it occupies (`world.surface-state`, File 18 §5.3), its position in the composition's ordering for that slot (§7.2), its typed per-instance configuration (validated against the contribution's configuration schema, §8.3), its data-source binding instance (§10), revision, `source_ref`, `provenance_refs`, and dependency references. A `ContributionInstance` is a settings/customization record (§3) referenced by the `SavedComposition` it belongs to; multiple instances of the same contribution kind may be placed independently, each with its own configuration, data binding, and refresh state (the multiple-terminal-sessions analog). A contribution instance self-registers its live state to the world model when it is activated — when it enters its context's composition — and on focus and content change, and unregisters when it is deactivated (`world.observation-state-update`, File 18 §8.1; §2.5).

The record's identity is its instance id, unique within the scope it is placed at; its ordering scope is the slot it occupies, where the composition's declared ordering fixes its position and no ordering holds across slots. Its locality is the customization record's (§18.1). Every vocabulary it writes durably closes at its owning file — `PresentationContributionKind` (§8.4) and `PresentationProminence` (`world.surface-state`, File 18 §5.3) — while the slot identifier is policy-owned and open (§11.2). It is retained until it is removed, and removal preserves its configuration as an orphaned customization record reclaimable on re-placement (§12.4). Its guarantee is bounded honestly: the record fixes what is placed, where, and at what prominence and occupancy, and never how much of the medium the presentation takes, which the presenting session resolves.

### 12.3 Configuration

Per-instance configuration is a settings/customization record resolved through the canonical cascade (`settings.scopes-profile-contexts-overlays`, File 15 §5.2); a contribution declares its configuration schema with typed defaults and declarative constraints (`settings.types-semantics-constraints`, File 15 §4) — the data source it binds, its presentation options, its density, its refresh behavior — and the customization surface renders configuration from that metadata (`settings.consequences-for-later-specs`, File 15 §21). Configuration follows progressive disclosure: essential options by default, advanced configuration revealed on demand (`ux-input/design-principles.md` realized). A contribution's configuration is overridable per instance and may carry a per-instance token overlay (§5.6), of which an accent is one family and never a separate field.

### 12.4 Lifecycle

- A contribution is added (placed into a slot, compatibility-checked, §11.2), moved (re-placed into another compatible slot), configured (its per-instance settings changed), enabled or disabled (withdrawn from presentation without losing configuration and refresh state — the withdraw-does-not-destroy rule), and removed (unplaced, its configuration preserved as an orphaned customization record reclaimable on re-placement, never destroyed, `settings.setting-definition` File 15 §3.4). Every operation is a `customize.contribution.*` capability (§19) and a settings/customization write, reversible and resettable (§3.2).
- A contribution that is disabled or not currently presented suspends its expensive presentation and data-refresh work while preserving its durable subscription and configuration (`ui.streaming-presentation`, File 37 §10.2's unattended-presentation rule; the persisted-versus-ephemeral discrimination); presenting it again re-syncs against the substrate without a gap. A contribution instance whose underlying contribution kind, data source, or capability becomes unavailable renders the typed placeholder and is not invocable, never a crash (§9.2).

### 12.5 Boundary

This section owns the contribution instance, its configuration, and its lifecycle. §11 owns the slot the instance is placed in; §10 owns the data binding; File 15 owns the configuration persistence; File 18 owns the live instance state. This file owns the placed contribution over them.

### 13.1 Definition

It is the realization of the charter's §5 requirement that the agent understand the interface structurally rather than from screenshots or raw coordinates.

### 13.2 Rule

- The structural projection is over `world.surface-state` (File 18 §5) — the active surface, the presented units, the primary unit, the focus target, selection, available capabilities, and `UiMode` File 18 holds and the presentation layer self-registers (`ui.world-state-integration`, File 37 §18) — plus this file's customization-facing extension: the active theme and ambient variant, the active composition, the active interaction-model lens (`ui.interaction-models`, File 37 §7.2), the slot model and its occupancy, the placed contribution instances and their kinds and configurations, and the available customization actions. The projection is policy-filtered for the consumer: it includes ids, roles, relationships, safe summaries, and redacts or omits fields according to File 15 agent exposure, File 06 policy, File 10 sensitivity, and File 22 secret rules. External, tool, connector, model, or plugin-rendered data keeps its authority class and source attribution. The agent reads this structured projection; it never scrapes the rendered presentation (`world.chosen-model`, File 18 §1; `perception.tiered-sensing`, File 19 §5.4).
- The projection is semantic and relational, not coordinate-based: it describes roles, presentation units, contributions, and slots and their containment, ordering, prominence, focus, selection, and occupancy relationships, and their primary-versus-secondary roles. A medium's spatial relations are one expression of containment, ordering and prominence and are carried as that, never as the relation itself (§13.4). Coordinates may exist as secondary metadata, but they are never the primary interface for reasoning (the charter's §5.2/§5.3 rule). A presentation unit, contribution, or control that cannot be represented structurally — that exposes no role, label, interaction kind, and state relationship sufficient for this projection, the world model, the rails, and assistive technology — is invalid (`worksurface.explicit-rejections`, File 25 §20; `ui.accessibility`, File 37 §14; §8.3). This is the same dual-purpose structural layer accessibility consumes (`codex_recommendations.md` §10.6 realized).
- The projection is bounded and event-first: it is compact (identifiers, roles, relationships, and short summaries, not resource bodies, `world.surface-state` File 18 §5.2), is bounded by a declared, settings-carried size budget with a stated default, and, when the structure exceeds that budget, elides typed named parts — the least prominent occupancy first — declaring what it elided and how the elided part is fetched, never truncating silently. It is refreshed event-first on the world-model and customization change events. It is the substrate the AI-assisted customization flow (§14) reads to inspect the current configuration and the explainable context the customization surface renders.

## 14. AI-Assisted Customization

Anchor: `customize.ai-assisted`

### 14.1 Definition

AI-assisted customization is the agent's participation in shaping the presentation — suggesting contributions, rearranging compositions, simplifying crowded presentations, creating workflow-oriented or per-use-case views, and personalizing startup compositions — in response to a natural-language request or its own observation, through the same customization layer the user uses. It is the realization of the charter's §10 requirement and the `worksurface.views-presets` (File 25 §7.4) capability-flow rule.

### 14.2 The One-Path Rule

AI-assisted customization uses the same paths as manual customization (`core.extension-integrity`, File 01 §7.10). There is no agent-only customization API, no agent-only customization store, and no separate AI-customization pathway. The agent reads the structural projection (§13) and proposes through the same `customize.*` capabilities the user invokes (§19); a natural-language customization request — one that names a target, a role or slot, and a desired composition — resolves through the control rails (`controlrail.input-resolution`, File 26 §4) into those capabilities. In a graphical frontend such a request reads "make this screen simpler," "show weather and my tasks here," "put my paper feed near the research area," or "make a dashboard for my morning workflow"; the wording is one medium's, the resolution is not. The agent customizes only what the surface's `customization_policy` permits for the AI source (§11.4).

### 14.3 The Customization Flow

An AI-assisted customization is a capability flow (`worksurface.views-presets`, File 25 §7.4):

1. **inspect** — the agent reads the policy-filtered structural projection (§13) and the current customization records through a `ReadOnly`, agent-invocable inspect capability (§19); it reasons over the structure, never coordinates
2. **propose** — the agent produces a typed customization proposal: a diff over the composition, contribution placements, theme, or configuration, carrying the base customization revision or resolved-state hash and a `CustomizationPreview` the user can see before it applies. The proposal is data, not an applied change; generating a proposal (including an AI-generated composition) is never a silent apply
3. **gate** — the proposal passes policy (`policy.effective-tier-resolution`, File 06 §4) and, for an agent-initiated contribution, the proposal-first source-approval flow (`policy.source-approval-flow`, File 06 §9); the customization-preview and confirm dialog render through the approval/elicitation contract verbatim (`policy.approval-ui-surface-contract`, File 06 §13; `ui.dialog-elicitation-notification`, File 37 §12), never a parallel approval shape
4. **commit** — on approval, the change revalidates its base revision or resolved-state hash, applies as a reversible customization record, and takes a snapshot of the prior state before the commit (§3.2, §17.3), so it can be reverted in one operation; a stale base returns a typed conflict and repair path, not an overwrite; the commit is a settings/customization write and, where it touches versioned state, a version-graph sibling (File 11)
5. **record provenance** — the change records `source_ref` and `provenance_refs` (the request or observation that prompted it, the proposal, and the actor) so the user can see why a customization was made and revert it (`core.evidence-provenance`, File 01 §7.12; the "why is this active?" explainer, §17.1)

Direct mutation of core UI code, a surface manifest, or runtime state outside this flow is invalid (`worksurface.views-presets`, File 25 §7.4; the charter's §11.1 rule).

### 14.4 Reversibility and the No-Trap Rule

Every AI-made customization is reversible and removable; the user is never trapped by an AI-made UI change (the charter's §4.4 rule). A reset restores the prior or default state, and the snapshot-before-commit (§14.3 step 4) makes the revert exact. The bounds on agent self-customization are settings, not hardcoded limits (`settings.settings-over-constants`, File 15 §13), and their canonical defaults protect: agent-initiated customization defaults to the proposal-and-approval posture rather than to automatic application, and the maximum number of active agent-made customizations defaults to a declared finite bound rather than to unbounded. An explicit user choice is what changes either, and a changed value is itself a recorded, reversible customization setting.

### 14.5 Boundary

This section owns the AI-assisted customization flow. §13 owns the projection it inspects; §19 owns the capabilities it proposes through; File 06 owns the policy and approval it passes; File 11 owns the snapshot it commits against; File 26 owns the rail it resolves through. This file fixes that AI customization is the one customization path.

## 17. Customization Safety, Reversibility, and the Deleted-Field Consequence

Anchor: `customize.safety-reversibility`

### 17.1 Reversibility

Every customization — a theme, a composition, a contribution placement, a configuration, a per-profile default, an AI-made change — is removable, reversible, and resettable (`core.non-destructive-by-default`, File 01 §7.13; the charter's §4.4 rule). A reset restores the default or profile-default; the prior value survives as a version-graph or settings sibling (§3.2); and the user is never trapped, whether the change was made manually or by the agent (§14.4). There is no destructive customization without explicit confirmation, and no AI customization that cannot be reverted in one operation. The "why is this active?" inspector is a uniform projection over every customization source — user, built-in seed, plugin default, profile seed, import, and AI proposal — rendered through File 37's inspection presentation before revert or repair.

### 17.2 Policy and Source Gating

A customization is gated by the surface's `customization_policy` (§11.4) and, where it touches policy-relevant state or comes from a plugin or the agent, by `policy.effective-tier-resolution` (File 06 §4) and the source-approval flow (`policy.source-approval-flow`, File 06 §9). A plugin or AI customization that exceeds its permitted kind, slot, source, or density bound is rejected with a typed diagnostic, never silently applied. A customization never pierces a `permission_floor` (`policy.permission-floor`, File 06 §7) and never grants authority a capability could not declare.

### 17.3 Snapshot Before Commit

A customization commit takes a snapshot of the prior customization state before applying, so the change is exactly revertible (§14.3). The snapshot is a version-graph or settings sibling (File 11; `settings.logical-persistence`, File 15 §17), not a parallel undo store; reverting a customization is the same operation as switching to any prior customization state. Commits are revision-safe: compare-and-commit uses the base revision or resolved-state hash and fails with a typed conflict if the target changed between preview and apply.

### 17.4 The Deleted-Field Consequence

The customization layer carries no participation-level, autonomy-mode, persona, agent-mode, plan-versus-build-mode, or phase field, in any form, at any layer. This is the unanimous, most-evolved canonical position (`core.interaction-shapes`, File 01 §2.2; `core.explicit-rejections`, File 01 §8; `world.surface-state`, File 18 §5.5; `worksurface.no-autonomy-field`, File 25 §13; `controlrail.no-autonomy-field`, File 26 §17; `settings.explicit-rejections`, File 15 §20; `ui.interaction-models`, File 37 §7). The customization layer renders the *consequences* the deleted fields once described:

- a **per-profile or per-use-case "mode"** is rendered as which theme, density, composition, contributions, and view preset are active — a `SavedComposition` plus token and per-profile-default state — never a backend mode field (§16, §5.8)
- a **"personality" preset** is rendered as a Memory or instruction preset governed by File 14 — a starting template the user edits — never a customization-layer autonomy field (§16.2)
- **autonomy** is rendered as the approval posture the policy layer resolves (`policy.effective-tier-resolution`, File 06 §4) and the pending approvals it raises — surfaced as the consequence of policy, never as a customization dial (`ui.interaction-models`, File 37 §7.3)
- **progressive disclosure** is rendered as which roles are bound, which presentation units and contributions are present and at what prominence, and which density applies — reachable by customizing more, never a mode (`core.product-thesis`, File 01 §1; `ui.interaction-models`, File 37 §7.3)

There is no participation-level, autonomy-mode, or persona customization event because there is no such field to change (§20).

### 17.5 Boundary

This section owns the safety, reversibility, and deleted-field rules. File 06 owns the policy and floor; File 11 owns the snapshot; File 14 owns the memory/instruction preset; Files 01/25/26/37 fix the deletion at their layers. This file fixes that customization is reversible and carries no autonomy field.

## 18. Persistence, Locality, and Portability

Anchor: `customize.persistence-locality`

### 18.1 What Is Durable, Device-Local, and Portable

- **Durable and (where its owner syncs) syncable** — the customization records: saved compositions, contribution placements and configurations, the active theme and ambient-variant selection, the information-density and information-scale preferences, per-profile UI defaults, and user-authored and plugin-contributed themes and contributions. They carry source/provenance references, revisions, and dependency closures; persist as settings/customization records and substrate (`settings.logical-persistence`, File 15 §17; `storage.consequences`, File 20 §18); and follow their declared locality (`settings.locality-sync-export`, File 15 §18): saved compositions, theme selection, density, and per-profile defaults are `Syncable` user preferences so a user's customization follows them across devices (`portability.what-replicates`, File 21 §5.3).
- **Device-local and rebuilt** — the first-presentation token cache (§6.2), device-bound presentation-context placement within its host environment (`ui.shell`, File 37 §4.5; `settings.locality-sync-export`, File 15 §18's `DeviceLocal`), physical presentation measurements, and device-bound contribution runtime state. These are device-local projections rebuilt per device; their loss is a rebuild, never a loss of a customization record.
- **Portable** — saved compositions, themes, contribution configurations, and view presets export and import over the `PortablePackage` (`portability.export-bundle`, File 21 §10); portable composition identity is the semantic composition and its dependency closure, never a profile's realization payload (§7.2). A plugin-sourced theme or contribution re-resolves and re-approves locally on import (imported trust is inert, `security.trust-model`, File 22 §9.7; `plugin.distribution`, File 35 §11.5), and an unresolved reference imports as an unavailable record with a typed diagnostic, never a silent substitution.
- **Durable, `Syncable`-eligible, and `Sensitive` by default** — the copy-override records (§3.4). User-authored text is `Sensitive` by default, so it rides the user's existing sensitive-sync consent instead of syncing silently; conflict identity is per `(target, exact locale, scope)` rather than over the override collection, concurrent writes from one base become typed settings conflicts with neither revision auto-winning and no wall-clock rule selecting a winner, and a reset is the causally descendant unset revision, not a deletion (File 21 §6.3). They travel in the `PortablePackage` as a selectable subset carrying provenance, target dependencies, and contract fingerprints, with typed gaps for what does not resolve; a `SharePackage` carries them only on explicit `Sensitive` opt-in and a `RecoveryArchive` after its typed `Sensitive` confirmation (`portability.export-bundle`, File 21 §10); import stages and validates them, preserves unresolved records inertly, and installs no missing plugin or locale pack.

### 18.2 Security and Hashing

A customization record, export, or sync stream contains no raw secret: a contribution's credential is a vault reference (`secret.backend-boundary`, File 22 §4; `settings.secret-boundary`, File 15 §10), never inline; raw secrets never sync, export, or materialize (`portability.sensitivity-egress`, File 21 §12). A customization record honors the sensitivity classification of what it renders in screenshots and exports (`ledger.sensitivity-aware-persistence-retention`, File 10 §10). Every hash a customization record relies on is computed over a declared `CanonicalEncoding`, never physical storage bytes (`core.canonical-hash`, File 01 §7.14); this file defines no new canonical hash and inherits each from its owning file.

### 18.3 Boundary

This section owns the durable-versus-device-local-versus-portable split for customizations. File 15 owns the settings persistence and locality; File 20 owns storage; File 21 owns sync and the portable bundle; File 22 owns the secret boundary and the import re-approval. This file classifies the customization records.

## 19. The `customize.*` Capability Surface

Anchor: `customize.capability-surface`

### 19.1 Closed Canonical Capabilities

The customization layer exposes its operations as built-in capabilities declared per `capability.declaration` (File 05 §3), flowing through the standard call pipeline (`run.call-pipeline`, File 04 §8.2) and policy (File 06). These compose with, and do not duplicate, the presentation capabilities File 37 declares (`ui.capability-surface`, File 37 §20, which routes composition, view-preset, density, and theme-reference writes here). The canonical families:

- **theme** — `customize.theme.list` / `customize.theme.get` / `customize.theme.preview` (`ReadOnly`, `ConcurrencySafe`); `customize.theme.set(theme_id, ambient_variant, scope, base_revision)` (a settings/customization write); `customize.theme.install(source)` / `customize.theme.author(definition)` (user-only, source-approval-gated, composed with File 35)
- **composition** — `customize.composition.list` / `customize.composition.get` (`ReadOnly`); `customize.composition.preview(operation_or_diff)` (`ReadOnly`); `customize.composition.save` / `customize.composition.switch` / `customize.composition.rename` / `customize.composition.reset` / `customize.composition.duplicate` / `customize.composition.set_default` (settings/customization writes carrying a base revision or resolved-state hash)
- **contribution** — `customize.contribution.list_kinds` / `customize.contribution.get` / `customize.contribution.list_instances` (`ReadOnly`); `customize.contribution.preview(operation_or_diff)` (`ReadOnly`); `customize.contribution.add` / `customize.contribution.move` / `customize.contribution.configure` / `customize.contribution.enable` / `customize.contribution.disable` / `customize.contribution.remove` (settings/customization writes carrying a base revision or resolved-state hash and slot-compatibility-checked); `customize.contribution.register` (a custom contribution kind, source-approval-gated, composed with File 35)
- **presentation preference** — `customize.preference.set(key, value, scope)` for the density, information-scale, and other presentation preferences this file names, each declared by the medium whose presentation it varies (composed with File 15, not duplicated)
- **copy** — `customize.copy.list_targets` / `customize.copy.list_overrides` / `customize.copy.get_effective` / `customize.copy.preview` (`ReadOnly`, `ConcurrencySafe`); `customize.copy.set(target, locale, scope, template, base_revision)` and `customize.copy.reset(target, locale, scope, base_revision)` (settings/customization writes carrying a base revision, the reset writing the causal unset revision §3.4 requires). A write to a `safety_class`-protected target, and every agent-, import-, or plugin-originated write, requires the preview form and the policy gate; the agent invokes the same capabilities under the same policy, and override text is attributed display data, never instruction. Bulk editing is an atomic transaction over the individual records, never a monolithic map write
- **AI-assisted flow** — `customize.inspect` (the policy-filtered structural projection and current customization records, `ReadOnly`, agent-invocable, §13); `customize.propose(diff, base_revision_or_hash)` (produce a typed customization proposal with a preview, `ReadOnly`, agent-invocable, never applies, §14); `customize.apply(proposal_id, base_revision_or_hash)` (commit an approved proposal after revision revalidation, policy-gated, snapshot-before-commit); `customize.revert(customization_ref)` (revert to a prior customization state)
- **profile defaults** — `customize.profile_defaults.get` / `customize.profile_defaults.apply` (apply a profile's UI defaults as profile-layer defaults at onboarding or on profile switch, composed with File 15 and File 35)

### 19.2 Rule

- The customization capabilities are built-in declarations under the one registry, carrying the touched-resource and tier metadata their effects warrant (the `setting` and presentation resource classes, `capability.touched-resources` File 05 §6; `settings.settings-capabilities` File 15 §16). Reads are `ReadOnly`; composition, contribution, theme-selection, and preference writes are settings/customization writes with the effective tier resolved from touched resources and policy; theme or contribution install and registration are user-only and source-approval-gated; `customize.inspect` and `customize.propose` are `ReadOnly` and agent-invocable but never apply; `customize.apply` is gated and snapshot-backed. Every nontrivial durable customization write has a preview/proposal form; a direct-manipulation preview may be presented transiently, but committing it still writes through the revision-safe capability path (realized in the windowed-desktop profile as a direct-manipulation gesture that renders before it commits, §7.7).
- Every customization capability is the single source for all its invocation paths — every control-rail entry class the client session declares, directly or through the profiles it declares (`controlrail.registry`, File 26 §14.2), the agent tool, the automation trigger, the external protocol (`core.extension-planes`, File 01 §6.14); the customization layer declares no out-of-band customization operation. The agent invokes these capabilities the same way the user does — through the one capability system under policy — so AI-assisted customization and manual customization are one path (§14). Custom customization operations register through the proposal-first mechanism (`capability.runtime-mutation`, File 05 §16.2) and never bypass policy.

### 19.3 Boundary

This section names the customization capability families and effect classes. File 05 owns the capability contract; File 06 owns tier resolution and approval; File 07 owns surfacing; File 04 owns execution; File 15 owns the settings the writes compose with; File 35 owns the plugin install the theme or contribution install triggers. This file declares the customization capabilities as built-ins.

## 20. Events

Anchor: `customize.events`

### 20.1 Rule

- The customization layer emits its consequential customization facts as `Custom { namespace: "customize", name, payload }` events (`ledger.custom-kind-registration`, File 10 §4.3) through the one event bus and ledger with the canonical envelope (`ledger.event-envelope`, File 10 §5.2): a theme changed or installed, a saved composition saved, switched, renamed, reset, duplicated, or set as default, a contribution added, moved, configured, enabled, disabled, or removed, a copy override set or reset, a customization proposed, applied, or reverted, and per-profile UI defaults applied. Each declares its payload schema, cross-reference keys, default sensitivity, retention, and owner per File 10. Contribution runtime events are `Custom { namespace: "contribution.runtime", name, payload }`, carry no authority, and are distinct from customization facts. Live surface-state changes (presentation-unit and contribution registration, focus, selection, mode) are owned by `world.state-change-events-reactivity` (File 18 §12) and emitted by the world model from the presentation layer's self-registration; this file consumes them and does not duplicate them. Presentation facts the frontend owns (a role bound, a view preset applied) are File 37's `ui` events; this file emits only its own customization facts.
- A customization event is live coordination; a consequential customization fact (a composition saved, a theme installed) is committed to the durable record by the settings or registry path, never inferred from event observation (`core.durable-history-transient-coordination`, File 01 §7.3). High-frequency transient customization activity (a direct manipulation in progress, an arrangement change in flight) is transient by default and not durable unless an explicit save commits it. There is no participation-level, autonomy-mode, or persona event because there is no such field (§17.4). Security-relevant customization facts — a theme or contribution installed from an untrusted plugin, a customization that touches policy-relevant state — carry the source and trust attribution File 35 fixes and default to the appropriate sensitivity.

### 20.2 Boundary

This section reserves the `customize` event namespace and declares customization-fact events only. File 10 owns the envelope, delivery, sensitivity, and custom registration; Files 18 and 37 own the live-state and presentation events this file consumes; File 35 owns the contribution events. This file emits through the shared bus.

## 21. Settings

Anchor: `customize.settings`

### 21.1 Rule

- Customization behavior is configurable through the one settings system (`core.settings-system`, File 01 §6.8; File 15); this file names the dimensions, the settings system owns the cascade and storage. Customization settings are namespaced keys resolved through the standard cascade (`settings.scopes-profile-contexts-overlays`, File 15 §5.2); the customization layer is not a durable settings scope, and per-customization variation is namespaced keys plus profile layers, never a new scope.
- The canonical customization settings dimensions include at least: the active theme and ambient variant (composed with File 37's theme-reference dimension), the information-density level and the medium's information-scale preference, the reduced-motion and maximum-conformance preferences (composed with File 37's accessibility dimensions); the default and startup `SavedComposition` or `ViewPreset` per surface and per scope, and whether saved compositions apply; the per-slot default contribution set and per-contribution-instance configurations; the per-surface customization-freedom and bound overrides the `customization_policy` permits (composed with File 25), including the aggregate active-contribution-runtime budget; the AI-assisted-customization enablement and bounds (whether the agent may inspect and propose customizations, the maximum active agent-made customizations, the default approval posture for agent-initiated customization); the plugin-UI-placement and theme or contribution install policy (composed with File 35); the token-cache and theme-switch behavior; and the per-profile UI default bundles (composed with File 15 profiles and File 35 bundles).
- Each customization setting declares its locality (`settings.locality-sync-export`, File 15 §18) — saved compositions, theme selection, density, and per-profile defaults are syncable user preferences; device-bound presentation-context placement and the token cache are device-local — and its agent exposure (`policy.agent-exposure-policy-settings`, File 06 §16.4; `settings.agent-exposure`, File 15 §8), so the agent cannot read or change security-sensitive customization configuration without policy. No customization behavior with meaningful variation is a hardcoded constant (`core.typed-configuration-failure`, File 01 §7.6; `settings.settings-over-constants`, File 15 §13).

### 21.2 Boundary

This section names the customization settings dimensions and their layer. File 15 owns the settings object model, the cascade, locality, agent exposure, and profiles; Files 25, 35, and 37 own the per-substrate settings the customization layer composes with. This file names the customization-relevant dimensions.

## 22. Explicit Rejections

Anchor: `customize.explicit-rejections`

The following are architecturally invalid for any later or per-surface spec:

- **A private customization store, runtime, or parallel persistence** — every customization is a settings/customization record persisted and resolved through the one settings substrate and rendered by File 37's composition model and registries; no frontend-local storage mechanism is a settings store, no per-surface customization config file is a live source of truth, and there is no parallel customization persistence (§3; `settings.explicit-rejections`, File 15 §20; `ui.renderer-boundary`, File 37 §16.4). The single device-local first-presentation token cache is a rebuildable projection, not a store (§6.2).
- **A parallel renderer table, theme table, contribution table, or composition model** — there is one `RendererRegistry` (File 37), one `ThemeRegistry`, one `ContributionRegistry`, and one composition model; a surface, contribution, or plugin contributes through them, never a parallel rendering path, theme store, contribution store, or composition model (§5.3, §9.2; `ui.explicit-rejections`, File 37 §23; `worksurface.explicit-rejections`, File 25 §20).
- **A literal bypassing the token system, a theme that fails its conformance floor presented as conformant, or a theme with styling authority** — every presentation property a renderer varies is a semantic or component token, a token whose medium declares a perceptual metric is encoded in it and relatively derivable, and a theme validates against the required-token and conformance floors; a renderer or theme that resolves a property from a literal is invalid; a theme that fails the active conformance profile is never silently presented as conformant; and a theme carries no executable content, selector- or rule-based styling authority, remote imports, or remote asset references (§4, §5.4; `ui.renderer-boundary`, File 37 §16.5; `ui.accessibility`, File 37 §14).
- **A contribution as a backdoor around the system boundaries** — a contribution's data and action access goes through the same capability, policy, secret, egress, and sandbox boundaries as every other consumer; a contribution is not a privileged path, references secrets only by vault reference, treats external content as data not instruction, and runs executable content only in the confined runtime (§10, §9.3; the charter's §7 rule; `secret.backend-boundary`, File 22 §4; `security.untrusted-content`, File 22 §12).
- **A contribution or composition that polls a substrate on a timer for live state** — contributions and customized presentations are event-first; a periodic refresh is a flagged, configurable fallback only where a source emits no change events (§10.5; `ui.streaming-presentation`, File 37 §10; `core.event-first-by-default`, File 01 §7.15).
- **A participation-level, autonomy-mode, persona, agent-mode, or phase field at the customization layer** — a per-profile or per-use-case default selects which theme, density, composition, and contributions are presented; a "personality" is a Memory or instruction preset governed by File 14; autonomy is the approval posture the policy layer resolves; the customization layer renders the consequences, never a mode field (§16, §17.4; `core.interaction-shapes`, File 01 §2.2; `core.explicit-rejections`, File 01 §8; `worksurface.no-autonomy-field`, File 25 §13; `ui.interaction-models`, File 37 §7).
- **A non-reversible or non-removable customization, or an AI customization that traps the user** — every customization is reversible, removable, and resettable, with a snapshot before commit; the user is never trapped by a customization, whether made manually or by the agent (§3.2, §14.4, §17; `core.non-destructive-by-default`, File 01 §7.13; the charter's §4.4 rule).
- **An agent-only customization API, store, or path, or a silent AI customization** — AI-assisted customization uses the same `customize.*` capabilities, registries, validation, and approval as manual customization; the agent inspects and proposes, and a proposal applies only through the policy-gated, snapshot-backed commit; there is no agent-only API, no agent-only store, and no silent apply (§14; `core.extension-integrity`, File 01 §7.10).
- **AI customization that reasons over raw coordinates as the primary interface** — the agent reasons over the semantic-relational structural projection (roles, presentation units, contributions, slots, and their relationships); coordinates are secondary metadata, never the primary interface; a presentation unit, contribution, or control that cannot be represented structurally is invalid (§13; the charter's §5 rule; `worksurface.explicit-rejections`, File 25 §20).
- **Plugin UI placement by arbitrary core-UI mutation, by load order, or as a forced placement** — a plugin contributes presentation contributions, themes, and presets through the registries and the source-approval path, its default placement is a proposal resolved through settings and the `customization_policy`, and it never edits core UI code or forces a placement (§15; `plugin.contribution-points`, File 35 §5.2; the charter's §11.1 rule).
- **A customization that exceeds the surface's `customization_policy`, slot compatibility, or density bound, or that pierces a permission floor** — placement is compatibility-checked and bound-enforced, the source (user/plugin/AI) must be permitted, and a customization never pierces a `permission_floor` or grants authority a capability could not declare (§11, §17.2; `worksurface.explicit-rejections`, File 25 §20; `policy.permission-floor`, File 06 §7).
- **Per-instance or per-plugin event namespaces for contribution runtimes** — contribution runtime events use the fixed `contribution.runtime` namespace with source and instance identity as envelope cross-references or payload fields; dynamic namespaces such as one namespace per contribution instance or plugin break File 10's registered custom-kind model and are invalid (§9.3, §20).
- **A raw secret in a customization record, export, or sync, or a customization synced as device-local-only state** — credentials are vault references, raw secrets never sync or export, and device-local customization state (the token cache, device-bound presentation-context placement) never syncs as authority (§18; `secret.backend-boundary`, File 22 §4; `portability.sensitivity-egress`, File 21 §12).
- **A hardcoded customization behavior, bound, or presentation value where meaningful variation belongs in settings** — themes, density levels, composition defaults, contribution sets, AI-customization bounds, and placement bounds are settings, not hardcoded constants (§21; `settings.settings-over-constants`, File 15 §13).

## 23. Consequences for Later Specs

Anchor: `customize.consequences-for-later-specs`

Later specs must follow these rules:

- The **per-surface specs** (27–32 and equivalent future surfaces) declare their `customization_policy` (`worksurface.views-presets`, File 25 §7.4) — which kinds of customization they permit, at which slots, by which sources, within which bounds — and this file realizes it as slots and placement (§11); they contribute their built-in `ViewPreset`s, presentation-unit kinds, and any surface contributions and per-surface token overlays through the one registries and the token system, declare no private customization store, renderer table, theme table, or contribution table, and render the deleted-field consequences (§17), never a participation, autonomy, or persona field. Their per-profile defaults are profile-layer defaults (§16).
- The **Extension and Plugin System** spec (File 35) contributes plugin contributions, themes, view presets, and presentation units through this file's `ContributionRegistry`, `ThemeRegistry`, preset library, and the `RendererRegistry`, under the bundle-granularity source approval, trust, attribution, and lifecycle it owns; this file places those contributions through the customization policy and the slot model, treating a plugin-sourced contribution identically to a built-in of the same kind (§15).
- The **Automation and Triggers** spec (File 33) and the **Workflows, Templates, and Reuse** spec (File 34) own the firing, run, and execution truth their contributions surface; a contribution that displays their output reads their observability and consumption contracts and the run-now and enable/disable controls, and never becomes the firing or run truth (§2.8, §10).
- The **Quality Control and Validation** spec validates customization conformance — that every customization is a settings/customization record and not a private store, that every theme passes the required-token and contrast floors, that every contribution and control exposes structural semantics, that every customization is reversible, that the AI customization path is the one capability path, and that no participation, autonomy, or persona field is reintroduced — through the registration validator and event and capability hooks, not a separate pipeline.
- The **Telemetry, Logging, and Observability** spec and the **Evaluation and Benchmarking** spec consume the customization events and the structural-understanding projection; they introduce no parallel customization-state store and honor the sensitivity and attribution of customization facts (§20).
- The **Runtime Infrastructure and Lifecycle** spec orchestrates the pre-presentation token resolution and the customization-record load around the storage lifecycle, the device-local rebuild of the token cache and the customization projections, and the registration of built-in and plugin contribution renderers and themes in the startup phase order; it places no parallel customization runtime and persists no customization state across sync that §18 declares device-local.
- The **Packaging, Platform, and Distribution** spec (File 43) owns the installer, the auto-updater, the platform window-decoration and tray mechanics, the sidecar lifecycle, the concrete pre-presentation token-resolution mechanism, and the bundling of the ship-with themes and plugins into the installer image; this file owns the theme, contribution, composition, and per-profile-default declarations that spec distributes and the token-cache contract.
