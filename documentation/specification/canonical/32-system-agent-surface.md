# System Agent Surface

## Status

Canonical. This file defines the `SystemAgent` work surface — the specialized environment for observing, configuring, maintaining, automating, and operating the host operating system and the machine it runs on. It is the sixth and final baseline built-in per-surface specification: it fills the `SurfaceContract` that `worksurface.surface-contract` (File 25 §4) delegates to each per-surface spec, and declares the system-operation workflows, presentation units, capabilities, and policies the System Agent surface contributes over the shared substrate. It owns user-facing system-operation workflows and specialized views; it owns no private architecture. It composes blocks, capabilities, capability policy, tool surfaces, execution, the world model, perception, the version graph, workspaces, the sandbox, context, artifacts, security, providers, the ledger, and every other substrate through the same contracts every surface uses. Later canonical files may refine it, but may not contradict it.

Resolved tensions:

- **A work surface versus a cross-cutting service.** `codex_recommendations.md` §8.1 classifies "System/OS capabilities" as a cross-cutting service rather than a surface, while §8.10 says system capabilities "should exist as capability families with an inspector surface, not as a chat-only concept," because "the user needs a place to see system snapshots, pending changes, rollbacks, and active monitors." `core.current-major-area-classification` (File 01 §5.7) classifies the System Agent as a work surface with heavy substrate dependencies, and `worksurface.surface-contract` (File 25 §4.4) names `SystemAgent` a baseline `SurfaceKind`. These reconcile the same way `teacher.chosen-model` (File 30 §1) reconciled "Teacher becomes a mode and service": the System Agent is a `WorkSurface` — the inspector and control environment §8.10 describes — whose `sys.*` capability family is a borrowable cross-surface service (`worksurface.actions-declaration`, File 25 §6.3, §18). This file resolves toward the duality (§3.4): a work surface that also exposes a borrowable service face, with no per-surface system-mode field (§22). The chat-only framing is superseded.
- **A private system pipeline, task store, change log, rollback DAG, watch store, and audit log versus the shared substrate.** The source material accreted a private eleven-stage middleware pipeline and five private tables — `system_changes`, `system_watches`, `system_scheduled_tasks`, `system_rollback_dag`, and `system_audit_log` (`unit12-infrastructure.md` D12.1 sections 24–26). The canon already owns each of these: `run.call-pipeline` (File 04 §8.2) is the one capability-call pipeline, `ledger.execution-ledger` (File 10 §3) and the version graph (File 11) record changes, `artifact.provenance` (File 09 §15) is the dependency chain a multi-step rollback walks, `controlrail.chosen-model` (File 26 §1)'s `Trigger` rail plus the one scheduler own watches and scheduled tasks, and `ledger.hash-chained-audit-log` (File 10 §16.4) plus `security.audit-crypto` (File 22 §14) own the hash-chained audit log. This file resolves toward the shared substrate (§7, §9, §12, §21): the eleven-stage lifecycle is the canonical capability-call pipeline carrying the surface's contributed posture, the change history is a ledger and version-graph projection, the rollback dependency order is a provenance traversal, watches and scheduled tasks are `Trigger`-rail entries over the one scheduler, and the audit log is the canonical device-local hash-chained audit overlay. The surface introduces no private pipeline engine, task store, change log, rollback store, watch store, or audit file.
- **"No sandboxing for system operations" versus the one Sandbox at the operating-system-confined tier.** `domains/system-agent/overview.md` argues "No sandboxing for system operations — by definition, system agent needs OS access," substituting rate limiting, a blacklist, and logging. `sandbox.consequences-for-later-specs` (File 23 §21) makes the one `Sandbox` contract the single owner of process spawning, confinement, and killability, and `sandbox.isolation-tiers` (File 23 §4) defines the `OsConfined` tier for "shell, code-execution, preview, and subprocess-wrapper processes that must run native binaries but stay confined." This file resolves toward the canonical contract (§7, §14): a system operation runs at the `OsConfined` tier through the one `Sandbox`; the broad host access it needs is granted explicitly through its `FilesystemPolicy` and `NetworkPolicy`, not by escaping the sandbox; the sandbox provides killability, declared-scope enforcement, resource limits, and the elevated-helper boundary, not denial of the access the operation legitimately requires. The no-sandbox position is superseded; the rate-limiting, denied-operation, and logging substitutes map to the policy layer, stuck detection, and the audit overlay.
- **A script-based elevation strategy versus the one-shot elevated helper.** `domains/system-agent/overview.md` chooses "Approach 3 (script-based)" — generate a script, the user runs it — as the elevation strategy; `unit11c-system-agent.md` D11.SA.3 replaces it with a one-shot elevated helper that runs a single command and exits, the main process staying unprivileged. `sandbox.elevated-helper` (File 23 §11) is exactly that contract: a separate, least-privilege, lazily-installed helper over local inter-process communication with a hardcoded command allowlist, the main process never elevated. This file resolves toward the canonical elevated helper (§14): a privileged system operation crosses the elevated-helper boundary under the policy floor and typed confirmation; the surface opens no private elevation path and the script-based strategy is the retired pattern.
- **A private scheduler versus the one scheduler reached through the Trigger rail.** The source material proposes a System Agent scheduler with its own `system_scheduled_tasks` table and `system_monitor` polling subagent (`unit11c-system-agent.md` D11.SA.6, D11.SA.9), while `systems/19-scheduling-pipeline.md` §19.1 defines a general scheduler and `unit14-systems.md` D14.SP.2 fixes that "there is one scheduler" and "the System Agent's `sys.schedule.create` tool is a thin alias" over it with the action pre-filled as an agent invocation. This file resolves toward the one scheduler (§12): `sys.schedule.*` and `sys.monitor.*` are capabilities the surface declares, but the scheduling and watch evaluation are `Trigger`-rail entries (`controlrail.chosen-model`, File 26 §1) over the one scheduler and the world model; the deep scheduling, eligibility, enablement, and non-interactive-execution-safety mechanics belong to File 33 (Automation and Triggers), and this file frames the System Agent as one consumer. The surface owns no private scheduler.
- **A polling watch monitor versus event-first monitoring.** The source material backs watches with a `system_monitor` subagent that "polls every N seconds" (`unit11c-system-agent.md` D11.SA.9). `perception.triggers` (File 19 §8.1) makes capture event-first, with capture-on-interval "a flagged configurable fallback only where a source emits no change events" (`perception.triggers`, File 19 §8.2), and `core.invariants` (File 01) forbids time-based polling unless unavoidable. This file resolves toward event-first monitoring (§12): a watch on a file, directory, process, port, or service is event-first over `Perception`'s sensors and the world model; a watch on a continuous metric with no change event — processor load, memory pressure, thermal state — uses a flagged, configurable sampling interval as the explicit exception, never as the default mechanism. A threshold crossing is an event, not a poll result.
- **A separate sensitive-operation audit file versus the canonical audit overlay.** `domains/system-agent/overview.md` routes system changes to a "Debug log" because the normal event stream is "too sensitive," and `unit11c-system-agent.md` D11.SA.12 proposes a separate append-only hash-chained `~/.atlas/audit.log`. `ledger.hash-chained-audit-log` (File 10 §16.4) is the canonical device-local hash-chained audit overlay with a reserved membership, and `security.audit-crypto` (File 22 §14) owns its collision-resistant hash-chain primitive. This file resolves toward the canonical overlay (§21): the System Agent's world-affecting operations register into the reserved audit-overlay membership, recorded with sensitivity classification through the one bus; the surface opens no side-channel debug-log or private audit file, and the "too sensitive for the normal stream" framing is replaced by per-entry sensitivity classification (`ledger.sensitivity-aware-persistence-retention`, File 10 §10).
- **Per-operation undo plus a rollback DAG versus the reversal model over the shared substrate.** `domains/system-agent/overview.md` stores per-change before-state snapshots in a rollback database, and `unit11c-system-agent.md` D11.SA.13 adds a rollback DAG with Kahn's-algorithm reverse-topological traversal. The version graph owns workspace-file history and reversal (`version.consequences-for-later-specs`, File 11 §24), and `artifact.provenance` (File 09 §15) owns the dependency chain. This file resolves toward a reversal model over the shared substrate (§9): a reversible operation's before state is a committed `Observation`, its inverse is declared metadata, a rollback is a fresh inverse capability invocation, and a multi-step rollback walks the change records' dependency chain in reverse order — the provenance derivation chain, of which the reverse-topological order is the implementation. Workspace-file changes defer to the version graph; the surface introduces no private rollback store, and the Kahn's-algorithm detail is implementation, not canonical body.
- **Windows-primary versus cross-platform-first-class.** `domains/system-agent/overview.md` frames "Initial focus: Windows (primary)" with macOS and Linux "future." `unit11c-system-agent.md` D11.SA.3, aligning with `unit10-gui-control.md` D10.3, corrects this to all three desktop platforms first-class with per-platform backend dispatch. This file resolves toward cross-platform-first-class (§14): the configuration store, package manager, service controller, and elevation facility are replaceable per-platform backends behind capability sub-modes (`capability.capability`, File 05 §2.3) and the cross-platform realization (`sandbox.cross-platform`, File 23 §15), and a capability whose platform mechanism is absent reports unavailable rather than failing the surface. The Windows-primary framing is the retired pattern; the Windows registry is a platform-gated capability beside the cross-platform configuration store.
- **An autonomy/participation dial versus permission tiers.** Some system overviews and profile framings carried a participation or thoroughness mode gating approval and behavior. `worksurface.no-autonomy-field` (File 25 §13), `policy.chosen-model` (File 06 §1), and `world.surface-state` (File 18 §5.5) delete the autonomy field at every layer. This file carries no autonomy field (§22): System Agent autonomy is capability permission tiers, leases, and approval posture plus the user's direction; progressive disclosure is which presentation units are active and which view preset is applied; the executor thoroughness level (`unit11-cross-tool-learning.md` CT.21) is a workflow parameter, not an autonomy mode.

## 1. Chosen Model

Anchor: `sys.chosen-model`

ATLAS3 has one `SystemAgent` `WorkSurface`. It is the specialized environment for observing and operating the host operating system and the machine it runs on — reading system information, health metrics, processes, services, devices, the network, the environment, and the filesystem; installing and removing software; starting and stopping services; configuring the network, the configuration store and the registry, environment variables, and device settings; cleaning up, backing up, and restoring files; building, previewing, and running scripts; and scheduling and monitoring system work — and it is one instance of the `WorkSurface` primitive `worksurface.work-surface` (File 25 §3) defines, classified `SystemAgent` by `core.current-major-area-classification` (File 01 §5.7).

The System Agent surface owns user-facing system-operation workflows and specialized views; it owns no private architecture (`worksurface.no-private-architecture`, File 25 §12). It is declared by one `SurfaceContract` (§3) registered in the `SurfaceRegistry` (`worksurface.registry`, File 25 §10), and it composes the shared substrate — blocks, capabilities, capability policy, tool surfaces, execution, the world model, perception, the version graph, workspaces, context assembly, retrieval, memory, routing, artifacts, storage, sync, security, the sandbox, providers, and the ledger — through each one's canonical contract.

The load-bearing model of the System Agent surface is the **safe-system-operation reframe**. The machine is unowned, externally-mutable, shared with the user and with software the system does not control, and the most dangerous subject any surface acts on: a single operation can uninstall software, stop a service the user depends on, delete files, change a network or security setting, or shut the machine down. Four consequences follow:

- **The machine is observed structured-first, not command-output-first.** The machine's state is read through `Perception`'s `SystemMetric`, `Process`, `Environment`, `Filesystem`, and `Network` sensors (`perception.sensor`, File 19 §4.3, §7.7) as structured observations — a health snapshot, a process list, an environment snapshot, a filesystem snapshot — before a free-form shell command's parsed output, per the `SensingTier` strategy (`perception.tiered-sensing`, File 19 §5) and the structured-data-first invariant (`core.world-model`, File 01 §6.7). The surface owns no private machine-state model and is never learned-about by scraping command output when a structured sensor is available.
- **A system operation is a policy-gated, observation-grounded, previewed, verified, audited, and where-possible reversible capability invocation, not a blind shell command.** An operation passes through the one capability-call pipeline (`run.call-pipeline`, File 04 §8.2) carrying the System Agent's contributed posture: a pre-execution guardrail and policy floor, a dry-run preview, the one approval router with typed confirmation for high-blast-radius operations, confinement through the one `Sandbox`, post-execution verification against a fresh observation, the audit overlay, and a recorded reversal where the operation is reversible (§7). A blind shell command is the escape hatch under the dedicated capabilities, not the model.
- **Reliability is dedicated-capability-first with shell as the escape hatch.** When a dedicated `sys.*` capability covers the intent — install a package, restart a service, set a configuration value — the surface prefers it over a hand-written shell command, because the dedicated capability carries the typed schema, the preview, the per-platform backend, the postcondition, and the reversal (`unit11-cross-tool-learning.md` CT.16); raw shell and script execution remain available as the escape hatch for what no dedicated capability covers (§10).
- **Gathered machine state and recorded work are durable, not transcript prose.** A captured machine state is an `Observation` with a `StalenessFingerprint`; a recorded reusable operation sequence is a `Macro` or `WorkflowTemplate` `Artifact`; a diagnostics result is a `Report` `Artifact`; an authored script is a file `Artifact`; every consequential change is a ledger entry and an audit-overlay record (`artifact.observation`, File 09 §13, `artifact.artifact-kind` (File 09 §4), `ledger.hash-chained-audit-log` (File 10 §16.4)). Change history and system history are projections over the one ledger, the one version graph, and the one block pool; the surface introduces no parallel state, change, task, watch, rollback, or audit store.

`SystemAgent` is the canonical surface name; the `surface_id` is `system_agent` and equals the subsystem id (`capability.capability-source`, File 05 §9.1, `worksurface.work-surface` (File 25 §3.3)). Earlier vocabulary that named the same surface — "System Agent domain", "OS control", the participation levels — is source vocabulary only and does not survive as canonical terminology or as a parallel primitive. The anchor namespace for this file is `sys.*`, deliberately distinct from File 07's `surface.*` (tool surfaces), File 25's `worksurface.*`, File 26's `controlrail.*`, File 27's `coder.*`, File 28's `web.*`, File 29's `data.*`, File 30's `teacher.*`, and File 31's `gui.*`. The capability family `sys.*` consists of capability ids in the one registry, not anchors.

### 1.1 Boundary

This file defines what the System Agent surface is and what it declares and contributes. It does not define how the `SurfaceContract` is registered or composed (File 25), how its tool surface composes (File 07), how its live state is held (File 18), how the machine is sensed (File 19), how its confined work runs and elevates (File 23), how its history is versioned (File 11), how its operations are gated (File 06), how its work is scheduled (File 26 and File 33), or how its views render (the UI specs).

### 2.2 With File 23 (Sandbox, Process Control, and Isolation)

The boundary is load-bearing, because the System Agent is File 23's heaviest consumer: every system operation that mutates the machine or runs a native binary runs confined through the one `Sandbox` contract (`sandbox.consequences-for-later-specs`, File 23 §21). It declares system-operation `SandboxProfile`s (`sandbox.contract`, File 23 §3) and runs at the `OsConfined` tier (`sandbox.isolation-tiers`, File 23 §4) for native-binary execution, escalating to `Virtualized` only where a generated or untrusted script's trust class requires it; the broad host filesystem and network access a system operation needs is granted explicitly through its `FilesystemPolicy` and `NetworkPolicy` (`sandbox.filesystem-enforcement`, File 23 §7, `sandbox.network-enforcement` (File 23 §8)), not by escaping the sandbox. A spawned process — a package manager, a service controller, a script interpreter — is a `ManagedProcess` in a `ProcessGroup` (`process.spawning`, File 23 §5, `process.groups` (File 23 §6)), killable categorically and individually (`process.killability`, File 23 §10), with a finite, configurable, killable wall-clock safety guard (`sandbox.resource-limits`, File 23 §9.3 — decisive only without a completion signal, otherwise a last-resort backstop). A privileged operation crosses the elevated-helper boundary (`sandbox.elevated-helper`, File 23 §11); the main process never elevates. An attempt to act outside a declared or leased scope is the canonical declared-versus-observed violation (`sandbox.declared-vs-observed`, File 23 §13), including the typed `ElevationMismatch` when an operation requires an integrity level the current process lacks.

### 2.3 With File 19 (Perception) and File 18 (World Model)

The System Agent senses the machine through `Perception` and reasons over the world model; it owns no private machine-state model. File 19 owns the `SystemMetric`, `Process`, `Environment`, `Filesystem`, and `Network` sensors and the `Liveness` sensor (`perception.sensor`, File 19 §4.3, §7.7), the `SensingTier` strategy (`perception.tiered-sensing`, File 19 §5), the capture pipeline and producer normalization (`perception.capture-pipeline`, File 19 §6), the trigger model (`perception.triggers`, File 19 §8 — event-first, polling a flagged fallback), the staleness fingerprint and the stagnation signal (`perception.output-contract`, File 19 §9), and the capture-privacy and redaction contract (`perception.capture-privacy`, File 19 §10). This file consumes the sensors' structured output and never owns a private capture pipeline (`perception.explicit-rejections`, File 19 §18). The machine and its operating system are an externally-mutable, partly self-describing source: the operating system exposes structured introspection that the sensors capture, and what the sensors do not cover is captured by parsing a confined command's output as a lower-tier fallback. File 18 owns the `Device`, `Process`, and `Sandbox` `WorldEntity` kinds (`world.world-entity`, File 18 §4.3), the environment and temporal facts (`world.environment-temporal-connection-facts`, File 18 §6.1 — operating system and platform, shell, working directory, locale and timezone, network connectivity posture, and the relevant permission states), the durability tiers, the availability evaluator and the System Agent surface's named availability checks (`world.state-aware-capability-availability`, File 18 §9.3), and snapshot resolution; this file self-registers its presentation units and contributes the world facts its work observes, registering `Custom` world-entity kinds only where a durable, queryable live system entity — an enabled watch, an active long-running operation — is genuinely warranted.

### 2.4 With Files 05, 06, 07 (Capabilities, Policy, Tool Surfaces)

System Agent capabilities are `Capability` declarations in the one registry (`capability.chosen-model`, File 05 §1) with `source: Subsystem { subsystem_id: system_agent }`, with per-platform variants as capability sub-modes (`capability.capability`, File 05 §2.3) and previews, postconditions, reversal, and replay class as declared metadata (`artifact.capability-metadata-declarations`, File 09 §16.2; `capability.execution-semantic-fields`, File 05 §3.6). ### 2.5 With File 10 (Ledger, Events, Hooks) and File 22 (Security)

### 2.6 With Files 08, 09, and 11 (Blocks, Artifacts, Version Graph)

System observations and outputs flow as `Block`s through the one pool (`block.cross-surface-interoperability`, File 08 §12); large command output and large backups resolve from the content-addressed blob store as `External` content (`block.block-content`, File 08 §4). ### 2.7 With File 13 (Context Assembly) and Files 16, 17 (Model Strategy, Provider Layer)

It assembles every model request through the one `ContextAssemblyService` (`context.chosen-model`, File 13 §1): captured machine state is a `RuntimeState` part, captured command output, log content, and file content the surface did not author are `untrusted_source_data` (`context.authority-classes`, File 13 §2.3), and large captures are referenced rather than flooded into context (`context.current-input-oversize-handling`, File 13 §7). The deep scheduling, eligibility, enablement, watch evaluation, and non-interactive-execution-safety mechanics belong to File 33 (Automation and Triggers), and this file frames the System Agent as one consumer (§12).

### 2.9 With Files 15, 20, 21, 24

A surface emits events through the one ledger and bus with system facts as `Custom { namespace: "system_agent" }` (`ledger.custom-kind-registration`, File 10 §4.3); System Agent settings are namespaced `surface.system_agent.*` keys plus profile layers (`settings.consequences-for-later-specs`, File 15 §21); durable System Agent state persists as substrate families with large backups and captures in the content-addressed store (`storage.consequences`, File 20 §18) under the locality split (`worksurface.persistence-locality`, File 25 §16 — change records, watches, scheduled-task bindings, and the audit chain are device-local; scripts, macros, workflow templates, and configuration definitions sync); durable System Agent state rides the syncable substrate and the `PortablePackage` (`portability.consequences`, File 21 §18), and the audit chain never syncs (`ledger.hash-chained-audit-log`, File 10 §16.4); the surface renders over a bound `Workspace` (`workspace.conversation-binding`, File 24 §7), materializes its scripts, backups, and reports through the disk↔substrate mirror (`workspace.materialization`, File 24 §10), and uses the `ATLAS.system_agent.md` instruction qualifier (`workspace.instruction-files`, File 24 §9).

## 3. The System Agent `SurfaceContract`

Anchor: `sys.surface-contract`

### 3.1 Definition

The System Agent `SurfaceContract` is the one typed, source-authored declaration of the System Agent surface, admitted to the `SurfaceRegistry` (`worksurface.surface-contract`, File 25 §4). It carries the required `SurfaceContract` sections — Identity (§3.2), State (§4), Actions (§5), Views (§16), and Context-and-execution policy (§15) — each filled with system-operation content and declaring by reference every field whose contract lives in another file.

### 3.2 Identity

The System Agent surface declares:

- `surface_id`: `system_agent`, equal to its `subsystem_id`; the value `routing.run-intent` (File 03 §4.3)'s `primary_surface` resolves to for system-operation work, the prefix of its settings namespace (`surface.system_agent.*`) and its instruction-file qualifier (`ATLAS.system_agent.md`); the capability and anchor namespace is the shorter `sys.*`
- `surface_kind`: `SystemAgent` (`worksurface.surface-contract`, File 25 §4.4)
- `display_name`, `description`, `short_description`: localized per the canonical descriptor discipline (`capability.display-fields`, File 05 §3.2); never hardcoded into surface logic
- `keywords`: the routing- and discovery-relevant terms the surface is discovered by (representative: system, os, install, uninstall, package, service, process, registry, config, network, firewall, environment, disk, cleanup, backup, schedule, monitor, shutdown, script, maintenance, diagnose)
- `availability_predicate`: a world predicate (`world.state-aware-capability-availability`, File 18 §9.2) — the System Agent surface is activatable on any host platform; read-only introspection and health are available wherever the platform's introspection facility is present, while a specific mutating capability whose per-platform backend is absent reports unavailable through its named availability check (§5.5) rather than failing the whole surface (§14), and the surface stays inspectable when no operation is currently permitted

### 3.3 The Required-Section Map

The remaining required sections are filled as: State by §4, Actions by §5, Views by §16, Context-and-execution policy by §15. The system-operation workflow semantics (§6–§14) elaborate what those sections produce; they are surface workflows over the declared capabilities, not additional contract sections. The declaration is immutable for a registered `surface_contract_version`; contract updates create a new version (`worksurface.surface-contract`, File 25 §4.2). Registry state (trust, scoped enable, availability) lives on the registered entry, not the declaration.

### 3.4 The Surface-and-Service Duality

The System Agent has two faces over one declaration, the same duality `teacher.surface-and-service` (File 30 §1.2) fixes for the Teacher surface:

- a **work surface**: a focus environment with system-inspection and control projections — the machine's health, the change history and its reversal plans, the active watches, the scheduled tasks, the audit record, and script authoring and confined command execution — the inspector surface `codex_recommendations.md` §8.10 describes
- a borrowable **cross-surface service**: the `sys.*` capability family is borrowable (subject to policy, §18) so any surface that legitimately needs an operating-system operation — the Coder surface installing a build dependency, the Data Processor surface starting a local database, the Web surface configuring a proxy — reaches it in place, realizing `codex_recommendations.md` §8.1's "System/OS capabilities" cross-cutting service through borrow rather than a peer-domain duplication

Neither face is a mode. There is no system-mode, participation, or autonomy field on the declaration, on a view preset, or on the live state (§22); the service face is capability borrow and the surface face is presentation activation.

### 3.5 Boundary

This section fixes the contract's System Agent content at the section level and the surface-and-service duality. File 25 owns the contract shape, the registry, and the substrate-service-management boundary; the per-section System Agent semantics are §§4–21.

## 4. State Declaration — Presentation Units and Selection

Anchor: `sys.state-declaration`

### 4.1 Definition

The System Agent surface declares the presentation units it can register and the selection kinds it produces. A presentation unit is an independently addressable projection of substrate or work state (`worksurface.state-declaration`, File 25 §5.3); declaring one assumes no pane, tab, region, or simultaneity. This is the static counterpart of the live `SurfaceState` (`world.surface-state`, File 18 §5): this file declares the shape, File 18 holds the live values. A presentation unit self-registers its live state to the world model when it is activated — when it enters its context's composition, at any prominence — and updates on focus, selection, and content change (`world.observation-state-update`, File 18 §8.1); a unit the surface fails to register is a blind spot the agent cannot use.

### 4.2 Declared Presentation-Unit Kinds

The System Agent surface declares the following presentation-unit kinds, drawn from the canonical baseline (`worksurface.state-declaration`, File 25 §5.3) plus System Agent `Custom` kinds registered through the proposal-first mechanism. Each declares the typed shape of its compact state-field summary (a metric value, a change id, a service name, a watch id — never the full captured snapshot, `world.surface-state` (File 18 §5.2)), the selection kinds it produces, its structural semantics, and its control affordances:

- `health` — the composite machine-health projection over the latest `SystemHealthSnapshot` observation (§6): the current processor, memory, disk, network-throughput, battery, thermal, and update-status summary; produces metric selections; a projection over the `SystemMetric` sensor's captures, never a private metric store
- `changes` — the change history: the chronological list of recorded system changes, each with its operation, target, reversibility, and verified outcome, and the per-change and multi-step rollback affordances, a projection over the ledger and the change-record observations (§9), not a private change log
- `rollback` — the rollback view: the dependency-ordered reversal plan for a multi-step operation, a projection over the change records' dependency chain (§9), not a private rollback store
- `monitors` — the active-watch list: the enabled monitors and their target, threshold, last evaluation, and recent threshold crossings, a projection over the `Trigger`-rail watch entries and the world model (§12), not a private watch store
- `scheduled` — the scheduled-task list: the system scheduled tasks, their trigger, next run, and recent execution outcomes, a projection over the one scheduler's entries (§12), not a private task store
- `audit` — the audit view: the chronological, redacted, verifiable record of world-affecting system operations, a projection over the device-local hash-chained audit overlay (`ledger.hash-chained-audit-log`, File 10 §16.4), read-only, not a private audit file
- `console` — the script-and-command projection: script authoring with its dry-run preview, and confined command execution as a `ManagedProcess` on a pseudo-terminal (§10) producing `TerminalOutput` observations; a projection over the sensor and the managed process, never a private execution path. How a client presents either half is its own, realized in the windowed-desktop profile as a console (`ui.layout`, File 37 §5)
- `processes` — the process and service list: running processes and managed services with their resource use, status, and the operations available on each, a projection over the `Process` sensor and the world model
- `inspector` — the system-object inspector: the structured detail of a selected process, service, package, device, configuration key, or environment variable, a projection over the captured observation
- `activity` — the operation activity projection: the safe-operation lifecycle progress of the active task — preview, approval, execution, verification, and reversal recording — a projection over the ledger and event stream (`run.presentation`, File 04 §25), not a private log

A unit kind this surface declares is a shared substrate projection, not a private store: `inspector` is a canonical baseline kind and the surface's remaining kinds, `activity` and `monitors` among them, are registered `Custom` kinds over the same shared substrate (`worksurface.state-declaration`, File 25 §5.3), and a presentation unit one surface declares may be composed into another surface's presentation — a Coder surface composing the health or process unit — without changing the primary surface (`worksurface.state-declaration`, File 25 §5.4).

### 4.3 Selection Kinds

The System Agent surface produces selections of canonical kind — representatively `Text`, `File`, and `BlockRange` (`world.surface-state`, File 18 §5.4) — plus registered `Custom` system-object selection kinds where a selection addresses a process, service, package, device, configuration key, environment variable, change record, watch, or scheduled task. A selection carries a short summary and a typed reference (a process identifier, a service name, a configuration key path, a change id), not the captured content.

### 4.4 The Static-versus-Live Split

The declaration is the static shape; the live values — which units are active and at what prominence, which is primary, what is focused and selected, the current `UiMode`, and the available-capability list — are the live `SurfaceState` File 18 holds. The System Agent surface declares no participation, autonomy, system-mode, or thoroughness-mode field on its state (§22); `UiMode` is interaction state, never an autonomy control, and its member set is `world.surface-state` (File 18 §5.5)'s alone — this file restates it nowhere. The read-only-introspection-versus-mutation distinction is a function of which capabilities the run invokes and what policy permits, not a state-machine mode.

### 4.5 Boundary

This section declares the System Agent presentation-unit and selection shape. File 18 holds the live values and owns the self-registration contract; the UI specs own how a unit is presented (`ui.layout`, File 37 §5); the health, change-history, rollback and console rendering are replaceable implementations behind the units.

## 5. Actions Declaration — the System Agent `SubsystemSurfaceSpec`

Anchor: `sys.actions-declaration`

### 5.1 Definition

The System Agent surface's actions declaration is its `SubsystemSurfaceSpec` (`surface.subsystem-surface-spec`, File 07 §5) plus the artifact, observation, and sensor kinds it primarily produces or exposes and the approval posture it contributes. This file references the `SubsystemSurfaceSpec` contract; it owns no zone, composition, or borrowing mechanics, which are File 07's.

### 5.2 Contributed Capabilities and Zones

The System Agent surface contributes its capabilities to the one registry with `source: Subsystem { subsystem_id: system_agent }`, declared per `capability.declaration` (File 05 §3) and registered through the proposal-first path (`capability.runtime-mutation`, File 05 §16.2). The capability families the surface contributes or relies on, and their default zone (`run.zones`, File 04 §10.2, `surface.zone-model` (File 07 §3)):

- **System introspection and health** (`Primary`): read system information and the composite health snapshot; list and inspect processes, services, network adapters, disks and usage, environment variables, users and groups, displays, audio devices, and power state (§6, §8); read operations producing observations
- **Package management** (`Primary`): search, inspect, list installed, install, uninstall, update, and update-all software through the available per-platform package manager (§8); install/uninstall/update are mutating and tier-gated
- **Service management** (`Primary`): list, inspect, start, stop, restart, enable, and disable system services and daemons through the per-platform service controller (§8)
- **Process management** (`Primary`): terminate a process, adjust its priority, and watch a process (§8, §12); terminate is an irreversible, tier-gated mutation
- **Network configuration** (`Primary`): set DNS, enable and disable adapters, add/remove/list firewall rules, and get/set the proxy (§8); reversible mutations carrying their prior state
- **The configuration store** (`Primary`): read, write, and delete cross-platform configuration values through the per-platform configuration store, the Windows registry as a platform-gated capability beside it, and set/unset environment variables and add/remove `PATH` entries (§8); reversible mutations
- **Device, display, audio, and power** (`Primary`): set resolution and scaling, set the default audio device, get/set volume and brightness, and sleep/restart/shutdown the machine (§8); power-state operations are high-blast-radius and tier-gated
- **Filesystem maintenance** (`Primary`): clean up temporary, cache, log, and trash content; find duplicate and large files; organize by rule; and back up and restore to a location, each with a dry-run preview (§8); destructive maintenance is reversibility-classified and tier-gated
- **Scripts and command execution** (`Primary`): preview, execute, list, and apply a script template, and run a confined shell command on a pseudo-terminal (§10); the escape hatch under the dedicated capabilities, confined and audited
- **Change history and rollback** (`Primary`): list recorded changes and roll a change or a multi-step operation back (§9)
- **Monitoring and watches** (`Primary`): create, list, and stop a watch and read its history, declared here and realized as `Trigger`-rail entries over the world model and the one scheduler (§12)
- **Scheduled tasks** (`Primary`): list, create, delete, enable, disable, and run-now a scheduled system task, as thin aliases over the one scheduler reached through the `Trigger` rail (§12)
- **Planning, discovery, and orchestration** (`Primary`): the shared `plan` capability (§15.5), the discovery and borrow capabilities (`tool.search`, `tool.borrow`, `surface.late-loading-runtime-discovery` (File 07 §7)), and the sub-agent-spawn capability for long-running execution, background monitoring, package installation with progress, and scheduled-task tracking (§13, §15.5)
- **Borrowable** capabilities: file read/create/edit/list (to read and write configuration files and save reports and scripts), memory recall and store (to recall and pin remembered machine configurations and known-good setups), web search and fetch (to look up an update URL, a package, or documentation), knowledge search (to consult documented runbooks before acting), and the coder code-execution capability (to compute over captured machine state) — present in the `Borrowable` zone for occasional cross-surface reach
- **Default-deferred families** (the surface's `default_deferred_families`, `surface.subsystem-surface-spec` (File 07 §5.1) — deferred out of the surface's default zones into the `Deferred` zone, not impossible to use; still reachable by explicit search, borrow, reroute, or user override with a typed denial where policy forbids): the GUI Control desktop-puppeting capability family (the GUI Control surface puppets applications; the System Agent operates the operating system, §18), the browser-navigation capability family (the Web surface drives the browser), and the data-processor and teacher families, which are out of scope for default System Agent composition but may be borrowed when captured machine data needs dataset processing or a maintenance procedure needs to be taught

The capability lists are representative hints, not a closed fence (§5.4). The full set varies with installed capabilities, plugins, the active workspace's per-workspace zone overrides, registered system extensions, and the active platform.

### 5.3 Produced Kinds and Exposed Sensors

The System Agent surface declares the artifact, observation, and sensor kinds it primarily produces or exposes (`worksurface.actions-declaration`, File 25 §6.2):

- **Primary `ArtifactKind`s**: `Macro` (a recorded, parameterized, replayable system operation sequence, shared with the GUI Control and Web surfaces, `artifact.artifact-kind` (File 09 §4)), `WorkflowTemplate` (a reusable system automation), and `Report` (a diagnostics or maintenance report); an authored script and a backup are saved as file `Artifact`s; System Agent-specialized kinds register through the canonical mechanism. The surface introduces no `Script` or change-record artifact kind: a script is a file artifact, and a change is a ledger entry plus before-state observation (§9)
- **Primary `ObservationKind`s**: the reused `ProcessState` (a captured process and listening-port snapshot), `EnvironmentSnapshot` (captured environment variables, working directory, shell, and operating-system facts), `FileSnapshot`, `WorkspaceSnapshot`, and `TerminalOutput` (a captured command, its output, and its exit code) (`artifact.observation`, File 09 §13.2), plus the registered `Custom` kinds `SystemStateSnapshot` (the before-or-after state of a configuration, registry, service, network, environment, or device mutation — the reversal's anchor) and `SystemHealthSnapshot` (a composite machine health and metric capture), produced through the canonical `observation.commit` path
- **Exposed sensors**: the `SystemMetric` sensor (processor, memory, disk, network throughput, battery, thermal, and idle state), the `Process` sensor (running processes and listening ports), the `Environment` sensor (operating-system facts, shell, working directory, locale, connectivity, and permission states), the `Filesystem` sensor (file and directory state), the `Network` sensor (network configuration and responses), and the `Liveness` sensor (service and integration lifecycle) (`perception.sensor`, File 19 §4.3), each with its declared privacy class; the surface consumes these sensors' structured output and owns no capture mechanics

### 5.4 The Hint-not-Fence Rule

The System Agent surface's `primary_capability_ids` are a hint about what is most relevant for system-operation work, not a fence around what the agent may invoke (`worksurface.actions-declaration`, File 25 §6.3). The agent reaches any capability in the one registry through the discovery and borrow capabilities, subject to policy; a System Agent run that needs `web.fetch` to look up a package, file write to save a generated script, or the coder code-execution capability to compute over a large captured process table borrows it and remains in the System Agent surface, with the ledger recording both the originating surface and the borrowed-capability source. Cross-surface access defaults to search-and-borrow, never silent autoload (`run.consequences-for-later-specs`, File 04 §29).

### 5.5 Contributed Approval Posture and Named Availability Checks

The System Agent surface contributes a default approval posture and references the policy templates, reusable rules, and gates File 06 owns; it evaluates no policy itself:

- **Asymmetric-blast-radius posture** (§11): read-only introspection and health default to `ReadOnly`; user-scope preference changes (volume, brightness, dark mode) default to `WorkspaceWrite`; mutating system operations — package install/uninstall, service control, configuration and registry writes, network changes, process termination, environment changes — default to `UserApproval`; and a destructive, irreversible, or security-sensitive operation carries the `Denied`-floor typed-confirmation rule (`policy.permission-floor-typed-confirmation`, File 06 §7) that an `AlwaysAllow` on the underlying capability does not lift (§11.3). The surface contributes the destructive-operation, sensitive-target, and denied-operation escalation templates as approval-policy templates and named checks (`policy.approval-policy-templates`, File 06 §12.4)
- **Guardrail denied-operation rules**: structurally-catastrophic operations are `Denied`-floor reusable-policy rules (`policy.built-in-reusable-policy-rules`, File 06 §11.5) the pre-execution guardrail enforces (§7.3, §11.2) — a shipped floor family Atlas denies unconditionally, and an extensible family a user, a workspace, or an approved source may add to but never subtract from (§11.2); a denied operation returns a typed denial in-band, never an unhandled failure
- **Untrusted-content posture**: command output, log content, file content the surface did not author, process names, and any text captured from the machine enter the model request as `untrusted_source_data` (`context.authority-classes`, File 13 §2.3) and carry no capability or policy authority (`security.untrusted-content`, File 22 §12); this is the surface's default and is non-negotiable (§11)
- **Dedicated-tool-preference posture**: when a dedicated `sys.*` capability covers the intent, the surface prefers it over a hand-written shell command. The trigger is a proposed free-form shell or script invocation whose pattern matches a registered dedicated capability, which the built-in `prefer_dedicated_tools` rule declares (`policy.built-in-reusable-policy-rules`, File 06 §11.5); the outcome is its template validator's verdict under the resolved dedicated-tool preference mode (`policy.settings-resolution-for-policy`, File 06 §16.1) — `Strict` yields an actionable `RedirectSuggestion` naming the dedicated capability and its suggested arguments, terminal for the current proposal; `Warn` yields `NoOpinion` and a typed `RedirectAdvisory`; `Off` yields `NoOpinion` and no advisory (`policy.approval-policy-templates`, File 06 §12.3) — and a redirected invocation is a new proposal that runs the complete capability-call pipeline, granted no authority by the redirect. It is never an out-of-band rewrite of the user's or agent's command (§10.3)
- **Self-modification posture**: generic process, service, configuration, filesystem, and shell-mediated operations reject Atlas-owned critical targets before dispatch (§11.3), while legitimate Atlas lifecycle and security operations route through dedicated Atlas capabilities and their own policy floors
- **Batched approval**: a multi-step operation — a setup sequence, a cleanup batch, a maintenance routine — presents through the shared batched-approval flow (`policy.batched-approval-flow`, File 06 §5.5), so approval is granted once over the previewed batch rather than once per step
- **Elevated and credential handoffs**: a privileged operation crosses the elevated-helper boundary under typed confirmation (§14, `sandbox.elevated-helper` File 23 §11); a credential prompt, an interactive installer, a hardware confirmation, or any interaction the agent must not complete on the user's behalf is an elicitation handoff to the user (§13, `controlrail.elicitation` File 26 §13)
- **Sensitive-content posture**: captured configuration values, environment variables, command output, and backups may contain secrets and personal data; the surface follows the secret/personal-data detection and redaction contract (`security.secret-detection-redaction`, File 22 §7) — a detected secret or personal value is redacted before any capture, event, log, audit payload, export, or sync stream, and a value supplied into a credential or secret-bearing operation is never materialized raw (`secret.backend-boundary`, File 22 §4)

The System Agent surface registers named availability checks (`world.state-aware-capability-availability`, File 18 §9.3) the world model evaluates against the current snapshot — representative: a-package-manager-is-available, a-service-controller-is-available, a-configuration-store-is-available, the-platform-is-windows (for registry capabilities), an-elevation-facility-is-available, a-display-or-audio-or-power-facility-is-available, and a-backup-destination-is-reachable — each a pure function of the world snapshot that gates the availability of specific capabilities and affordances so a capability whose per-platform backend is absent reports unavailable without failing the surface (§14).

## 6. System Observation and the Machine Model

Anchor: `sys.observation`

### 6.1 Definition

System observation is the System Agent surface's structured model of the machine — its health, processes, services, environment, network, devices, and filesystem state — the input to every operation and the verification of every change. The System Agent surface is structured-data-first: it reads the machine through `Perception`'s system, process, environment, filesystem, and network sensors (`perception.sensor`, File 19 §4.3, §7.7) and the `SensingTier` strategy (`perception.tiered-sensing`, File 19 §5), and parses a free-form command's output only when no structured sensor covers the need (`core.world-model`, File 01 §6.7). The surface owns no private machine-state model; it consumes the sensors' structured output and projects it into the `Device` and `Process` world entities and the health, process, and object-detail presentation units it declares (§4.2).

### 6.2 The Tiered Machine Representation

A facet of the machine is sensed at one or more tiers, mapped onto the canonical `SensingTier` order (`perception.tiered-sensing`, File 19 §5.1):

- **`Structured`** (the default and primary representation): the operating system's own structured introspection — the process table and resource counters, the service inventory and status, the installed-package list, the network adapter and routing configuration, the environment block, the device inventory, and the filesystem metadata — captured through the system, process, environment, filesystem, and network sensors. This is the primary input to the model: it is precise, semantically rich, cheap, and deterministic, and it gives each system object a stable reference the surface resolves to the actual object without ambiguity.
- **`Grounded`/`Raw`** (when the structured tier is absent or insufficient): a confined shell command's parsed output, for a facet the structured sensors do not expose or a per-platform facility that only emits text. The command runs confined (§10), its output is a `TerminalOutput` observation, and its parse is the surface's extraction over a lower tier; the surface must not parse command output when a structured sensor covers the facet (`perception.tiered-sensing`, File 19 §5.2).

The composite health snapshot (`SystemHealthSnapshot`) is a structured `SystemMetric` capture; the process, environment, and filesystem snapshots are structured captures through their sensors; a before-or-after change snapshot (`SystemStateSnapshot`) is the structured capture of the specific object a mutation targets.

### 6.3 Observations, Fingerprints, and Freshness

A deliberately captured machine state is an `Observation` block with a `StalenessFingerprint` (`artifact.observation`, File 09 §13, `perception.output-contract` (File 19 §9.3)): a `SystemHealthSnapshot`, a `ProcessState`, an `EnvironmentSnapshot`, a `FileSnapshot`, or a `SystemStateSnapshot`. The captured structured state is cached per object and invalidated event-first on a relevant operating-system event — a process create or exit, a service state change, a configuration write, a filesystem change (`perception.triggers`, File 19 §8.1) — so repeated reads of an unchanged object hit the cache; the cache is a rebuildable projection, never a durable fact (`core.projection`, File 01 §6.11). A continuous metric with no change event — processor load, memory pressure, thermal state — uses a flagged, configurable sampling interval as the explicit exception (`perception.triggers`, File 19 §8.2), never a default polling correctness rule. System memory — what the surface knows of the machine across captures — is the version-graph and observation history, not a private store.

### 6.4 Read-before-Act and Staleness

A system operation that depends on a prior capture revalidates currency before dispatching (`run.call-pipeline`, File 04 §8.2, `perception.output-contract` (File 19 §9.3)): the prior capture records the targeted object's staleness fingerprint, the operation carries the expected fingerprint and target reference, and a mismatch — the service already stopped, the package already at the target version, the configuration value already changed by another process — returns a typed `StateChangedSinceObservation` error rather than acting on a stale assumption. The agent receives the typed error in-band and may re-capture and retry, re-resolve the target, or stop. This is the system realization of the canonical stale-state revalidation; the surface enforces no separate mechanism. Where an operation is idempotent against a target end-state — ensure a service is running, ensure a package is installed at a version — the operation declares it, so a no-op end-state is a success rather than a failure.

### 6.5 Boundary

This section owns the system-observation workflow and the command-output parse as a fallback extraction. File 19 owns the sensors, the tier strategy, the capture pipeline, the trigger model, the staleness fingerprint, and the stagnation signal; File 09 owns the observation kinds; File 18 owns the device and process entities the observation projects into. The system-introspection facilities are replaceable implementations behind the sensors.

## 7. The System Operation Model and the Safe-Operation Lifecycle

Anchor: `sys.operation-model`

### 7.1 Definition

A system operation is a capability invocation that reads or mutates the host machine. Its safety is not a private pipeline; it is the canonical capability-call pipeline (`run.call-pipeline`, File 04 §8.2) carrying the System Agent's contributed previewable, approvable, sandboxed, verified, audited, and reversible posture. The surface introduces no private middleware engine, guardrail chain, or execution path.

### 7.2 The Safe-Operation Lifecycle Maps onto Canonical Owners

The source material's eleven-stage system-execution pipeline (`unit11c-system-agent.md` D11.SA.14) — parse, pre-guardrail, preview, approve, sandbox, execute, verify, post-guardrail, log, record-rollback, emit — is realized stage for stage over the canonical substrate, each stage owned by an existing file:

- **Parse** — input validation against the capability's input schema (`run.call-pipeline`, File 04 §8.2); a malformed argument is a typed error before any effect
- **Pre-guardrail** — the proposal, policy, and pre-execution hooks the call pipeline runs before dispatch (`run.call-pipeline`, File 04 §8.2 steps 5–6, `ledger.hook` (File 10 §7), `policy.built-in-reusable-policy-rules` (File 06 §11.5)) and the policy floor (`policy.effective-tier-resolution`, File 06 §4): the denied-operation reusable rules (§11.2) reject a structurally-forbidden operation, and captured untrusted content is stripped of authority (`security.untrusted-content`, File 22 §12)
- **Preview** — the capability's dry-run and preview (`capability.execution-semantic-fields`, File 05 §3.6): a mutating operation captures and commits its before-state `SystemStateSnapshot` `Observation` via `observation.commit` (§6.4) and produces a typed change preview — the before state, the proposed after state, the touched resources, the reversibility class, and the predicted blast radius — without effect, carried in the approval payload (§11) and exposed through the change and activity projections (§4.2)
- **Approve** — the one approval router (`policy.approval-router`, File 06): immediate allow for read-only and low-tier operations, `UserApproval` for mutations, the `Denied`-floor typed-confirmation gate for destructive/irreversible/sensitive operations (§11.3), and the batched-approval flow for multi-step operations (§5.5)
- **Sandbox** — confinement through the one `Sandbox` at the `OsConfined` tier with the operation's explicit filesystem and network policy, and the elevated-helper boundary for a privileged operation (§14, `sandbox.contract` File 23 §3, `sandbox.elevated-helper` (File 23 §11))
- **Execute** — the capability invocation over the shared run lifecycle (`run.execution-entry`, File 04 §4), streaming partial progress for a long-running operation (`run.streaming-partial-execution`, File 04 §12)
- **Verify** — a fresh post-execution observation (§6) and a postcondition `Validation` (`artifact.validation-critique`, File 09 §14): the surface verifies the declared end state — package identity, source, installed version, executable path, service identity and state, configuration value, or equivalent target-specific fact — and, when it cannot prove the stronger claim, reports which evidence class it actually obtained under the evidence precedence its operation category declares (§8.3 declares package management's; every other category declares its own where that category is defined), together with a typed mismatch where the end state is not established at all. The verification records the evidence links that establish the class it reports (`artifact.validation-critique`, File 09 §14.1); the class is never a separate stored field
- **Post-guardrail** — the post-execution hooks (`ledger.hook`, File 10 §7) and the stuck/loop detection (`run.stuck-detection`, File 04 §20.3): an anomalous result or a runaway sequence injects a corrective signal or escalates to a hard stop (§11.4)
- **Log** — the durable ledger entry (`ledger.execution-ledger`, File 10 §3) and, for a world-affecting operation, the reserved hash-chained audit-overlay record (`ledger.hash-chained-audit-log`, File 10 §16.4)
- **Record-reversal** — the declared inverse recorded as the reversal, referencing the before-state `Observation` committed at Preview (§9); a reversible operation is rollback-able, an irreversible one is flagged
- **Emit** — the events on the one bus, system facts as `Custom { namespace: "system_agent" }` (§21.2)

The lifecycle is contributed posture over the one pipeline; the surface evaluates no policy, opens no sandbox, and writes no audit file of its own.

### 7.3 The Pre- and Post-Guardrails Are Hooks and Policy, Not a Private Chain

The pre- and post-guardrails are the canonical blocking hooks and policy floor, not a private guardrail middleware. The pre-guardrail is the approval router's blocking participation plus the denied-operation reusable rules evaluated at `ToolCallProposed` (`ledger.hook`, File 10 §7, `policy.built-in-reusable-policy-rules` (File 06 §11.5)); a denied call returns a typed denial in-band as a tool result (`run.denial-is-in-band`, File 04 §8.3), never an unhandled exception. The post-guardrail is the post-execution hook plus the verification and stuck-detection signals. Both obey the canonical hook authority, priority, and fail-direction rules (`ledger.authority-classes`, File 10 §7.4); the surface registers its system guardrails as hooks and reusable rules, not as a parallel chain.

### 7.4 Boundary

This section owns the safe-operation lifecycle as contributed posture and its mapping to canonical owners. File 04 owns the run and the call pipeline; File 06 owns the policy, the approval router, and the gates; File 23 owns the sandbox and the elevated helper; File 19 and File 09 own the verification observation and the postcondition validation; File 10 owns the ledger, the hooks, and the audit overlay. This file declares the posture and the mapping; those files own the mechanisms.

## 8. Operation Categories

Anchor: `sys.operation-categories`

### 8.1 Definition

The operation categories are the workflow groupings of the `sys.*` capability family (§5.2). Each category is a set of capabilities over a replaceable per-platform backend, observed structured-first (§6), gated by the safe-operation lifecycle (§7), and reversible where the underlying operation allows (§9). This section names the categories and their distinctive contracts; the per-platform mechanisms are replaceable implementations behind the capabilities (§14).

### 8.2 Introspection and Health

Read-only capabilities produce observations and never mutate: system information, the composite health snapshot, the process and listening-port list, the service inventory, network adapters and routing, disks and usage, environment variables, users and groups, displays, audio devices, and power state. These are the structured tier (§6.2), available wherever the platform's introspection facility is present, and default to the `ReadOnly` tier. The health snapshot is the `health` presentation unit's projection and the canonical first read on entering the surface.

### 8.3 Package and Service Management

Package management dispatches to the available per-platform package manager as a capability sub-mode: a single intent — install a package — resolves to the platform's manager, and a package-name mapping resolves a logical name to the platform-specific identifier where they differ, the mapping being settings-overridable and never hardcoded (`settings.settings-over-constants`, File 15 §13). The preview carries the logical request, resolved package id, manager/backend, mapping source and source version, selected channel or repository when known, dependency changes, and trust status; plugin, community, or imported mappings require source approval, while user mappings remain audit-visible settings overrides. Install, uninstall, update, and update-all stream progress (`run.streaming-partial-execution`, File 04 §12), carry dependency changes in the preview, verify the post-install state using the strongest identity evidence the platform's manager makes available, in the precedence this category declares — a signature or content hash over the installed artifact, then the package-manager receipt with its source identity, then the reported installed version with its channel or repository, then the executable path and the version it reports — and the verification records the evidence links that establish the class it reports (`artifact.validation-critique`, File 09 §14.1); the reported installed version is the minimum acceptable class, so a result resting on the executable path alone does not reach it and reports a typed verification mismatch rather than a silent success. A reversal is recorded where the manager supports removal. Service management dispatches to the per-platform service controller for list, inspect, start, stop, restart, enable, and disable, verifying the resolved service identity and post-operation service state and recording the prior state as the reversal.

### 8.4 Process, Network, and Configuration

Process management lists, inspects, watches (§12), adjusts the priority of, and terminates a process; termination is irreversible and tier-gated, and the surface terminates an arbitrary process only under approval, distinct from killing a `ManagedProcess` the system itself spawned (`process.killability`, File 23 §10). Network configuration sets DNS, enables and disables adapters, manages firewall rules, and gets/sets the proxy, each recording the prior configuration as the reversal and re-validating any destination through egress governance (`security.egress-governance`, File 22 §11). The configuration store reads, writes, and deletes cross-platform configuration values through the per-platform configuration store, with the Windows registry as a platform-gated capability beside it (registry capabilities register only where the platform provides the registry, §14); a configuration write captures the prior value as a `SystemStateSnapshot` before state and records the reversal. Multi-target configuration, registry, firewall, environment, and `PATH` mutations declare `atomic`, `staged_compensating`, or `best_effort_partial` semantics; a partial failure records every successful step and offers rollback only for steps whose inverse remains valid. Environment-variable and `PATH` operations declare their scope — current process, child processes, user session, persistent user profile, machine/global profile, service environment, or shell startup file — and preview when the change becomes visible and which processes need restart or relogin; verification checks the declared scope, not only the current process environment.

### 8.5 Device, Power, and Filesystem Maintenance

Device, display, audio, and power operations set resolution and scaling, the default audio device, volume, brightness, and the power state; sleep, restart, and shutdown are high-blast-radius terminal handoff operations that carry the typed-confirmation gate (§11.3). Their preflight preview carries active runs, managed processes, unsaved materialization risk, whether Atlas can resume, and whether cancellation remains possible; postcondition verification occurs only if and when the app resumes and can observe the machine again. Filesystem maintenance — cleanup of temporary, cache, log, and trash content; duplicate and large-file discovery; rule-based organization; and backup and restore — runs with a dry-run preview as the default first step (`unit11c-system-agent.md` D11.SA.10): the preview enumerates exactly what will be removed, moved, or copied, and the operation proceeds only on approval of the preview. A maintenance operation within the bound workspace is a sibling-block version with version-graph reversal (`version.version-switching`, File 11 §8); a maintenance operation outside the workspace records its before state where the content is recoverable and is flagged irreversible where it is not (§9). Backup is an incremental, optionally encrypted and compressed, retention-policied copy verified after completion, integrating with scheduled tasks (§12) for recurring backups and riding the workspace materialization and content-addressed store for its destination (`workspace.materialization`, File 24 §10). Backup previews classify the destination as local filesystem, removable, network, connector/cloud, or external endpoint; network, removable, cloud, and external movement route through egress governance, encryption uses vault-backed `SecretRef`s, retention cleanup is a destructive maintenance operation, and ordinary backups never include raw vault secrets.

### 8.6 Boundary

This section names the operation categories and their distinctive contracts. File 05 owns the capability declarations and sub-mode mechanism; File 23 owns the confinement and the per-platform realization; File 06 owns the tier gating; File 09 and File 11 own the reversal and the version-graph file history. The per-platform package managers, service controllers, configuration stores, and device facilities are replaceable implementations behind the capabilities.

## 9. Change Records, Reversibility, and Rollback

Anchor: `sys.reversibility`

### 9.1 Definition

A change record is how the System Agent surface remembers a mutation so the user can review and reverse it. It is not a private change log or rollback store; it is a ledger entry plus committed observations plus a declared reversal over the shared substrate. The surface's reversibility model makes a system change reviewable and, where the operation allows, reversible, without a parallel store.

### 9.2 The Change Record

A mutating system operation records a change as: the durable ledger entry the pipeline already writes (`ledger.execution-ledger`, File 10 §3), the before-state `SystemStateSnapshot` `Observation` it captured and committed at the preview stage (§7.2, §6.4), the after-state observation it captured at verification, and the declared reversal (§9.3). The before-state observation the reversal references is exactly the one committed at the preview stage, not a fresh capture taken at reversal time. The `changes` presentation unit and `sys.change.list` are a projection over these (`run.presentation`, File 04 §25); there is no `system_changes` table. The change record carries the operation, the target, the reversibility class, the initiator (user or agent), and the verified outcome, with secrets and personal data redacted (`security.secret-detection-redaction`, File 22 §7).

### 9.3 Reversibility and the Reversal Declaration

Every mutating system capability declares its reversibility through the canonical `reversibility_class` metadata field (`artifact.capability-metadata-declarations`, File 09 §16.2; `capability.execution-semantic-fields`, File 05 §3.6, whose closed values are `none`, `compensable`, and `reversible`). This surface additionally declares WHICH reversal mechanism realizes a non-`none` class — a surface-local reversal-strategy annotation layered over the canonical field, never a replacement vocabulary for it:

- **Inverse-capability reversal** (canonical class `compensable`, or `reversible` for a self-symmetric operation) — the operation declares an inverse capability and the before state needed to apply it (a configuration write declares the configuration delete or the prior-value write; a service stop declares the service start; an adapter disable declares the adapter enable). The reversal is the inverse capability plus the captured before state.
- **Snapshot-restore reversal** (canonical class `compensable` — the compensating action is the restore) — the operation is reversible only by restoring a captured snapshot (a registry-tree change, a backup-restore), so the before-state `Observation` or a content-addressed backup is the reversal's required input.
- **No reversal** (canonical class `none`) — the operation cannot be undone (process termination, a destructive format, an unrecoverable delete). It declares `none`, carries the `Denied`-floor typed-confirmation gate (§11.3), and records no reversal.

A workspace-file mutation is not reversed through this model: it is a sibling-block version, and its reversal is a version switch (`version.version-switching`, File 11 §8), the version graph being the single file-history mechanism (`workspace.materialization`, File 24).

### 9.4 Rollback Is a Fresh Inverse, Not Historical Replay

`sys.change.rollback` reverses a recorded change by invoking its declared inverse as a fresh capability invocation over the current machine state — the same observe, preview, approve, sandbox, execute, verify, audit lifecycle as any forward operation (§7) — not by replaying the historical ledger. Historical ledger replay reconstructs a prior execution for audit and debugging and must never re-apply live system effects (`ledger.replay-semantics`, File 10 §11). A rollback revalidates that the change is still in effect before reversing it (the service is still stopped, the value is still changed) and returns a typed result when the machine has moved on. A rollback is itself an audited, reversible-where-applicable operation.

### 9.5 Multi-Step Rollback Walks the Provenance Chain

A multi-step operation — install a package, configure it, start its service, add a user to a group — records each change with a `conditioned_on` dependency edge (`block.canonical-edge-kinds`, File 08 §5.2) on the changes it depends on, the edge carried on the dependent change's before-state `Observation` block. A multi-step rollback walks that dependency network in reverse order — the provenance closure over the `conditioned_on` edges (`artifact.provenance`, File 09 §15.2) — reversing each reversible step from the most dependent to the least, and stops with a typed partial-rollback result at the first irreversible step or unreversable failure, never silently. The reverse-dependency order is the provenance traversal; its concrete algorithm is a replaceable implementation, and there is no `system_rollback_dag` table. The dependency-ordered reversal plan is exposed as the `rollback` presentation unit's projection over the change records (§4.2).

### 9.6 Boundary

This section owns the reversibility model and the rollback workflow. File 05 and File 09 own the reversal-and-postcondition capability metadata; File 09 owns the before-state observation and the provenance chain; File 11 and File 24 own the version-graph file history; File 10 owns the ledger the change record projects over and the replay semantics rollback must not invoke for live effect. This file declares the reversal model; those files own the mechanisms.

## 10. Scripts and Command Execution

Anchor: `sys.scripts-execution`

### 10.1 Definition

Script and command execution is the System Agent surface's escape hatch for what no dedicated `sys.*` capability covers: building, previewing, and running a shell script, and running a single confined shell command. It is dedicated-capability-first — a covered intent prefers its dedicated capability (§5.5) — and every script and command runs confined through the one `Sandbox`, gated by the safe-operation lifecycle, and audited.

### 10.2 The Script Builder and the Confined Command

A script is authored — by the agent or the user — as a file `Artifact` with a language hint (`artifact.artifact-kind`, File 09 §4), source identity, and trust state, inspectable and versioned through the one version graph. Plugin, community, imported, or downloaded scripts and templates require source approval before execution; agent-generated scripts default to generated/untrusted and use the stricter sandbox profile until the user approves or promotes them. `sys.script.preview` produces a dry-run or static preview of what the script will do where the interpreter supports it; `sys.script.execute` runs the script as a `ManagedProcess` on a pseudo-terminal at the `OsConfined` tier under a system `SandboxProfile` (`process.spawning`, File 23 §5.4, `sandbox.isolation-tiers` (File 23 §4)), with its environment constrained to the declared allowlist (`process.spawning`, File 23 §5 `EnvPolicy`), its output captured as a `TerminalOutput` observation, and a finite, configurable, killable wall-clock safety guard, never a correctness condition (`sandbox.resource-limits`, File 23 §9.3). Shell and script capabilities must not accept or compose command strings containing inline secret values. Credentials are supplied through mechanisms that do not expose them in the command line or process table — sandbox `EnvPolicy` injection with `SecretRef` resolution, stdin, a restrictive temporary credential file cleaned up after use, or the operation's native credential-store integration — and the pre-dispatch guardrail rejects detected secret patterns with `SecretInCommandLine` before dispatch. A successful, reusable script or operation sequence is promotable to a `WorkflowTemplate` or `Macro` `Artifact` and to a reusable workflow through the automation-reuse path (`run.automation-reuse`, File 04 §26). The confined command (`sys.script.execute` of a single command, or the borrowed neutral shell capability) is the same model: a confined `ManagedProcess`, output as observation, audited.

### 10.3 The Neutral Shell Capability and the Dedicated-Tool Boundary

Free-form shell and command execution is a neutral capability over the one `ManagedProcess` model (`process.spawning`, File 23 §5), not a System Agent-private operation: the Coder surface surfaces it for development work in the workspace (`coder.actions-declaration`, File 27 §5.2), and the System Agent surface surfaces it for system administration. The System Agent surface owns the high-level `sys.*` operation families above raw shell, not exclusive ownership of the shell itself; the GUI Control surface excludes operating-system-level operations from its default zones (`gui.actions-declaration`, File 31 §5.2) and reaches them only by borrow or reroute (`gui.cross-surface`, File 31 §18.4). When the agent attempts a covered operation through raw shell — installing a package by hand, editing a configuration file by `sed`, terminating a process by a kill command — the surface prefers, and redirects to, the dedicated `sys.*` capability that carries the preview, the per-platform backend, the postcondition, and the reversal (`unit11-cross-tool-learning.md` CT.16): under the resolved `Strict` mode the `prefer_dedicated_tools` template emits an actionable `RedirectSuggestion` naming that capability and its suggested arguments, terminal for the proposed shell call; under `Warn` it returns `NoOpinion` with a typed `RedirectAdvisory`; under `Off` it returns `NoOpinion` and no advisory (`policy.approval-policy-templates`, File 06 §12.3), the mode resolving through the policy settings (`policy.settings-resolution-for-policy`, File 06 §16.1). The redirected invocation is a new proposal that runs the complete capability-call pipeline. It is never an out-of-band rewrite of the user's or agent's command, and the redirect grants its target no authority. Dangerous-pattern denials and dedicated-tool redirects are policy reusable rules/templates evaluated at proposal time; the shell service remains neutral and confined. Confined output that would expose secrets or personal data is redacted before it becomes an observation, an event, or an audit payload (§5.5).

### 10.4 Boundary

This section owns the script-and-command workflow and the dedicated-tool boundary. File 23 owns the `Sandbox`, the `ManagedProcess`, the pseudo-terminal, the environment allowlist, and killability; File 09 owns the file artifact, the `TerminalOutput` observation, and the workflow-promotion artifacts; File 04 owns the automation-reuse path; File 27 owns the Coder surfacing of the shared shell capability. The shell, interpreter, and pseudo-terminal mechanisms are replaceable implementations behind the capabilities.

## 11. Safety, Approval Posture, and Cascading-Damage Limits

Anchor: `sys.safety`

### 11.1 Definition

The System Agent surface acts on the most dangerous subject any surface touches: the machine the user depends on. Its safety is the structural realization of that **asymmetric blast radius** over the shared policy, world-model, perception-privacy, audit, and stuck-detection substrates; it introduces no private heuristic engine, rate-limiter watchdog, blacklist store, or monitoring subsystem. The old "rate limiting plus a blacklist plus logging" substitutes map onto the policy reusable rules, stuck detection, and the audit overlay.

### 11.2 The Guardrail Denied-Operation Rules

Structurally-catastrophic operations are `Denied`-floor reusable-policy rules (`policy.built-in-reusable-policy-rules`, File 06 §11.5) the pre-execution guardrail enforces (§7.3). The shipped floor family is the operations Atlas denies unconditionally on every platform: recursively deleting an operating-system root or critical system directory, overwriting or reformatting a whole disk or the boot volume, and disabling the security, audit, or update subsystem the system itself depends on. Beside it stands an extensible denied-operation family a user, a workspace, or an approved source may add rules to through the reusable-rule set, never a hardcoded constant (`settings.settings-over-constants`, File 15 §13); an added rule narrows and a shipped floor rule is not removable through it (`policy.effective-tier-resolution`, File 06 §4.2). Both are denied at the floor; a denial is returned in-band as a typed result (`run.denial-is-in-band`, File 04 §8.3), and the floor is not liftable by `AlwaysAllow` or `agent.unrestricted_mode` (§11.3).

### 11.3 Destructive-, Irreversible-, and Sensitive-Operation Escalation

The surface contributes approval-policy templates (`policy.approval-policy-templates`, File 06 §12.4) and named availability checks (`world.state-aware-capability-availability`, File 18 §9.3) that escalate by the operation's blast radius, evaluated by the one policy layer:

- a destructive or irreversible operation — process termination, an unrecoverable delete, a disk operation, a power shutdown, a security-setting change, an account modification — escalates to the `Denied`-floor typed-confirmation gate (`policy.permission-floor-typed-confirmation`, File 06 §7), and because the danger is per-target rather than per-capability, an `AlwaysAllow` on the underlying capability does not lift the destructive-target confirmation
- an operation on a security-sensitive target — the firewall, the security or antivirus service, the audit subsystem, an administrator account, a boot or recovery configuration — escalates all operations on that target's context and composes the File 22 trust model with the surface's contributed sensitive-target policy
- an operation requiring an integrity level the current process lacks surfaces the elevation requirement and crosses the elevated-helper boundary under typed confirmation (§14), with the typed `ElevationMismatch` (`sandbox.declared-vs-observed`, File 23 §13) returned rather than a silent failure when elevation is unavailable
- a generic system operation whose resolved target is Atlas-owned critical state is rejected with `SelfModificationBlocked` before dispatch. This includes `sys.process.*`, `sys.service.*`, `sys.config.*`, shell-mediated equivalents, and `sys.filesystem.*` operations whose target overlaps the Atlas data root, database file, blob store, vault file, workspace `.atlas/` internals, audit overlay, sandbox/elevated-helper state, policy kernel, or active managed-process controller. The critical target set is derived from runtime-known identities and data locations, not a hardcoded path list. Legitimate Atlas lifecycle and security actions use dedicated Atlas capabilities, never generic OS mutation.

These are contributed posture over the one policy layer, evaluated against the world snapshot; the surface evaluates no policy itself.

### 11.4 Cascading-Damage Limits

Cascading-damage protection bounds a runaway sequence of high-blast-radius operations. A detected loop or stagnation is `run.stuck-detection` (File 04 §20.3) plus the stagnation signal (`perception.output-contract`, File 19 §9.6), which injects a corrective signal and escalates to a hard stop. A sustained burst of mutating operations without intervening user confirmation is governed by a configurable risk budget since the last confirmation or safe point. The budget is a declared, state-driven function over the operation count, the destructive or sensitive target class, repeated same-target mutation, unresolved verification failures, and the loop and stagnation signals — never an elapsed-time threshold as the correctness mechanism — resolved through the settings cascade as `surface.system_agent.cascading_damage_budget` (§21.3), never a hardcoded constant (`settings.settings-over-constants`, File 15 §13). Its shipped default accumulates risk units since that point — one unit for each mutating operation, one added unit for each operation whose target is in a destructive or sensitive class, one added unit for each repeated mutation of the same target, and one added unit for each unresolved verification failure and each loop or stagnation signal — and is exhausted at twenty risk units, a capacity an ordinary unattended sequence reaches, because a budget no sequence reaches bounds nothing. Exhaustion escalates the next mutating operation to fresh user confirmation and is surfaced typed, never a silent stop. Any elapsed-time guard is only a finite, configurable, killable safety guard — decisive without a completion signal, otherwise a last-resort backstop — never the correctness mechanism (`sandbox.resource-limits`, File 23 §9.3). The surface owns the cascading-damage posture and the signals it observes; it owns no private rate-limiter watchdog or monitoring store.

### 11.5 Untrusted Captured Content and Sensitive-Content Redaction

All content the surface captures from the machine that it did not itself author — command and script output, log content, file content, process and service names, configuration values read from the machine — is `untrusted_source_data` (`context.authority-classes`, File 13 §2.3) and can never, by its own text, widen a lease, lift a permission floor, lift a typed-confirmation requirement, lower a sensitivity classification, or authorize an operation (`security.untrusted-content`, File 22 §12.2). An instruction found in a log line, a file, or a process's output reaches the runtime as data the user or policy still gates, never as a command; this is non-negotiable. Captured configuration values, environment variables, command output, and backups that bear secrets or personal data are redacted before any capture becomes a durable observation, an event, an audit payload, a log, an export, or a sync stream (`security.secret-detection-redaction`, File 22 §7, `secret.backend-boundary` (File 22 §4)), and a credential value supplied into an operation is never materialized raw. Redaction of `TerminalOutput` is defense-in-depth, not permission to put secrets in command lines; `SecretInCommandLine` is rejected before process dispatch (§10.2).

### 11.6 Boundary

This section owns the System Agent safety posture and its mapping to canonical owners. File 06 owns the policy templates, the reusable rules, the typed-confirmation gate, and the batched-approval flow; File 22 owns the untrusted-content rule, the secret and personal-data detection, the trust model, and the egress governance; File 04 owns the stuck detection; File 18 owns the sensitive-target facts and the availability checks; File 23 owns the resource and safety guards and the elevation boundary. This file declares the posture and the mapping; those files own the mechanisms.

## 12. Monitoring, Watches, and Scheduled Tasks

Anchor: `sys.monitoring-scheduling`

### 12.1 Definition

Monitoring and scheduling are how the System Agent acts on the machine without a person present: a watch fires work when a system condition crosses a threshold, and a scheduled task fires work on a time or event trigger. The surface declares the watch and scheduled-task capabilities, but the evaluation and scheduling are `Trigger`-rail entries over the world model and the one scheduler, event-first, with the deep mechanics deferred to the Automation and Triggers spec. The surface owns no private watch store, scheduler, or monitoring subsystem.

### 12.2 Watches Are Event-First Over Perception and the World Model

A watch — on a file, a directory, a process, a port, a service, a metric, or a log pattern — is realized through `Perception`'s sensors and the world model, event-first (`perception.triggers`, File 19 §8.1): a filesystem, process, port, or service watch fires on the corresponding operating-system event, and a threshold crossing is an `AppEvent` on the one bus, not a poll result. A watch on a continuous metric with no change event — processor load, memory pressure, thermal state — uses a flagged, configurable sampling interval as the explicit exception (`perception.triggers`, File 19 §8.2), the only permitted polling and never the default. Each watch declares its `WatchPolicy` — edge-triggered or level-triggered behavior, reset condition, threshold hysteresis or equivalent state predicate, and deduplication key (`automation.watch`, File 33 §4.3) — and its `OverlapPolicy` — the maximum-outstanding-run behavior by which repeated firings while a prior run is unresolved skip with a typed reason, queue, replace, or run in parallel (`automation.overlap`, File 33 §12.1; burst COALESCING is the shared fire-admission debounce, `automation.watch` File 33 §4.3, not an overlap mode). `sys.monitor.watch`, `sys.monitor.list_watches`, `sys.monitor.stop_watch`, and `sys.monitor.history` declare and inspect watches; a threshold crossing fires a `Trigger`-rail entry (`controlrail.chosen-model`, File 26 §1) producing a `RunIntent` (`routing.trigger-kinds-routing`, File 03 §2.1) whose action — a notification, a script, an agent invocation, or a recorded incident — is the trigger's task. The watch definition's durable store and evaluation scheduling belong to File 33 (Automation and Triggers); the active-watch set is exposed as the `monitors` presentation unit's projection over the active trigger entries and the world model.

### 12.3 Scheduled Tasks Are Aliases Over the One Scheduler

A scheduled system task — recurring, one-time, file-change, or event-triggered — is a `Trigger`-rail entry over the one scheduler, not a private scheduler. `sys.schedule.create` and its siblings are thin aliases over the unified scheduler with the action pre-filled as a system-agent invocation (`unit14-systems.md` D14.SP.2): the schedule, its trigger, its persistence, and its execution log are the scheduler's, and a workflow or pipeline a scheduled task runs is the unified execution graph (`systems/19-scheduling-pipeline.md` §19.3, the shared execution DAG, `run.execution-entry` File 04 §4). A natural-language automation request resolves through the shared automation-creation path (`unit11-cross-tool-learning.md` CT.9). The scheduled-task set is exposed as the `scheduled` presentation unit's projection over the scheduler's entries; there is no `system_scheduled_tasks` table owned here. The deep scheduling, eligibility, enablement, missed-trigger handling, and non-interactive-execution safety belong to File 33 (Automation and Triggers), and the automation object — trigger, task template, world selector, capability scope, validation policy, failure handling, output contract (`codex_recommendations.md` §9.3) — is that spec's contract; a successful multi-step system operation is eligible for automation suggestion through the automation-reuse path (`run.automation-reuse`, File 04 §26).

A schedule, watch, or workflow template may sync as an inert definition. Activation on a device creates a device-local binding only after platform, target, permission, sandbox, source-approval, policy, and egress checks pass. Active firing state, last-run state, missed-trigger state, and before-state observations remain device-local.

### 12.4 Non-Interactive-Execution Safety

A watch- or schedule-triggered system task runs non-interactively, so the safety posture is stronger, not weaker: a non-interactive run pins the System Agent surface, its capabilities, and its policies at save time the way routing does, runs at or below the approval posture the user authorized for unattended work, confines through a system `SandboxProfile`, and records every operation to the audit overlay. Standing authorization may cover only operations whose effective policy can be satisfied without fresh typed confirmation. If the run reaches a typed-confirmation or `Denied`-floor operation, it parks in `awaiting_user`, notifies through the control rail, and resumes only after the user supplies fresh confirmation (`policy.permission-floor-typed-confirmation`, File 06 §7). The deep non-interactive-safety mechanics belong to File 33 (Automation and Triggers); this file fixes that an unattended system task is never a weaker-safety path.

### 12.5 Boundary

This section owns the monitoring-and-scheduling workflow and the event-first rule. File 19 owns the sensors and the trigger model; File 26 owns the `Trigger` rail; File 33 (Automation and Triggers) owns the scheduler, the watch store, the automation object, and the non-interactive-execution mechanics; File 04 owns the execution graph and the automation-reuse path. This file declares the capabilities and defers the mechanics.

## 13. User Takeover, Intervention, and Metacognition

Anchor: `sys.takeover-intervention`

### 13.1 Definition

User takeover and intervention are how the user steers a running system task, and metacognition is how the agent reflects before a high-blast-radius operation. Both are the shared run lifecycle and the elicitation rail, not a private task store or a private reflection engine.

### 13.2 Control, Takeover, and Intervention

A system task is a run (File 04) over the System Agent surface; the run carries the canonical `control` field (`run.minimum-durable-reconstruction`, File 04 §2.6) recording whether the agent or the user is driving. During a long-running operation — a package install, a backup, a cleanup, a script — the user may interject through user intervention (`run.user-intervention`, File 04 §17.1): the run pauses (`run.pause-resume`, File 04 §17.2), the user injects guidance ("skip that directory", "stop before the service restart"), and the agent incorporates it and continues, redirects, or stops (`unit11c-system-agent.md` D11.SA.7). The user takes over and hands back; on hand-back the surface reconciles from fresh observations of the current machine state (§6). While a run holds control of the machine, the current control holder and an immediate takeover control are continuously available; where a client surfaces them is its own, realized in the windowed-desktop profile as an activity-panel placement (`ui.rail-presentation`, File 37 §11). The control transition is the canonical run control transition, never a private ownership field, and there is no `system_tasks` store.

### 13.3 The Needs-Help Handoff

A condition the agent must not complete on the user's behalf — a credential or password prompt, an interactive installer choice, a hardware or physical confirmation, an operating-system permission dialog, or a destructive operation the user must perform — is an elicitation handoff (`controlrail.elicitation`, File 26 §13) to the user, who completes the interaction; the run then resumes with the established state. The handoff is the canonical elicitation rail, not a private dialog subsystem; the surface declares which conditions trigger a handoff.

### 13.4 Metacognition Is the Plan Capability and a Reflection Critique

The pre-destructive reflection the source material proposes as dedicated "think" tools (`unit11c-system-agent.md` D11.SA.8, the metacognitive pattern from `serena`) is realized through the shared `plan` capability and an advisory reflection `Critique`, not a private think subsystem: before a high-blast-radius or multi-step operation, the agent may call the shared `plan` capability (`run.task-promotion-task-updates`, File 04 §18) to produce an editable `Plan` block enumerating what it will change and why, and a reflection sub-agent role (§15.5) may produce an advisory `Critique` block (`artifact.validation-critique`, File 09 §14) assessing task adherence and completeness. These are carried in the activity projection (§4.2) and are tools and blocks, not a phase machine or an autonomy mode (§22).

### 13.5 Boundary

This section owns the takeover, intervention, and metacognition workflow. File 04 owns the run, the `control` field, intervention, pause-resume, and the `plan` capability; File 26 owns the elicitation rail; File 09 owns the `Plan` and `Critique` blocks; File 18 owns the world-state reconciliation. This file presents them as the System Agent affordances.

## 14. Elevation, Isolation, and Cross-Platform Realization

Anchor: `sys.elevation-isolation-platform`

### 14.1 Definition

The System Agent runs confined, elevates only through the one-shot helper, and is cross-platform-first-class. Its contract is platform-invariant over replaceable per-platform backends, and a capability whose platform mechanism is absent reports unavailable rather than failing the surface.

### 14.2 Isolation and the Elevated Helper

A system operation that runs a native binary — a package manager, a service controller, a script interpreter — runs as a `ManagedProcess` at the `OsConfined` tier through the one `Sandbox` (`sandbox.isolation-tiers`, File 23 §4), with the broad host filesystem and network access it needs granted explicitly through its `FilesystemPolicy` and `NetworkPolicy`, not by escaping confinement; a generated or untrusted script runs at the tier its trust class requires, up to `Virtualized` (`sandbox.isolation-tiers`, File 23 §4.3). A privileged operation — one requiring administrator or superuser rights — crosses the elevated-helper boundary (`sandbox.elevated-helper`, File 23 §11): a separate, least-privilege, lazily-installed helper runs the single command over local inter-process communication against a hardcoded command allowlist and exits, the main process never elevating, no agent or automation driving the helper through ordinary capability paths, and the operation gated by the policy floor and typed confirmation (§11.3). An operation requiring an integrity level the process lacks returns the typed `ElevationMismatch` (`sandbox.declared-vs-observed`, File 23 §13) with the elevation-remediation path, never a silent failure.

### 14.3 Platform-Invariant Contract Over Replaceable Mechanisms

The host platforms are first-class; no platform is the canonical mechanism (`sandbox.cross-platform`, File 23 §15). The package manager, the service controller, the configuration store, the registry, the environment-persistence mechanism, the system-introspection facility, the device and power facilities, the shell and pseudo-terminal, and the privilege-elevation facility are replaceable implementations behind the capabilities' sub-modes (`capability.capability`, File 05 §2.3) and File 23's cross-platform realization; the surface depends on the contract, never on a platform-specific facility the contract does not expose. A capability whose mechanism a platform lacks — the Windows registry on a non-Windows platform, a service controller a platform does not run — is registered only where its mechanism is available and reports unavailable elsewhere (`sandbox.cross-platform`, File 23 §15.3, `world.environment-temporal-connection-facts` (File 18 §6.4)). The cross-platform configuration store is the registry's first-class peer, not its afterthought; the Windows-primary framing is deleted (§22). The mobile and constrained-platform subset excludes the operations the platform does not host.

### 14.4 First-Run Permission and Setup

A system operation may require an operating-system permission, an installed helper, or a platform facility that is not present by default. The surface surfaces these as explicit setup flows (`sandbox.cross-platform`, File 23 §15.4, `perception.capture-privacy` (File 19 §10.1)): a capability whose required permission or helper is not present reports the requirement with a clear explanation and a guided setup step, the dependent capability disabled until setup completes and the independent capabilities continuing. The surface may guide the user and verify completion after the user acts, but any setup command it presents must come from built-in release metadata, signed or update metadata, or source-approved extension metadata; absent a trusted setup source, the surface explains the requirement and asks the user to complete setup manually rather than inventing an elevated command. It never silently grants permissions, installs the elevated helper without consent, or elevates without the policy floor and confirmation. The `availability_predicate` and the named availability checks (§5.5) gate the surface and its capabilities on the current permission and platform state.

### 14.5 Boundary

This section owns the elevation, isolation, and cross-platform stance and the first-run setup workflow. File 23 owns the `Sandbox`, the isolation tiers, the elevated helper, the declared-versus-observed enforcement, and the per-platform realization; File 19 owns the permission model; File 18 owns the platform facts. The per-platform backends are replaceable implementations behind the contracts.

Planning is the optional shared `plan` capability (`run.task-promotion-task-updates`, File 04 §18): the agent may call it for a high-blast-radius or multi-step operation to produce an editable `Plan` block, and a complex maintenance task may decompose into child runs (`run.child-runs-multi-agent-work`, File 04 §16) — a coordinator plus per-target executors — but there is no planning phase, no planner-versus-executor model split, no phase state machine, and no per-surface "thoroughness mode" toggle (the executor thoroughness level is a workflow parameter, `unit11-cross-tool-learning.md` CT.21). The surface declares its spawnable sub-agent types (`run.child-runs-multi-agent-work`, File 04 §16, `worksurface.runtime-execution-declaration` (File 25 §9.2)) — representatively a long-running-operation executor, a background monitor, a package-installer-with-progress, a scheduled-task tracker, and a trajectory-reflection role producing advisory `Critique` blocks — and declares default run budgets as advisory ceilings overridable per scope, never hidden hard limits (`run.budgets-limits`, File 04 §21).

### 15.6 Instruction-File Qualifier and Workspace Relationship

The System Agent surface declares its instruction-file qualifier — the `ATLAS.system_agent.md` variant of the `ATLAS.md` hierarchy (`workspace.instruction-files`, File 24 §9.2) — and its model-request instruction contribution: the surface's identity, the machine and platform facts, the untrusted-captured-content discipline, the safety posture, the dedicated-tool-preference rule, and the system-operation guidance, assembled by context assembly into the `InstructionSources` region with the correct authority class (`context.instruction-sources-workspace-files`, File 13 §16); the contribution is one attributed assembly part, never a private prompt the surface owns, and content captured from the machine is never instruction authority regardless of its text (§11.5). The surface's views render over the bound `Workspace` (`workspace.conversation-binding`, File 24 §7); its authored scripts, backups, reports, and saved templates materialize through the disk↔substrate mirror and File 23's filesystem boundary (`workspace.materialization`, File 24 §10); its per-surface working convention defaults to a configurable `system/` convention. The surface owns no workspace identity, disk-history store, or parallel materialization path.

## 18. Cross-Surface Composition

### 18.1 Definition

Cross-surface composition is how the System Agent surface composes with other surfaces: the System Agent capabilities other surfaces borrow, the captured machine state that composes into other surfaces' outputs, the surface boundaries it respects, and the capabilities it borrows in place.

### 18.2 System Agent Capabilities Borrowed by Other Surfaces

### 18.4 Surface Boundaries and Borrowing in Place

The System Agent surface operates at the operating-system level. It does not puppet foreign applications: clicking, typing into, and reading an application's window are the GUI Control surface's (`gui.cross-surface`, File 31 §18.4), and where a system task needs an application driven — a graphical installer with no command-line path, an application's own settings UI — the System Agent borrows the GUI Control capability or reroutes, never puppeting through a System Agent-private path. It does not drive the browser: web search, fetch, and browser automation are the Web surface's, borrowed for an update-URL lookup. The two boundaries are reciprocal — the GUI Control surface excludes operating-system-level operations from its default zone and reaches them through System Agent borrow (`gui.actions-declaration`, File 31 §5.2) — and the two surfaces compose through borrow and reroute, never a shared private mechanism. A System Agent run that needs a capability outside the surface — file write to save a script, web fetch to look up a package, the coder code-execution capability to compute over captured state, memory recall of a known-good configuration — borrows it in place and remains in the System Agent surface (§5.4); it reaches another surface's workflow only through a routing reroute or explicit user override, never by silent surface change.

### 18.5 Boundary

This section owns the System Agent cross-surface composition. File 07 owns borrowing; Files 08 and 09 own the shared pools; File 03 and File 04 own reroute; the GUI Control and Web surfaces own the application-puppeting and browser boundaries. The borrowing surfaces own their own workflows.

## 19. World-Model, Perception, and Observation Integration

Anchor: `sys.world-perception`

### 19.1 Definition

The System Agent surface integrates with the world model and perception by self-registering its presentation units and state, contributing the world facts its work observes, exposing the sensors it consumes, and producing the observations its runs depend on — all through the canonical contracts (`worksurface.world-perception-integration`, File 25 §15).

### 19.2 Self-Registration and World Facts

The System Agent surface self-registers its presentation units, focus, and selection to the one world model when a unit is activated and on focus and content change, and unregisters when it is deactivated (`world.observation-state-update`, File 18 §8.1); a unit it fails to register is a blind spot. Its own units' state is learned through self-registration, never through perception scraping (`perception.tiered-sensing`, File 19 §5.4). The system facts its work observes — the `Device` (the machine and its platform, hardware, and capabilities), the `Process` (running processes and their state), and the `Sandbox` entities, plus the environment and temporal facts (operating system and platform, shell, working directory, locale and timezone, network connectivity, and permission states, `world.environment-temporal-connection-facts` (File 18 §6.1)) — are the canonical entity and fact kinds File 18 already declares (`world.world-entity`, File 18 §4.3); the surface contributes their observed facts through perception, not a private store. Services, installed packages, network configuration, scheduled tasks, and active watches are observed facts and, where a durable queryable live entity is warranted (an enabled watch, an active long-running operation), `Custom` world-entity kinds registered through the canonical mechanism, never a private store. The world model holds the live values; the surface produces the observations that update them.

### 19.3 Sensors and Observations

The System Agent surface declares the sensors it exposes — `SystemMetric`, `Process`, `Environment`, `Filesystem`, `Network`, and `Liveness` (`perception.consequences-for-later-specs`, File 19 §19) — and consumes their structured output; perception owns the capture mechanics, the sensitive-source detection, and the redaction, and the surface owns no private capture pipeline (`perception.explicit-rejections`, File 19 §18). It is structured-data-first: it reads through the structured sensors, parsing a confined command's output only for a facet no sensor covers (§6). It produces `ProcessState`, `EnvironmentSnapshot`, `FileSnapshot`, `WorkspaceSnapshot`, `TerminalOutput`, `SystemStateSnapshot`, and `SystemHealthSnapshot` observations through the canonical `observation.commit` path (§5.3) where a run depends on them for verification, reversal, or replay; transient captures remain transient until a captured state is deliberately committed as an observation.

### 19.4 Availability

The System Agent surface's available-operation list is the available-capability list the world model's availability evaluator computes for the surface's scope (`world.state-aware-capability-availability`, File 18 §9), filtered by the active surface state, the granted permissions, and the platform; the surface registers the named availability checks of §5.5 (the package-manager, service-controller, configuration-store, platform, elevation, device-facility, and backup-destination checks) and maintains no private available-operation store.

### 19.5 Boundary

This section owns the System Agent world-model and perception integration. File 18 owns the entity catalogue, self-registration, durability tiers, and availability evaluator; File 19 owns the sensors, capture, privacy, and redaction; File 09 owns the observation blocks; File 23 owns the process and sandbox snapshots. This file integrates through them.

## 20. Persistence, Locality, and Portability

Anchor: `sys.persistence-locality`

### 20.1 Definition

The System Agent surface's durable state persists as substrate families through the one storage contract, splits by locality the way a workspace's does, and moves cross-installation through the canonical portability mechanisms. The surface introduces no private durable store.

### 20.2 What Persists and Where

The surface's durable state — its registered `SurfaceContract` versions, its registered `Custom` kinds and system extensions, its scoped enable state and settings, its authored scripts, saved macros and workflow templates, diagnostics reports, and the blocks, artifacts, versions, committed observations, change records, and audit entries its work produces — persists as substrate families and content-addressed blobs through the storage contract (`storage.durable-substrate`, File 20 §3, `storage.consequences` (File 20 §18)); large backups and large captures resolve from the content-addressed blob store (`storage.blob-store`, File 20 §6). The surface's live state — the active presentation units, focus, selection, the latest captures, the structured-state cache, sandbox and process handles, and active operations — is computed and rebuilt from self-registration and the version-graph projection, never a durable fact (`worksurface.persistence-locality`, File 25 §16.1); its loss is a rebuild, never data loss.

### 20.3 Locality

The System Agent surface's identity splits by locality the way a workspace's does (`worksurface.persistence-locality`, File 25 §16.2, `workspace.locality` (File 24 §4)): the surface's logical declaration, its authored scripts, its saved macros and workflow templates (as definitions), its configuration definitions, and its diagnostics reports sync, while device-bound state — change records (a change describes what happened on a specific machine), the active machine state, sandboxes and processes, active watch bindings and scheduled-task bindings, firing state, last-run state, missed-trigger state, and the device-specific reversal before-states — is device-local and never syncs as ordinary data, because a change and its rollback apply only on the device where the change happened (`portability.what-replicates`, File 21 §5). The hash-chained audit overlay is device-local and never syncs (`ledger.hash-chained-audit-log`, File 10 §16.4). A macro, workflow template, script, watch definition, or schedule definition that depends on a device-specific package, service, or path syncs only as an inert definition; activation on another device creates a local binding after revalidating the platform, target, per-platform backend, permissions, source approval, policy, sandbox profile, egress posture, and availability. No raw secret, credential, or unredacted sensitive value is materialized, exported, or synced (`secret.backend-boundary`, File 22 §4, `security.secret-detection-redaction` (File 22 §7)).

### 20.4 Portability

The surface's syncable durable state rides the syncable substrate and the `PortablePackage` for cross-device and cross-installation movement (`portability.consequences`, File 21 §18); a script, a workflow template, a macro, and a diagnostics report export losslessly with the content-addressed blobs they reference, unless policy or sensitivity filtering omits them with typed provenance gaps. Device-bound state and the audit overlay are not transported. The surface may declare a lossy convenience export (a rendered report, a script listing), but it passes through egress governance, audit recording, and sensitivity filtering (`security.egress-governance`, File 22 §11) and uses no private export path. Every hash the surface relies on — a capture content hash, a blob address, a staleness fingerprint, an audit-chain entry hash, an export-bundle hash — is computed over a declared `CanonicalEncoding`, never physical storage bytes (`core.canonical-hash`, File 01 §7.14); the surface defines no new canonical hash, and the audit-chain entry hash is `security.audit-crypto` (File 22 §14)'s.

### 20.5 Boundary

This section declares the System Agent persistence and locality classification. File 20 owns the storage substrate, the blob store, and rebuild orchestration; File 21 owns replication and the package; File 22 owns the secret, egress, and audit-cryptography boundaries; File 24 owns the workspace locality split; File 11 owns the version-graph projection; File 10 owns the device-local audit overlay.

## 21. Capability, Event, and Settings Surface

Anchor: `sys.capability-event-settings`

### 21.1 Capabilities

The System Agent surface contributes its capabilities to the one Capability Registry as `Subsystem`-sourced built-ins (`capability.declaration`, File 05 §3), tier-gated by policy (File 06), surfaced through tool-surface composition (File 07), and invoked through the shared pipeline (`run.call-pipeline`, File 04 §8.2). The capability families are enumerated in §5.2. Each capability declares its touched resources (notably the process, service, package, configuration, registry, network, device, power, and filesystem resources, registered as extension resource classes per `capability.extension-resource-classes` (File 05 §6.3)), permission tier and floor, reversibility class and declared inverse (§9.3), preview and dry-run behavior, postcondition validation, concurrency, replay class, and produced block and observation kinds; an operation that depends on a prior capture declares the stale-state revalidation pattern (§6.4), and a capture declares its `replay_class` so a recorded observation replays from its capture rather than a live re-capture (`capability.replay-class`, File 05 §7.3). The surface introduces no parallel capability registry and no out-of-band operation path, and every System Agent capability is the single source for all its invocation paths (`core.extension-planes`, File 01 §6.14).

### 21.2 Events

The System Agent surface emits its events through the one event bus and ledger with the canonical envelope (`ledger.event-stream`, File 10 §5), stamped with the `backend_id` dimension that demultiplexes concurrent operations, sandboxes, and processes (`ledger.event-envelope`, File 10 §5.2). Surface-lifecycle and tool-surface events are owned by Files 25, 07, and 18 and flow through their vocabularies; world-entity, observation, version, artifact, run-control, cancellation, trigger-firing, schedule lifecycle, watch evaluation, eligibility, missed-trigger, and scheduler events are owned by Files 18, 09, 11, 04, and File 33 (Automation and Triggers) and flow through theirs. System-specific facts that no canonical or owning-file vocabulary already defines register as `Custom { namespace: "system_agent", name, payload }` extensions (`ledger.custom-kind-registration`, File 10 §4.3) — representatively the operation-previewed, operation-executed-and-verified, change-recorded, rollback-executed, package-installed, service-state-changed, elevation-required, and needs-help-handoff signals — each declaring its payload schema, cross-reference keys, default sensitivity, and retention. A world-affecting system operation defaults to the `Sensitive` classification (`ledger.sensitivity-aware-persistence-retention`, File 10 §10, `cross-cutting/events.md` realized) because a configuration path, a machine name, or a process command can leak; an innocuous read (system version, font list) may be classified `Public` per-emit, and a secret-bearing value is never carried raw. A world-affecting operation also registers into the reserved hash-chained audit-overlay membership (`ledger.hash-chained-audit-log`, File 10 §16.4), which is device-local, append-only, verifiable, and cannot be silently disabled (`unit11-cross-tool-learning.md` CT.20). The surface opens no side-channel store or notification path.

### 21.3 Settings

The System Agent surface's behavior is configurable through the one settings system (`core.settings-system`, File 01 §6.8, File 15) as namespaced keys under `surface.system_agent.*`, resolved through the standard cascade and composed with the per-substrate settings the owning files own (the sandbox, isolation, and elevation settings of File 23, the perception sensor, capture-privacy, redaction, and trigger settings of File 19, the policy, approval-template, reusable-rule, and tier settings of File 06, the model settings of File 16, the context and compaction settings of File 13, the trigger, scheduler, and automation settings of File 26 and File 33, the audit and event settings of File 10, and the secret, trust, and egress settings of File 22). Representative System Agent settings dimensions: the default and per-scope sandbox profile and isolation tier per operation category, the denied-operation reusable-rule set, the destructive-, irreversible-, and sensitive-target escalation templates, the sensitive-target categories, the cascading-damage risk budget (`surface.system_agent.cascading_damage_budget`, §11.4), the per-platform backend preference and the package-name mapping overlay, the first-run helper/setup metadata source, the metric-watch sampling interval (the flagged polling exception), the default watches and scheduled tasks per profile, the dedicated-tool-preference and redirect-suggestion posture, the backup destination, encryption, compression, and retention policy, the per-surface workspace convention, and the default view preset. The surface is not a durable settings scope (`settings.scopes-profile-contexts-overlays`, File 15 §5.1); per-surface variation is namespaced keys plus profile layers. Settings whose values are security-sensitive (the sandbox profile and isolation tier, the denied-operation set and escalation templates, the sensitive-target categories, the cascading-damage risk budget, the package-name mapping overlay, first-run helper/setup metadata sources, default watch and scheduled-task enablement, backup destination and retention policy, shell redirect posture, elevation policies, and extension enablement) declare conservative agent exposure (`policy.agent-exposure-policy-settings`, File 06 §16.4); no System Agent behavior with meaningful variation is a hardcoded constant (`settings.settings-over-constants`, File 15 §13).

### 21.4 Boundary

This section names the System Agent capability, event, and settings surface. File 05 owns the capability contract; File 06 owns policy; File 10 owns the event bus, custom-kind registration, and the audit overlay; File 15 owns the settings model and cascade; the owning substrate files own the per-substrate settings the surface composes with.

## 22. Explicit Rejections

Anchor: `sys.explicit-rejections`

The following are architecturally invalid for the System Agent surface and for any later spec that extends it:

- **A private system-execution pipeline or guardrail middleware engine** — the safe-operation lifecycle is the canonical capability-call pipeline carrying the surface's contributed previewable, approvable, sandboxed, verified, audited, and reversible posture; the pre- and post-guardrails are blocking hooks and policy reusable rules, not a private middleware chain (§7; `run.call-pipeline`, File 04 §8.2, `ledger.hook` (File 10 §7)).
- **A private `system_changes`, `system_watches`, `system_scheduled_tasks`, `system_rollback_dag`, or `system_audit_log` store** — a change is a ledger entry plus before/after observations, a watch and a scheduled task are `Trigger`-rail entries over the one scheduler, the rollback dependency order is a provenance traversal, and the audit log is the canonical device-local hash-chained audit overlay (§7, §9, §12, §21; `ledger.execution-ledger` (File 10 §3), `ledger.hash-chained-audit-log` (File 10 §16.4), `version.explicit-rejections` (File 11 §23)).
- **A private system-memory or machine-state store** — remembered machine preferences and runbooks go through Memory, live machine facts go through the world model, captured states are `Observation`s, and reusable procedures are `Artifact`s or `WorkflowTemplate`s; the System Agent creates no `system_memory`, `known_machine_state`, or equivalent parallel store (§6, §19).
- **"No sandboxing for system operations," or a private sandbox, process spawner, or kill path** — every system operation that runs a native binary runs at the `OsConfined` tier (escalating to `Virtualized` per trust) through the one `Sandbox` and the `ManagedProcess`/`ProcessGroup` model, with broad host access granted explicitly through the operation's filesystem and network policy, not by escaping confinement (§7, §14; `sandbox.explicit-rejections`, File 23 §20, `sandbox.isolation-tiers` (File 23 §4)).
- **A script-based or session-long elevation strategy, or the main process running elevated** — a privileged operation crosses the one-shot, least-privilege, hardcoded-allowlist elevated-helper boundary under the policy floor and typed confirmation; the main process never elevates (§14; `sandbox.elevated-helper`, File 23 §11).
- **A private scheduler, watch poller, or monitoring subsystem** — `sys.schedule.*` is a thin alias over the one scheduler, watches are event-first `Trigger`-rail entries over Perception and the world model, and the deep scheduling and watch mechanics belong to File 33 (Automation and Triggers); metric sampling is a flagged configurable exception, never the default (§12; `controlrail.chosen-model`, File 26 §1, `perception.triggers` (File 19 §8)).
- **Time-based behavior as a correctness condition** — monitoring, change detection, and readiness are event-first; the only permitted timers are the flagged, configurable metric-sampling interval where a source emits no change event and the finite, configurable, killable wall-clock and cascading-damage safety guards (`sandbox.resource-limits`, File 23 §9.3 — decisive only without a completion signal, otherwise a last-resort backstop) (§6.3, §11.4, §12.2; `perception.triggers`, File 19 §8, `sandbox.resource-limits` (File 23 §9.3)).
- **A per-operation undo database plus a separate rollback DAG store** — reversibility is declared capability metadata, a change's before state is a committed `Observation`, a rollback is a fresh inverse capability invocation, and a multi-step rollback walks the change records' provenance dependency chain in reverse; workspace-file changes are reversed through the version graph (§9; `artifact.provenance`, File 09 §15, `version.version-switching` (File 11 §8)).
- **Historical ledger replay re-applying live system effects** — rollback re-applies a declared inverse against the current state as a fresh, audited, approved operation; ledger replay reconstructs prior executions for audit and debugging without live effect (§9.4; `ledger.replay-semantics`, File 10 §11).
- **Authority granted by captured machine content** — command output, log lines, file content, configuration values, and process names captured from the machine hold no capability or policy authority; all captured machine content the surface did not author is `untrusted_source_data` (§11.5; `security.untrusted-content`, File 22 §12).
- **A separate "too sensitive for the normal stream" debug-log audit path** — world-affecting operations register into the canonical reserved hash-chained audit overlay with per-entry sensitivity classification; the surface opens no side-channel debug or audit file (§21.2; `ledger.hash-chained-audit-log`, File 10 §16.4, `ledger.sensitivity-aware-persistence-retention` (File 10 §10)).
- **A per-tool `AlwaysAllow` lifting a destructive-, irreversible-, or denied-operation gate** — the danger is per-target, so a destructive or irreversible operation, a sensitive-target context, and a structurally-catastrophic operation escalate to the `Denied`-floor typed-confirmation gate or are denied at the floor regardless of an `AlwaysAllow` on the underlying capability, and `agent.unrestricted_mode` does not lift the floor (§11; `policy.permission-floor-typed-confirmation`, File 06 §7, `policy.built-in-reusable-policy-rules` (File 06 §11.5)).
- **A private heuristic engine, rate-limiter watchdog, blacklist store, or monitoring subsystem for safety** — the asymmetric-blast-radius safety is the policy reusable rules and templates, the typed-confirmation gate, stuck/stagnation detection plus a state-driven risk budget, the perception capture-privacy and redaction, and the audit overlay; the rate-limit/blacklist/logging substitutes map onto those owners (§11; `policy.consequences-for-later-specs`, File 06 §18, `world.explicit-rejections` (File 18 §16), `run.consequences-for-later-specs` (File 04 §29)).
- **Persisting or exporting an unredacted secret, credential, or sensitive value** — secret and personal values are detected and redacted before any capture, event, audit payload, log, export, or sync stream, and a credential supplied into an operation is never materialized raw (§11.5; `security.secret-detection-redaction`, File 22 §7, `secret.backend-boundary` (File 22 §4)).
- **Inline secrets in shell or script command lines** — command strings, process tables, shell history, terminal observations, logs, and audit payloads are not secret-bearing channels; shell and script capabilities reject detected inline secrets with `SecretInCommandLine` and use vault-backed non-command-line credential delivery instead (§10.2, §11.5).
- **Generic System Agent mutation of Atlas-owned critical state** — Atlas process/service identities and Atlas-owned filesystem paths, including the data root, database, blob store, vault, `.atlas/` internals, audit overlay, sandbox/elevated-helper state, policy kernel, and managed-process controller, are not targets for generic `sys.process.*`, `sys.service.*`, `sys.config.*`, `sys.filesystem.*`, or shell-mediated mutation; legitimate Atlas lifecycle and security changes use dedicated Atlas capabilities (§11.3).
- **A System Agent autonomy, participation, system-mode, thoroughness-mode, persona, or phase field** — at any layer, in any form; System Agent autonomy is capability permission tiers, leases, and approval posture plus user direction, progressive disclosure is which presentation units are active and which view preset is applied, the per-profile specialization is a settings overlay and view preset (§16.2), the executor thoroughness level is a workflow parameter, and the `plan` capability is a tool, not a phase machine (§13.4, §16.2; `worksurface.no-autonomy-field`, File 25 §13). There is no planner-versus-executor model split and no participation dial.
- **A view preset that silently changes backend policy** — applying a System Agent view preset changes presentation only and never silently changes model selection, context policy, execution entry, budget, sandbox profile, or approval posture (§16.2; `worksurface.views-presets`, File 25 §7.2).
- **Driving foreign applications or the browser through a System Agent-private path** — the System Agent operates the operating system; puppeting an application's window is the GUI Control surface's (reached by borrow or reroute) and driving the browser is the Web surface's; the System Agent owns no application-automation or browser path (§18; `gui.cross-surface`, File 31 §18.4).
- **A Windows-primary or single-platform framing** — the host platforms are first-class over replaceable per-platform backends, the cross-platform configuration store is the Windows registry's first-class peer, and a capability whose platform mechanism is absent reports unavailable rather than failing the surface (§14; `sandbox.cross-platform`, File 23 §15).
- **Naming a specific package manager, service controller, configuration store, shell, elevation facility, or system-introspection library as the canonical semantics** — these are replaceable implementations behind the surface's capabilities, sensors, and sandbox; the canonical contract is the behavior, never the tool (Source Resolution; `core.extension-integrity`, File 01 §7.10).

## 23. Consequences for Later Specs

Anchor: `sys.consequences-for-later-specs`

Later specs must follow these rules:

- This is the **sixth and final baseline built-in per-surface specification**. The canonical work-surface baseline — Coder (File 27), Web (File 28), Data Processor (File 29), Teacher (File 30), GUI Control (File 31), and System Agent (File 32) — is now complete; every baseline surface fills File 25's `SurfaceContract`, owns user-facing workflows and specialized views, and owns no private architecture. A new surface registers through the same `SurfaceRegistry` path at flat cost (`worksurface.registry`, File 25 §10) and may not invent a work-surface primitive that bypasses the contract. The System Agent operates at the operating-system level while the GUI Control surface puppets applications and the Web surface drives the browser; the surfaces compose through borrow and reroute, not a shared private mechanism, and the other surfaces keep the System Agent capability family out of their default loaded zones, reaching it only by explicit borrow under the System Agent approval posture, sandbox, and audit (§18).
- The **Automation and Triggers** spec owns the deep mechanics of the watches and scheduled tasks this file frames as `Trigger`-rail entries (§12): the watch and schedule store, watch evaluation, trigger eligibility and enablement, missed-trigger handling, the automation object (trigger, task template, world selector, capability scope, validation policy, failure handling, output contract, `codex_recommendations.md` §9.3), the graduation of a successful multi-step system operation into a reusable automation (`run.automation-reuse`, File 04 §26), and non-interactive-execution safety — confined to a system `SandboxProfile`, pinning the System Agent surface and its policies at save time the way routing does, parking on any typed-confirmation or `Denied`-floor operation until fresh user confirmation, and never spawning an untracked or non-killable process. It introduces no parallel system-execution path; `sys.schedule.*` and `sys.monitor.*` remain aliases over the one scheduler and the world model.
- The **Workflows, Templates, and Reuse** spec owns the `WorkflowTemplate` and `Macro` promotion path this file consumes (§10.2): a successful system operation sequence promotes to a reusable workflow or macro through the canonical reuse path, never a System Agent-private script registry.
- The **Quality Control and Validation** and **Evaluation and Benchmarking** specs own the postcondition-validation and the system-operation evaluation surfaces this file produces into (§7, §9): a system operation's postcondition is a `Validation`, its reflection is a `Critique`, and its safe-operation lifecycle is replayable for audit and evaluation through the one ledger.
- The **Runtime Infrastructure and Lifecycle** and **Packaging, Platform, and Distribution** specs own the background-worker lifecycle a long-running monitor or operation runs under (`run.child-runs-multi-agent-work`, File 04 §16, confined per File 23) and the per-platform helper-binary and elevated-helper packaging this file's elevation and cross-platform realization references (§14; `sandbox.elevated-helper`, File 23 §11); they introduce no parallel system-operation, scheduler, or audit path.
- The **UI Shell**, **UI Customization**, and **Telemetry and Observability** specs own the rendering of the presentation units and view presets §4 and §16 declare — how a medium presents and composes the units it presents is theirs (`ui.layout`, File 37 §5), as is how it renders their substrate content (`ui.substrate-rendering`, File 37 §9) — and the system-metric and operation telemetry surfaces; they consume the data contracts this file specifies and own no system-operation behavior.
