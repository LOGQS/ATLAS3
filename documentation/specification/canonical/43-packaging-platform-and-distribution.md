# Packaging, Platform, and Distribution

## Status

Canonical. This file defines the build-time and install-time layer of ATLAS3: how the application is built into per-platform, per-architecture release artifacts; how those artifacts are signed, integrity-verified, and identified; how they are installed, integrated with the host operating system, updated, and uninstalled; the inventory of bundled and downloadable helper binaries and runtime assets the installer carries or fetches; the built-in ship-with content bundled into every install; the registration of the platform crash handler and the browser-extension native-messaging host; and the distribution channels through which the application reaches the user. It owns the *delivery* side of the system — what ships, how it is signed, where it is placed, how the operating system is told about it, how a new version is produced and staged, and how packaged built-ins are verified before they become trusted runtime inputs — and it introduces the net-new primitives the running layers reference but do not own: the `ReleaseArtifact` and its `ReleaseManifest`, the `ReleaseProvenance` reference, the `Installer` contract, the `UpdateChannel`, the `StagedUpdate` record, the `BundledBinary`, `RuntimeAsset`, and `SidecarInventory`, the `PlatformIntegration` registration set, the `BuiltinBundle` and its signed item manifest, and the `PlatformCrashHandler` registration. It is the static counterpart of the running runtime (File 42): Packaging produces, signs, places, and stages; the Runtime starts, supervises, drains, and relaunches. Later canonical files may refine it, but may not contradict it.

Resolved tensions:

- **A packaging runtime versus a build-and-deliver layer.** The corpus is full of "updater services," "package managers," and "extension stores" that own loops, state, and execution. Resolved decisively toward the build-and-deliver framing, the same substrate-not-engine reframe File 41 made for observability and File 42 made for the runtime: Packaging produces immutable signed artifacts at build time, places a read-only image and registers it at install time, and stages a new version at update time; it runs no agent loop, owns no durable runtime state, and hosts no work surface. Everything that *runs* — the relaunch, the sidecar supervision, the crash recovery — is the Runtime's (File 42). This is the load-bearing reframe of this file.
- **In-place update versus apply-on-restart with staged rollback.** Mutating a running installation risks a half-applied update and a corrupt run. Resolved (consistent with `runtime.update-relaunch`, File 42 §18) toward apply-on-restart: this file produces, signs, verifies, downloads, and stages the new version and signals readiness; the Runtime drains and relaunches into the staged version; File 20's last-known-good marker and the pre-stable recovery-check list guard a bad update and roll it back. This file never mutates the running image.
- **A mandatory code-signing certificate versus integrity-always with signing-where-available.** A paid operating-system code-signing certificate (Apple Developer ID, Windows Authenticode) is unavailable under the zero-monetary-spend constraint, yet update integrity must never be optional. Resolved toward integrity-always-plus-signing-where-available: every update package carries a signature over its content hash verified against a public key bundled in the application (a free signing keypair, the committed realization being the Tauri-updater minisign-style scheme), and this verification is mandatory; operating-system notarization and authenticode signing are a declared funded-future extension that, when present, additionally satisfies the platform's gatekeeper, and unsigned or ad-hoc-signed binaries handle the platform's quarantine attribute explicitly. The *trust class* an install or update confers stays File 22's (`security.trust-model`, File 22 §9.4): the application's own installation trust is inherited by bundled content, and evidence-based `Verified` requires verifiable authorship evidence such as a trusted signature.
- **Bundle everything versus lazy-download versus a hybrid.** Bundling every packaged runtime payload makes a fast offline install but a large download; lazy-downloading everything makes a small installer but a network-dependent first use. Resolved toward a hybrid keyed by a closed `BundlingStrategy`: eager-bundle only what every launch requires, lazy-download large optional payloads on first use of the feature that needs them, install-on-demand the elevated helper and VM-guest binaries, and separately-publish the browser extension. The installer stays under a per-platform size budget, lazy components are hosted on a free-for-open-source release host with a mirror, and a payload that cannot be obtained degrades its feature gracefully rather than blocking the application.
- **One distribution route versus many over one artifact identity.** Resolved toward many distribution routes delivering the same signed `ReleaseArtifact`: direct download and a free-for-open-source release host as primary, package-manager manifests (the committed realizations being Homebrew, Scoop, winget, Flatpak, and the native Linux package formats) as additional routes, the CLI via a language package manager or a shell installer, and the browser extension via the browser stores. The distribution route is provenance, not a different product; every route resolves to the same verifiable artifact content hash.
- **Who registers the native-messaging host.** File 36 owns the native-messaging *session protocol* and the peer-identity handshake; the host *registration* — the per-platform manifest placement that lets the browser find the application binary, written on first use of the external browser backend and removed on uninstall — is install-and-platform-integration work. Resolved here: this file owns the registration and the extension publication; File 36 owns the protocol; the protocol-version-skew handshake that surfaces "update the extension" is File 36's.
- **Who owns the crash handler.** File 41 observes and owns the in-app diagnostic bundle and the telemetry-consent contract; File 22 owns the redaction detector. The native crash *handler registration* — installing the platform-level capture so a crash is recorded even when the application's own loop is gone — is install-and-platform work. Resolved here: this file registers the platform crash handler and bundles the reporter; the raw crash capsule feeds the Runtime's unclean-shutdown recovery path, remains restricted local staging, and becomes an egress-eligible diagnostic only after File 22 redaction and File 41 consent.
- **A heavy net-new object set versus a minimal one.** Resolved toward minimal, the same discipline File 42 applied: `ReleaseArtifact` (+ `ReleaseManifest` and a provenance reference), `Installer`, `UpdateChannel`, `StagedUpdate`, `BundledBinary`, subordinate `RuntimeAsset` (+ `SidecarInventory` and the closed `BundlingStrategy`), `PlatformIntegration` (+ the closed `PlatformIntegrationKind`), `BuiltinBundle` (+ signed item manifest), and the `PlatformCrashHandler` registration. Everything else is consumed from its owning layer.

## 1. Chosen Model

Anchor: `packaging.chosen-model`

### 1.1 Definition

ATLAS3 has one packaging, platform, and distribution layer. It is a build-time and install-time layer that:

- **builds** the application into immutable, signed, content-identified `ReleaseArtifact`s, one per platform, architecture, and channel, each described by a `ReleaseManifest`;
- **installs** a `ReleaseArtifact` by placing a read-only application image under the platform installation directory and registering the application with the operating system through the `PlatformIntegration` set;
- **bundles** the ship-with content — the built-in capability declarations, the canonical kind catalogues, the surface contracts, the default settings and profiles, the ship-with plugins and themes, the built-in evaluation suites and golden fixtures, and the seed files — into the install image as the `BuiltinBundle`, the `Builtin` source the running layers register at first run;
- **carries** the packaged runtime inventory through the `SidecarInventory`, eager-bundling some `BundledBinary`s and `RuntimeAsset`s, lazy-downloading others, and installing some on demand;
- **delivers** a new version through an `UpdateChannel` by producing, signing, verifying, downloading, and staging it, then signalling the Runtime to apply it on restart;
- **registers** the platform crash handler and the browser-extension native-messaging host.

It is the realization of the packaging, persistence-placement, security-boundary, and provider-integration concerns the Infrastructure layer (`core.system-layers`, File 01 §2.5) names, and the static counterpart of the Runtime (File 42): the Runtime hosts the *running* application; this file produces, signs, places, registers, and stages *what runs*.

### 1.2 Purpose

Every running layer assumes a delivered, installed, registered, and updatable application and a stock of bundled content, and delegates the delivery to this file. File 42 needs a staged update to relaunch into and a sidecar binary inventory to run under its managed-service contract and a platform crash handler to feed its recovery path. File 20 needs an installation image to sit beside the data root it owns and a last-known-good guard the update relaunch consults. File 22 needs signed artifacts whose integrity it can verify and whose installation trust it can confer. File 36 needs the native-messaging host registered so the browser extension can reach the backend. Files 05, 07, 09, 12, 24, 27, 35, 38, and 40 need their built-in declarations, kinds, surface contracts, default settings, ship-with plugins, themes, and evaluation fixtures shipped in every install as the `Builtin` source. This file is the single place those delivery mechanics become concrete, so that no later spec invents a parallel installer, a second updater, an ungoverned download path, a private ship-with channel, or an unsigned artifact.

### 1.3 Rule

- There is one packaging, platform, and distribution layer. No subsystem, surface, plugin, or connector ships a parallel installer, a private auto-updater, a second release channel, an ungoverned binary-download path, a separate ship-with channel, or an artifact whose integrity is not verifiable. Every shipped build is a `ReleaseArtifact`, every delivered helper binary or runtime asset is in the `SidecarInventory`, every operating-system registration is a `PlatformIntegration`, and every ship-with declaration is part of the `BuiltinBundle`.
- This layer builds and delivers; it does not run. It produces, signs, places, registers, bundles, and stages; it hosts no agent loop, owns no durable runtime state of record, executes no work surface, and registers no `SurfaceContract`. Everything that runs — the relaunch into a staged update, the supervision of a delivered sidecar, the recovery after a crash the registered handler captured — is the Runtime's (File 42), the storage substrate's (File 20), or the owning layer's.
- An update applies on restart, never in place. This file produces, signs, verifies, downloads, and stages a new version and signals readiness; the Runtime drains and relaunches into it; File 20's last-known-good marker and this file's pre-stable recovery-check list guard it and roll back a bad update. Mutating the running image is rejected.
- Integrity is always verifiable; the trust class is File 22's. Every update package's signature over its content hash is verified before staging; operating-system notarization and authenticode are a declared extension; the application's installation trust and the trust class of any installed or updated source are File 22's.
- The installed image is read-only; the data root is the running layers'. The installer places a read-only application image under the platform installation directory and ensures the user-writable data root can be created; the data root itself, the single-instance lock, the substrate, the vault, and every durable runtime fact are created and owned at runtime by Files 20, 22, and 24, never written by the installer beyond first-creation enablement.
- The agent suggests; the user installs and updates. The agent may surface that an update is available or that a feature needs a downloadable binary, but installing, updating, registering autostart, and the other consequential delivery actions are user-gated and policy-bound (Files 05, 06); no agent, automation, or update silently mutates the installed image, the platform registrations, or the channel.

### 1.4 Net-New Objects and Supersession

The net-new noun-objects this file introduces are deliberately minimal: `ReleaseArtifact` (+ `ReleaseManifest` and `ReleaseProvenance` reference), `Installer`, `UpdateChannel` (+ the closed `UpdateChannelKind` set), `StagedUpdate`, `BundledBinary` and subordinate `RuntimeAsset` (+ the `SidecarInventory` they compose and the closed `BundlingStrategy` set), `PlatformIntegration` (+ the closed `PlatformIntegrationKind` set), `PlatformTarget` (+ the closed tier model), `BuiltinBundle` (+ its signed item manifest), and the `PlatformCrashHandler` registration. Everything else is consumed: the run model and relaunch from File 42, the storage lifecycle and last-known-good from File 20, the trust model and signing-as-evidence from File 22, the sandbox and elevated-helper process model from File 23, settings and the bootstrap boundary from Files 15 and 42, the plugin lifecycle from File 35, the native-messaging session from File 36, the diagnostic bundle and consent from File 41, the capability declaration and event envelope from Files 05 and 10.

`ReleaseArtifact` supersedes any earlier vocabulary that named the same delivered build: "the installer", "the build output", "the release", "the package", "the bundle", "the dmg", "the exe", "the AppImage", "the binary". `UpdateChannel` supersedes "release channel", "track", "ring", "stable/beta/nightly stream". `BundledBinary` supersedes "sidecar binary", "helper binary", "external bin", "bundled dependency", "vendored runtime" for executable or loadable-code payloads; `RuntimeAsset` names non-executable runtime payloads such as model weights, OCR language data, WebAssembly standard libraries, and equivalent data assets that share the same integrity and placement discipline. `Sidecar` remains the canonical term for the *running* form, which is a `ManagedProcess` (File 23) the Runtime supervises; the `BundledBinary` is the packaged artifact it runs from. `PlatformIntegration` supersedes "OS integration", "shell integration", "file association", "protocol handler", "autostart entry", "tray registration". `BuiltinBundle` supersedes "ship-with content", "bundled assets", "built-in declarations", "the installer image's content". These are the canonical typed shapes the rest of this file uses; earlier names from source material map into them.

This model elaborates `core.system-layers`, `core.stack-commitments`, `core.extension-planes`, `core.extension-integrity`, `core.non-destructive-by-default`, `core.closed-canonical`, `core.canonical-hash`, and `core.projection` (File 01). It discharges the delivery concerns deferred by `runtime.update-relaunch`, `runtime.process-topology`, `runtime.crash-recovery`, and `runtime.consequences-for-later-specs` (File 42); the built-in-declaration packaging mandated by `capability.lifecycle` (File 05), `artifact.consequences-for-later-specs` (File 09), `surface.consequences-for-later-specs` (File 07), `workspace.consequences-for-later-specs` (File 24), `coder.consequences-for-later-specs` (File 27), and `eval.consequences-for-later-specs` (File 40); the native-messaging-host registration deferred by `integration.mcp-session` (File 36); the platform crash-handler registration deferred by `observability.boundaries-with-adjacent-layers` and the observability consequences (File 41); and the installer, window-decoration, first-paint-cache, and ship-with-theme bundling deferred by File 37 and `customize.consequences-for-later-specs` (File 38). Cross-file references prefer stable anchors; generated line numbers or drift-prone section numbers are not normative.

## 2. Boundaries with Adjacent Layers

Anchor: `packaging.boundaries`

### 2.1 With File 42 (Runtime Infrastructure and Lifecycle)

The `42↔43` seam is the central boundary and is fixed (`runtime.update-relaunch`, `runtime.process-topology`, and `runtime.boundaries-with-adjacent-layers`, File 42): Packaging **delivers and stages binaries and registers platform handlers**; the Runtime **starts, supervises, drains, and relaunches them**. This file produces, signs, downloads, and stages a new version and signals readiness; File 42 performs the graceful shutdown and relaunches into the staged version and runs the startup self-checks. This file ships the `SidecarInventory`; File 42 runs each compatible `BundledBinary` as a `ManagedProcess` under its managed-service start-health-supervise-reap lifecycle contract and lets owning features load compatible `RuntimeAsset`s. This file registers the `PlatformCrashHandler`; File 42's crash-recovery path consumes the unclean-shutdown evidence it captures (`runtime.crash-recovery`, File 42). This file owns no boot graph, no shutdown contract, no worker, no transport, and no relaunch mechanics; it produces what the Runtime brings up.

### 2.2 With File 20 (Storage and Persistence)

File 20 owns the data root, the single-instance lock-file *placement*, the substrate, the blob store, schema migration, the pre-migration backup, the last-known-good marker, garbage collection, and the storage-side reconstruction internals (`storage.physical-layout-locality`, File 20 §8; `storage.backup-integrity-recovery`, File 20 §12; `storage.lifecycle-reconstruction`, File 20 §13). The split is install-image-versus-data-root: this file's installer places the read-only application image under the platform installation directory (`storage.physical-layout-locality`, File 20 §8.3: "the installation directory is read-only to the running application; only the data root is user-writable") and ensures the user-writable data root can be created, but never writes the substrate, the lock, the vault, or any durable fact into it — those are created at runtime by Files 20, 22, and 24. A staged update this file produces is applied by File 42's relaunch and guarded by File 20's last-known-good marker and pre-migration backup (`storage.backup-integrity-recovery`, File 20 §12.3); this file's pre-stable recovery-check list composes with that guard.

### 2.3 With File 22 (Security, Credentials, and Trust Boundaries)

File 22 owns the trust model, the trust classes, the install-time capability-manifest review flow, the integrity-verification *semantics*, the code-signing-as-evidence-path, the secret vault, the egress governance, the audit cryptography, and the privilege-separation pairing credential (`security.trust-model`, `security.secret-vault`, and `security.device-trust`, File 22). The split is artifact-production-versus-trust-decision: this file produces signed `ReleaseArtifact`s and update packages and verifies their signature over their content hash before staging, and it ships the per-platform signing posture; File 22 decides what trust an installed or updated source carries — the application's installation trust is the root the verified `BuiltinBundle` inherits, and evidence-based `Verified` requires the verifiable authorship evidence a trusted signature provides. The no-code-signing-certificate-in-v1 reality is realized exactly as File 22 fixes it: ship-with content inherits installation trust after bundle-manifest verification, the update signature verification is mandatory and free, and operating-system notarization is the declared funded-future evidence path. A raw crash capsule this file's handler captures stays restricted local staging until File 22's secret detector produces a redacted diagnostic for display or egress.

## 3. The `ReleaseArtifact` and the `ReleaseManifest`

Anchor: `packaging.release-artifact`

### 3.1 Definition

A `ReleaseArtifact` is one immutable, signed, content-identified build output for a single `PlatformTarget` (platform and architecture, §4) and a single `UpdateChannel` (§11), at a single version. A `ReleaseManifest` is the signed descriptor a channel serves: it names the current version, the channel, the release notes and publication instant, the build-provenance reference, and, per `PlatformTarget`, the artifact location, the signature, and the content hash. The `ReleaseArtifact` is what an `Installer` installs and an update delivers; the `ReleaseManifest` is what the update check reads.

### 3.2 Rule

- A `ReleaseArtifact` carries: a stable application identity, a semantic `version`, the `PlatformTarget`, the `UpdateChannel`, the read-only application image (the binary, the bundled frontend assets, the eager `BundledBinary`s and `RuntimeAsset`s, and the `BuiltinBundle`), and an integrity descriptor — the content hash over the artifact's opaque byte payload and the signature over that hash (§5). The artifact is immutable: a change produces a new version and a new artifact, never a mutation of a published one.
- A `ReleaseManifest` carries: the application identity, the `version`, the `UpdateChannel`, the publication instant, the human-readable release notes, the minimum-compatible version for the update gate (§11.3), the signed `ReleaseProvenance` reference, and, per `PlatformTarget`, the artifact location, the signature, and the content hash. The manifest is itself signed; the update check verifies the manifest signature before trusting any artifact reference it carries.
- A `ReleaseProvenance` reference is integrity-bound to the manifest and artifact (`packaging.release-provenance`). It records at least the source revision or source package identity, toolchain identity, dependency lock hash, frontend asset hash, `BuiltinBundle` item-manifest hash, `SidecarInventory` hash, and builder identity where available. The exact CI provider, log format, SBOM encoding, and artifact-hosting layout are realization choices.
- The integrity descriptor adopts File 21 §10.4's typed-versus-opaque split (`portability.export-bundle`, File 21 §10.4): an opaque payload — the artifact image and any bundled binary or runtime asset it carries — is content-hashed over its bytes, while a typed record — the `ReleaseManifest`, the `ReleaseProvenance` reference, and the `BuiltinBundle` item manifest — is hashed over a declared `CanonicalEncoding`, never over incidental physical bytes (`core.canonical-hash`, File 01 §7.14). Two distribution routes may serve the same artifact identity; the content hash is the artifact's identity across routes and mirrors, so a mirror or a package manager that re-hosts the same artifact is verified against the same hash.
- A `ReleaseArtifact` is reproducible to the degree the toolchain allows: the build is deterministic where its inputs are pinned, so an independent rebuild of the same version and target can be compared against the published content hash. Where full bit-for-bit reproducibility is not achievable, the build pins its inputs and records the toolchain identity, and the integrity guarantee rests on the signature, not on rebuild equality.
- The committed realizations are the platform installer formats the desktop-shell bundler produces; the contract — an immutable, signed, content-identified per-target build and a signed per-channel manifest — is independent of any one format or bundler.

### 3.3 Boundary

This section owns the artifact and manifest contract and the integrity descriptor. The signing mechanism is §5; the platform targets and the build are §4; the channels and the update check that reads the manifest are §11; the last-known-good guard the staged artifact is applied against is File 20's (§12.3).

## 4. Platform Targets and the Build

Anchor: `packaging.build-targets`

### 4.1 Definition

A `PlatformTarget` is a (platform, architecture) pair for which a `ReleaseArtifact` is built. The platform-tier model is the closed classification of how supported each platform is. The build is the pipeline that produces the per-target artifacts from the one source tree, including the frontend asset bundle the desktop shell wraps.

### 4.2 The Platform-Tier Model

The platform tiers are a closed canonical set:

- **First-class desktop** — Windows, macOS, and Linux, each on its supported architectures. A first-class target is built, signed-where-available, integrity-verified, and released on every channel; its capabilities are the full surface.
- **Deferred mobile** — a mobile platform (the committed realization being a mobile build of the same Rust core with a mobile shell) carrying a reduced capability surface, feature-gated at build time so desktop-only mechanisms (interactive process terminals, browser automation, desktop GUI control, the VM sandbox) are excluded. Mobile is a declared planned target, not a v1 release target.
- **Architecturally-open, not-a-distribution-target** — a platform the architecture must not foreclose but that this file does not distribute to (the committed example being a platform whose only distribution path is a paid, review-gated store incompatible with the zero-monetary-spend and minutes-away-self-distribution constraints). Such a platform receives no `ReleaseArtifact`; the architecture remains free of any decision that would prevent later support.

A capability that requires a mechanism a target does not provide returns a typed unsupported result on that target, composing the platform-as-availability rule (`capability.platform-availability`, File 05 §9.4) and the headless-and-multi-front parity rule (`runtime.service-graph`, File 42 §9.4). The tier set is final: exactly these three tiers, with no `Custom` extension grant (`core.closed-canonical`, File 01 §6.16). A future platform is admitted by adding its `PlatformTarget` to the open target catalogue (§4.1) and classifying it into one of the three tiers, not by extending the tier set, so a new platform never needs a parallel build system.

### 4.3 Rule

- The build produces one `ReleaseArtifact` per first-class `PlatformTarget` per channel from the one source tree. The committed realization is a single application binary per platform that compiles the per-platform mechanism variants behind feature gates and platform-conditional compilation, rather than a separate codebase per platform; a build target selects the variants its platform provides.
- The frontend asset bundle (the rendered shell's markup, scripts, styles, the bundled localization assets, the design-token and theme assets, and the typed inter-process-communication bindings generated from the backend's typed surface) is built and embedded as read-only assets in the artifact. The frontend bundler and framework are committed realizations behind the contract; no canonical rule depends on a specific bundler, and the localization and theme assets are bundled with the frontend, never loaded from a network at runtime and never stored in browser local storage (`settings.local-toml-overlay`, File 15; the no-local-storage rule).
- A release channel is a build configuration, not a separate codebase: a channel selects feature-flag and capability-exposure configuration at build time (the committed realization being channel-keyed feature-flag arrays), so a beta or nightly artifact is the same code with a different configuration, never a fork. A feature absent from a channel's configuration is dead-code-eliminated from that channel's artifact where the toolchain supports it.
- The build pins its inputs (the toolchain version, the dependency lock, the bundled-binary and runtime-asset versions, and the `BuiltinBundle` item-manifest hash) and records the pinned set in the signed `ReleaseProvenance` reference, so a `ReleaseArtifact`'s provenance is inspectable and an independent rebuild is comparable (§3.2).
- The build, the continuous-integration pipeline, the per-target build environments, and the release automation are realization concerns this file frames but does not freeze; the canonical requirements are the per-target artifact, the signed manifest, the pinned-input provenance, and the channel-as-configuration rule.

### 4.4 Boundary

This section owns the platform-tier model, the per-target build, the frontend-bundle embedding, and the channel-as-configuration rule. The artifact and manifest are §3; signing is §5; the per-platform mechanism realizations the variants select are File 23's and the owning surface specs'; the headless and command-line build parity is File 42's (§9.4).

## 5. Code Signing, Notarization, and Integrity

Anchor: `packaging.signing-integrity`

### 5.1 Definition

Signing is the cryptographic attestation that a `ReleaseArtifact` or update package was produced by the application's release process and not altered since. Notarization is an operating-system vendor's additional attestation that a signed binary has passed the vendor's checks. Integrity verification is the recipient's confirmation, before installing or staging, that an artifact matches its signed content hash. This section owns the posture; File 22 owns the trust class an installed or updated source carries.

### 5.2 Rule

- **Update-package integrity verification is mandatory.** Every update package carries a signature over its content hash, verified against a public key embedded in the running application before the package is staged. The committed realization is the desktop-shell updater's signing-keypair scheme (a free signing key, not a paid certificate); a package whose signature does not verify against the embedded key is rejected, recorded, and never staged. This verification is non-optional and is independent of any operating-system certificate.
- **Update-signing keys are versioned trust anchors** (`packaging.update-signing-key-rotation`). A new update-signing key is accepted only through a key-transition record or manifest signed by an already trusted update key, or through an explicit reinstall/manual trust-recovery path governed by File 22. A revoked key, compromised key, or downgrade to an older signing key is rejected and surfaces a typed recovery state. This file owns the delivery-key acceptance path; File 22 owns the trust response and recovery policy.
- **Operating-system signing and notarization are a declared funded-future extension.** Where a code-signing certificate is available (Apple Developer ID, Windows authenticode, or an equivalent), the artifact is additionally signed and, where the platform requires, notarized, so the operating system's gatekeeper accepts it without a warning. The zero-monetary-spend reality is that v1 ships without a paid certificate (`security.trust-model`, File 22 §9.4): the signing infrastructure is specified as the extension path, and an unsigned or ad-hoc-signed artifact is the v1 norm. Acquiring and managing the certificate, when funding or a foundation grant makes it available, is this file's concern; the trust class the signature establishes is File 22's.
- **Unsigned and ad-hoc-signed binaries handle the platform quarantine explicitly.** Where a platform marks a downloaded binary with a quarantine attribute that its gatekeeper enforces, the installer or the first-run flow handles the attribute explicitly for the application's own bundled binaries (the committed realization being the macOS quarantine-attribute removal for the application's bundled helper binaries after a verified download), so a verified-but-unsigned helper runs without a silent gatekeeper interception. The quarantine handling never extends to content the application did not produce and verify.
- **The trust class is File 22's.** This file produces and verifies signed artifacts; File 22 decides what trust an installed or updated source carries (`security.trust-model`, File 22 §9): the application's installation trust is the root the `BuiltinBundle` inherits, a signature is one evidence path to `Verified`, and an integrity-verification failure on a delivered artifact is a tamper signal File 22 treats as such. This file never claims a trust guarantee its signing posture cannot prove.
- **Downloaded packaged runtime payloads are verified before use.** A lazy-downloaded or install-on-demand `BundledBinary` or `RuntimeAsset` (§9) is verified against the content hash the `SidecarInventory` records before it is placed, loaded, or run; an unverifiable download is discarded, recorded, and the dependent feature degrades gracefully (§9.5). A partial download is never run or loaded (§9.4).

### 5.3 Boundary

This section owns the signing posture, the mandatory update-integrity verification, the notarization extension path, and the quarantine handling. The trust class, the integrity-verification semantics, and the tamper-signal response are File 22's (§9); the audit recording of a delivery action is File 10's (§16.4); the content hash encoding is File 01's (§7.14).

## 6. The `Installer`

Anchor: `packaging.installer`

### 6.1 Definition

The `Installer` is the per-platform contract by which a `ReleaseArtifact` is placed on a device, registered with the operating system, and later removed. It places a read-only application image, ensures the user-writable data root can be created, registers the `PlatformIntegration` set, runs install and uninstall hooks, and removes the image and registrations on uninstall.

### 6.2 Rule

- **The installation image is read-only; the data root is the running layers'.** The installer places the application image — the binary, the frontend assets, the eager `BundledBinary`s, eager `RuntimeAsset`s, and the `BuiltinBundle` — under the platform installation directory (the committed realizations being the platform program directory, the platform application bundle, and the platform library directory), read-only to the running application (`storage.physical-layout-locality`, File 20 §8.3). It ensures the user-writable data root (the committed realization being the platform per-user application-data directory, the `~/.atlas/` shorthand resolving per platform) can be created; the data root, the substrate, the single-instance lock, the vault, and every durable fact are created and owned at runtime by Files 20, 22, and 24, never written by the installer beyond first-creation enablement.
- **Install is per-user by default and needs no standing elevation.** The base install requires no administrator privilege; the running application is unprivileged (`security.threat-model`, File 22 §3.3; `runtime.process-topology`, File 42 §4.3: "the core process never runs elevated"). Only the elevated helper's first-use installation prompts for elevation (§13), and only a system-wide install variant, where offered, requests it at install time.
- **The installer runs declared pre/post install and uninstall hooks.** The hooks perform the platform-registration and first-creation steps — creating the start-menu and desktop entries, registering the platform integrations (§7), checking for and refusing to clobber an incompatible prior installation, repairing missing or stale owned registrations, and ensuring the data root is creatable — and the uninstall hooks reverse the registrations. A hook performs delivery and registration work only; it runs no business logic and writes no durable user data.
- **The first run is handed to the running application.** The installer may launch the application on completion; the first-run experience — the data-root creation, the substrate open and migration, the `BuiltinBundle` registration, the vault unlock, the profile pick, and the onboarding — is the running application's (Files 20, 42, 35, 15, and the onboarding owner), not the installer's. Any license or terms acceptance the distribution requires is presented at install or first run as a declared step, recorded, and never silently assumed.
- **Core first run is offline-capable.** The installed image plus the verified `BuiltinBundle` is sufficient for first-run startup, core local conversation/workspace operation, settings/profile registration, and safe UI boot without network. Lazy sidecars, optional models, external integrations, and separately published extensions may remain unavailable with typed acquisition paths; no core local startup path depends on a live distribution host.
- **Uninstall is non-destructive to user data by default** (`packaging.uninstall-data-boundary`). Uninstall removes the installation image, the platform integrations, the native-messaging host registration (§8), and the elevated helper (§13), and it terminates a running instance through the platform's graceful-then-forceful process termination before replacing or removing the image (the committed realization being a graceful window-close or signal, a grace period, then a forceful process-tree termination). It preserves the user-writable data root by default (`core.non-destructive-by-default`, File 01 §7.13). Any option to remove user data is a separate storage/security-governed wipe with preview, explicit scope, typed confirmation, vault handling, audit-overlay handling, and backup/export options where safe; the uninstaller never silently deletes the substrate, the vault, the workspaces, or the audit overlay.

### 6.3 Boundary

This section owns the install and uninstall contract and the image-versus-data-root split. The platform-integration registrations are §7; the data root, lock, and substrate are File 20's; the vault is File 22's; the workspaces are File 24's; the first-run registration of the `BuiltinBundle` is the owning layers'; the graceful-then-forceful termination mechanics are File 23's and File 42's.

## 7. Platform Integration

Anchor: `packaging.platform-integration`

### 7.1 Definition

A `PlatformIntegration` is a registration by which the installed application is made known to and reachable from the host operating system. The `PlatformIntegrationKind` set is the closed catalogue of those registrations.

### 7.2 The Closed `PlatformIntegrationKind` Set

The canonical set is closed-canonical-plus-`Custom`:

- `ApplicationEntry` — the start-menu, application-launcher, dock, or desktop shortcut and the application's registration as an installed application
- `FileAssociation` — the association of file types the application opens with the application, so a double-click or an "open with" routes to it
- `ProtocolHandler` — the registration of the application's deep-link scheme handler (the committed realization being an `atlas`-scheme handler), so a deep link routes to the running instance through the single-instance handoff (`runtime.process-topology`, File 42 §4.4)
- `NotificationRegistration` — the registration the operating system requires to deliver native notifications on the application's behalf
- `TrayItem` — the system-tray or menu-bar item and its menu, the persistent affordance for show, pause, and quit
- `Autostart` — the login-item or autostart entry that launches the application at user login, opt-in and user-revocable, never on by default
- `UninstallRegistration` — the operating-system uninstall-registry or package-database entry that lets the platform's "installed applications" surface and uninstall the application
- `DisplayAndWindowMechanics` — the platform-level high-density-display awareness and window-decoration mechanics the binary registers at startup (the committed realizations being the per-monitor display-awareness call and the platform window-decoration mode), which the shell's window presentation (File 37) sits on
- `EnvironmentReconstruction` — the reconstruction of the execution environment a process launched by an operating-system mechanism (autostart, a login agent, an installer-created shortcut, or a host that strips the environment) needs, rebuilding the search path and key variables from the platform's authoritative configuration (the committed realization being the registry-or-profile path reconstruction with a defined precedence)
- `Custom { integration_id }` — a registered integration outside the set, admitted through source approval (File 06 §9)

### 7.3 Rule

- A `PlatformIntegration` is registered at install (or, where the platform requires user consent or the integration is opt-in, on first use of the feature that needs it) and is reversed on uninstall. Every integration carries an ownership record: integration kind, platform identity, installed artifact identity, registration path or key, owning app id, and the hash of the registered payload where applicable. Install, update, repair, and uninstall reconcile this desired state against the platform state, fixing missing or stale owned registrations without mutating registrations owned by other applications.
- Consequential integrations are user-gated. `Autostart` is opt-in and off by default and is user-revocable through settings (§15); `FileAssociation` and `ProtocolHandler` registration is presented where the platform expects user confirmation; the agent may propose enabling an integration but never registers one unattended (`packaging.capability-surface-events`, §14).
- The single-instance OS facility is placed, not owned, here. Where the platform offers a single-instance mechanism, this file's installer or first-run registers it; the *acquisition*, the running-instance handoff, and the stale-lock reclaim are File 42's (`runtime.process-topology`, File 42 §4.4), and the lock-file placement under the data root is File 20's (§8.3). A `ProtocolHandler` deep link routes to the running instance through that handoff and then through the canonical external-protocol/navigation rail (`controlrail.external-protocol-rail`, File 26 §12): external deep links reveal or navigate by typed target by default, into the renderer root the presentation layer's window-resolution rule resolves and under its typed window-creation limits so repeated links never spawn windows without bound (`ui.shell`, File 37 §4.4), and any consequential action they encode enters the normal capability-policy path rather than executing from the OS payload (`packaging.protocol-handler-rail`).
- The binary registers its `DisplayAndWindowMechanics` and `EnvironmentReconstruction` at startup, before any platform-interface or window call, because a launched process may have an incomplete environment or an unset display-awareness state; these registrations are platform-variant code compiled into or resolved at runtime from the artifact, keyed by the operating-system version where the platform interface varies by version (the committed example being build-number-keyed platform-interface selection).
- The application binds no application-level network port of record (`runtime.process-topology`, File 42 §4.3); no `PlatformIntegration` opens or registers one. The frontend bridge is native inter-process communication (File 42 §10), so the installer registers no port, no local server, and no firewall exception for an application server.

### 7.4 Boundary

This section owns the platform-integration registration set and its install-and-uninstall lifecycle. The window presentation the display mechanics support is File 37's; the single-instance acquisition and handoff are File 42's; the lock-file placement is File 20's; the deep-link routing target is the running instance (File 42); the native-messaging-host registration is §8.

## 8. The Native-Messaging Host and Browser-Extension Distribution

Anchor: `packaging.native-messaging-host`

### 8.1 Definition

The native-messaging host is the per-platform registration that lets a browser extension discover and launch the application's backend as a native-messaging peer. Browser-extension distribution is the separate publication of the application's browser extension to the browser stores. This section owns the registration and the publication; File 36 owns the session protocol the host serves.

### 8.2 Rule

- **The host registration is per-platform and binds the extension identity.** The application registers a native-messaging-host manifest at the platform-specific location each browser expects (the committed realizations being the per-user native-messaging-hosts directory on the Unix platforms and the per-user registry key on Windows), naming the application binary the browser launches and binding the permitted extension identities, so only the published extension can connect. The registration is written on first use of the external browser backend and removed on uninstall (`integration.mcp-session`, File 36 §6.2; `web.*` external backend).
- **The host registration is update- and repair-aware.** The native-messaging host is an owned `PlatformIntegration` record with browser family, extension identity, host binary path, installed artifact identity, manifest hash, and registration source. Startup, update, and repair reconcile the desired registration against the actual platform manifest; a manifest pointing at an old, moved, or untrusted app path is stale, surfaced, and not used until repaired.
- **The browser extension is published separately, not bundled.** The extension is published to the browser stores under the application's publisher (the committed realizations being the Chrome Web Store and the Edge Add-ons store) with its own store signing, update, and review cycle; it is never embedded in the application installer, because embedding it fights the browser's extension-security model. On first use of the external backend, the application surfaces a one-click install that opens the store listing; the extension is not a `BundledBinary` and not a `Sidecar` (`GLOSSARY`).
- **The session protocol and the skew handshake are File 36's.** The registered host serves the native-messaging session File 36 defines, valid only when authenticated, local, session-bound, and peer-identity-checked (`integration.mcp-session`, File 36 §6.2); the protocol-version-skew handshake that surfaces an "update the extension" notification is File 36's. This file registers the host and publishes the extension; it owns no message, no session, and no protocol.
- **The host registration honors the secret boundary.** The host manifest names the binary and the permitted extension identities; it carries no secret material, and the channel it enables carries `SecretRef`s and capability-scoped handles, never raw secret material (`secret.backend-boundary`, File 22 §4; `runtime.transports`, File 42 §10.3).

### 8.3 Boundary

This section owns the host registration placement, the extension-identity binding, the write-on-first-use and remove-on-uninstall lifecycle, and the extension publication. The session protocol, the transport, and the skew handshake are File 36's; the transport implementation is File 42's (§10); the running browser process a managed browser backend spawns is File 23's.

## 9. The Sidecar Inventory and Bundled-Binary Model

Anchor: `packaging.sidecar-inventory`

### 9.1 Definition

A `BundledBinary` is a helper executable or loadable-code runtime the application ships, separate from the main binary, that the Runtime runs as a `ManagedProcess` (File 23) or loads as an in-process runtime. A `RuntimeAsset` is a non-executable payload a bundled runtime or feature requires (`packaging.runtime-asset`): model weights, OCR language data, WebAssembly standard libraries, extension data, or equivalent runtime data. The `SidecarInventory` is the one catalogue for both, each with its `BundlingStrategy`, its per-platform asset identity, its content hash, its compatibility metadata, and its dependency declaration. The `BundlingStrategy` set is the closed classification of how a packaged runtime payload reaches the device.

### 9.2 The Closed `BundlingStrategy` Set

- `Eager` — bundled inside the installer image and present on every install; used for what every launch requires or what is small enough that lazy delivery is not worth the network dependency
- `LazyDownload` — not in the installer; downloaded, verified, and placed on first use of the feature that needs it, from the distribution host (§9.6); used for large optional helpers
- `InstallOnDemand` — installed only after the user first invokes the operation that needs it, with any elevation or platform-specific setup the install requires; used for the elevated helper and the VM-guest binaries (§13)
- `SeparatelyPublished` — not delivered by this layer at all; obtained through its own channel (the browser extension through the browser stores, §8) or the user's package manager (a platform daemon the application declines to bundle, the committed example being the Wayland input daemon), with the application's first-run flow detecting absence and guiding the install

The packaged-runtime `Sidecar` taxonomy is canonical and homed here: a bundled external binary the application ships is a `BundledBinary`; a non-executable payload it ships or downloads for that binary is a `RuntimeAsset`; the browser extension is `SeparatelyPublished` and not a sidecar; a user-package-manager dependency is `SeparatelyPublished` and not a sidecar.

### 9.3 Rule

- The `SidecarInventory` is the one catalogue of `BundledBinary`s and `RuntimeAsset`s. The committed inventory includes the metasearch backend, the optional challenge-solver, the Python-in-WebAssembly runtime and its standard-library payload, the small JavaScript engine, the embedded analytical SQL engine, the vector-search extension, the optical-character-recognition engine and language data, the per-platform elevated helper, and the per-platform VM-guest binaries, plus the in-binary-linked WebAssembly host and search binary; each entry declares its `BundlingStrategy`, its per-platform asset identity, its content hash, its compatibility metadata, and its dependencies. The exact inventory and sizes are realization facts this file frames, not a frozen canonical list; the contract is that every helper or runtime payload the application runs, loads, or depends on is an inventory entry with a strategy and a verifiable identity.
- A runtime component linked into the main binary rather than shipped as a separate file — the in-binary-linked WebAssembly host and the in-process search binary — is a compat-identity-only `SidecarInventory` entry: `Eager` by construction, covered by the application image's content hash rather than a separate asset hash, and carrying its compatibility identity for skew accounting, with no separate placement, download, or spawn.
- A `BundledBinary` or `RuntimeAsset` is identified per platform by a stable asset name and verified by content hash (§5.2). A `LazyDownload` or `InstallOnDemand` payload is downloaded with resume and bounded retry, tracked as in-progress until complete, verified against the inventory's content hash, placed with the execute permission or data-file placement its kind requires and the platform quarantine handling the platform needs (§5.2), and only then run or loaded; a partial or unverifiable download is discarded and never run or loaded.
- A `BundledBinary` or `RuntimeAsset` declares its dependencies. Where a binary needs a shared library, an auxiliary binary, or a runtime data payload the inventory also ships, the dependency is declared so the placement ensures it is present before the binary runs or the feature loads; the runtime resolves the shared-library search path to the placed location at spawn (the committed realization being the platform shared-library path injection). A dependency on a system component the application does not ship (a system browser engine, a system daemon) is a `SeparatelyPublished` declaration, detected at first use with guided install.
- A `BundledBinary` or `RuntimeAsset` declares compatibility metadata: supported application version range or release-artifact identity set, sidecar protocol or API version where relevant, ABI/runtime constraints, and downgrade policy. The Runtime may run or load only a placed payload whose compatibility declaration matches the current application. An incompatible, downgraded, or stale payload is marked unavailable until replaced, never used opportunistically (`packaging.sidecar-compatibility`).
- The `BundlingStrategy` honors a size budget. The installer stays under a per-platform size budget by keeping large optional helpers out of the installer image and delivering them `LazyDownload`; the eager set is only what every launch requires plus negligible-size content. The budget and the per-binary strategy are settings-tunable for a user who prefers a full offline install (§15).
- The running form is the Runtime's. This file ships the packaged runtime payload; File 42 runs compatible `BundledBinary`s as `Sidecar`s under its managed-service lifecycle and File 23 confines executable processes as `ManagedProcess`es. This file owns the inventory, the delivery, and the verification; it owns no spawn, no health check, no supervision, and no reaping.

### 9.4 Download, Placement, and the Partial-Download Rule

A `LazyDownload` or `InstallOnDemand` acquisition matches the per-platform asset, downloads it with redirect-following, range-based resume, and bounded retry, tracks the in-progress download distinctly from a completed one (the committed realization being an in-progress suffix), verifies the completed download against the inventory content hash, and only then places it with the needed execute permission or runtime-data placement and quarantine handling. A download that fails verification or completes only partially is discarded with a typed, recorded outcome and is never placed, run, or loaded. The acquisition is event-first and bounded; it is not a timed poll.

### 9.5 Hosting and Graceful Degradation

- Lazy-downloadable `BundledBinary`s and `RuntimeAsset`s are hosted on a free-for-open-source release host as the primary source (the committed realization being the project's release host), with a mirror as a fallback (the committed realization being a peer-to-peer mirror, the way operating-system images are distributed), under the zero-monetary-spend constraint.
- A `BundledBinary` or `RuntimeAsset` that cannot be obtained degrades the feature that needs it gracefully: the feature is unavailable with a typed reason and a manual-install or retry path, the application and its independent features continue, and the degradation is surfaced as state, never a crash or a silent absence (`runtime.operational-health`, File 42 §16.3). The application starts and runs with any subset of optional packaged runtime payloads present.
- Superseded downloaded payloads are cleaned up by state, never by age: the payload is no longer referenced by the current `SidecarInventory`, not needed by last-known-good rollback, not active in any Runtime process, and replaced by a verified compatible payload. Stale payloads surface in packaging/storage accounting and cleanup records audit facts (`packaging.runtime-payload-cleanup`).

### 9.6 Boundary

This section owns the `BundledBinary` and `RuntimeAsset` model, the `SidecarInventory`, the `BundlingStrategy` set, the compatibility metadata, the download-and-placement contract, the state-driven cleanup contract, the size budget, and the hosting-and-degradation posture. The running sidecar's supervision is File 42's; the process confinement is File 23's; the integrity verification is §5; the browser extension's publication is §8; the elevated helper's process model is File 23's and its first-use install is §13.

## 10. The Built-In Ship-With Bundle

Anchor: `packaging.builtin-bundle`

### 10.1 Definition

The `BuiltinBundle` is the set of ship-with content packaged into every install image as the `Builtin` source. It is the single channel through which the system's built-in declarations, default content, and ship-with examples reach the device; the running layers register it at first run through their own paths.

### 10.2 Rule

- **The `BuiltinBundle` is the one ship-with channel.** It packages, at minimum: the built-in `CapabilityDeclaration`s for every canonical capability across the substrate services and surfaces (`capability.lifecycle`, File 05; the canonical discovery capabilities, File 07); the canonical kind catalogues (artifact, observation, evidence-relation, citation-reference, and block kinds, File 09); the built-in `SurfaceContract`s and their contributed capabilities, custom kinds, and panels (Files 07, 25, and 27); the default `SettingDefinition`s and the profile bundles (File 15); the ship-with per-profile plugins (File 35); the ship-with themes (File 38); the built-in evaluation suites and golden fixtures with no parallel evaluation distribution path (File 40); and the seed files (the package-name-mapping seed (File 32 §8.3), the default-watch set (File 33 §15.2), and equivalent ship-with seeds). No subsystem ships a parallel built-in channel.
- **The bundle carries a signed item manifest** (`packaging.builtin-item-manifest`). The `BuiltinBundle` item manifest lists each shipped item with source-qualified id, owning layer and registry, item kind, schema/version, canonical content hash, dependency/order hints where needed, sensitivity/trust source, and registration path. The manifest hash is part of `ReleaseProvenance` (§3.2), and the item manifest is the replayable index the owning layers consume for first-run registration, tombstone-aware re-seed, and bundle drift detection.
- **Packaging delivers; the owning layers register.** This file packages the `BuiltinBundle` into the read-only installation image; each item is registered at first run through its owning layer's path — plugins through File 35's first-run copy-and-register, settings and profiles through File 15, capabilities through File 05's built-in-first registration order, evaluation suites through File 40, themes through File 38. This file owns the bundling and the integrity of the shipped content; the owning layers own the registration semantics.
- **The install-plus-override discipline holds.** Ship-with content lives read-only in the installation image; on first run, the items the user can modify (plugins, themes, profile defaults) are copied into the user-writable data root where the user may edit, disable, or remove them (`plugin.distribution`, File 35 §11.4). A later application update re-delivers the read-only ship-with content; the re-seed is idempotent and tombstone-aware — a user-removed ship-with item is not silently re-resurrected on update, though the system may offer to re-add it, and a re-seed of a profile-layer default never overrides an explicit user value (`settings.profiles`, File 15 §7.3).
- **The ship-with content inherits installation trust only after manifest verification.** A `BuiltinBundle` item is the `Builtin` source and carries the application's installation trust (`security.trust-model`, File 22 §9.4) only after the loaded content verifies against the signed item manifest at startup or lazily before the item is copied, registered, rendered, or loaded. A mismatch is a tamper signal File 22 treats as such; the item is not registered as trusted `Builtin` content. A ship-with item's contributions are ordinary registrations carrying their `Builtin` source, never a privileged side door.
- **The lazy-population strategy applies.** Where the ship-with content is large (the per-profile plugins), only the active profile's content is copied eagerly on first run and the rest are copied on activation (`plugin.distribution`, File 35 §11.4); the rest of the `BuiltinBundle` that the running application needs at startup (capability declarations, kind catalogues, default settings) is registered eagerly.

### 10.3 The First-Paint Cache

Anchor: `packaging.first-paint-cache`

The concrete first-paint cache mechanism File 38 defers here is a device-local rebuildable projection of the settings-resolved theme, seeded at build or first run so the shell paints the correct theme before the settings service has resolved (`customize.consequences-for-later-specs`, File 38). This file owns the concrete mechanism — a device-local cache the renderer reads on first paint and the running application rewrites when the resolved theme changes or when the cache key invalidates; File 38 owns that the theme is a setting and the cache is a projection. The cache key includes the theme id/version, color scheme, accessibility-conformance profile, token-system/schema version, and renderer/theme-engine version. Packaging invalidates the cache when an update changes any delivered token schema or theme-engine input. The cache is never a source of truth and never syncs; its loss is a repaint with the default until the setting resolves.

### 10.4 Boundary

This section owns the `BuiltinBundle` packaging, the signed item manifest, load-time manifest verification, the install-plus-override discipline, the tombstone-aware re-seed, and the first-paint-cache mechanism. The registration semantics of each item are the owning layer's (Files 05, 09, 15, 35, 38, 40); the plugin first-run copy-and-register and the agent-never-installs rule are File 35's; the theme declarations are File 38's; the evaluation-suite registration is File 40's; the installation-trust class and tamper response are File 22's.

## 11. Update Channels and Apply-on-Restart Delivery

Anchor: `packaging.update-delivery`

### 11.1 Definition

An `UpdateChannel` is a named release stream a device subscribes to. Apply-on-restart delivery is the pipeline by which this file checks the channel's `ReleaseManifest`, downloads and verifies the new `ReleaseArtifact`, stages it, and signals the Runtime to apply it on the next restart.

### 11.2 The Closed `UpdateChannelKind` Set

The canonical channels are closed-canonical-plus-`Custom`: `Stable` (the default release stream), `Beta` (a pre-release stream for early testing), `Nightly` (an automated frequent build with version bumping), and `Custom { channel_id }` (an organization-hosted or self-hosted stream). The device subscribes to exactly one channel at a time; switching channels is a user action recorded as a setting (§15). A `Custom` channel is a new executable-code source: its signing keys, manifest endpoint or package source, expected publisher identity, and minimum-version policy enter source approval under File 22 and policy review under File 06 before use.

### 11.3 Rule

- **The update pipeline is check, download, verify, stage, signal.** This file checks the subscribed channel's signed `ReleaseManifest`, compares the offered version to the installed version, rejects a network-offered downgrade unless the user explicitly initiated a deliberate rollback, downloads the matching per-`PlatformTarget` `ReleaseArtifact`, verifies the manifest signature and the artifact's signature over its content hash (§5), stages the verified artifact, and signals the Runtime that a staged update is ready. The Runtime drains and relaunches into it (`runtime.update-relaunch`, File 42 §18); this file never mutates the running image and never relaunches. The downgrade rule does not block File 20's local last-known-good rollback, which is recovery to a previously verified local installed version rather than acceptance of a network-served older version (`packaging.network-downgrade-rejection`).
- **Updates are opt-in and never silently network-applied by default.** An update is checked and applied only on the user's explicit action or under an explicit, user-configured update policy (§15); the default is to surface availability, not to apply automatically. The check is event-first or user-initiated, not a tight timed poll; where a periodic check is configured it is a flagged, configurable cadence (`core.event-first-by-default`, File 01 §7.15), never a correctness condition.
- **The updater is disableable, and a package-managed install suppresses self-update.** The updater honors a startup-only disable flag (the committed realization being the `ATLAS_DISABLE_UPDATER` bootstrap variable, File 42 §14) so an enterprise or packaged deployment can turn it off. When the application was installed and is managed by an external package manager or a desktop wrapper that owns updates, the application's own self-update is suppressed and update responsibility defers to the managing channel (the committed realization being a launched-by-manager marker the build honors); the application never fights its package manager for control of its own binary.
- **Staging is atomic and device-local** (`packaging.staged-update`). A `StagedUpdate` record carries the current version, target version, channel, manifest hash, artifact hash, artifact location, sidecar and built-in bundle hash changes where relevant, verification status, pre-apply backup or last-known-good reference, and staging state. Only a complete, verified `StagedUpdate` may be signalled to Runtime. A crash during staging leaves an inert incomplete record that is resumed or cleaned up by state, not by time.
- **Pre-stable recovery checks gate marking an update stable.** After a relaunch into a staged update, before the new version is recorded as the last-known-good (File 20 §12.3), the application runs a recovery-check list — at minimum the substrate schema integrity, the settings loadability, the core-service startability, the eager-loaded-binary presence, and the ship-with-content validity — and, on failure, rolls back to the last-known-good version and the pre-migration backup (`storage.backup-integrity-recovery`, File 20 §12.3), recording the failed checks. A schema migration an update applies is paired with a reversal or, where the migration is not reversible, staged so the rollback restores the pre-migration backup rather than relying on a down-migration; this file's update never leaves the substrate half-migrated (`storage.schema-migration`, File 20 §10.3).
- **A minimum-version gate may force an update only for unsafe work** (`packaging.minimum-version-gate`). A channel's `ReleaseManifest` may declare a minimum-compatible version; an installed version below it is gated so a server-side protocol or security floor can force clients off an unsafe version. The gate may block update-dependent network services, connector protocols, extension protocols, or other unsafe functionality. It must preserve local read/export/recovery access whenever the installed binary can safely open the substrate; if schema or security invariants prevent safe substrate open, the user gets a recovery/export or reinstall path rather than an unexplained lockout. The gate is a delivery decision; it never bypasses the user-gated apply or the integrity verification.
- **Delta and full delivery are both permitted.** An update may be delivered as a full artifact or as a delta against the installed version where the format supports it; either way the *result* is verified against the new version's content hash before staging (§5), so a delta that does not reconstruct the verified artifact is rejected. The choice is a delivery optimization, never a relaxation of the integrity guarantee.

### 11.4 Boundary

This section owns the channels, the source approval boundary for `Custom` channels, the check-download-verify-stage-signal pipeline, the `StagedUpdate` record, the network-offered downgrade rejection, the opt-in posture, the disable and package-managed-suppression rules, the pre-stable recovery checks, the minimum-version gate, and delta-versus-full delivery. The relaunch is File 42's (§18); the last-known-good marker, the pre-migration backup, and the schema migration are File 20's; the signing is §5; the recovery-check failures and the rollback record into the ledger and audit overlay (File 10 §16.4).

## 12. The Platform Crash Handler

Anchor: `packaging.crash-handler`

### 12.1 Definition

The `PlatformCrashHandler` is the native crash-capture handler the installer registers so that an abrupt termination of the application — a crash that bypasses the graceful shutdown and the application's own loop — is captured at the platform level. This section owns its registration and bundling; File 42 consumes its evidence for recovery, File 41 governs its consent, and File 22 redacts its payload.

### 12.2 Rule

- **This file registers the handler and bundles the reporter.** The installer or the first-run flow registers the platform-level crash handler (the committed realizations being a native signal-or-exception handler that writes a crash record and a bundled crash-reporting component) so a crash is captured even when the application's own loop is gone, and bundles the reporter into the installation image. The handler captures a minimal crash capsule — the fault, the version, the platform, and the minimal diagnostic state — to a restricted device-local location.
- **The captured crash feeds the Runtime's recovery path.** A crash record and the unclean-shutdown marker (`storage.lifecycle-reconstruction`, File 20 §13; `runtime.crash-recovery`, File 42 §13) let the next startup detect the unclean prior shutdown, reconcile orphans, and surface the recovery to the user; this file's handler produces the evidence, the Runtime consumes it. A crash during a staged-update relaunch feeds the pre-stable recovery check and the rollback (§11.3).
- **Raw crash capsules are restricted local staging, not diagnostics** (`packaging.raw-crash-capsule`). Because the native crash handler may run after the application loop is gone, it may persist only a minimal raw crash capsule in restricted device-local staging. That capsule is classified as highly sensitive, excluded from model context, sync, logs, and egress, and is readable only by the next startup's recovery/redaction path. File 22's secret detector produces the redacted diagnostic record before display, export, or upload; File 41's `TelemetryConsent` gates any egress. The local-first zero-egress default holds, so the default is to capture locally and never upload absent opt-in. The in-app `DiagnosticBundle` the user assembles is File 41's; this file's handler is the platform-level capture that feeds it.
- **Release-channel analytics obey the same boundary.** Update-channel telemetry and release-channel analytics this file distributes are governed by File 41's consent and zero-egress default and File 22's redaction; they are never a side channel and never egress content File 41 and File 22 exclude.

### 12.3 Boundary

This section owns the crash-handler registration, the reporter bundling, the restricted local raw-capsule staging rule, and the release-channel-analytics distribution boundary. The recovery path that consumes the crash evidence is File 42's; the unclean-shutdown marker is File 20's; the redaction detector and tamper/sensitivity response are File 22's; the consent contract, the in-app diagnostic bundle, and the metric projections are File 41's.

## 13. The Elevated-Helper Distribution

Anchor: `packaging.elevated-helper`

### 13.1 Definition

The elevated helper is the small per-platform `BundledBinary` that performs the privileged operations the unprivileged application cannot, run as a separate elevated process. This section owns its distribution and first-use installation; File 23 owns its process model and command allowlist, and File 22 owns its pairing credential.

### 13.2 Rule

- **The inventory ships the helper per platform; it installs on first elevated use.** The `SidecarInventory` carries the per-platform elevated helper as an `InstallOnDemand` `BundledBinary` (§9.2) with the same compatibility and downgrade rules as every packaged runtime payload (§9.3); it is not installed at application-install time, and the application installs unprivileged. Only when the user first attempts an operation that needs elevation does the application install the helper, with the platform's elevation prompt (the committed realizations being the platform privilege-elevation flow on each operating system) and the platform's privileged-execution mechanism (the committed realizations being the per-platform setuid or manifest-driven elevation).
- **The process model and the allowlist are File 23's; the pairing credential is File 22's.** The helper runs a one-shot, narrow, versioned command from File 23's declared allowlist and exits, the main process stays unprivileged, and every elevated operation records into the audit overlay (`sandbox.elevated-helper`, File 23; `security.audit-crypto`, File 22). The helper is paired to the main process by a shared secret (`security.device-trust`, File 22); this file ships the binary and installs it, File 23 confines and drives it, File 22 owns the pairing credential.
- **Uninstall removes the helper.** Uninstalling the application removes the elevated helper and its registrations; the user may also uninstall the helper alone, leaving the application running unprivileged. The helper's removal is recorded.

### 13.3 Boundary

This section owns the elevated helper's distribution and first-use installation. The one-shot process model, the command allowlist, the sandbox, and the privileged execution are File 23's (§11); the pairing credential and the audit recording are File 22's; the platform package-manager dependencies the helper needs are §9's `SeparatelyPublished` declarations.

### 14.1 The Capability Surface

This layer exposes its read and operational facts and controls as canonical capabilities (declared per File 05, gated per File 06), surface-and-service in nature, with no packaging-mode field:

Reads are `ReadOnly` and agent-invocable under the standard agent-exposure rules; the consequential delivery controls (apply update, change channel, register autostart, install the native-messaging host, uninstall) are user-gated and policy-bound — the agent may surface that an update is available or that a feature needs a runtime payload, but it never applies an update, changes a channel, registers an integration, or installs unattended (`capability.runtime-mutation`, File 05 §16.2; `plugin.distribution`, File 35 §11.3). The install of the application itself is performed by the `Installer` (§6), not an in-application capability.

### 14.2 Events

This layer emits and consumes through the one event bus (File 10 §5), registering packaging-specific facts as `Custom { namespace: "packaging" }` extensions (File 10 §4.3): an update available, downloaded, verified, staged, applied, or rolled back; a `StagedUpdate` created, completed, or discarded; a recovery-check failure; a `BundledBinary` or `RuntimeAsset` downloaded, verified, failed, marked stale, or cleaned up; a platform integration registered, repaired, or removed; a native-messaging host installed, repaired, or removed; an elevated helper installed or removed; and a built-in bundle manifest mismatch. It introduces no new top-level event or ledger-entry kind and no parallel bus. Consequential and security-relevant delivery facts (an update applied or rolled back, the native-messaging host installed, the elevated helper installed, a manifest mismatch, or a stale host repair) commit to the ledger and record into the device-local hash-chained audit overlay (`ledger.hash-chained-audit-log`, File 10 §16.4; `security.audit-crypto`, File 22 §14); transient delivery coordination (download progress) flows on the bus under its delivery class. No update, integration change, runtime-payload acquisition, or built-in verification failure is silent; each records a typed fact.

### 14.3 Boundary

File 05 owns the capability declaration and registry; File 06 owns the policy gating; File 10 owns the envelope, the catalogue, the delivery split, and the audit overlay; File 42 owns the relaunch path after a staged-update-ready signal; File 22 owns the audit cryptography. This section declares the packaging capability set and event vocabulary.

## 15. Settings

Anchor: `packaging.settings`

Every packaging mechanism with meaningful variation is configurable through `settings.setting-definition` (File 15), with namespaced keys (`packaging.*`) declaring scope, agent exposure (`policy.agent-exposure-policy-settings`, File 06 §16.4), locality, and export/sync behavior. Packaging settings that bind to one device or platform default to device-local. At minimum, settings support:

- the subscribed `UpdateChannel` and the update policy: auto-check enablement and cadence (default surface-not-apply), whether an available update applies on next restart automatically or only on user action, and the minimum-version-gate behavior;
- the updater-disable surface for the bootstrap disable flag and the package-managed-suppression behavior;
- the platform-integration toggles: autostart enablement (default off), file-association and protocol-handler registration, the tray item, and the notification registration;

- the crash-handler enablement and the release-channel-analytics opt-in (composed with File 41's `TelemetryConsent`, never a parallel store);
- the first-paint-cache behavior, cache invalidation inputs, and the ship-with re-seed and tombstone policy (composed with Files 35 and 38's settings, never duplicated);
- the native-messaging-host registration enablement per browser.

Specific defaults belong to tested settings profiles, not hardcoded constants (`settings.settings-over-constants`, File 15 §13). Agent exposure of packaging settings is conservative: the channel, the update policy, and the platform integrations are `OnRequest` to read; their mutation and the delivery controls are user-gated; no packaging behavior is a hidden hardcoded branch where a meaningful variation exists. Packaging settings are predominantly device-local — the channel, the installed runtime-payload set, the platform registrations, and the host paths bind to the device; a portable packaging setting (a user-facing update-preference or analytics opt-in declared safe to sync) is the exception, allowed only when platform-independent.

## 16. Persistence, Locality, and Replay

Anchor: `packaging.persistence-replay`

### 16.1 What Is Immutable, Device-Local, and Never-Synced

- **Immutable and content-identified (this layer's artifacts):** a `ReleaseArtifact` and its `ReleaseManifest` are immutable and identified by content hash (§3); a published artifact is never mutated, and a mirror or package manager re-hosting it is verified against the same hash. These are distribution artifacts, not durable runtime state.
- **Read-only installation image:** the installed application image — the binary, the frontend assets, the eager `BundledBinary`s, eager `RuntimeAsset`s, and the `BuiltinBundle` — is read-only to the running application (§6.2); the running application never writes it, and a downloaded runtime payload is placed in the user-writable data root, not the read-only image.
- **Device-local install state (never synced):** the installed version and channel, the platform-integration ownership records, the native-messaging-host registration, the set of placed `BundledBinary`s and `RuntimeAsset`s, the elevated-helper installation and pairing, the first-paint cache, the `StagedUpdate` record, and the update policy are device-local and never sync (`storage.physical-layout-locality`, File 20 §8.3; the distribution-is-not-portability rule, File 21 §2); the one exception is a user-facing update preference explicitly declared platform-independent and safe to sync (§15), which travels as a portable setting rather than device-local install state. The application is installed per device; installing it on another device is a fresh distribution-channel install. Executable artifacts, runtime assets, and installer payloads are never replicated as ordinary sync data (`portability.what-replicates`, File 21 §5).
- **Computed / rebuildable projections:** the first-paint cache and the `SidecarInventory` presence state are device-local rebuildable projections (`core.projection`, File 01 §6.11); their loss is a rebuild — a repaint with the default theme, a re-resolution of which binaries and runtime assets are present — never a loss of a durable fact.

### 16.2 Reconstruction and Replay

- The install state reconstructs at startup from the placed image and the device-local install record; the running application verifies `BuiltinBundle` content against the signed item manifest before trusted registration, re-derives the owning layers' first-run paths, re-resolves which `BundledBinary`s and `RuntimeAsset`s are present and compatible, reconciles owned platform registrations, and rebuilds the first-paint cache from the settings-resolved theme and cache key. It re-derives nothing from a live mutable source and re-queries no live endpoint for a historical fact (`context.assembly-replay-snapshot`; `provider.token-source`, File 17).
- Replay reads recorded packaging facts (an update applied at a recorded version, a binary placed) for a historical view; it re-runs no install, downloads no artifact, and applies no update for a replayed run. A run's recorded application version anchors the version in effect for replay.
- This file defines no new hash algorithm and no new canonical encoding; every hash reuses the canonical hashing of File 01 (`core.canonical-hash`, File 01 §7.14) under File 21 §10.4's typed-versus-opaque split (`portability.export-bundle`, File 21 §10.4): the typed records — manifest, provenance, item-manifest, and staged-update — hash over a declared `CanonicalEncoding`, never over physical bytes, while the opaque payloads — the artifact image and each `BundledBinary` and `RuntimeAsset` — are content-hashed over their bytes. Golden encoding tests pin those hash encodings against silent drift.

### 16.3 Boundary

This section owns the immutable-artifact, read-only-image, and device-local-install-state classification and the reconstruction rule. The data root, the substrate, and the last-known-good marker are File 20's; the sync exclusion and the portable package are File 21's; the trust state is File 22's; the running install reconstruction's lifecycle is File 42's.

## 17. Operating Constraints

Anchor: `packaging.operating-constraints`

This layer operates under these constraints, all configurable as settings (§15) with the stated canonical defaults:

- **Build-and-deliver, not run.** This layer produces, signs, places, registers, bundles, and stages; it runs no agent loop, owns no durable runtime state of record, executes no work surface, and hosts no running lifecycle. Everything that runs is the Runtime's, the storage substrate's, or the owning layer's.
- **Apply-on-restart, never in place.** An update is produced, signed, verified, downloaded, and staged here as a complete `StagedUpdate` and applied by the Runtime's relaunch against File 20's last-known-good guard; the running image is never mutated, and a bad update rolls back.
- **Integrity always; trust class is File 22's.** Every update package's signature over its content hash is verified before staging; operating-system notarization is a declared funded-future extension; the trust an install or update confers is File 22's, and the application's installation trust is its root.
- **Read-only image; data root is the running layers'.** The installer places a read-only image and ensures the data root is creatable; the data root, the substrate, the lock, the vault, and every durable fact are created and owned at runtime, never written by the installer.
- **Local-first and zero-spend-aware.** The installer stays under a per-platform size budget, large optional runtime payloads are lazy-downloaded from a free-for-open-source host with a mirror, a missing optional payload degrades its feature gracefully, core first run works without network, and open-source and commercial distribution are always minutes away. No paid certificate or store is assumed in v1.
- **The agent suggests; the user installs and updates.** The agent surfaces availability and need; installing, updating, changing the channel, registering autostart, and installing the native-messaging host are user-gated and policy-bound; no agent, automation, or update silently mutates the installed image, the registrations, or the channel.
- **Distribution is not portability.** This layer distributes the application and its executable artifacts to any device; it never replicates them as ordinary sync data, and File 21's sync never distributes the application.
- **Secret boundary and consent across delivery.** No native-messaging registration, crash diagnostic, or telemetry channel carries raw secret material; a raw crash capsule remains restricted local staging until File 22's detector produces a redacted diagnostic and File 41's consent gates any egress; the local-first zero-egress default holds.
- **No silent delivery action.** An update applied or rolled back, a recovery-check failure, a runtime payload downloaded or failed, an integration registered or removed, and a native-messaging host or elevated helper installed each record a typed fact; nothing installs, updates, registers, or degrades without a recorded transition.

## 18. Explicit Rejections

Anchor: `packaging.explicit-rejections`

The following shapes are wrong for this layer:

- a packaging runtime, a private auto-update service that owns a loop or durable state, a parallel installer, a second release channel system, or any layer-owned execution — this layer builds and delivers; everything that runs is the Runtime's (File 42)
- an in-place update that mutates the running installation — updates apply on restart from a staged, verified artifact against File 20's last-known-good guard; a silent self-restart loop and a half-applied update are rejected
- an update package staged without verifying its signature over its content hash, or a downloaded runtime payload placed, loaded, or run without content-hash verification, or a partial download ever loaded or run
- accepting a new update-signing key because it appeared in a downloaded manifest without an already trusted key-transition path or explicit trust recovery
- accepting a network-offered downgrade to an older version absent explicit user-initiated rollback; local last-known-good recovery is separate and remains allowed
- a staged update represented only by an implicit directory or partial file set — only a complete, verified `StagedUpdate` can signal readiness to Runtime
- a remote minimum-version gate that denies safe local read/export/recovery access to user data when the installed binary can safely open the substrate
- claiming a trust guarantee the signing posture cannot prove, or treating the absence of a paid certificate as a reason to skip the free update-integrity verification — integrity verification is mandatory and free; operating-system notarization is the declared evidence path, and the trust class is File 22's
- the installer writing the substrate, the single-instance lock, the vault, or any durable user data into the data root, or treating the installation image as writable by the running application — the image is read-only and the data root is the running layers'
- a silent or destructive uninstall, or an uninstaller-private deletion of the data root, vault, substrate, workspaces, or audit overlay — uninstall preserves user data by default, removes the registrations and the native-messaging host and the elevated helper, and routes data removal through the storage/security wipe path
- autostart on by default, a consequential platform integration registered unattended, an orphaned registration left behind on uninstall, or duplicate/stale platform registrations caused by non-idempotent installer logic
- the application binding an application-level network port of record, or the installer registering a local server, a fixed port, or a firewall exception for one — the frontend bridge is native inter-process communication (File 42 §10)
- a protocol handler that executes consequential actions directly from an operating-system-delivered payload — external protocol invocations enter the canonical rail and policy path (`controlrail.external-protocol-rail`, File 26 §12)
- embedding the browser extension in the application installer, or owning the native-messaging session protocol here — the extension is separately published to the browser stores, this file registers the host, and File 36 owns the protocol and the skew handshake
- a native-messaging host registration that survives update or repair while pointing at an old, moved, or untrusted application path
- bundling every helper binary or runtime asset regardless of size, or lazy-downloading what every launch requires, or exceeding the per-platform installer size budget — the `BundlingStrategy` is eager only for what every launch needs and lazy or on-demand otherwise
- a `BundledBinary` or `RuntimeAsset` whose acquisition blocks the application or whose absence crashes a feature — a missing optional payload degrades its feature gracefully with a typed reason and a manual-install path
- running or loading an incompatible, downgraded, stale, partial, or unverifiable `BundledBinary` or `RuntimeAsset`
- time-based cleanup of superseded runtime payloads as a correctness mechanism — cleanup is state-driven and preserves rollback-needed and active payloads
- a parallel ship-with channel, a built-in declaration that bypasses the `BuiltinBundle` and the owning layer's first-run registration, a ship-with item registered as a privileged side door, or trusted `Builtin` registration without verification against the signed item manifest
- silently re-resurrecting a user-removed ship-with item on update, or a re-seed of a profile-layer default overriding an explicit user value
- a first-paint cache that survives a token-schema or renderer/theme-engine version change across an update
- a crash diagnostic, telemetry channel, or release-channel analytic that egresses without File 41's consent or File 22's redaction, or a raw crash capsule that enters logs, model context, sync, or telemetry
- a packaged release whose core first-run startup requires a live network connection to the distribution host
- a timed poll as the update-check or download mechanism's correctness condition — the check is user-initiated or a flagged configurable cadence, and the download is event-first and bounded
- the agent applying an update, changing the channel, registering autostart, installing the native-messaging host, or installing a binary unattended — these are user-gated; the agent suggests, never installs
- replicating an executable artifact, a binary, or an installer payload as ordinary sync data, or conflating application distribution with data portability (File 21 §2)
- a hidden hardcoded channel, size budget, bundling strategy, integration default, or update policy where a meaningful variation belongs in a setting (`settings.settings-over-constants`, File 15 §13)
- a new top-level `AppEvent` or `LedgerEntryKind` for packaging, or a parallel packaging bus — the layer registers `Custom { namespace: "packaging" }` extensions on the one bus and records security-relevant delivery into the one audit overlay
- generated line numbers or drift-prone section numbers as normative cross-file references where a stable canonical anchor exists

## 19. Consequences for Later Specs

Anchor: `packaging.consequences-for-later-specs`

Every later spec that ships built-in content, adds a helper binary or runtime asset, registers a platform handler, defines an update-affecting compatibility requirement, or distributes an executable contribution consumes this layer as defined here. The canonical principles later specs follow:

- ship every built-in declaration, default setting, profile, ship-with example, evaluation suite and fixture, theme, and seed as `BuiltinBundle` content packaged into the install image, represented in the signed item manifest, verified before trusted registration, and registered at first run through the owning layer's path carrying its `Builtin` source and installation trust; never invent a parallel ship-with channel
- declare every helper executable as a `BundledBinary` and every non-executable runtime payload as a `RuntimeAsset` in the `SidecarInventory` with a `BundlingStrategy`, a per-platform asset identity, a content hash, compatibility metadata, and a dependency declaration; never download, load, or run an unverified, partial, incompatible, or downgraded payload, and degrade gracefully when an optional payload is absent
- register every operating-system-facing registration as an owned, idempotently reconciled `PlatformIntegration` reversed on uninstall; never leave an orphaned registration and never register a consequential integration unattended
- deliver every application update as a signed, verified `ReleaseArtifact` over an approved `UpdateChannel`, represented by a complete `StagedUpdate` for the Runtime's apply-on-restart relaunch against File 20's last-known-good guard; never mutate the running image, never skip integrity verification, and never accept a network-offered downgrade absent explicit user-initiated rollback
- route every native-messaging-host registration through this file and every browser extension through its store; route every raw crash capsule through File 22's redaction before diagnostic display/export and every release-channel analytic through File 41's consent
- distribute executable artifacts and runtime assets through this layer's channels, never through File 21's sync; bind device-specific delivery state device-local and never sync it

Specific integration contracts:

- the **Runtime** (File 42) relaunches into the `StagedUpdate` this layer produces, runs each delivered compatible `BundledBinary` under its managed-service lifecycle, loads compatible runtime assets only through their owning feature, and consumes the crash evidence the registered handler captures; the running lifecycle is the Runtime's, the delivery is this layer's
- the **storage** (File 20) layer's last-known-good marker and pre-migration backup guard the staged update this layer's relaunch applies; its wipe, export, and backup paths govern any uninstall-time data removal; the data root this layer's installer ensures is creatable is created and owned by storage and workspaces (Files 20, 24)
- the **security** (File 22) layer decides the trust class an installed or updated source carries, handles tamper signals from artifact or built-in manifest mismatches, redacts raw crash capsules before diagnostics or egress, and owns the elevated helper's pairing credential; this layer produces verifiable signed artifacts and ships the per-platform elevated helper and the native-messaging host
- the **sandbox** (File 23) layer spawns, confines, and reaps the `BundledBinary`s this layer ships and owns the elevated helper's one-shot process model; this layer ships the binary and runtime-asset inventory and installs the elevated helper on first use
- the **plugin** (File 35) layer registers the ship-with plugins this layer bundles, owns the plugin install/update lifecycle, and consumes this layer's installer image and discovery endpoints; this layer bundles the ship-with plugins and delivers the application
- the **MCP and external integrations** (File 36) layer owns the native-messaging session protocol the host this layer registers serves and the protocol-skew handshake; this layer registers the host and publishes the extension
- the **observability** (File 41) layer owns the in-app diagnostic bundle and the telemetry consent the crash diagnostics and the release analytics this layer distributes pass; this layer registers the platform crash handler and bundles the reporter
- the **UI shell and customization** (Files 37, 38) layers own the shell, the windows, and the theme and widget declarations this layer distributes; this layer owns the installer, the platform window-decoration mechanics, the first-paint-cache mechanism, and the bundling of the ship-with themes
- the **evaluation** (File 40) layer's built-in suites and golden fixtures are `BuiltinBundle` content; this layer introduces no parallel evaluation distribution path
