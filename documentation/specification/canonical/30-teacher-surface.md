# Teacher Surface

## Status

Canonical. This file defines the `Teacher` work surface — the specialized environment for teaching and learning: explaining concepts, building curricula and courses, generating and grading assessments, running interactive practice and multi-agent classrooms, spaced-repetition study, and tracking learner mastery. It is the fourth per-surface specification: it fills the `SurfaceContract` that `worksurface.surface-contract` (File 25 §4) delegates to each per-surface spec, and declares the teaching-specific workflows, panels, capabilities, and policies the Teacher surface contributes over the shared substrate. It owns user-facing educational workflows and specialized views; it owns no private architecture. It composes blocks, artifacts and evidence, capabilities, execution, the version graph, memory, retrieval, the world model, perception, the sandbox, workspaces, security, providers, and every other substrate through the same contracts every surface uses. Later canonical files may refine it, but may not contradict it.

## 1. Chosen Model

Anchor: `teacher.chosen-model`

ATLAS3 has one `Teacher` `WorkSurface`. It is the specialized environment for teaching and learning — explaining, building curricula and courses, generating and grading assessments, running interactive practice and multi-agent classrooms, conducting spaced-repetition study, and tracking learner mastery — and it is one instance of the `WorkSurface` primitive `worksurface.work-surface` (File 25 §3) defines, classified `Teacher` by `core.current-major-area-classification` (File 01 §5.5).

The Teacher surface owns user-facing educational workflows and specialized teaching views; it owns no private architecture (`worksurface.no-private-architecture`, File 25 §12). It is declared by one `SurfaceContract` (§3) registered in the `SurfaceRegistry` (`worksurface.registry`, File 25 §10), and it composes the shared substrate — blocks, artifacts and evidence, capabilities, capability policy, tool surfaces, execution, the world model, perception, the version graph, retrieval, memory, routing, context assembly, workspaces, storage, sync, security, the sandbox, providers, and the ledger — through each one's canonical contract.

The load-bearing model of the Teacher surface is the **artifactized, mastery-tracked-tutor reframe**: an educational result is a durable, identified, versioned, evidence-bearing `Artifact` — a `Lesson`, `Curriculum`, `Quiz`, `ExerciseSet`, `FlashcardSet`, or `Rubric` — and learner mastery is durable substrate state, not a transcript answer and not a row in a private teaching table. Four consequences follow:

- **An educational result is a durable, evidence-bearing artifact, not transient prose.** A lesson is a `Lesson` `Artifact` revision (`artifact.artifact-kind`, File 09 §4) composed of sections, examples, and exercises; a course is a `Curriculum` artifact; an assessment is a `Quiz` or `ExerciseSet` artifact; a study set is a `FlashcardSet` artifact; an evaluation rubric is a `Rubric` artifact. Each carries provenance — the producing run, capability, inputs, and parameters (`artifact.provenance`, File 09 §15) — and each derived result links to its sources by `derives_from` (`block.canonical-edge-kinds`, File 08 §5.2). Educational content that makes a load-bearing factual claim is grounded: a lesson built from a document, a paper walkthrough, or a knowledge-base-grounded explanation cites its source through `Claim`, `Evidence`, and `Citation` (`artifact.claim` (File 09 §9), `artifact.evidence` (File 09 §11), `artifact.citation` (File 09 §12)), and an ungroundable assertion is flagged, not presented as fact. Artifact- and evidence-grade educational content is never stored only as an assistant message (§23).
- **Learner mastery is durable substrate state, not a private progress table.** What the learner knows, is learning, and struggles with is `Mastery` memory (`memory.kinds-scopes-facets`, File 14 §4.1 — "learning state, concept mastery, misconception, SRS-relevant progress, or teacher-facing competence signal"), reinforced by the assessment-result and observation blocks the learner's runs produce; the concept-and-prerequisite graph is the shared entity-relationship projection (`retrieval.source-records`, File 12 §4.2); the learner persona is a core-memory block (`memory.core-memory`, File 14 §5). Progress is a rebuildable projection over those, not a `teacher_progress` table (§12, §23).
- **The classroom, curriculum generation, and assessment loops are run and child-run structures over the one execution model.** A multi-agent classroom is a coordinator run plus role-differentiated child runs sharing one transcript (`run.child-runs-multi-agent-work` (File 04 §16), `intent.parallel-work` (File 02 §7.1)); curriculum-from-document and deep curricula are child-run structures mirroring web research (`web.research`, File 28 §9); adaptive assessment is a capability loop over mastery. The surface owns no private orchestrator, scheduler, or classroom table (§11, §23).
- **Teaching is also a borrowable cross-surface service.** The Teacher surface is the dedicated learning environment, and its `teacher.*` capabilities are borrowable by every other surface (§14, `worksurface.actions-declaration` File 25 §6.3) so teaching embeds into any work artifact — explaining a code change in the Coder surface, generating exercises from a dataset in the Data Processor surface, annotating a run, assessing an answer, or updating mastery. This is an instance of the general cross-surface rule: any surface may borrow another surface's capabilities through the shared borrow and policy mechanisms; Teacher's service face is teaching-specific, not a special interoperability primitive and not a per-surface teacher-mode autonomy field (§22).

`Teacher` is the canonical surface name; the `surface_id` is `teacher` and equals the subsystem id (`capability.capability-source`, File 05 §9.1, `worksurface.work-surface` (File 25 §3.3)), the value `routing.run-intent` (File 03 §4.3)'s `primary_surface` resolves to for teaching work, the prefix of its settings namespace (`surface.teacher.*`) and its instruction-file qualifier (`ATLAS.teacher.md`). The contributed capability namespace is `teacher.*`. Earlier vocabulary that named the same surface — "teacher domain", "tutor mode", "coach", "learning mode", "educator domain" — is source vocabulary only and does not survive as canonical terminology or a parallel primitive; "tutor" and "coach" survive as informal synonyms. The Teacher surface is independent of any specific external learning vault or skill; such systems are import/export targets or external skills, referenced not owned (§18). The anchor namespace for this file is `teacher.*`, deliberately distinct from File 07's `surface.*` (tool surfaces), File 25's `worksurface.*`, File 26's `controlrail.*`, File 27's `coder.*`, File 28's `web.*`, and File 29's `data.*`; the capability families `teacher.*` are capability ids in the one registry, not anchors, disambiguated by context.

### 1.1 Boundary

This file defines what the Teacher surface is and what it declares and contributes. It does not define how the `SurfaceContract` is registered or composed (File 25), how its tool surface composes (File 07), how its live state is held (File 18), how a lesson materializes (File 24), how its mastery memory is stored or ranked (File 14, File 12), how its confined practice code runs (File 23), how its history is versioned (File 11), or how its views render (the UI specs).

### 1.2 Teacher Is a Work Surface and a Borrowable Service

Anchor: `teacher.surface-and-service`

The Teacher surface has two faces, and they do not conflict. As a **work surface**, it is the dedicated learning environment a learner or educator activates to read lessons, follow a curriculum, sit a classroom session, take an assessment, or run a study session, with its own panels, view presets, and default policies (§3–§16). As a **service**, its `teacher.*` capabilities are registry capabilities (`capability.chosen-model`, File 05 §1) that every other surface borrows in place (`worksurface.actions-declaration`, File 25 §6.3): a Coder run borrows `teacher.explain_code` to walk through a change, a Data Processor run borrows `teacher.quiz.generate` to build practice from a dataset, a System Agent run borrows `teacher.explain` to annotate a maintenance action, and any run borrows `teacher.assess` and the mastery-update capability to record what the learner demonstrated. The service face means teaching can embed in the work artifact and environment through the shared borrow mechanism and the teaching cross-cutting affordance (`worksurface.views-presets`, File 25 §7.5), not through a "teaching mode" field on each surface (§22). This is not unique to Teacher: Coder, Web, Data Processor, GUI Control, and System Agent capabilities are likewise borrowable where their contracts, availability, and policy permit. A surface borrowing a teaching capability remains in its own surface; the Teacher surface owns the capability, the borrowing surface's workflow is its own, and the ledger records the cross-surface reach.

## 4. State Declaration — Panels and Selection

Anchor: `teacher.state-declaration`

### 4.1 Definition

The Teacher surface declares the panels it can mount and the selection kinds it produces. This is the static counterpart of the live `SurfaceState` (`world.surface-state`, File 18 §5): this file declares the shape, File 18 holds the live values. Panels self-register their live state to the world model on mount and update on focus, selection, and content change (`world.observation-state-update`, File 18 §8.1); a panel the surface fails to register is a blind spot the agent cannot use.

### 4.2 Declared Panel Kinds

The Teacher surface declares the following panel kinds, drawn from the canonical baseline (`worksurface.state-declaration`, File 25 §5.3) plus teaching `Custom` kinds registered through the proposal-first mechanism. Each declares the typed shape of its compact state-field summary (a lesson id, a concept, a selected exercise, a card id — never the resource body, `world.surface-state` (File 18 §5.2)), the selection kinds it produces, and its control affordances:

- `lesson` — a lesson reader over a `Lesson` artifact: rendered sections, worked examples, inline runnable code, math, and diagrams; carries the active lesson id, the focused section, and per-section understanding state; produces `BlockRange`, `Text`, and `CodeRange` selections; the math, code, and diagram rendering is the shared interactive-artifact runtime, a replaceable implementation behind the panel
- `curriculum` — a concept-map and skill-tree view over a `Curriculum` artifact and the concept-prerequisite graph (§8): nodes are concepts with mastery-derived status, edges are prerequisites, a node opens its lesson; a projection over the shared entity-relationship graph and `Mastery` memory, not a private skill-tree store; produces concept and lesson selections
- `classroom` — a multi-agent classroom view (§11): the shared transcript of the coordinator and role-differentiated agent runs, the whiteboard/canvas, spotlighted elements, the student panel, and a user-interject control; a projection over the classroom's blocks and the version tree, not a private classroom store; produces agent, turn, and `Region` selections
- `assessment` — a quiz and exam view over a `Quiz` artifact (§9): the current question, answer entry per question type, progress, flag-for-review, and post-submission per-question feedback; an interactive-artifact rendering whose submitted attempts and kept session records persist as blocks; produces question and answer selections
- `practice` — a practice view (§10): a problem, starter code, progressive hints, a run control over borrowed code execution, and per-test pass/fail; produces `CodeRange` and problem selections
- `flashcard` — a spaced-repetition review view over a `FlashcardSet` artifact (§10): the current card front/back, the grade-recall control, and the review-due queue derived from `Mastery` memory; produces card selections
- `sources` — the course-materials view: the documents, files, and knowledge-base entries feeding the lessons (§13), with per-source extraction and grounding state and grounded-span navigation; produces `File`, `Text`, and source-reference selections
- `progress` — a learner-progress view: a projection over `Mastery` memory and the assessment blocks (§12) showing concepts learned, in progress, and struggling, performance over time, and recommended next steps; a charting projection (borrowed `data.chart`) over substrate state, not a private metrics store; produces concept selections
- `activity` — the teaching activity feed: the run's explanation, generation, grading, and classroom progress, a projection over the ledger and event stream (`run.presentation`, File 04 §25), not a private log
- `inspector` — context, mastery, lineage, and validation inspection as `PanelKind: inspector` projections over substrate state (`worksurface.views-presets`, File 25 §7.5)

A panel kind a teaching panel declares is a shared substrate projection, not a private widget: the `lesson`, `assessment`, `flashcard`, and `practice` kinds render `Block`s and `Artifact`s from the one pool (`worksurface.state-declaration`, File 25 §5.4), and another surface may embed a teaching panel — a Coder surface embedding a `lesson` panel to explain a change, a Data Processor surface embedding a `practice` panel — without changing its primary surface. The Teacher surface may itself embed a borrowed panel — an `editor` panel for graded code, a `chart` panel for progress, a `browser` panel for a reference source — without a primary-surface change (`worksurface.state-declaration`, File 25 §5.4).

### 4.3 Selection Kinds

The Teacher surface produces selections of canonical kind `Text`, `BlockRange`, `CodeRange`, `Region`, and `File` (`world.surface-state`, File 18 §5.4), plus registered `Custom` selection kinds for teaching structure: a `Concept` selection (a node in the concept graph), a `Question` selection (one assessment item), a `Card` selection (one flashcard), and a `Section` selection (one lesson section). A selection carries a short summary and typed bounds — a concept id, a question id, a card id, a section id — not the selected content.

### 4.4 The Static-versus-Live Split

The declaration is the static shape; the live values — which panels are open, which is primary, what is focused and selected, the current `UiMode`, the active lesson, course, classroom, and learner, and the available-capability list — are the live `SurfaceState` File 18 holds. The Teacher surface declares no participation, autonomy, or interaction-shape field on its state (§22); `UiMode` (`Normal`, `CommandPalette`, `Modal`, `Fullscreen`, `Handsfree`, and the surface's registered modes) is interaction state, never an autonomy control (`world.surface-state`, File 18 §5.5). The explanation mode (lecture versus Socratic), the depth level (Quick/Standard/Deep), and the per-profile distinction (student, educator) are presentations and workflow parameters (§7, §16), not state-machine modes.

### 4.5 Boundary

This section declares the teaching panel and selection shape. File 18 holds the live values and owns the self-registration contract; the UI specs own panel presentation; the lesson, classroom, assessment, flashcard, math, code, and diagram runtimes are replaceable implementations behind the panels.

### 5.5 Contributed Approval Posture and Named Availability Checks

The Teacher surface contributes a default approval posture and references the policy templates and rules File 06, File 22, and File 23 own; it evaluates no policy itself:

- **Read-default posture**: explaining, reading progress, searching course materials, and answering a question produce content without escalation and are `ReadOnly` or `WorkspaceWrite` by their touched resources (`policy.effective-tier-resolution`, File 06 §4)
- **Content-generation posture**: generating a lesson, a curriculum, a quiz, an exercise set, or a flashcard set is `WorkspaceWrite` — no approval prompt, but tracked in the version tree as an artifact revision; bulk generation (a full curriculum, a chapter of lessons, an item bank) presents through the shared batched-approval flow (`policy.batched-approval-flow`, File 06 §5.5), not a private approval flow
- **Destructive posture**: resetting a learner's progress or mastery, deleting a curriculum or course, and an irreversible bulk overwrite escalate to `UserApproval`; a destructive reset of learner data carries the `Denied`-floor typed-confirmation rule (`policy.permission-floor-typed-confirmation`, File 06 §7), because learner history is not casually recoverable
- **Untrusted-content posture**: ingested study documents, fetched reference material, and content returned by a knowledge-base or web source enter the model request as `untrusted_source_data` (`context.authority-classes`, File 13 §2.3) and carry no capability or policy authority (`security.untrusted-content`, File 22 §12); this is non-negotiable (§8.6)
- **Learner-data sensitivity posture**: learner progress, mistakes, mastery, and persona are `Sensitive` by default (`block.sensitivity`, File 08 §9, `secret.backend-boundary` File 22 §4); they are governed on export and egress (§18, §22.3) and are not materialized or shared raw
- **Code-execution posture**: graded code, practice code, and runnable lesson examples run through the borrowed coder code-execution capability under its `SandboxProfile` (§15.4) and its approval posture; the Teacher surface adds no private execution path
- **Egress posture**: exporting or sharing learning material that contains learner data or sensitive content is governed egress requiring explicit opt-in (`security.egress-governance`, File 22 §11); raw learner data never egresses

The Teacher surface registers named availability checks (`world.state-aware-capability-availability`, File 18 §9.3) the world model evaluates against the current snapshot — representative: vision-model-available (figure and scanned-document teaching), code-execution-available (graded and practice code), document-source-present (teach-from-document), knowledge-base-available (grounded explanation), lesson-active, curriculum-active, classroom-active, and assessment-active — each a pure function of the world snapshot that gates the availability of specific capabilities and affordances.

## 6. The Artifactized-Education Contract

Anchor: `teacher.artifactized-education`

### 6.1 Definition

The artifactized-education contract is the set of rules by which the Teacher surface produces educational results: a result is a durable, versioned, evidence-bearing `Artifact` revision produced by teaching capabilities, recorded as a citable block linked to its inputs by `derives_from`, with learner mastery carried as `Mastery` memory and assessment blocks — never as transcript prose and never as a row in a private teaching table.

### 6.2 Educational Result as Artifact Revision

A lesson the surface produces is a `Lesson` `Artifact` whose content is the source of truth (`artifact.artifact-version`, File 09 §6, `block.kind-catalogue` (File 08 §3.1)); a course is a `Curriculum` artifact; an assessment is a `Quiz` or `ExerciseSet` artifact; a study set is a `FlashcardSet` artifact; an evaluation rubric is a `Rubric` artifact. Generating, regenerating ("explain that again, simpler"), or editing a result creates a new artifact version — a sibling `Artifact`-kind block linked by `supersedes` when it revises an existing artifact, or a fresh artifact when it produces a new one — committed through the canonical version-creation path (`artifact.version-creation`, File 09 §6.3) and materialized through the workspace mirror where the artifact's `MaterializationPolicy` is `InWorkspace` (`artifact.artifact-materialization`, File 09 §7, `workspace.materialization` (File 24 §10)). An educational result therefore carries review and validation state (§9), provenance (`artifact.provenance`, File 09 §15), and version history — it is never only transcript prose, and artifact-grade educational content is never stored only as an assistant message (§23). A teaching turn that produces only a transient spoken explanation in a conversation commits no artifact; the durable artifact commits when the user or run keeps the lesson, assessment, or study set, with atomic, partial-safe materialization for streamed content (`run.streaming-partial-execution`, File 04 §12, `block.live-partial-write-capabilities` (File 08 §7.5)).

### 6.3 A Lesson Is a Composed Block, Not a `LessonBlock` Kind

A `Lesson` is an `Artifact` of kind `Lesson` whose version is a `Composed` block (`block.block-content`, File 08 §4) whose ordered `children_block_ids` are the lesson's typed parts — a text section, a worked example, an inline runnable code block, a figure or diagram, a math block, an interactive element, or an embedded exercise. The surface introduces no `LessonBlock` block kind (the proposed `LessonBlock` is the deleted pattern, §23); a lesson is an `Artifact`-kind block, and its parts are existing block kinds plus registered `Custom` kinds for genuinely new teaching parts. A `Curriculum` is likewise a composed artifact whose children reference its lessons and carry the ordering and prerequisite affordances; editing the sequence creates a new curriculum version, and the lessons themselves are immutable blocks. Lesson, curriculum, and assessment history and revert are projections over the version graph (§2.7), exactly as `coder.file-history` (File 27 §8) and `data.notebooks` (File 29 §10) project theirs.

### 6.4 Lineage and Evidence Grounding

Every derived educational result records its lineage as `derives_from` edges (`block.canonical-edge-kinds`, File 08 §5.2) from the produced artifact version to its source documents, prior lessons, datasets, and inputs, with the producing run and capability recorded in the ledger (`run.execution-ledger`, File 04 §23.1); "what produced this lesson, and from which sources" is answered by `provenance.query_derivation_chain` (`artifact.provenance`, File 09 §15.3). Educational content that makes a load-bearing factual claim is grounded: a lesson built from a document, a paper walkthrough, a knowledge-base-grounded explanation, or a factual claim in a generated curriculum cites its source through a `Citation` carrying a `SourceSpan` and, where load-bearing, a `Claim` with `Evidence` (`artifact.citation` (File 09 §12), `artifact.claim` (File 09 §9), `artifact.evidence` (File 09 §11)); a claim that cannot be grounded to a source is flagged for review or excluded, never presented as established fact, exactly as web synthesis (`web.evidence-citation-trust`, File 28 §10.4) and data extraction (`data.extraction`, File 29 §8.4) ground their outputs. Pedagogical framing, worked examples, and the model's general explanation do not each require a citation — the grounding rule applies to load-bearing factual assertions, especially in document-derived, paper-walkthrough, and research-mode teaching — matching the proportionate-provenance principle (`core.evidence-provenance`, File 01 §7.12).

### 6.5 Boundary

This section defines the artifactized-education contract. File 08 owns the block, content variants, and composition; File 09 owns the artifact, kinds, materialization, provenance, claims, evidence, and citations; File 11 owns the version commit; File 24 owns the disk mirror. This file owns the educational workflow over them.

## 7. Explanation, Modes, and Rendering

Anchor: `teacher.explanation`

### 7.1 Definition

The explanation contract is the set of rules by which the Teacher surface explains: explanation is one capability with typed sub-modes for delivery and modality, it adapts to the learner's mastery and persona, it grounds load-bearing facts, and its math, code, diagram, and media rendering is the shared interactive-artifact runtime. Explanation modes are workflow and interaction parameters, never autonomy modes.

### 7.2 The Explanation Capability and Its Sub-Modes

The explanation capability (`teacher.explain` and its variants — explain with style, explain code, explain a paper or document, define a term) takes a concept, a target, the learner context, and a configuration, and produces an explanation as durable lesson content or a transient conversational explanation. Its delivery and modality strategies are capability sub-modes within one capability, not separate model-facing calls (`capability.capability`, File 05 §2.3): the **lecture** sub-mode delivers a structured explanation; the **Socratic** sub-mode leads with a guided sequence of questions scoped to what the learner already knows, revealing and correcting a misconception and advancing toward the answer rather than stating it; the **multi-modal** sub-modes render the explanation as visual, code, mathematical, analogy, or diagram content; and the strategy-variant sub-modes produce alternative framings (from first principles, by analogy, by worked example) as sibling artifact candidates the learner chooses among, exactly as a best-of-N selection (`run.child-runs-multi-agent-work`, File 04 §16). The mode is a workflow parameter selected per request and by setting (lecture versus Socratic, the modality, the depth), never an autonomy mode and never a phase machine (§22). A `teacher.check_understanding` capability probes what the learner actually knows; its result feeds the Memory-governed `Mastery` update path (§12) and informs the next explanation's depth and mode.

### 7.3 Adaptation

Explanation adapts to durable substrate state, not a hidden per-surface dial: it reads the learner's `Mastery` memory (prior knowledge, struggles, misconceptions) and the learner-persona core-memory block (pace, difficulty preference, feedback style, language, accessibility) (`memory.core-memory`, File 14 §5, §19) and configures depth, modality, and tone accordingly. A remembered preference is applied as an attributed, inspectable input, not hidden behavior; the learner sees that a preference shaped the explanation and can override it (`memory.natural-use-inspectability`, File 14 §13). When prior knowledge or a prerequisite concept is relevant, the explanation links to it through the concept graph (§8) and recalls the prerequisite. Adaptive depth across a session is reaction to the live state and the user's request, not a pre-declared participation level.

### 7.4 Rendering

Lesson and explanation content renders through the shared interactive-artifact runtime (`artifact.artifact-materialization`, File 09 §7, the UI specs): mathematical notation, syntax-highlighted code with inline execution over borrowed code execution (§9, §15.4), diagrams and concept maps as `Diagram` artifacts, embedded media as `Image`/`Audio`/`Video` artifacts, and interactive elements whose state persists as blocks (§10.4). The math, code, diagram, and media renderers are replaceable UI implementations the artifact runtime selects; the durable content is the lesson artifact and its child blocks, never the rendered view. Rendering choices are UI-owned; this file owns the content-and-mode contract.

### 7.5 Boundary

This section owns the explanation workflow, modes, and content contract. File 09 owns the artifact and interactive-artifact runtime; File 14 owns the mastery and persona memory the explanation adapts to; File 05 owns the sub-mode-bearing capability; the UI specs own the rendering. The explanation model is the surface's default `ModelProfile` (§15.3); the math, code, and diagram renderers are replaceable implementations.

## 8. Curriculum, the Concept Graph, and Teach-from-Document

Anchor: `teacher.curriculum`

### 8.1 Definition

The curriculum contract is the set of rules by which the Teacher surface builds and navigates structured learning: a curriculum is a `Curriculum` artifact, the concept-and-prerequisite graph is the shared entity-relationship projection, "teach me from this document" is a borrowed-extraction workflow with source grounding, and a deep or perspective-guided curriculum is a child-run structure over the one execution model.

### 8.2 The Curriculum Artifact and the Concept Graph

A learning path is a `Curriculum` artifact (`artifact.artifact-kind`, File 09 §4) composed of an ordered lesson sequence, prerequisite relations, and progress affordances (checkpoints, recommended sequence). The concept-and-prerequisite graph — the skill tree the `curriculum` panel renders (§4.2) — is the shared entity-relationship projection (`retrieval.source-records`, File 12 §4.2), with concepts as entities and prerequisites as relations, projected with mastery-derived status from `Mastery` memory (§12); it is not a private `skill_tree` or `teacher_curricula` table (§23). Recommending the next lesson (`teacher.curriculum.get_next`) is a query over the concept graph and the learner's mastery: a concept is available when its prerequisites are mastered, recommended when it advances the goal, and deferred when its prerequisites are not yet met. A curriculum the user wants to reuse as a template is a `WorkflowTemplate` or a kept `Curriculum` artifact (`run.automation-reuse`, File 04 §26), not a private template store.

### 8.3 Teach-from-Document

The "teach me from this document" workflow (`teacher.curriculum.from_document`, `teacher.explain_from_document`, `teacher.explain_paper`) accepts a document — a file, a fetched page, or a mounted source — a goal, and the learner level, and produces a grounded curriculum or explanation: it borrows the data-extraction capability to parse the document into typed content and structured concepts (`data.extraction`, File 29 §8, borrowed in place per §14), identifies concepts, definitions, examples, exercises, and prerequisites, projects them into the shared concept graph (`retrieval.source-records`, File 12 §4.2), and generates a `Curriculum` of one lesson per concept with quizzes at section boundaries and practice from the examples. Every concept, definition, and load-bearing fact in the generated material grounds to a `SourceSpan` `Citation` in the document (§6.4); ungroundable content is flagged for review, not asserted. The generated lessons carry `derives_from` edges to the source document and tag their source so the learner can trace a lesson back to its origin. The document parsers and the optical-character-recognition engine are the Data Processor's replaceable implementations behind the borrowed extraction capability; the Teacher surface owns the curriculum intent, not the parser.

### 8.4 Deep, Perspective-Guided, and Research Curricula

A deep curriculum for a complex topic is a child-run structure over the shared execution substrate (`run.child-runs-multi-agent-work`, File 04 §16), mirroring web deep research (`web.research`, File 28 §9): the surface may discover diverse perspectives on the topic (beginner and expert, theoretical and applied, historical and current), spawn a research or curriculum child run per perspective that gathers and grounds material, filter by source quality, generate an outline, and write each section as a child-run-produced lesson under the grounding rule, cross-validating facts across sources. A research-style "learn by doing" curriculum (formulate a question, design and run experiments, analyze, write up) composes the same child-run structure with borrowed data extraction, charting, and code execution. The surface declares the spawnable curriculum and research sub-agent kinds (`worksurface.runtime-execution-declaration`, File 25 §9.2); child runs return through the canonical output contracts (`run.merge`, File 04 §16.4) and never mutate the coordinator's state directly. The three-mode depth control (Quick, Standard, Deep — a one-paragraph explanation, a lesson with example and quiz, or a full curriculum with practice and a review schedule) is a workflow parameter and an advisory budget (`run.budgets-limits`, File 04 §21), not an autonomy mode and not a phase machine (§22).

### 8.5 Boundary

This section owns the curriculum and concept-graph workflow. File 12 owns the entity-relationship projection and the retrieval substrate; File 29 owns the extraction capability the surface borrows; File 09 owns the `Curriculum` artifact and the citation grounding; File 04 owns the child-run structure; File 16 owns the model selection per research and writing role. The document parsers and extraction implementations are the Data Processor's, behind the borrowed capability.

### 8.6 Untrusted Source Material

All ingested study documents, fetched reference material, parsed content, and content returned by a knowledge-base or web source are `untrusted_source_data` (`context.authority-classes`, File 13 §2.3) and carry no capability or policy authority by their own text (`security.untrusted-content`, File 22 §12): an instruction found inside a study document — including a document bearing a familiar instruction-file name — reaches the runtime as data the user or policy still gates, never as a command. This is the surface's non-negotiable default. Teach-from-document borrows the shared retrieval substrate (`retrieval.consequences-for-later-specs`, File 12 §22) and consults the learner's own course materials before general model knowledge where the workflow prefers it (§13), committing extracted concepts and relationships into the shared entity-relationship projection rather than a private graph store.

## 9. Assessment, Grading, and Adaptive Difficulty

Anchor: `teacher.assessment`

### 9.1 Definition

The assessment contract is the set of rules by which the Teacher surface tests understanding: an assessment is a `Quiz` or `ExerciseSet` artifact, grading produces `Validation` blocks for objective checks and `Critique` blocks for subjective evaluation, adaptive difficulty is capability-internal item selection over mastery, and the item bank is artifact question-variants — never a private assessment or item-bank table.

### 9.2 Assessments as Artifacts and the Four Assessment Types

A quiz is a `Quiz` artifact and a practice set is an `ExerciseSet` artifact (`artifact.artifact-kind`, File 09 §4) carrying prompts, answer keys or grading policy, and feedback rules. The four assessment types are sub-modes of the assessment capabilities, not separate primitives: a **multiple-choice** item carries options with distractors drawn from common misconceptions; a **short-answer** item is graded against a rubric; a **code** item is evaluated by running it against test cases over borrowed code execution; a **free-form** item is evaluated for key concepts. An assessment is interactive: the learner answers through the `assessment` panel's interactive-artifact rendering, but only submitted attempts and explicitly kept session records become durable blocks or artifact versions (§10.4); transient focus, draft, flag, and progress state is live surface state, not a private session table.

### 9.3 Grading Produces Validation and Critique

Grading an answer produces durable, typed records, not prose. A submitted quiz answer, exercise response, flashcard recall grade, or practice solution creates a submitted-attempt block linked to the assessment artifact version, question or item ids, answer payload, rubric or grading-policy version, and the resulting `Validation` or `Critique`. An **objective** check — a multiple-choice key match, a code submission passing its test cases — produces a `Validation` block of an appropriate kind (`artifact.validation-critique`, File 09 §14) linked to the attempt and assessment by `validated_by`, carrying pass/fail per item. A **subjective** evaluation — a short-answer or free-form response graded against a rubric — produces a `Critique` block carrying the rubric-grounded findings and feedback, paired with a companion `EvaluatorScore` `Validation` whose `evaluator_class` records the rubric-grounded class verdict (a typed class, never a numeric score, `artifact.validation-critique`, File 09 §14.1). Model-mediated critiques record the submitted-attempt block, rubric artifact version, grading prompt or template version, model-selection record, provider/model descriptor, and relevant grader settings; historical inspection reads that recorded critique and never live re-grades. Code grading borrows the coder code-execution capability confined under its sandbox (§15.4); the test cases run confined and the result is captured as an observation feeding the validation. A `Rubric` artifact is the durable, reusable evaluation criteria a subjective grading reads. Misconception detection is a `Critique` finding plus a Memory-governed `Mastery` update proposal or policy-approved update (§12), surfaced to the learner, not silently dropped. Rejecting or correcting a mastery proposal does not delete the underlying attempt, validation, or critique.

### 9.4 Adaptive Difficulty and the Item Bank

Adaptive difficulty is capability-internal item selection, not a private engine: the assessment capability estimates the learner's current ability from `Mastery` memory and the assessment-block history, selects the next item near that ability to maximize information, and adjusts the estimate and difficulty on each correct or incorrect response, holding to a configurable baseline before adjusting. The specific selection model (an ability-and-information-driven model or a simpler heuristic), the ability estimator, and the baseline and adjustment thresholds are a capability strategy and settings, not canonical constants (§23, `settings.settings-over-constants` File 15 §13). The item bank is `Quiz`/`ExerciseSet` artifacts with question variants (multiple generated variants of an item on the same concept), and the per-item correctness statistics (which items are ambiguous, which discriminate well) are a rebuildable projection over the assessment blocks (`core.projection`, File 01 §6.11), not a private item-statistics table.

### 9.5 Boundary

This section owns the assessment, grading, and adaptive-difficulty workflow. File 09 owns the `Quiz`/`ExerciseSet`/`Rubric` artifacts, the submitted-attempt relationship to validation and critique records, and the validation-state derivation; File 04 §22 owns the completion floor (a run that required a recorded assessment does not complete on prose alone); File 23 (via the borrowed coder capability) confines code grading; File 14 owns the mastery the difficulty selection reads and updates through its proposal discipline. The adaptive-difficulty model and the grading rubric format are replaceable implementations and settings.

## 10. Practice, Spaced Repetition, and Flashcards

Anchor: `teacher.practice-srs`

### 10.1 Definition

The practice-and-study contract is the set of rules by which the Teacher surface drills and reinforces: practice problems run over borrowed code execution, study sets are `FlashcardSet` artifacts, spaced-repetition scheduling state lives in `Mastery` memory with an event-first review-due signal, and submitted interactive practice and review records persist as blocks — never a private flashcard or SRS-schedule table.

### 10.2 Practice

A practice problem (`teacher.practice.generate`/`teacher.practice.evaluate`) is generated as an `ExerciseSet` artifact carrying the problem, optional starter code, progressive hints (disabled by default, revealed on request), test cases, and a solution with explanation. A code practice problem runs the learner's solution against its tests over the borrowed coder code-execution capability confined under its sandbox (§15.4); the result feeds a `Validation` and a `Critique` with feedback. Progressive hints are revealed by explicit learner action; the solution is revealed per the configured policy (for example after a configurable number of attempts), and that policy is a setting, not a canonical constant.

### 10.3 Flashcards, Cloze, and Spaced Repetition

A study set is a `FlashcardSet` artifact (`artifact.artifact-kind`, File 09 §4) carrying cards (fronts, backs, tags, optional media) or cloze-deletion items generated from a passage. Spaced-repetition scheduling is `Mastery` memory, not a private schedule table: each card's or concept's review state — its recall strength, interval, and due condition — is carried as `Mastery` memory with time-bounded validity (`memory.validity-retention-short-term-memory`, File 14 §7), and a recall grade produces a Memory-governed `Mastery` update proposal or policy-approved update through the canonical memory-update path (`memory.learning-extraction`, File 14 §8). The review-due trigger owns no schedule state; it evaluates a declared due predicate over `Mastery` validity and card or concept ids. Event wakeups re-evaluate the predicate and fire a `RunIntent` to surface the due set; fallback checks are safety/recovery mechanisms only, never correctness conditions (`memory.validity-retention-short-term-memory`, File 14 §7, `core.event-first-by-default` File 01 §7.15). The specific spaced-repetition algorithm and its intervals are a capability strategy and settings, not canonical constants (§23). The surface introduces no `teacher_flashcards` or `teacher_srs_schedule` table and no hourly scheduler worker as a correctness mechanism.

### 10.4 Interactive Practice and Quiz State

Interactive lessons, quizzes, and flashcards render through the shared interactive-artifact runtime (`artifact.artifact-materialization`, File 09 §7). Submitted answers, recall grades, graded attempts, kept notes, and accepted session summaries persist as blocks or artifact versions; focus, cursor position, draft answers, temporary flags, and panel progress are live surface state unless explicitly committed. Committed interactive artifact state carries a `schema_version` and a load-state migration hook so it survives a runtime or schema update (matching the interactive-artifact schema-versioning the canon establishes). A quiz attempt and a study session are sequences of blocks whose history and revert live in the version graph (§2.7).

### 10.5 Boundary

This section owns the practice and spaced-repetition workflow. File 09 owns the `ExerciseSet`/`FlashcardSet` artifacts and the interactive-artifact runtime; File 14 owns the `Mastery` memory carrying SRS state and the validity-and-review semantics; File 23 (via the borrowed coder capability) confines practice code; File 26 owns the `Trigger` rail the review-due monitor uses. The spaced-repetition algorithm is a replaceable implementation and settings.

## 11. The Multi-Agent Classroom

Anchor: `teacher.classroom`

### 11.1 Definition

The multi-agent classroom is the Teacher surface workflow for running multiple agents in one teaching session — a teacher-and-assistant pair, a teacher-and-student-simulator, a debate, a critique workshop, or a director-led roundtable — where many agent runs share one transcript. It composes a coordinator run and role-differentiated child runs over the one execution model (`run.child-runs-multi-agent-work`, File 04 §16, `intent.parallel-work` (File 02 §7.1)); the surface owns no private orchestration, classroom, or turn store.

### 11.2 The Classroom as a Coordinator-Plus-Child-Run Structure

A classroom is a coordinator run that spawns role-differentiated child runs and sequences their turns into one shared transcript (`intent.parallel-work`, File 02 §7.1 — "structured multi-agent presentations (classrooms, debates, coordinator-worker patterns) where many agent runs share one transcript"). The **director** is the coordinator's speaker-selection: the `Sequential` strategy is deterministic round-robin (no model step), the `LlmDirected` strategy is a coordinator model step that decides the next speaker or cues the user or ends, and the `Event` strategy selects speakers by event rules; the director strategy is a workflow parameter, not an autonomy mode. The **agent roles** — teacher (leads), assistant (supports and rephrases), student (asks short questions), critic (challenges), debate sides, and peer (a learner at the user's level) — are the surface's `spawnable_subagent_types` (`worksurface.runtime-execution-declaration`, File 25 §9.2), each a child run whose role guideline is an instruction contribution and whose allowed actions are the capabilities available to that role. A `Classroom` is a `WorldEntity` (§20) and a version-tree projection of its turn blocks, not a `teacher_classrooms`/`teacher_classroom_turns` table (§23).

### 11.3 Interleaved Text and Action, Peer Context, and Scene Filtering

An agent turn is blocks plus capability invocations, not a private action vocabulary: the agent emits text (a `MessageAssistant` and its content blocks) interleaved with capability calls — a whiteboard draw is a `Diagram`/canvas capability producing a `Diagram` artifact or a canvas op, a spotlight or highlight is a surface-state or world-model op, a code execution is the borrowed coder capability, a chart is borrowed `data.chart`, and a media play is borrowed media — each flowing through the one capability pipeline, policy, and ledger (`run.call-pipeline`, File 04 §8.2). The classroom UI renders the actions alongside the streamed text. **Peer-context injection** — giving each agent a summary of what the others said so agents build on rather than echo each other — is the child-run explicit context-sharing policy (`run.isolation`, File 04 §16.2 — "context sharing must be explicit; a child run does not receive unrestricted parent context by default"), not a private mechanism. **Two-stage generation** — an outline of the session, then scene-by-scene play — is the shared `plan` capability producing a `Plan` block followed by execution (`run.task-promotion-task-updates`, File 04 §18), not a phase machine. **Scene-based action filtering** — certain actions available only in certain scenes (the whiteboard and the slide spotlight are mutually exclusive; students cannot draw) — is the availability evaluator over the live `SurfaceState` and the world model (`world.state-aware-capability-availability`, File 18 §9, via `availability_predicate`/`blocked_by` on the role's capabilities), not a private scene state machine.

### 11.4 Classroom Variants

The classroom structure carries the canonical teaching variants as run structures, not separate engines: a **teacher-and-assistant** or **teacher-and-student** pair makes a single tutor a multi-voice session; a **student-simulator** session (the Feynman technique) spawns a student-role child run that the user teaches, with the simulator asking clarifying questions at varying sophistication and flagging gaps, and a final `Critique` evaluating the user's explanations; a **debate** spawns two opposed sides while the learner observes and intervenes; a **critique workshop** spawns critics with differentiated lenses. The user is a participant in the shared transcript and may interject, take over, or steer at any turn (`run.user-intervention`, File 04 §17.1, via the Steering rail §17). Each variant is the same coordinator-plus-child-run structure with different roles and a different director strategy.

### 11.5 Boundary

This section owns the classroom presentation and the role and director declarations. File 04 owns the child-run model, isolation, parallelism, context-sharing, and merge, and the `plan` capability; File 02 owns the shared-transcript multi-agent shape; File 18 owns the availability evaluator the scene filtering uses; File 09 owns the `Diagram` artifact and the turn blocks; File 16 owns the per-role model selection. The surface introduces no parallel orchestrator, scheduler, or classroom table.

## 12. Learner State, Mastery, and Progress

Anchor: `teacher.learner-state`

### 12.1 Definition

The learner-state contract is the set of rules by which the Teacher surface knows and tracks the learner: mastery is `Mastery` memory, the learner persona is a core-memory block, progress is a rebuildable projection over mastery and the assessment blocks, and the learner is single per installation — never a private progress table and never a `user_id`-keyed learner record.

### 12.2 Mastery and the Learner Persona

What the learner knows, is learning, struggles with, and has misconceptions about is `Mastery` memory (`memory.kinds-scopes-facets`, File 14 §4.1), updated only through the canonical memory-update path (`memory.learning-extraction`, File 14 §8) as assessment attempts, critiques, understanding checks, and completed concepts produce evidence, and read by explanation, curriculum recommendation, and adaptive difficulty. Mastery and persona are `Sensitive` by default (§5.5) and follow the Memory substrate's privacy, inspection, and user-control rules (`memory.privacy-sensitivity-user-control`, File 14 §18): the learner may inspect, correct, export, and delete their mastery and persona. ### 12.3 Progress as a Projection

Learner progress — concepts learned, in progress, and struggling, performance over time, time on topic, and recommended next steps — is a rebuildable projection over `Mastery` memory and the assessment-result blocks (`core.projection`, File 01 §6.11), rendered in the `progress` panel through borrowed `data.chart` (§14). It is not a `teacher_progress` or `LearnerProgress` table; its loss is a recomputation, never data loss. The concept-graph status the `curriculum` panel shows (§8.2) is the same projection over the concept graph and mastery.

### 12.4 Single Learner, No `user_id`

The Teacher surface may consume that future scope once defined, but it does not define memory scope vocabulary and does not invent a parallel user table.

### 12.5 Boundary

## 13. Knowledge-Base Grounding and Source Materials

Anchor: `teacher.knowledge-grounding`

### 13.1 Definition

The knowledge-grounding contract is the set of rules by which the Teacher surface teaches from the learner's own materials: it borrows the shared retrieval substrate to index and search course materials, it grounds explanation in those materials with citation, it distinguishes source-bound teaching from general teaching, and it owns no private knowledge store.

### 13.2 Course Materials and Grounded Explanation

The Teacher surface registers a document as course material (`teacher.kb.import_document`) by committing it as a `KnowledgeEntry` and source records through the shared retrieval and ingestion substrate (`retrieval.knowledge-base` (File 12 §10), `retrieval.ingestion` (File 12 §14.3)), tagged as course material; searching course materials (`teacher.kb.search_materials`) borrows the shared knowledge and retrieval capabilities (`retrieval.capability-surface`, File 12 §13) with a course-material filter. The explanation flow consults the learner's course materials first where the workflow prefers grounding (a researcher's paper library, a student's textbook, an educator's curriculum): when the learner's materials address the concept, the explanation uses them and cites them (a `Citation` with a `SourceSpan`, §6.4). If the run is source-bound — for example "teach me from this PDF" or "quiz me only on this chapter" — uncovered concepts produce a typed provenance gap, a clarification request, or a visibly labeled outside-background segment accepted by the user or policy; they do not silently enter as course-material content. If the run is general teaching, the capability may fall back to labeled general model knowledge when the materials do not cover the topic. The surface introduces no private knowledge, index, or graph store (`retrieval.explicit-rejections`, File 12 §21); course-material grounding is the shared substrate with a teaching filter.

## 14. Teaching as a Cross-Surface Service and Cross-Surface Composition

Anchor: `teacher.cross-surface`

### 14.1 Definition

Cross-surface composition is how the Teacher surface composes with other surfaces: the teaching capabilities other surfaces borrow to embed teaching in their work, the teaching content that composes into other surfaces' outputs, and the capabilities the Teacher surface borrows in place.

### 14.2 Teaching Capabilities Borrowed by Other Surfaces

The Teacher surface exposes its explanation, assessment, mastery-update, and exercise-generation capabilities as registry capabilities other surfaces borrow in place (`worksurface.actions-declaration`, File 25 §6.3, `surface.subsystem-surface-spec` (File 07 §5.5)): the Coder surface borrows `teacher.explain_code` to walk through a change and `teacher.quiz.generate` to drill an API; the Data Processor surface borrows `teacher.explain` and `teacher.practice.generate` to teach a technique over a dataset; the System Agent surface borrows `teacher.explain` to annotate a maintenance action and expose its decision points; any surface borrows the assess-and-update-mastery capabilities to record what the learner demonstrated. This follows the same rule that lets the Teacher surface borrow Coder, Web, Data Processor, Memory, TTS, and media capabilities in place (§14.4): all surfaces may interact through capability borrowing without changing the active run's primary surface. A borrowing surface remains in its own surface; the capability-owning surface owns the capability, the borrowing surface's workflow is its own, and the ledger records the cross-surface reach. The teaching cross-cutting affordance (`worksurface.views-presets`, File 25 §7.5) lets a surface offer a "teach me this" or "quiz me on this" affordance over its own artifacts without becoming the Teacher surface and without a per-surface teacher-mode field (§22).

### 14.3 Teaching Content Composes Across Surfaces

Lessons, curricula, assessments, and progress visualizations compose into other surfaces' outputs through the one block and entity pools (`block.cross-surface-composition`, File 08 §12.3, `artifact.cross-surface-interoperability` (File 09 §17.3)): a report composed in conversation may carry a `Lesson` child the Teacher produced and a `Chart` child a progress projection produced; a coder code change may carry an explanatory `Lesson`; a research report's findings may seed a `Curriculum`. Cross-surface composition is a property of the shared pools, not a teaching-private integration.

### 14.4 Borrowing in Place

A teaching run that needs a capability outside the surface — `data.extract` to parse a textbook, the coder code-execution capability to grade or run code, `data.chart` to visualize progress, `web.fetch` or `web.search` for reference material, memory recall of a learner preference, text-to-speech for read-aloud, or media generation for a figure or a narrated walkthrough — borrows it in place and remains in the Teacher surface (§5.4), reached through a routing reroute or explicit user override (`routing.mid-execution-reroute`, File 03 §12), never by silent surface change. The Teacher surface teaches and assesses; it borrows extraction rather than re-owning the Data Processor's parsers, borrows code execution rather than owning a code IDE, borrows browsing rather than driving a browser, and borrows media generation rather than creating media. Other surfaces follow the same pattern when they borrow Teacher capabilities.

### 14.5 Boundary

This section owns the teaching cross-surface composition and service face. File 07 owns borrowing; Files 08 and 09 own the shared pools; File 03 and File 04 own reroute; File 25 §7.5 owns the cross-cutting affordance; the borrowing surfaces own their own workflows.

## 15. Context, Model, Execution, Sandbox, and Workspace Policy

Anchor: `teacher.policy-declaration`

### 15.1 Definition

The Teacher surface declares its default context, compaction, model, execution, budget, sandbox, and workspace policies by reference (`worksurface.context-model-declaration` (File 25 §8), `worksurface.runtime-execution-declaration` (File 25 §9)). It names which policies it defaults to; the policy mechanics stay with their owning files, and every default is overridable through the settings cascade (`settings.scopes-profile-contexts-overlays`, File 15 §5.2).

### 15.2 Default Context and Compaction Policy

The Teacher surface declares a default teaching-aware `ContextPolicy` and `CompactionPolicy` from the canonical families (`context.context-policies`, File 13 §4, `context.compaction` (File 13 §12)): the context policy assembles the learner persona, the active mastery for the concepts at hand, the active lesson or curriculum, and selected course materials as `RetrievedContext`, references large documents and courses rather than flooding context with full content (`context.current-input-oversize-handling`, File 13 §7, `context.virtual-paging` (File 13 §13)), and marks ingested and fetched material `untrusted_source_data` (§8.6); the compaction policy preserves the evidence and citation chains of grounded lessons (`artifact.evidence` (File 09 §11.5), `context.continuity-summaries` (File 13 §14)) and the continuity of a long tutoring or classroom session, paging out completed lessons to references. Every model request assembles through the one `ContextAssemblyService`; the surface creates no private model-request path.

### 15.3 Default Model Profile

The Teacher surface declares a default teaching-and-vision-capable `ModelProfile` and per-role preferences (`model.model-profile`, File 16 §4): the profile prefers a reasoning-capable model for explanation and curriculum design, prefers structured-output support for assessment-item generation and grading, prefers a vision-capable route where diagrams, figures, or scanned study materials are involved (§8.3), and prefers a lower-cost route for definition lookup, item-variant generation, and routine grading. Per-role preferences distinguish the explainer, the assessor, the grader, the lecturer, the director, the reflector, and the student-simulator roles (§11). Content sensitivity over learner data and ingested material is analyzed before model selection (`model.model-workload-requirements`, File 16 §5.3), so sensitive learner data selects a model satisfying the data-boundary requirement. The surface implements no private model-selection logic; selection stays the Model Strategy layer's, and the learner or educator may override the profile per scope.

### 15.4 Default Sandbox via Borrowed Code Execution

The Teacher surface runs no private sandbox: graded code, practice code, and runnable lesson examples run through the borrowed coder code-execution capability under the Coder surface's `SandboxProfile` (`coder.surface-contract`, File 27, `sandbox.contract` File 23 §3), confined to the workspace filesystem boundary, with the test cases and the learner's submission running confined and killable, and the result captured as an observation feeding a `Validation` (`run.streaming-partial-execution`, File 04 §12, `sandbox.consequences-for-later-specs` File 23 §21). Code snippets from ingested or fetched study material are `untrusted_source_data`; they execute only when transformed into an explicit code-execution invocation with visible arguments, policy evaluation, sandbox profile, and killability. A finite, configurable, killable wall-clock guard around a learner's submission with no completion signal (an infinite loop in a practice solution) is a safety guard, never a correctness condition (`sandbox.resource-limits`, File 23 §9.3). The Teacher surface declares no private sandbox profile and redefines no enforcement or kill semantics; it composes the coder profile by reference.

### 15.5 Default Execution Preset and the Plan Capability

The Teacher surface declares a default execution preset — the surface-runtime structure its teaching runs start from (`run.execution-entry`, File 04 §4) — as a model-and-tool agent loop over the shared run lifecycle: probe understanding, explain or generate, assess, propose or apply Memory-governed mastery updates, and recommend the next step, iterating until completion, pause, or user intervention. A classroom, a deep curriculum, or a paper walkthrough runs as the child-run structure (§11, §8.4) over the same semantics. Planning is the optional shared `plan` capability (`run.task-promotion-task-updates`, File 04 §18): the agent may call it to produce an editable `Plan` block — a curriculum outline, a classroom session outline — when the work's complexity warrants it. There is no planning phase, no planner-versus-executor model split, no phase state machine, and no per-surface "teaching mode" toggle; the `plan` capability is a normal block-producing tool any surface may use, and plan blocks live in the version tree (§22). Completion evidence is teaching-specific: an explanation that is kept commits a lesson artifact, an assessment commits its `Quiz`/`ExerciseSet` artifact and its `Validation`/`Critique` grading, and a study session commits its review state; prose-only completion is valid only for a transient conversational explanation that the run contract did not require to produce a durable artifact. The surface declares default run budgets as advisory ceilings overridable per scope, never hidden hard limits (`run.budgets-limits`, File 04 §21), and declares the teaching sub-agent kinds it spawns (§11, §8.4 — representatively a lecturer, an assessor, a reflector, a student-simulator, a debate side, and a director).

### 15.6 Instruction-File Qualifier and Contribution

The Teacher surface declares its instruction-file qualifier — the `ATLAS.teacher.md` variant of the `ATLAS.md` hierarchy (`workspace.instruction-files`, File 24 §9.2) — and its model-request instruction contribution: the surface's teaching identity, the learner-environment facts, the grounding and untrusted-material discipline, and the teaching guidance, assembled by context assembly into the `InstructionSources` region with the correct authority class (`context.instruction-sources-workspace-files`, File 13 §16). The surface's instruction contribution is one attributed assembly part among many, never a private prompt the surface owns. Instructions found inside ingested study documents, fetched material, or course content are untrusted data with no instruction authority, regardless of any familiar instruction-file name they bear (§8.6); only the workspace `ATLAS.md`/`ATLAS.teacher.md` hierarchy carries instruction authority, resolved through File 24.

### 15.7 Workspace Relationship

The Teacher surface's views render over the bound `Workspace` (`workspace.conversation-binding`, File 24 §7); its lessons, curricula, assessments, flashcard sets, reports, and exports materialize through the disk↔substrate mirror and File 23's filesystem boundary (§6.2); its per-surface working convention is a `teacher/` subdirectory (representatively `lessons/`, `courses/`, `assessments/`, and `exports/`) projected against the workspace mirror (`workspace.materialization`, File 24 §10). Workspace `.atlas/` may contain teaching settings, command definitions, and the `ATLAS.teacher.md` qualifier; learner data and any source credential are device-local and vault-held or memory-held under the sensitivity rules (§22.3) and never sync raw. The surface owns no workspace identity, disk-history store, or parallel materialization path.

### 15.8 Boundary

This section declares the teaching defaults by reference. File 13 owns context and compaction; File 16 owns the model profile and selection; File 04 owns the run, the execution structure, the `plan` capability, and budgets; File 23 and File 27 own the sandbox the surface borrows; File 24 owns the workspace and instruction files; File 15 owns the settings resolution.

The per-profile workflows the source material proposes — the ten learner profiles (researcher, software developer, office worker, student, creative, data analyst, solopreneur, casual user, power user, educator) — are presentation and customization seeds (emphasized capabilities, default depth, default panels, a persona seed), saved as view presets and settings/profile records (`settings.profiles`, File 15 §7), never autonomy or participation modes (§22): the **Student** profile is the primary one (emphasizing assessment, practice, spaced repetition, and study schedules); the **Educator** profile emphasizes lesson planning, rubric design, differentiation, and student-scenario simulation, and seeds the Mentor persona and the lesson-planning, quiz-generation, and rubric capabilities; the researcher profile emphasizes paper walkthroughs and citation-grounded depth; the developer profile emphasizes code explanation and graded practice. The user may save custom presets and override the default per scope; a packaged teaching extension (an `atlas-teaching`-style lesson-planning bundle, an `atlas-study`-style spaced-repetition bundle) contributes presets, knowledge, and capabilities through the proposal-first registration and source-approval path (§24), not a private surface variant.

The feed is a projection over the ledger and event stream, not a private log. The surface declares default inspectors (context, mastery, lineage, and validation inspection) as inspector-panel projections over substrate state. **Accessibility is a first-class teaching concern** (a learning surface serves learners with diverse needs): the surface honors the canonical accessibility requirements (semantic roles and labels on every panel and control affordance per `worksurface.state-declaration` File 25 §5.3 and §6.4, keyboard and screen-reader operability, and the broader UI accessibility baseline the UI specs own); generated lessons, diagrams, media, quizzes, and flashcards carry semantic headings, labels, alt text or descriptions for non-text content, captions or transcripts for audio/video where available, and keyboard-operable interaction descriptions; read-aloud of lessons and feedback uses the borrowed text-to-speech capability with the transcription always available alongside the audio (`controlrail.voice-rail`, File 26 §9, §17), and the learner persona's reading-level, dyslexia-friendly, and visual-impairment preferences (§19) configure rendering. Accessibility settings and persona preferences are configuration, never hardcoded.

The Teacher surface declares a customization policy (`worksurface.views-presets`, File 25 §7.4) describing which kinds of customization it permits — panel rearrangement, the lesson-and-exercise split, custom panel registration, and widget placement (a "today's scheduled learning tasks" or "review due" widget, a classroom or lesson utility widget) — resolved by the UI customization layer; the surface owns what kinds are allowed, not the concrete placement mechanics. Surface morphing — projecting the teaching panels and active view preset when the Teacher surface becomes the active presentation surface — is a UI projection driven by the `SurfaceContract`, the live `SurfaceState`, and the routing decision (`worksurface.views-presets`, File 25 §7.3); it changes presentation, not the work model. Conversation is an always-available control rail and an expand/collapse view, never forced to occupy the primary pane during teaching work (`worksurface.activation-shell`, File 25 §11.3); a teaching conversation may move between conversation-first and a teaching-surface focus over time without changing the work model.

A review-due or scheduled-study monitor that depends on a local source syncs as a definition, not as an active local binding; activation on another device revalidates the source.

### 21.4 Portability

The surface's durable teaching state rides the syncable substrate and the `PortablePackage` for cross-device and cross-installation movement (`portability.consequences`, File 21 §18); a lesson, its curriculum, its assessments, and the study sets derived from it export losslessly with the captured support content required to reproduce them — source excerpts, citations, artifact versions, and the content-addressed blobs they reference — unless policy or sensitivity filtering omits them with typed provenance gaps. Derived indexes, the concept-graph projection, and the progress projections are rebuilt on receive rather than transported. The surface may declare a lossy convenience export (a study deck, a textbook, a slide deck, a vault) per §18, passing through egress governance and sensitivity filtering. The surface persists no raw secret, raw credential, or raw learner data in any materialized, exported, or synced state, and exposes no absolute host path to the model by default (`secret.backend-boundary`, File 22 §4). Every hash the surface relies on — an artifact content hash, a blob address, a projection cache key, an export-bundle hash — is computed over a declared `CanonicalEncoding`, never physical bytes (`core.canonical-hash`, File 01 §7.14); the surface defines no new canonical hash and inherits each from its owning file.

### 21.5 Boundary

This section declares the teaching persistence and locality classification. File 20 owns the storage substrate, the blob store, and rebuild orchestration; File 21 owns replication and the package; File 22 owns the secret, learner-data, and egress boundaries; File 14 owns the memory persistence; File 24 owns the workspace locality split; File 11 and File 12 own the version-graph and index projections.

## 22. Capability, Event, and Settings Surface

Anchor: `teacher.capability-event-settings`

### 22.1 Capabilities

The Teacher surface contributes its capabilities to the one Capability Registry as `Subsystem`-sourced built-ins or source-approved teaching adapters over neutral capabilities (`capability.declaration` (File 05 §3), `capability.adapter-capabilities` (File 05 §17.4)), tier-gated by policy (File 06), surfaced through tool-surface composition (File 07), and invoked through the shared pipeline (`run.call-pipeline`, File 04 §8.2). The capability families are enumerated in §5.2. Each capability declares its touched resources (notably lesson and learner-data resources, study files, and the borrowed code, extraction, and network resources, `capability.touched-resources` (File 05 §6.2)), permission tier and floor, reversibility, concurrency, replay class, validation path, and produced block, artifact, and observation kinds; the surface introduces no parallel capability registry and no out-of-band action path, and every teaching capability is the single source for all its invocation paths (`core.extension-planes`, File 01 §6.14), including the borrowable cross-surface service face (§14). A grading or assessment capability declares its `replay_class` and records the invocation identity needed for replay and audit — submitted attempt, rubric or grading-policy version, prompt/template version, model-selection record, provider/model descriptor, and relevant grader settings — so a recorded grading replays from its `Validation`/`Critique` blocks and observations rather than a live re-grade (`capability.replay-class`, File 05 §7.3).

### 22.2 Events

The Teacher surface emits its events through the one event bus and ledger with the canonical envelope (`ledger.event-stream`, File 10 §5). Surface-lifecycle and tool-surface events are owned by Files 25, 07, and 18 and flow through their vocabularies; artifact, version, validation, observation, and provenance events are owned by Files 09 and 11 and flow through theirs; memory events (mastery updates, learner-state proposals) are owned by File 14. Teaching-specific facts that no canonical or owning-file vocabulary already defines register as `Custom { namespace: "teacher", name, payload }` extensions (`ledger.custom-kind-registration`, File 10 §4.3) — representatively the lesson-generated signal, the curriculum-from-document-built signal, the classroom-turn-taken signal, the review-due signal (which the review-due `Trigger` consumes, §17.4), the concept-mastered and misconception-detected signals, and the assessment-graded signal — each declaring its payload schema, cross-reference keys, default sensitivity (an event carrying learner progress or a mistake is classified `Sensitive`), and retention. The surface opens no side-channel store or notification path; events that touch learner data never carry raw material (`ledger.sensitivity-aware-persistence-retention`, File 10 §10).

### 22.3 Learner Data, Egress, and Settings

Learner data — mastery, mistakes, progress, persona — is `Sensitive` by default (`block.sensitivity`, File 08 §9, `secret.backend-boundary` File 22 §4) and held as `Mastery` and core memory through the Memory substrate under its privacy and user-control rules (`memory.privacy-sensitivity-user-control`, File 14 §18); only redaction-safe summaries enter the model context, an event, a log, or syncable projections permitted by Memory and portability policy, and raw learner data never enters an export, a share, or a sync stream without explicit opt-in. Learner mastery and persona sync eligibility is resolved by File 14 and File 21, not by Teacher settings alone. Any credential a borrowed source needs (a knowledge-base connector, a web source) is vault-held and resolved at point of use (`security.credentials`, File 22 §6), and any outbound fetch checks its destination against egress policy (`security.egress-governance`, File 22 §11). The Teacher surface's behavior is configurable through the one settings system (`core.settings-system`, File 01 §6.8, File 15) as namespaced keys under `surface.teacher.*`, resolved through the standard cascade and composed with the per-substrate settings the owning files own (the sandbox settings via the borrowed coder profile of Files 23/27, the workspace and instruction-file settings of File 24, the context and compaction settings of File 13, the model and vision-route settings of File 16, the policy settings of File 06, the retrieval and knowledge settings of File 12, the memory and SRS-validity settings of File 14, the egress and credential settings of File 22, the perception sensor settings of File 19, the voice and text-to-speech settings of File 26/File 19, the trigger and automation settings of File 26 and File 33). Representative teaching settings dimensions: the default explanation mode and depth; the adaptive-difficulty strategy and baseline; the spaced-repetition algorithm and intervals; the knowledge-base-first grounding preference; the per-profile customization seeds and default view preset; the accessibility and read-aloud defaults; the learner-persona defaults; the export formats and egress policy; the classroom default director strategy and roles; and the bulk-generation batched-approval defaults. The surface is not a durable settings scope (`settings.scopes-profile-contexts-overlays`, File 15 §5.1); per-surface variation is namespaced keys plus profile layers. Settings whose values are sensitive (learner-data export and egress policy, credential bindings) declare conservative agent exposure (`policy.agent-exposure-policy-settings`, File 06 §16.4); no teaching behavior with meaningful variation is a hardcoded constant (`settings.settings-over-constants`, File 15 §13).

### 22.4 Boundary

This section names the teaching capability, event, learner-data, egress, and settings surface. File 05 owns the capability contract; File 06 owns policy; File 10 owns the event bus and custom-kind registration; File 14 owns the learner-state memory and its privacy; File 22 owns the sensitivity, credential, and egress boundaries; File 15 owns the settings model and cascade; the owning substrate files own the per-substrate settings the surface composes with.

## 23. Explicit Rejections

Anchor: `teacher.explicit-rejections`

The following are architecturally invalid for the Teacher surface and for any later spec that extends it:

- **An educational result stored only as transcript prose, or a lesson dropped on disk without an artifact** — a lesson, curriculum, assessment, study set, or rubric is a durable, versioned, evidence-bearing `Lesson`/`Curriculum`/`Quiz`/`ExerciseSet`/`FlashcardSet`/`Rubric` `Artifact` revision; storing artifact-grade educational content only as an assistant message is message inflation (`artifact.consequences-for-later-specs`, File 09 §22) and is rejected (§6.2).
- **A `LessonBlock` block kind, or a parallel artifact store for teaching** — a lesson is an `Artifact`-kind composed block whose parts are existing block kinds plus registered `Custom` kinds; there is no `LessonBlock` (§6.3; `block.explicit-rejections`, File 08 §15, `artifact.explicit-rejections` (File 09 §21)).
- **Parallel `teacher_curricula`, `teacher_lessons`, `teacher_progress`, `teacher_classrooms`, `teacher_classroom_turns`, `teacher_flashcards`, `teacher_srs_schedule`, or `teacher_exports` tables** — curricula and lessons are artifacts, progress and mastery are `Mastery` memory plus assessment blocks plus a rebuildable projection, a classroom is a coordinator-plus-child-run structure plus a `Classroom` world entity plus a version-tree projection of turn blocks, flashcards are a `FlashcardSet` artifact with SRS state in `Mastery` memory, and an export is a transient run (§6, §10, §11, §12, §18; `version.explicit-rejections`, File 11 §23). If a feature seems to need a new durable teaching table, it is reframed as a block, artifact, memory, observation, edge, or projection under the canonical registries.
- **A `LearnerContext.user_id` field or a `user_id`-keyed learner record** — Atlas is single-user; the learner persona is a core-memory block and progress is a projection, and multi-learner support is a memory scope introduced only by a future multi-profile spec, never a parallel user table (§12.4; `memory.kinds-scopes-facets`, File 14 §4.2).
- **A private classroom orchestration engine, director runtime, or turn store** — a classroom is a coordinator-plus-child-run structure over the one execution model, the director is the coordinator's speaker-selection, the interleaved actions are capability invocations, peer-context is child-run context-sharing, and the two-stage outline is the `plan` capability (§11; `run.consequences-for-later-specs`, File 04 §29, `worksurface.no-private-architecture` (File 25 §12)).
- **A private spaced-repetition scheduler worker as a correctness mechanism, or a time-based review-due timer** — SRS state is `Mastery` memory validity, the review-due trigger is event-first with fallback checks only where no event signal exists, and the only permitted timer is a finite, configurable, killable wall-clock guard on a long-running operation (§10.3, §17.4; `memory.validity-retention-short-term-memory`, File 14 §7, `world.explicit-rejections` (File 18 §16)).
- **A private adaptive-difficulty engine or item-statistics table, or a hardcoded algorithm or numbers** — adaptive difficulty is capability-internal item selection over `Mastery` memory and the assessment-block history, the item bank is artifact question-variants, item statistics are a rebuildable projection, and the difficulty model, the spaced-repetition algorithm, the baselines, and the intervals are a capability strategy and settings, never canonical constants (§9.4, §10.3; `settings.settings-over-constants`, File 15 §13).
- **A private knowledge, index, or concept-graph store** — teaching extraction commits concepts and prerequisites into the shared entity-relationship projection, and course materials are `KnowledgeEntry` and source records in the shared substrate; the surface owns the teaching intent, not a parallel retrieval or graph store (§8, §13; `retrieval.explicit-rejections`, File 12 §21).
- **Ungrounded educational content presented as fact** — a lesson, paper walkthrough, or knowledge-base-grounded explanation that makes a load-bearing factual claim grounds it to a `SourceSpan` `Citation`, and an ungroundable claim is flagged or excluded, not asserted; URL or reference fields ground to captured anchors (§6.4, §8.3; `artifact.citation`, File 09 §12).
- **Silent general-knowledge fallback in a source-bound run** — when the run contract is "from this document", "only this chapter", or equivalent, uncovered concepts produce a provenance gap, clarification request, or visibly labeled outside-background segment accepted by the user or policy. General model knowledge may support general teaching, but it may not silently become source-grounded course material (§13.2).
- **Authority granted by ingested study material** — an instruction inside a study document, a fetched reference, or a familiar-named instruction file in course material holds no capability or policy authority; all ingested and fetched content is `untrusted_source_data` (§8.6; `security.untrusted-content`, File 22 §12).
- **A private model-request assembly path or private model-selection logic** — every teaching model request assembles through the one `ContextAssemblyService` with ingested material marked untrusted, and the surface declares a default `ModelProfile` (including the vision route) without implementing selection (§15.2, §15.3; `context.consequences-for-later-specs`, File 13 §22, `model.consequences-for-later-specs` (File 16 §16)).
- **A private sandbox or code-execution path for graded or practice code** — graded code, practice code, and runnable examples run through the borrowed coder code-execution capability under its `SandboxProfile`; the surface opens no private sandbox and redefines no enforcement or kill semantics (§15.4; `sandbox.explicit-rejections`, File 23 §20).
- **Implicit execution of code from course material** — code snippets in ingested or fetched study material remain untrusted data until a visible code-execution capability invocation proposes execution through policy and the borrowed Coder sandbox (§15.4).
- **A teaching autonomy, participation, interaction-shape, persona-as-autonomy, or teaching-mode field** — at any layer, in any form; teaching autonomy is capability permission tiers, leases, and approval posture plus user direction, progressive disclosure is which panels and view preset are open, the explanation modes (lecture/Socratic) and the depth levels (Quick/Standard/Deep) and the per-profile workflows are presentations and workflow parameters, and the codex "teacher as a mode and service" target is realized through borrowable capabilities and the cross-cutting affordance, not a per-surface mode field (§1.2, §7, §14, §16; `worksurface.no-autonomy-field`, File 25 §13). There is no `Drive`/`Supervise`/`Collaborate`/`Delegate` dial and no participation level.
- **A view preset that silently changes backend policy** — applying a teaching view preset (minimal, study, course, classroom, assessment, or a per-profile seed) changes presentation only and never silently changes model selection, context policy, execution entry, budget, sandbox profile, or approval posture (§16.2; `worksurface.views-presets`, File 25 §7.2).
- **Materializing or exporting raw learner data, or treating learner state as non-sensitive** — learner mastery, mistakes, progress, and persona are `Sensitive`, held in the Memory substrate, redacted in model context and events, and egress-governed on export and share (§12.2, §18, §22.3; `secret.backend-boundary`, File 22 §4).
- **Driving a browser or a desktop application directly** — the Teacher surface borrows the Web surface's browsing for web reference material and never drives a browser or a foreign desktop application itself; desktop automation is the GUI Control surface's (§2.13, §5.2).
- **Naming a specific adaptive-difficulty model, spaced-repetition algorithm, document parser, optical-character-recognition engine, text-to-speech engine, charting or diagram renderer, classroom runtime, or interactive-artifact runtime as the canonical semantics** — these are replaceable implementations behind the surface's capabilities and panels; the canonical contract is the behavior, never the library or the algorithm (Source Resolution; `core.local-extensibility`, File 01 §7.10).
- **Generic educational correctness judges as canonical defaults** — teaching validators must be tied to a `Rubric`, a source-grounding contract, an accessibility target, an assessment policy, or another named validation target. Broad "correctness" or "hallucination" judges may be user/plugin-defined validators, but they are not canonical teaching defaults without calibration and a narrow target.

## 24. Consequences for Later Specs

Anchor: `teacher.consequences-for-later-specs`

Later specs must follow these rules:

- The remaining **per-surface specs** (GUI Control, System Agent) declare their own `SurfaceContract`s to File 25's shape, the same way this file does for Teacher; they may borrow the Teacher surface's explanation, assessment, exercise-generation, and mastery-update capabilities to embed teaching in their work (§14.2) but introduce no private teaching mechanism. The Teacher surface borrows coder code-execution, data extraction and charting, and web search and fetch in place, never by silent surface change.
- The **Automation and Triggers** spec owns the deep mechanics of the review-due and scheduled-study monitors this file frames as `Trigger`-rail entries (§17.4): scheduling, eligibility, enablement, event-first change detection with flagged fallback, and non-interactive-execution safety for a teaching monitor, pinning the Teacher surface and its policies at save time the way routing does; it introduces no parallel teaching execution path.
- The **Workflows, Templates, and Reuse** spec treats reusable curricula and lesson templates (§8.2), the teaching default workflows (§17.3), and custom commands (§17.2) as reusable workflow and command definitions over `WorkflowTemplate` and `Curriculum` artifacts, and treats a successful teaching run as a promotable workflow; teaching outputs that warrant durable identity become artifact versions through the canonical mechanism.
- The **Extension and Plugin System** and **MCP and External Integrations** specs may contribute teaching capabilities, lesson-planning and spaced-repetition bundles (an `atlas-teaching`-style or `atlas-study`-style plugin with its tools, knowledge entries such as pedagogical taxonomies and rubric examples, workflows, the Mentor persona seed, and view presets), document parsers, text-to-speech engines, and external course-material and learning-vault integrations through the proposal-first registration and source-approval path; a plugin-contributed teaching capability, bundle, or connector participates in the one registry, policy layer, sandbox, egress governance, and ledger exactly as a built-in does.
- The **UI Shell, Layout, Presentation, and Interaction Models** and **UI Customization, Widgets, and Theming** specs render the teaching panels — the lesson reader, the curriculum concept map and skill tree, the classroom view with whiteboard and student panel, the assessment and practice views, the flashcard review, the sources and progress views, the activity feed, the command palette, the keybinding contexts, and the view presets — over the teaching and behavior contracts this file fixes; lessons, quizzes, and flashcards render through the shared interactive-artifact runtime, math and diagrams through the shared renderers, and the accessibility presentation (read-aloud, screen-reader, keyboard, dyslexia-friendly and visual-impairment accommodation) over the persona and accessibility settings this file declares; presentation may vary freely, the work model cannot. The adaptive-difficulty model, the spaced-repetition algorithm, the classroom runtime, and the interactive-artifact and rendering runtimes are their implementation choices behind the panels and capabilities.
- The **Quality Control and Validation** spec registers narrow teaching validators (assessment grading tied to a `Rubric` or grading policy, citation-grounding and factuality checks for grounded lessons, rubric-conformance checks, and accessibility checks) producing `Validation`/`Critique`/`Observation` blocks and integrating through the completion-verification hook surface and the event and capability hooks, not a separate pipeline; the Educator-profile factuality default is a quality-control posture, not a private gate, and generic uncalibrated correctness judges are not canonical defaults.
- The **Telemetry, Logging, and Observability** spec consumes the teaching events and the per-call attribution this file and File 10 emit, with learner-data events classified `Sensitive`; it renders the teaching run inspector from the version graph, ledger, mastery memory, and observation handles, never by re-running an explanation, re-extracting a document, or re-grading an assessment for a historical view.
- The **Evaluation and Benchmarking** spec verifies the teaching round-trips — explanation-to-lesson-artifact, document-to-grounded-curriculum, quiz-generation-and-grading-to-`Validation`/`Critique`, practice-code-to-validation, classroom-as-child-run-structure, mastery-update-to-memory, flashcard-review-to-mastery-validity, and the lossless lesson-and-curriculum export round-trip — replaying over recorded blocks, observations, and immutable references, not a live re-explanation or re-grade, and verifying that no instruction in untrusted study material escalated authority and that no ungrounded factual claim was presented as evidence-backed.
- The **Runtime Infrastructure and Lifecycle** spec orchestrates teaching surface, borrowed-sandbox, and index startup and reconstruction around the storage lifecycle File 20 owns, reaping orphaned classroom and teaching child runs at restart and rebuilding the concept-graph, progress, and item-statistics projections as projections; it reimplements no teaching execution, grading, or indexing.
- The **Packaging, Platform, and Distribution** spec ships the built-in declarations for the canonical teaching capabilities, the Teacher `SurfaceContract`, the teaching `Custom` event and entity kinds, and the default teaching settings as the `Builtin` source in every install, packages the adaptive-difficulty strategy, the spaced-repetition strategy and review-due trigger integration, the document parsers, the text-to-speech engine, the charting and diagram renderers, and the classroom and interactive-artifact runtimes behind their contracts, and makes the Teacher surface available on the mobile and other target platforms its packaging supports.
