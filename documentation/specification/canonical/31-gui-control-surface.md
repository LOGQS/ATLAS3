# GUI Control Surface

## Status

Canonical. This file defines the `GuiControl` work surface — the specialized environment for observing, interacting with, automating, and controlling the desktop and the foreign applications running on it ("computer use"). It is the fifth per-surface specification: it fills the `SurfaceContract` that `worksurface.surface-contract` (File 25 §4) delegates to each per-surface spec, and declares the desktop-control workflows, panels, capabilities, and policies the GUI Control surface contributes over the shared substrate. It owns user-facing desktop-control workflows and specialized views; it owns no private architecture. It composes blocks, capabilities, execution, the world model, perception, the version graph, workspaces, the sandbox, context, artifacts, security, providers, and every other substrate through the same contracts every surface uses. Later canonical files may refine it, but may not contradict it.

## Scope

This file defines:

- the `GuiControl` `WorkSurface` and its `SurfaceContract` (`worksurface.work-surface`, File 25 §3, `worksurface.surface-contract` (File 25 §4)): identity, declared panels and selection kinds, the `SubsystemSurfaceSpec` and contributed capabilities, view presets and inspectors, and default context, model, execution, sandbox, and workspace policies
- the **perception-grounded, adapter-first desktop-control reframe**: a desktop action is a policy-gated, observation-grounded, verified, recorded `Capability` invocation against the unowned environment — not a blind coordinate click; the surface observes the desktop **structured-first** through `Perception` (the `DesktopAccessibilityTree` sensor before grounded vision before a raw screenshot), reasons over the world model's desktop entities, and records its work as durable `Macro`/`ScreenshotSeries` `Artifact`s and `AccessibilityTreeSnapshot`/`Screenshot` `Observation`s, not as transcript prose
- the desktop-observation contract: the tiered perception of a desktop and its windows (the structured accessibility/automation representation before grounded element detection before a raw screenshot) realized through `Perception`'s `DesktopAccessibilityTree` and `Screen` sensors and `VisualGrounding`/`Ocr` processors, with element-tree fingerprints, role-category filtering, modal-scope restriction, and staleness revalidation
- the element model and addressing: how a captured desktop element is referenced for action, the staleness-fingerprint revalidation a mutation depends on, and the read-before-act discipline
- action execution and the observe-act-verify loop: the element-grounded action capabilities, the structured-first tier-selected input dispatch, coordinate-space mapping for vision-grounded actions, post-action verification, and stagnation detection
- adapter-first automation: the registered application-adapter mechanism (element-identity strategy, common actions and postconditions, state extraction, failure-recovery hints, policy defaults) with generic accessibility as the default fallback and vision as the final recovery tier
- macros, recording, and replay: the `Macro` artifact, element-based recording, parameterization, and revalidating replay
- the GUI Control safety posture: the asymmetric-blast-radius approval posture, destructive-action and sensitive-application escalation, active-window scoping, cascading-damage limits, and screenshot redaction — all over the shared policy, world-model, perception-privacy, and stuck-detection substrates
- user takeover and task control: the run-control handoff by which the user takes over and hands back a desktop task, and the needs-help elicitation handoff
- the sandbox, isolation tiers, and the operating modes: the graphical-control `SandboxProfile`s, the active-desktop / background / virtualized operating modes mapped to the canonical isolation tiers, the presentation-isolation-is-not-a-security-tier rule, and the elevated-helper boundary for privileged desktop operations
- cross-platform realization and first-run setup: the platform-invariant contract over replaceable per-platform accessibility, input, and capture mechanisms, the operating-system permission and display-server setup flows, and multi-monitor and scale-factor handling
- the GUI Control rails, cross-surface composition, the world-model and perception integration, and the GUI Control capability, event, and settings surface

Where the source material describes a GUI mechanism the canon has already settled horizontally — desktop observation and the accessibility-tree capture, screen capture and grounding, the world-entity model, the sandbox and isolation tiers, the elevated helper, process killability, the version graph, artifacts and observations, the policy layer, stuck detection, the elicitation rail — this file consumes the settled contract and adds only the GUI-specific presentation and workflow. Resolved tensions:

- **Desktop state as screenshots versus structured-first.** The earliest framing held that "GUI control will mostly work with screenshots." The most-evolved source material (`unit10-gui-control.md` D10.13, `02-perception-pipeline.md`, the planned pipeline) instead makes the structured accessibility/automation tree the primary representation (the dominant share of tasks), with element detection over a screenshot as the bridge and the raw screenshot as the fallback. This is exactly `perception.tiered-sensing` (File 19 §5)'s structured-data-first invariant and `core.world-model` (File 01 §6.7). This file resolves toward structured-first (§6): the desktop's machine-readable element tree is the `Structured` tier, grounded element detection and optical-character recognition over a screenshot is the `Grounded` tier, and the raw screenshot is the `Raw` tier — realized through `Perception`'s `DesktopAccessibilityTree` and `Screen` sensors, not a private state model. The screenshot-primary framing is superseded.
- **A private GUI sandbox abstraction versus a graphical-control `SandboxProfile`.** The source material accreted a `GuiSandbox` trait with its own capability shape (the "fourth sandbox abstraction"). `sandbox.contract` (File 23 §3) is the one execution-containment contract with per-consumer `SandboxProfile` defaults and per-surface capability extensions, and `sandbox.consequences-for-later-specs` (File 23 §21) names "a graphical-control session" and "graphical input and observation" as a per-surface extension over the base contract. This file resolves toward the canonical contract (§13): the GUI Control surface declares graphical-control `SandboxProfile`s over the one `Sandbox` contract and extends it only with its graphical-input and screen-observation capability surface; it opens no private sandbox.
- **The operating modes as a private taxonomy versus isolation tiers plus a presentation facet.** The source material defines three operating modes — active desktop, smart-background (window cloaking plus virtual-desktop placement), and full virtual machine — with a private `IsolationLevel` enum. `sandbox.isolation-tiers` (File 23 §4) is the canonical `IsolationTier` ordinal, and `sandbox.isolation-tiers` (File 23 §4.3) fixes that **window cloaking and virtual-desktop placement are a presentation facet, not a security tier**: a mode that visually separates the agent's windows but shares the registry, environment, filesystem, network, process table, clipboard, global shortcuts, application profiles, and other session-global state provides `None` security isolation with a presentation overlay. This file resolves toward the canonical mapping (§13): the active-desktop mode is the `None` tier on the user's real session, the background mode is the `None` tier with a presentation overlay, and the virtualized mode is the `Virtualized` tier; the "smart-background" presentation is owned here, the isolation tier stays File 23's.
- **A private action wire format, provider adapter, and coordinate-normalizer registry versus capability sub-modes plus the provider and perception layers.** The source material proposes a canonical action wire format, per-provider action adapters, a coordinate-normalizer registry, and a provider-loop registry. `capability.capability` (File 05 §2.3) already fixes that a capability handles input variants internally as sub-modes; the vision/grounding model is selected through `model.model-selection-algorithm` (File 16 §7) and executed through the provider layer (File 17); and `perception.capture-pipeline` (File 19 §6.5) fixes that perception records the coordinate space and produces observation coordinates in a declared space while "mapping a model-produced coordinate back to a screen action is the per-surface action executor's concern." This file resolves toward those contracts (§8): the action format is a capability-declaration and implementation concern kept out of the body; the per-provider coordinate translation is the surface's action-executor mapping over `Perception`'s recorded coordinate space and scale factors; the provider-specific adapters and the grounding-model lifecycle are replaceable implementations behind the action and grounding capabilities. The application-level adapter-first concern (§9) is a distinct, separately-resolved matter.
- **Generic-only automation versus adapter-first automation.** `codex_recommendations.md` §8.4 evaluates pure generic accessibility, pure vision, and adapter-first automation, and resolves: "the strongest system uses app adapters whenever known, accessibility trees as default generic access, and vision as fallback or fusion," introducing an application-adapter registry whose adapters carry an element-identity strategy, common actions and postconditions, state extraction, failure-recovery hints, and policy defaults, with generic accessibility/automation as the fallback and vision as the final recovery tier. This file adopts the adapter-first reframe (§9): an application adapter is a registered extension over the generic perception-and-action substrate, preferred when a known adapter matches the foreground application, with generic accessibility (the structured tier) as the default and vision (the grounded and raw tiers) as the final recovery tier. Adapters ride the capability registry and the proposal-first registration path; they are not a private registry.
- **A private GUI task store and watchdog subsystem versus run control, intervention, stuck detection, and the elicitation rail.** The source material proposes a private task table with an ownership-control field, a per-action rate-limiter watchdog, and a catalog of reactive monitors. `run.minimum-durable-reconstruction` (File 04 §2.6) carries the run `control` field, `run.user-intervention` (File 04 §17.1) and `run.pause-resume` (File 04 §17.2) own takeover and resume, `run.stuck-detection` (File 04 §20.3) and `perception.output-contract` (File 19 §9.6) own loop and stagnation detection, `sandbox.resource-limits` (File 23 §9) owns event-driven resource thresholds, and `controlrail.elicitation` (File 26 §13) owns the elicitation handoff. This file resolves toward those owners (§11, §12): user takeover is run control plus intervention, cascading-damage protection is stuck detection plus a configurable state-driven risk budget, and the needs-help condition is an elicitation handoff; the surface owns no private task store, watchdog subsystem, or monitoring store.
- **An autonomy/participation dial versus permission tiers.** Some GUI overviews carried a `Drive`/`Supervise`/`Collaborate`/`Delegate` participation level (default `Collaborate`) gating approval and error escalation. `worksurface.no-autonomy-field` (File 25 §13), `policy.chosen-model` (File 06 §1), and `world.surface-state` (File 18 §5.5) delete the autonomy field at every layer. This file carries no autonomy field (§22): GUI Control autonomy is capability permission tiers, leases, and approval posture plus the user's direction; progressive disclosure is which panels and view preset are open.
- **Windows-primary versus cross-platform-first-class.** Version-1.0 source material framed Windows as primary with macOS and Linux "future." `unit10-gui-control.md` D10.3 corrects this to all three desktop platforms first-class. This file resolves toward cross-platform-first-class (§14): the contract is platform-invariant over replaceable per-platform accessibility, input, and capture mechanisms (`sandbox.cross-platform`, File 23 §15), and a capability whose platform mechanism is absent reports unavailable rather than failing the surface. The Windows-primary framing is the retired pattern.

## 1. Chosen Model

Anchor: `gui.chosen-model`

ATLAS3 has one `GuiControl` `WorkSurface`. It is the specialized environment for observing and controlling the desktop and the foreign applications running on it — looking at the screen and the operating system's accessibility/automation tree, finding and inspecting interactive elements, clicking, typing, scrolling, dragging, launching and switching applications, managing windows, and recording and replaying action sequences — and it is one instance of the `WorkSurface` primitive `worksurface.work-surface` (File 25 §3) defines, classified `GuiControl` by `core.current-major-area-classification` (File 01 §5.6).

The GUI Control surface owns user-facing desktop-control workflows and specialized views; it owns no private architecture (`worksurface.no-private-architecture`, File 25 §12). It is declared by one `SurfaceContract` (§3) registered in the `SurfaceRegistry` (`worksurface.registry`, File 25 §10), and it composes the shared substrate — blocks, capabilities, capability policy, tool surfaces, execution, the world model, perception, the version graph, workspaces, context assembly, retrieval, memory, routing, artifacts, storage, sync, security, the sandbox, providers, and the ledger — through each one's canonical contract.

The load-bearing model of the GUI Control surface is the **perception-grounded, adapter-first desktop-control reframe**. The GUI Control surface is the desktop sibling of the Web surface (`web.chosen-model`, File 28 §1): where the Web surface drives a browser, the GUI Control surface drives the whole desktop, and both sense and act on an unowned, opaque, externally-mutable environment through `Perception`. Four consequences follow:

- **The desktop is observed structured-first, not screenshot-first.** A desktop window's interactable state is read through `Perception`'s `DesktopAccessibilityTree` sensor (`perception.sensor`, File 19 §4.3) as an `AccessibilityTreeSnapshot` `Observation` (`artifact.observation`, File 09 §13.2) — the structured `Structured` tier — before grounded element detection over a `Screenshot` (the `Grounded` tier) and before the raw screenshot itself (the `Raw` tier), per the `SensingTier` strategy (`perception.tiered-sensing`, File 19 §5). The surface owns no private state model and is never screen-scraped to learn its own panels' state (`world.observation-state-update`, File 18 §8.1).
- **A desktop action is a policy-gated, observation-grounded, verified, recorded capability invocation, not a blind coordinate click.** An action resolves a target element against the captured structured state, revalidates currency before dispatch (`run.call-pipeline`, File 04 §8.2), passes through the one policy layer with the surface's contributed approval posture (File 06), dispatches through the confined input mechanism, and verifies its effect against a post-action capture. A blind coordinate click is the fallback of last resort, not the model.
- **Reliability is adapter-first with a generic fallback.** When a registered application adapter matches the foreground application, the surface prefers its element-identity strategy, common actions, postconditions, and recovery hints (§9, `codex_recommendations.md` §8.4); generic accessibility (the structured tier) is the default access; vision (the grounded and raw tiers) is the final recovery tier.
- **Gathered desktop state and recorded work are durable, not transcript prose.** A captured element tree is an `AccessibilityTreeSnapshot` `Observation` with a `StalenessFingerprint`; a captured screen is a `Screenshot` `Observation`; a recorded action sequence is a `Macro` `Artifact`; a captured action sequence's screens are a `ScreenshotSeries` `Artifact` (`artifact.artifact-kind`, File 09 §4, `artifact.consequences-for-later-specs` (File 09 §22)). Desktop history and task history are projections over the one version graph and the one block pool; the surface introduces no parallel state, task, macro, or capture store.

`GuiControl` is the canonical surface name; the `surface_id` is `gui_control` and equals the subsystem id (`capability.capability-source`, File 05 §9.1, `worksurface.work-surface` (File 25 §3.3)). Earlier vocabulary that named the same surface — "GUI control domain", "computer use", "desktop control", "Mode 3", the participation levels — is source vocabulary only and does not survive as canonical terminology or as a parallel primitive. The anchor namespace for this file is `gui.*`, deliberately distinct from File 07's `surface.*` (tool surfaces), File 25's `worksurface.*`, File 26's `controlrail.*`, File 27's `coder.*`, File 28's `web.*`, File 29's `data.*`, and File 30's `teacher.*`. The capability family `gui.*` consists of capability ids in the one registry, not anchors.

### 2.3 With File 23 (Sandbox, Process Control, and Isolation)

The GUI Control surface runs all confined execution through the one `Sandbox` contract (`sandbox.consequences-for-later-specs`, File 23 §21). It declares graphical-control `SandboxProfile`s (`sandbox.contract`, File 23 §3) and extends the base contract only with its graphical-input and screen-observation capability surface; it redefines no lifecycle, filesystem/network/resource enforcement, or kill semantics. The operating modes map to the `IsolationTier` ordinal (`sandbox.isolation-tiers`, File 23 §4): the active-desktop mode is `None` on the user's real session, the background mode is `None` with a presentation overlay, and the virtualized mode is `Virtualized`; window cloaking and virtual-desktop placement are a presentation facet, not a security tier (`sandbox.isolation-tiers`, File 23 §4.3). A foreign application the surface launches is a `ManagedProcess` in a `ProcessGroup` (`process.spawning`, File 23 §5, `process.groups` (File 23 §6)), killable categorically and individually (`process.killability`, File 23 §10). Privileged desktop operations cross the elevated-helper boundary (`sandbox.elevated-helper`, File 23 §11); the main process never elevates.

### 2.4 With Files 08, 09, and 11 (Blocks, Artifacts, Version Graph)

Desktop observations and outputs flow as `Block`s through the one pool (`block.cross-surface-interoperability`, File 08 §12). A captured element tree is an `AccessibilityTreeSnapshot` `Observation`, a captured screen is a `Screenshot` `Observation`, each with a `StalenessFingerprint` (`artifact.observation`, File 09 §13); a recorded action sequence is a `Macro` `Artifact` and a captured screen sequence is a `ScreenshotSeries` `Artifact` (`artifact.artifact-kind`, File 09 §4) with materialization, validation, and provenance (`artifact.provenance`, File 09 §15). Task history and action-replay views are projections over the one version graph (`version.consequences-for-later-specs`, File 11 §24); the surface introduces no parallel task, macro, capture, or history store (`version.explicit-rejections`, File 11 §23).

### 2.5 With File 13 (Context Assembly) and File 16/17 (Model Strategy, Provider Layer)

It assembles every model request through the one `ContextAssemblyService` (`context.chosen-model`, File 13 §1): the captured structured desktop state is a `RuntimeState` part, captured foreign-application content is `untrusted_source_data` (`context.authority-classes`, File 13 §2.3), a screenshot enters as a multimodal part only when a vision consumer requires it (§6), and trajectory-image retention under budget is File 13's (`context.virtual-paging`, File 13 §13, `perception.cost-fidelity` (File 19 §11.3)). ### 2.6 With Files 05, 06, 07 (Capabilities, Policy, Tool Surfaces)

## 6. Desktop Observation and the Tiered Perception Contract

Anchor: `gui.desktop-observation`

### 6.1 Definition

Desktop observation is the GUI Control surface's structured model of the desktop and a target window, the input to every action and extraction. The GUI Control surface is structured-data-first: it reads a window through `Perception`'s `DesktopAccessibilityTree` sensor (`perception.sensor`, File 19 §4.3) and the `SensingTier` strategy (`perception.tiered-sensing`, File 19 §5), and never through a screenshot when a structured representation is available and sufficient (`core.world-model`, File 01 §6.7). The surface owns no private desktop-state model; it consumes the sensors' structured output and projects it into the `DesktopWindow`/`DesktopApplication` world entities and the `screen` and `element_tree` panels.

### 6.2 The Tiered Desktop Representation

A desktop window is sensed at one or more tiers, mapped onto the canonical `SensingTier` order (`perception.tiered-sensing`, File 19 §5.1):

- **`Structured`** (the default and primary representation): the operating system's accessibility/automation tree for the window — element role, name, bounds, state, available interaction patterns, keyboard-focusability, and the structural hierarchy — captured through the `DesktopAccessibilityTree` sensor's batched property retrieval (`perception.per-modality-contracts`, File 19 §7.2). This is the primary input to the model: it is precise, semantically rich, far cheaper in tokens than a screenshot, deterministic, and gives each interactable element a stable reference the surface resolves to the actual element without coordinate ambiguity, and it works on windows that are not in the foreground.
- **`Grounded`** (when the structured tier is absent or insufficient): element detection and optical-character recognition over a screenshot, for a canvas-rendered application, an accessibility-poor application, or a custom control the accessibility tree does not expose. The grounded tier is a `Perception` processor (`VisualGrounding`/`Ocr`, File 19 §4.5, §7.4) over a `Screenshot` capture, keyed by the processor invocation (`perception.output-contract`, File 19 §9.4), and merges with the structured tier where their regions correspond (`perception.tiered-sensing`, File 19 §5.3). Structured state wins by default for semantic and actionability attributes — role, name, state, interaction affordance; the grounded tier adds elements the structured tier missed; disagreements are typed conflict facts, never silently resolved.
- **`Raw`** (when the capture need requires pixels): the screenshot itself, for a vision model, for visual evidence, for coordinate grounding of a vision-based action, or for the screen-view presentation. The screenshot is a `Screenshot` `Observation` captured only when needed.

The surface must not skip an available cheaper tier when that tier satisfies the need (`perception.tiered-sensing`, File 19 §5.2): the structured tree is read first, grounded detection is added when the structured tier is insufficient, and a screenshot is captured only for a vision consumer, visual evidence, or coordinate grounding.

### 6.3 Embedded Web Content and Modal Scope

Where a target window hosts embedded web content, the structured capture separates that content and hands it to the `BrowserPage` sensor where one is available (`perception.per-modality-contracts`, File 19 §7.2, §7.3), so a browser window's page is read as web content, not as opaque desktop pixels; driving the page itself is the Web surface's, reached by reroute or borrow (§18). If no `BrowserPage` sensor or Web capability is available for a page-like region, GUI Control may interact with it only as opaque desktop content — accessibility elements, screenshots, coordinates, and captured text with `untrusted_source_data` authority — and must not claim DOM, cookie, network, browser-history, page-execution, or browser-session semantics. When a modal element is present in the window, the structured capture restricts the interactable set to the modal's subtree, so the model does not attempt to act on elements a modal has disabled (`perception.per-modality-contracts`, File 19 §7.2). Known safe informational modals may be handled under ordinary policy; unknown, destructive, permission, payment, login, captcha, or security-sensitive modals trigger confirmation or elicitation handoff rather than heuristic dismissal.

### 6.4 Role-Category Filtering and the Model-Facing Projection

The GUI Control surface owns the desktop-extraction semantics over the captured tree: it classifies elements into interactive, content, and structural roles and, by default, projects only the interactable and content roles into the model-facing representation, with the structural scaffolding available on explicit request. The compact projection still preserves the structural context needed for correct targeting: relevant parent labels, group or menu ancestry, modal scope, table/header associations, and nearby label/value relationships. Each projection may assign observation-local ordinal labels to visible candidates; an annotated screenshot rendered from the same capture uses the same ordinals, but the ordinal is only an alias within that capture and never durable identity. Atlas-owned windows and elements are excluded from the GUI model-facing target set; Atlas UI state enters through self-registration and substrate projections, not by treating Atlas as a foreign desktop application. This is the surface's extraction over the shared sensor (`retrieval.ingestion`, File 12 §14.2 delegates extraction semantics to the owning surface); the sensor owns the capture, the surface owns the role classification and the compact, token-efficient model-facing projection. The model-facing representation carries identifiers, roles, names, bounds, and state summaries, not the full property set or the raw pixels, and large captures are referenced rather than flooded into context (`context.current-input-oversize-handling`, File 13 §7).

### 6.5 Observations, Fingerprints, and Freshness

A deliberately captured desktop state is an `Observation` block: the structured tree is an `AccessibilityTreeSnapshot` observation and a captured screen is a `Screenshot` observation (`artifact.observation`, File 09 §13.2), each carrying a `StalenessFingerprint` (`perception.output-contract`, File 19 §9.3). The captured structured state is cached per window and invalidated event-first on an operating-system UI event — a window create or destroy, a foreground change, a structure or property change (`perception.triggers`, File 19 §8.1) — so repeated reads of an unchanged window hit the cache; the cache is a rebuildable projection, never a durable fact (`core.projection`, File 01 §6.11). A captured-state staleness bound is a flagged, configurable fallback only where a source emits no change event, never a correctness condition (`perception.triggers`, File 19 §8.2). Desktop memory — what the surface knows of a window across captures — is the version-graph and observation history, not a private store.

### 6.6 Boundary

This section owns the desktop-observation workflow and the role-category extraction. File 19 owns the sensors, the tier strategy, the capture pipeline, the modal-scope and embedded-web-content rules, the coordinate-space recording, the staleness fingerprint, and the stagnation signal; File 09 owns the observation kinds; File 18 owns the desktop entities the observation projects into. The accessibility/automation engine, the grounding model, and the optical-character-recognition engine are replaceable implementations behind the sensor and processors.

## 7. Element Model, Addressing, and Staleness

Anchor: `gui.element-model`

### 7.1 Definition

The element model is how the GUI Control surface references a captured desktop element for action and revalidates its currency before acting. The surface addresses an element by its reference within a capture, never by re-deriving it from pixels at action time when a structured reference exists.

### 7.2 Element Addressing

A captured element carries a stable reference within its snapshot, scoped to the capturing window so references are unambiguous across windows. An action targets an element by, in preference order: its structured element reference within the current capture (the primary path, resolving to the actual element through the accessibility/automation interface without coordinate ambiguity), its accessibility/automation identity attributes where the structured reference is stale but the element is re-findable, a screen coordinate within the element's captured bounds (a fallback), or a vision-grounded coordinate produced by the grounded tier (the final fallback). A reference is valid only within its capture; a fresh capture produces fresh references, and an action on a reference from a superseded capture revalidates before dispatch (§7.3).

### 7.3 Read-before-Act and Staleness

A desktop action that depends on a prior capture revalidates currency before dispatching (`run.call-pipeline`, File 04 §8.2, `perception.output-contract` (File 19 §9.3)): the prior capture records the window's element-tree staleness fingerprint, the action carries the expected fingerprint and target reference, and a mismatch — the window's structure changed, the foreground switched, the element moved or disappeared — returns a typed `StateChangedSinceObservation` error rather than dispatching against a stale or wrong element. The agent receives the typed error in-band and may re-capture and retry, re-resolve the element by its identity attributes, fall to the grounded or raw tier, or stop. This is the desktop realization of the canonical stale-state revalidation; the surface enforces no separate mechanism.

### 7.4 Element Inspection

The element inspector (the `element_tree` panel and the inspect-element capability, §4.2) is a projection over the captured `AccessibilityTreeSnapshot`: it presents an element's role, name, identity attributes, bounds, state, available interaction patterns, parent and children, and grounding caption and confidence where the grounded tier contributed them. It is a read-only inspector projection over the observation, not a private element store, and a comparison view between two captures is a diff over two observations, not a separate record.

### 7.5 Boundary

This section owns the element addressing and the read-before-act discipline. File 19 owns the capture and the staleness-fingerprint computation; File 09 owns the observation the reference is scoped to; File 04 owns the stale-state revalidation pipeline. The element-resolution mechanism is a replaceable implementation behind the action capabilities.

## 8. Action Execution and the Observe-Act-Verify Loop

Anchor: `gui.action-execution`

### 8.1 Definition

Action execution is how the GUI Control surface changes the desktop: an action resolves a target against the captured structured state, passes through policy with the surface's approval posture, dispatches through the confined input mechanism at the cheapest reliable tier, and verifies its effect. The surface owns no private input mechanism, sandbox, or kill path (`sandbox.consequences-for-later-specs`, File 23 §21).

Atlas-owned windows and elements are not valid GUI Control targets. The world model knows Atlas-owned windows through self-registration and process identity (`world.observation-state-update`, File 18 §8.1); if an action resolves to Atlas's own UI, the action is rejected before dispatch with typed `SelfInteractionBlocked`. Atlas settings, approvals, conversations, and data are managed through Atlas capabilities, settings APIs, and control rails, never by puppeting Atlas's own UI.

### 8.2 The Structured-First Input Dispatch

A desktop action dispatches through the confined graphical-input mechanism at the cheapest tier that reliably performs it, mirroring the structured-first observation: a programmatic invocation through the accessibility/automation interface's interaction patterns where the element exposes one (the precise, focus-free, primary path for the dominant share of actions), a targeted platform event where the element does not expose a pattern but accepts one, and a synthetic hardware-level input event as the last resort where neither is available. The resolved dispatch records whether it is `disruptive_input`: real cursor movement, global keyboard input, foreground focus capture, clipboard mutation, or another user-visible shared-session effect. Disruptive input is surfaced in approval and escalates by default in active-desktop mode, and in background mode when the shared-session effect can affect the user's foreground or global state. If text entry uses the clipboard as an implementation fallback, the resolved dispatch records that fact; secret or credential values are not placed on the system clipboard unless typed policy explicitly permits that call, and any permitted clipboard use restores prior clipboard state where the platform supports it and records residual risk. The selected dispatch tier and disruption facts are recorded on the action for replay and audit; the concrete per-platform mechanisms are replaceable implementations behind the action capabilities (§14). The dispatch runs confined under the graphical-control `SandboxProfile` (§13), and the mechanism that injects input is File 23's, not a private path.

### 8.3 Coordinate Mapping and Vision-Grounded Actions

When an action targets a coordinate produced by a vision model — a click resolved by the grounded tier, or a user's visual description — the surface maps that coordinate from the model's recorded coordinate space to screen pixels through the declared per-display scale factors before dispatch (`perception.capture-pipeline`, File 19 §6.5). The model's coordinate output is keyed by the producing model identity (`perception.output-contract`, File 19 §9.4) and the screenshot it was produced over records its coordinate space and scale factors; the surface's action executor performs the mapping File 19 §6.5 assigns to it. A coordinate produced in an unrecorded or unresolvable coordinate space is a typed error, never a blind dispatch — the reliability failure most often cited in computer-use agents is a silent coordinate-space mismatch, and the surface forbids it. The per-provider coordinate spaces and the grounding-model output formats are replaceable implementations behind the action and grounding capabilities, not canonical body content.

### 8.4 The High-Level Act/Observe/Extract Layer

Above the low-level interaction capabilities, the GUI Control surface contributes three high-level capabilities that encapsulate the structured-capture → model → execute pattern, mirroring the Web surface's layer (`web.browser-sessions`, File 28 §7.4):

- **act** — a natural-language instruction ("click the Save button") resolved against the captured structured state (§6): the surface captures the structured state, the model selects the target element and intended effect, the surface executes the appropriate low-level action, and a post-action structured capture diff confirms the effect (§8.5). If the window changed or the expected effect did not occur, the operation returns a typed mismatch or no-effect outcome or re-enters the loop for re-observation.
- **observe** — find candidate actions for an instruction without executing, for previews, planned-action batches, and confirmation
- **extract** — schema-driven structured extraction from the captured structured state into a typed result, validated against the requested schema; extracted content is durable (a file `Artifact` or a block), and extracted values that the schema asks to be grounded reference the captured element or region they came from

The three primitives are the agent's preferred surface; the low-level interaction capabilities remain available as escape hatches. The model used for act, observe, and extract is selected through the Model Strategy layer (`model.model-selection-algorithm`, File 16 §7), defaulting to the conversation's model with the vision route where grounded sensing is needed; the surface invokes no model directly (§5.5).

### 8.5 Post-Action Verification and Stagnation

A state-changing action verifies its effect against a post-action capture: the surface diffs the post-action structured state against the pre-action state and against the expected outcome, and surfaces a typed mismatch when the action had no observed effect or the wrong effect. Repeated identical actions with no observed effect are a loop, detected by `run.stuck-detection` (File 04 §20.3) over the action history and the stagnation signal `perception.output-contract` (File 19 §9.6) emits over consecutive identical captures; a detected loop injects an in-band corrective signal to the model and escalates to a hard stop after repeated detection, never silently. The verify and wait capabilities are explicit conditions (an element appears, a window opens, the application reaches an idle state) driven by operating-system UI events, never fixed delays — a fixed post-action sleep is rejected as racy (§22), and a bounded, killable script-predicate or idle wait is a safety guard around a condition, never a hidden polling correctness rule (`perception.triggers`, File 19 §8).

### 8.6 Boundary

This section owns the action-execution and observe-act-verify workflow. File 23 owns the `Sandbox`, the input-injection confinement, and killability; File 19 owns the captures, the coordinate-space recording, and the stagnation signal; File 04 owns the run, the stuck detection, and the call pipeline; File 16 owns the model selection. The input-injection mechanism and the per-platform dispatch tiers are replaceable implementations behind the action capabilities.

## 9. Adapter-First Automation and the Application-Adapter Registry

Anchor: `gui.adapter-first`

### 9.1 Definition

Adapter-first automation is the GUI Control surface's reliability model: when a registered application adapter matches the foreground application, the surface prefers its application-specific knowledge; generic accessibility (the structured tier) is the default access for any application; and vision (the grounded and raw tiers) is the final recovery tier. This realizes `codex_recommendations.md` §8.4's resolution that "the strongest system uses app adapters whenever known, accessibility trees as default generic access, and vision as fallback or fusion."

### 9.2 The Application Adapter

An application adapter is a registered declaration of application-specific automation knowledge for one application or family of applications, carrying: an element-identity strategy (how to find a known element reliably across versions of the application), common actions and their postconditions (the expected verifiable state after each), state extraction (how to read the application's salient state structurally), failure-recovery hints (what to do when an expected element is missing or an action has no effect), and policy defaults (the approval posture for the application's known destructive or sensitive operations). An adapter is preferred when its `availability_predicate` matches the foreground `DesktopApplication` (§5.5); when no adapter matches, the surface uses generic accessibility; when generic accessibility is insufficient, it falls to the grounded and raw vision tiers.

### 9.3 Adapters Ride the Registry, Not a Private Store

An application adapter is a registered extension over the generic perception-and-action substrate, not a private registry or a parallel automation engine. Adapters register through the proposal-first mechanism (`capability.runtime-mutation`, File 05 §16.2) as `Subsystem`- or plugin-sourced contributions, gated by source approval (`policy.source-approval-flow`, File 06 §9) and trust establishment (`security.trust-model`, File 22 §9); a community-trust adapter's contributed policy defaults are narrowing-only and never lift a floor (`policy.effective-tier-resolution`, File 06 §4.2). An adapter contributes its actions as capabilities or adapter capabilities over the generic action capabilities (`capability.adapter-capabilities`, File 05 §17.4), so an adapter action runs through the same observation, policy, dispatch, verification, and ledger path as a generic action, with the ledger recording both the adapter and the resolved generic action. The surface introduces no private adapter store, registry, or execution path; an adapter is a registered contribution to the one capability registry.

### 9.4 Boundary

This section owns the adapter-first reliability model and the adapter contract. File 05 owns the capability and adapter-capability declarations and the registration; File 06 owns source approval and the policy resolution; File 22 owns adapter trust; File 18 owns the foreground-application fact the adapter matches against. The application-specific automation knowledge an adapter carries is the adapter's; this file fixes that an adapter is a registered extension, not a private engine, and that generic accessibility is the default and vision the final recovery tier.

## 10. Macros, Recording, and Replay

Anchor: `gui.macros`

### 10.1 Definition

A macro is a recorded desktop action sequence the user may parameterize and replay. A macro is a `Macro` `Artifact` (`artifact.artifact-kind`, File 09 §4) over the shared substrate; the surface owns no parallel macro store. Macro recording and replay are the desktop analog of the Web surface's macros (`web.artifacts`, File 28 §11.4), and the `Macro` artifact kind is shared across the GUI Control and Web surfaces (`artifact.consequences-for-later-specs`, File 09 §22).

### 10.2 Element-Based Recording

A recorded macro carries capability-level steps with element-based selectors, parameter slots, secret references, and required application and window preconditions; it is not blind coordinate replay. A recorded step prefers a stable element identity (the accessibility/automation identity attributes and role) over a screen coordinate, so the macro survives a resolution, scale-factor, or window-position change; a coordinate-only step is a fallback step that requires stronger revalidation on replay. The recording captures the semantic action and its target, not the raw input events. A recorded sequence's captured screens may be retained as a `ScreenshotSeries` `Artifact` for review.

### 10.3 Revalidating Replay

Macro playback is fresh execution over a saved `Macro` artifact, not historical ledger replay. Playback invokes the macro's steps through the same desktop-control capabilities, policy, and ledger recording as any current action, with parameter substitution and sensitive values masked (§11). Playback revalidates the application and window precondition and the target element's identity before each dependent step, resolving the element by its identity attributes with a graduated fallback to the grounded and raw tiers, and pauses or fails typed when a precondition does not hold. Historical ledger replay reconstructs a prior macro execution for audit and debugging and must not dispatch live GUI input (`ledger.replay-semantics`, File 10 §11). The surface introduces no separate session-recording store, and the macro covers the reuse case a full deterministic event recording would otherwise require. Promoting a successful desktop sequence to a reusable macro or workflow is the Workflows-and-Reuse path (`run.automation-reuse`, File 04 §26).

### 10.4 Boundary

This section owns the macro recording and playback workflow. File 09 owns the `Macro` and `ScreenshotSeries` artifact kinds, materialization, validation, and provenance; File 19 owns the captures the recording is built from; File 10 owns the ledger that records playback and reconstructs historical executions without side effects; File 04 owns the workflow-promotion path. The macro format is a capability-declaration concern; this file owns the workflow.

## 11. Safety, Approval Posture, and Cascading-Damage Limits

Anchor: `gui.safety`

### 11.1 Definition

The GUI Control surface has **asymmetric blast radius**: a single action in a foreign application can be catastrophic and irreversible — sending an unfinished message, confirming a payment, deleting files, triggering a system operation, acting in the user's authenticated session. The surface's safety is the structural realization of that asymmetry over the shared policy, world-model, perception-privacy, and stuck-detection substrates; it introduces no private heuristic engine, watchdog subsystem, or monitoring store.

### 11.2 Untrusted Foreign Content

All content the surface captures from a foreign application — screen text, element names and values, extracted data, the return value of any inspection — is `untrusted_source_data` (`context.authority-classes`, File 13 §2.3) and can never, by its own text, widen a lease, lift a permission floor, lift a typed-confirmation requirement, lower a sensitivity classification, or authorize an action (`security.untrusted-content`, File 22 §12.2). An instruction found on the screen or in an element's text reaches the runtime as data the user or policy still gates, never as a command. This rule is the surface's default and is non-negotiable.

### 11.3 Destructive-Action and Sensitive-Context Escalation

The surface contributes approval-policy templates (`policy.approval-policy-templates`, File 06 §12.4) and named availability checks (`world.state-aware-capability-availability`, File 18 §9.3) that escalate by the action's blast radius, evaluated by the one policy layer:

- a state-changing action whose resolved target matches a destructive pattern — an irreversible send, delete, format, purchase, confirm, or system operation — escalates to the `Denied`-floor typed-confirmation gate (`policy.permission-floor-typed-confirmation`, File 06 §7), and because the danger is per-target rather than per-capability, an `AlwaysAllow` on the underlying action capability does not lift the destructive-target confirmation
- an action whose foreground `DesktopApplication` is in a sensitive category — a password manager, a banking, medical, payment, or user-defined sensitive application — escalates all actions in that application's context, surfacing the sensitive-context indicator and requiring explicit confirmation; the foreground-application-in-an-allowed-category named check (`world.state-aware-capability-availability`, File 18 §9.3) is the world-fact half of this, and the application-category posture composes the File 22 trust model with the surface's contributed category policy
- an action whose target window is not the foreground window escalates to confirmation showing both the targeted and the foreground window, so the agent does not act in an application the user is using without the user's awareness
- an action whose resolved dispatch is `disruptive_input` escalates according to the user's shared-control settings: active-desktop mode surfaces the real cursor, keyboard, focus, clipboard, or shared-session effect before dispatch; background mode escalates when the effect can affect the user's foreground or global session state

These are contributed posture over the one policy layer, evaluated against the world snapshot; the surface evaluates no policy itself.

### 11.4 Cascading-Damage Limits

Cascading-damage protection bounds a runaway sequence of high-blast-radius actions. A detected loop or stagnation is `run.stuck-detection` (File 04 §20.3) plus the stagnation signal (`perception.output-contract`, File 19 §9.6), which injects a corrective signal and escalates to a hard stop (§8.5). A sustained burst of state-changing actions without intervening user confirmation is governed by a configurable risk budget since the last confirmation or safe checkpoint; the budget is state-driven, using action count, destructive or sensitive target class, repeated same-resource mutation, unresolved verification failures, and loop/stagnation signals. Any elapsed-time guard is only a finite, configurable, killable safety guard — decisive without a completion signal, otherwise a last-resort backstop — never the correctness mechanism (`sandbox.resource-limits`, File 23 §9.3). The surface owns the cascading-damage posture and the entities and signals it observes; it owns no private rate-limiter watchdog or monitoring store.

### 11.5 Capture Privacy and Redaction

Screen and accessibility-tree captures of a foreign application may contain secrets and personal data; the surface consumes the perception capture-privacy contract (`perception.capture-privacy`, File 19 §10) rather than a private redaction: a sensitive-application capture is held in memory for the immediate operation and not persisted as a durable observation unless the user permits (`perception.capture-privacy`, File 19 §10.3); secret-marked fields, credential-bearing values, and detected personal data are redacted before any capture becomes a durable observation, an event, a log, an export, or a sync stream (`perception.capture-privacy`, File 19 §10.4, `secret.backend-boundary` (File 22 §4)); a value the agent types into a credential field is supplied masked and is never materialized raw (§5.5), including through clipboard-backed typing unless typed policy explicitly permits that call (§8.2); and biometric identification of any person incidentally captured is forbidden absent an explicit authorized capability and consent (`perception.capture-privacy`, File 19 §10.7). The user's per-application and per-region capture rules are perception settings (`perception.settings`, File 19 §17) composed through the surface's settings namespace (§21).

### 11.6 Boundary

This section owns the GUI Control safety posture and its mapping to canonical owners. File 06 owns the policy templates, the typed-confirmation gate, and the batched-approval flow; File 22 owns the untrusted-content rule, the secret detection, and the trust model; File 19 owns the capture privacy, sensitive-source detection, and redaction; File 04 owns the stuck detection; File 18 owns the foreground-application fact and the availability checks; File 23 owns the resource and safety guards. This file declares the posture and the mapping; those files own the mechanisms.

## 12. User Takeover and Task Control

Anchor: `gui.takeover-task-control`

### 12.1 Definition

User takeover is how the user takes manual control of a running desktop task and hands it back, and how the agent surfaces a condition it must not handle alone. It is the run `control` field plus user intervention and the elicitation handoff, not a private task store.

### 12.2 Control and Takeover

A desktop task is a run (File 04) over the GUI Control surface; the run carries the canonical `control` field (`run.minimum-durable-reconstruction`, File 04 §2.6) recording whether the agent or the user is currently driving. The user takes over through user intervention (`run.user-intervention`, File 04 §17.1): the run pauses or shifts into a user-selected shared-control behavior (`run.pause-resume`, File 04 §17.2), the agent stops emitting conflicting actions, and the user acts manually. On hand-back, the surface reconciles from the current world state and fresh observations, producing a concise summary of relevant state deltas; raw manual input recording, takeover screenshot series, or detailed action reconstruction is off by default and requires explicit consent, policy gating, visible indication, and sensitivity filtering. The user may configure per-scope shared-control behavior for active-desktop work: stop on any user mouse or keyboard input, pause and ask, yield temporarily while the user acts, or allow collaborative interleaving with clear cursor/action indication. These are control/posture settings, not autonomy fields. The user hands control back, and the run resumes from the reconciled state. The take-over affordance and the active-control indicator are presented in the activity panel (§4.2); while a run can send input to a real or shared desktop, the UI exposes an immediate stop/takeover affordance, with background mode clearly marked as presentation isolation rather than security isolation. The control transition is the canonical run control transition, never a private ownership field.

### 12.3 The Needs-Help Handoff

A condition the agent must not perform on the user's behalf — a login, a multi-factor prompt, a payment, a captcha, an operating-system permission dialog, an unknown or security-sensitive modal, or a destructive operation the user must perform — is an elicitation handoff (`controlrail.elicitation`, File 26 §13) to the user, who completes the interaction; the run then resumes with the established state. The handoff is the canonical elicitation rail, not a private modal subsystem; the surface declares which conditions trigger a handoff and what the user is asked to do.

### 12.4 Boundary

This section owns the takeover and handoff workflow. File 04 owns the run, the `control` field, intervention, and pause-resume; File 18 owns the world-state reconciliation; File 26 owns the elicitation rail. This file presents them as the takeover and needs-help affordances.

## 13. Sandbox, Isolation, and the Operating Modes

Anchor: `gui.sandbox-isolation-modes`

### 13.1 Definition

The GUI Control surface runs all confined execution through the one `Sandbox` contract and declares graphical-control `SandboxProfile`s for its operating modes. The surface owns no private sandbox; the modes are profiles at canonical isolation tiers, and the visual separation of the agent's work from the user's is a presentation facet, not a security tier.

### 13.2 The Operating Modes as Isolation Tiers

The GUI Control surface declares its operating modes as graphical-control `SandboxProfile`s over the one `Sandbox` contract (`sandbox.contract`, File 23 §3), mapped onto the canonical `IsolationTier` (`sandbox.isolation-tiers`, File 23 §4):

- **active-desktop** — the agent operates the user's real session, sharing the real desktop, windows, and input; the `IsolationTier` is `None` (`sandbox.isolation-tiers`, File 23 §4.1 — "active-desktop graphical control where the agent operates the user's real session"); the only protections are the application-layer policy and approval posture (§11) and the user's ability to take over (§12)
- **background** — the agent's work is visually separated from the user's through window cloaking and virtual-desktop placement so it does not disrupt the user's foreground, but it shares the same registry, environment, filesystem, network, process table, clipboard, global shortcuts, notification area, temporary locations, single-instance application locks, and other session-global state; the `IsolationTier` is `None` with a presentation overlay (`sandbox.isolation-tiers`, File 23 §4.3), and the cloaking is presentation, not containment
- **virtualized** — the agent operates a separate execution environment (a virtual machine or equivalent) with its own operating system; the `IsolationTier` is `Virtualized`, with a separate-kernel realization where policy or the trust class requires a kernel boundary; this is the mode for untrusted automation or for a desktop the user must not be in

The surface presents the mode as a workflow and presentation choice; the isolation tier, the confinement, and the kill semantics stay File 23's. Untrusted code or an untrusted application runs at the tier its trust class requires and never below it (`sandbox.isolation-tiers`, File 23 §4.3); the background mode's presentation overlay is never presented as a security boundary. When shared-session leakage matters, the run uses virtualized mode or explicit application-profile isolation.

### 13.3 Window Cloaking Is Presentation, Not Security

The background mode's window cloaking and virtual-desktop placement are a presentation facet the surface owns, not a security tier (`sandbox.isolation-tiers`, File 23 §4.3). A run that requires a real isolation boundary uses the virtualized mode; a run in the active-desktop or background mode has `None` security isolation and is governed by policy, approval, and the user's control, not by the visual separation. This is load-bearing: presenting cloaking as containment would misrepresent an unisolated session as isolated.

### 13.4 Launched Applications and Privileged Operations

A foreign application the surface launches is a `ManagedProcess` in a `ProcessGroup` confined by the active mode's `SandboxProfile` (`process.spawning`, File 23 §5, `process.groups` (File 23 §6)), killable categorically and individually (`process.killability`, File 23 §10), spawned with an explicit program, an environment allowlist, and an explicit application-profile binding: reuse the user's current profile, use an isolated agent profile, use a workspace-scoped profile, or use a disposable profile. Background and unattended automation default away from silently reusing the user's primary profile when a separate profile is available; reusing the primary profile remains an explicit user and policy choice. GUI Control may terminate processes it launched under this model; arbitrary process kill, service management, daemon control, and force-termination of applications it did not launch belong to System Agent or File 23 capabilities borrowed or rerouted under policy. A privileged desktop operation the user authorizes — one requiring administrator or superuser rights — crosses the elevated-helper boundary (`sandbox.elevated-helper`, File 23 §11) under the policy floor and typed confirmation; the main process never elevates, and no agent, adapter, or automation drives the helper through ordinary capability paths.

### 13.5 Boundary

This section owns the operating-mode declaration and the presentation-isolation rule. File 23 owns the `Sandbox` contract, the `IsolationTier` ordinal, the `ManagedProcess`/`ProcessGroup` model, the confinement and kill semantics, and the elevated-helper process. The per-platform virtual-desktop, window-cloaking, and virtualization mechanisms are replaceable implementations behind the contract; this file maps the modes onto the tiers and owns the presentation facet.

## 14. Cross-Platform Realization and First-Run Setup

Anchor: `gui.cross-platform-setup`

### 14.1 Definition

The GUI Control surface is cross-platform-first-class: its contract is platform-invariant over replaceable per-platform accessibility, input, and capture mechanisms, and a capability whose platform mechanism is absent reports unavailable rather than failing the surface. The first-run permission and setup flows are part of the contract.

### 14.2 Platform-Invariant Contract Over Replaceable Mechanisms

The desktop platforms — and the desktop-class platforms the surface targets — are first-class; no platform is the canonical mechanism (`sandbox.cross-platform`, File 23 §15, `perception.per-modality-contracts` (File 19 §7.2)). The accessibility/automation interface, the input-injection mechanism, the screen-capture mechanism, the window and virtual-desktop facilities, and the privilege-elevation facility are replaceable implementations behind the sensor, action, and sandbox contracts; the surface depends on the contract, never on a platform-specific facility the contract does not expose. A capability whose mechanism a platform lacks — input injection without a display-server input mechanism, virtual desktops on a platform without them — is registered only where its mechanism is available and reports unavailable elsewhere (`sandbox.cross-platform`, File 23 §15.3, `world.environment-temporal-connection-facts` (File 18 §6.4)). The mobile subset excludes the desktop-control capabilities where the platform does not host them.

### 14.3 First-Run Permission and Setup

Desktop observation and control require operating-system permissions and, on some platforms, a display-server input mechanism that is not present by default. The surface consumes the perception permission model (`perception.capture-privacy`, File 19 §10.1): a sensor whose accessibility, screen-capture, or input permission is not granted reports `PermissionRequired`, and the permission acquisition is an explicit flow the surface surfaces with a clear explanation of why the permission is needed. A hardware- or display-server-dependent capability — an input daemon requiring a kernel device, a platform requiring an accessibility service be enabled — is detected at first use and surfaced as a setup step (`sandbox.cross-platform`, File 23 §15.4), with the dependent capability disabled until setup completes and the independent capabilities continuing. The surface may guide the user, open the relevant system-settings location where the platform permits, and verify completion after the user acts; it must not silently grant permissions, install helpers, approve accessibility access, or drive elevated prompts by GUI-puppeting the operating system. Setup steps are capability and policy flows with typed outcomes. The `availability_predicate` and the named availability checks (§5.5) gate the surface and its capabilities on the current permission and platform state.

### 14.4 Multi-Monitor and Scale Factors

A desktop spans displays with differing geometry and scale factors; the surface consumes the perception coordinate-space and fidelity contract (`perception.capture-pipeline`, File 19 §6.5): a capture records its display geometry, resolution, scale factor, and the multi-display arrangement, and the `Display` and `VirtualDesktop` world entities (`world.world-entity`, File 18 §4.3) carry the per-display geometry and assignment. An action's coordinate mapping (§8.3) uses the captured per-display scale factors, so a click on a high-density display maps correctly to physical pixels and a window movement across displays with differing scaling is handled, not assumed.

### 14.5 Boundary

This section owns the cross-platform stance and the first-run setup workflow. File 23 owns the cross-platform realization and the per-platform mechanism resolution; File 19 owns the permission model, the coordinate-space recording, and the capture mechanisms; File 18 owns the display entities and the platform facts. The per-platform accessibility, input, capture, virtual-desktop, and elevation mechanisms are replaceable implementations behind the contracts.

## 17. Rails and Control Affordances

Anchor: `gui.rails`

### 17.1 Definition

The GUI Control surface declares its control affordances — the user-facing ways to invoke its capabilities — and binds them to the control rails (`controlrail.consequences-for-later-specs`, File 26 §21). It declares which capabilities bind to which default shortcuts, slash commands, and menu entries, registers surface-scoped keybinding contexts and custom commands, and introduces no private rail, invocation registry, or rail autonomy field.

### 17.2 Slash, Custom Commands, Keybindings, and the Palette

The GUI Control surface's control affordances include slash commands resolved through the slash-command rail (`controlrail.consequences-for-later-specs`, File 26 §21) — representatively control, automate, record-macro, and inspect commands — and workspace-local custom commands stored in the workspace `.atlas/commands/` directory (`workspace.internal-layout`, File 24 §8.3), each a declarative definition resolved through the capability system, never an out-of-band execution path. The surface registers surface-scoped keybinding contexts the keymap resolves chords against (`controlrail.consequences-for-later-specs`, File 26 §21): representatively a screen-view context (stop the task, take over), an inspector context (inspect element, compare captures), and a macro context (start and stop recording, play). Its capabilities and custom commands surface in the command palette through the command rail's palette lens (subsystem-neutral, searching the available-capability list). The surface declares the default desktop-control workflow commands — representatively automate a desktop task, record a macro, inspect a window, and extract content from the screen — as capabilities and command definitions reachable through every rail. The handsfree and voice rail may drive the surface's capabilities as full capabilities (`controlrail.voice-rail`, File 26 §9 — voice and handsfree are `UiMode`s (`world.surface-state`, File 18 §5.5), not a separate path), and a scheduled or event-triggered desktop task is a `Trigger`-rail entry (§2.8). Voice and external-protocol invocation of GUI capabilities are the rail layer's.

## 18. Cross-Surface Composition

Anchor: `gui.cross-surface`

### 18.1 Definition

Cross-surface composition is how the GUI Control surface composes with other surfaces: the GUI Control capabilities other surfaces borrow, the captured content that composes into other surfaces' outputs, the surface boundaries it respects, and the capabilities it borrows in place.

### 18.2 GUI Control Capabilities Borrowed by Other Surfaces

The GUI Control capability family is excluded from the Coder, Web, Data Processor, Teacher, and System Agent surfaces' default loaded zones (`coder.actions-declaration` (File 27 §5.2), `web.actions-declaration` (File 28 §5.2), `data.actions-declaration` (File 29), `teacher.actions-declaration` (File 30), `sys.actions-declaration` (File 32 §5.2)) and reached only by explicit borrow (`surface.subsystem-surface-spec`, File 07 §5.5) with a typed denial where policy forbids (`policy.approval-flows`, File 06 §5.1). A surface that genuinely needs to drive a desktop application — the Teacher surface demonstrating software interactively, the Data Processor surface extracting from a desktop application with no other interface — borrows the GUI Control capability in place under the GUI Control approval posture and sandbox, with the ledger recording the cross-surface reach; the borrowing surface's workflow is its own, the GUI Control surface owns the capability.

### 18.3 Captured Content Composes Across Surfaces

Captured desktop content — extracted data, `ScreenshotSeries` artifacts, `AccessibilityTreeSnapshot` observations — composes into other surfaces' outputs through the one block and entity pools (`block.cross-surface-composition`, File 08 §12.3, `artifact.cross-surface-interoperability` (File 09 §17.3)): an extracted table flows into a Data Processor dataset, a captured screen series into a Teacher lesson, a captured value into a report. Cross-surface composition is a property of the shared pools, not a GUI-private integration.

### 18.4 Surface Boundaries and Borrowing in Place

The GUI Control surface drives the desktop and foreign applications. It does not define browser-page semantics: when a target window hosts a browser page and a `BrowserPage` sensor or Web capability is available, the page is handed to Web by reroute or borrow (§6.3, `routing.mid-execution-reroute` File 03 §12). If Web semantics are unavailable, GUI Control may interact with the visible page-like region only as opaque desktop content and untrusted captured data, never as DOM, browser session, cookie, network, page-script, or browser-history state. It also does not perform operating-system-level operations: System Agent operates at the operating-system level while GUI Control puppets applications; arbitrary process kill, service management, daemon control, and OS configuration are System Agent/File 23 capability paths, not GUI-private actions. A GUI Control run that needs a capability outside the surface — file create to save an extract, the coder code-execution capability to compute over captured state, web fetch to read help for an unfamiliar interface, memory recall of a known-application workflow, data processing, or lesson generation — borrows it in place and remains in the GUI Control surface (§5.4); it reaches another surface's workflow only through a routing reroute or explicit user override, never by silent surface change.

### 18.5 Boundary

This section owns the GUI cross-surface composition. File 07 owns borrowing; Files 08 and 09 own the shared pools; File 03 and File 04 own reroute; the Web and System Agent surfaces own the browser-page and operating-system boundaries. The borrowing surfaces own their own workflows.

## 19. World-Model, Perception, and Observation Integration

Anchor: `gui.world-perception`

### 19.1 Definition

The GUI Control surface integrates with the world model and perception by self-registering its panels and state, contributing the world facts its work observes, exposing the sensors it consumes, and producing the observations its runs depend on — all through the canonical contracts (`worksurface.world-perception-integration`, File 25 §15).

### 19.2 Self-Registration and World Facts

The GUI Control surface self-registers its panels, focus, and selection to the one world model on mount, focus, and content change, and unregisters on unmount (`world.observation-state-update`, File 18 §8.1); a panel it fails to register is a blind spot. Its own panels' state is learned through self-registration, never through perception screen-scraping (`perception.tiered-sensing`, File 19 §5.4), and Atlas-owned windows are marked from self-registration and process identity so GUI Control can omit them from its foreign-application target projection and block self-interaction (§8.1). The desktop entities its work observes — `DesktopWindow` (title, application reference, bounds, focus and minimized state, display reference), `DesktopApplication` (process relation, executable identity, lifecycle, sensitive-category classification), `Display` (geometry, resolution, scale factor, arrangement), `VirtualDesktop` (assignment and display references), `Device`, `Process`, and `Sandbox` — are the canonical entity kinds File 18 already declares (`world.world-entity`, File 18 §4.3); the surface contributes their observed facts through perception, not a private store, and the foreground application is the canonical environment fact (`world.environment-temporal-connection-facts`, File 18 §6.1). The world model holds the live values; the surface produces the observations that update them, and is never screen-scraped to learn its own state (`world.explicit-rejections`, File 18 §16).

### 19.3 Sensors and Observations

The GUI Control surface declares the sensors it exposes — the `DesktopAccessibilityTree` sensor (the structured element tree), the `Screen` sensor (a screenshot for the grounded and raw tiers and the screen view), and the `Environment` sensor (the foreground application, display geometry, and permission states) — and consumes their structured output (`perception.consequences-for-later-specs`, File 19 §19); perception owns the capture mechanics, the sensitive-source detection, the redaction, and the consent, and the surface owns no private capture pipeline (`perception.explicit-rejections`, File 19 §18). It is structured-data-first: it observes through the accessibility/automation tree, capturing a screenshot only for a vision consumer, visual evidence, or coordinate grounding (§6). It produces `AccessibilityTreeSnapshot` and `Screenshot` observations through the canonical `observation.commit` path (§5.3) where a run depends on them for revalidation or replay; transient captures remain transient until a captured state is deliberately committed as an observation.

### 19.4 Availability

The GUI Control surface's available-action list is the available-capability list the world model's availability evaluator computes for the surface's scope (`world.state-aware-capability-availability`, File 18 §9), filtered by the active surface state, the granted permissions, and the platform; the surface registers the named availability checks of §5.5 (the accessibility-permission, input-mechanism, display-server, active-window, foreground-category, vision-model, and known-adapter checks) and maintains no private available-action store.

### 19.5 Boundary

This section owns the GUI world-model and perception integration. File 18 owns the entity catalogue, self-registration, durability tiers, and availability evaluator; File 19 owns the sensors, capture, privacy, and redaction; File 09 owns the observation blocks; File 23 owns the process and sandbox snapshots. This file integrates through them.

## 20. Persistence, Locality, and Portability

Anchor: `gui.persistence-locality`

### 20.1 Definition

The GUI Control surface's durable state persists as substrate families through the one storage contract, splits by locality the way a workspace's does, and moves cross-installation through the canonical portability mechanisms. The surface introduces no private durable store.

### 20.2 What Persists and Where

The surface's durable state — its registered `SurfaceContract` versions, its registered `Custom` kinds and application adapters, its scoped enable state and settings, its recorded macros, and the blocks, artifacts, versions, committed observations, and extracted content its work produces — persists as substrate families and content-addressed blobs through the storage contract (`storage.durable-substrate`, File 20 §3, `storage.consequences` (File 20 §18)); captured screens resolve from the content-addressed blob store (`storage.blob-store`, File 20 §6). The surface's live state — active panels, focus, selection, the active target window, the live captures, the structured-state cache, sandbox and process handles, and the loaded grounding model — is computed and rebuilt from self-registration and the version-graph projection, never a durable fact (`worksurface.persistence-locality`, File 25 §16.1); its loss is a rebuild, never data loss.

### 20.3 Locality

The GUI Control surface's identity splits by locality the way a workspace's does (`worksurface.persistence-locality`, File 25 §16.2, `workspace.locality` (File 24 §4)): the surface's logical declaration, its recorded macros (as element-based definitions), portable application-adapter declarations and metadata, and its saved extracted content sync, while device-bound runtime state — the live desktop, windows, displays, sandboxes, processes, virtual desktops, captures, executable adapter mechanisms, native hooks, local processor bindings, device-specific paths, and the loaded grounding model — is device-local and rebuilds, installs, or re-captures per device and never syncs as ordinary data (`portability.what-replicates`, File 21 §5 — displays, windows, sandboxes, and capture state never sync). A macro or adapter that depends on a device-specific application, executable mechanism, or path syncs as a definition; activation on another device revalidates the application, permissions, platform, source approval, sandbox profile, and availability before use. No raw secret, credential, or unredacted sensitive capture is materialized, exported, or synced (`secret.backend-boundary`, File 22 §4, `perception.capture-privacy` (File 19 §10.4)).

### 20.4 Portability

The surface's durable state rides the syncable substrate and the `PortablePackage` for cross-device and cross-installation movement (`portability.consequences`, File 21 §18); a recorded macro, an extracted artifact, and a saved capture export losslessly with the content-addressed blobs they reference, unless policy or sensitivity filtering omits them with typed provenance gaps. The structured-state cache and the loaded grounding model are rebuilt or reloaded on receive, never transported. The surface may declare a lossy convenience export (a rendered screenshot series or a macro listing), but it passes through egress governance, audit recording, and sensitivity filtering (`security.egress-governance`, File 22 §11) and uses no private export path. Every hash the surface relies on — a capture content hash, a blob address, a staleness fingerprint, an export-bundle hash — is computed over a declared `CanonicalEncoding`, never physical bytes (`core.canonical-hash`, File 01 §7.14); the surface defines no new canonical hash.

### 20.5 Boundary

This section declares the GUI persistence and locality classification. File 20 owns the storage substrate, the blob store, and rebuild orchestration; File 21 owns replication and the package; File 22 owns the secret and egress boundaries; File 24 owns the workspace locality split; File 11 owns the version-graph projection.

## 22. Explicit Rejections

Anchor: `gui.explicit-rejections`

The following are architecturally invalid for the GUI Control surface and for any later spec that extends it:

- **A private desktop-state model, screenshot-primary sensing, or a private capture pipeline** — desktop state is read structured-first through `Perception`'s `DesktopAccessibilityTree` sensor and the tier strategy; a screenshot is the grounded/raw fallback tier, never the primary representation, and the surface owns no capture mechanics (§6; `perception.tiered-sensing`, File 19 §5, `perception.explicit-rejections` (File 19 §18)).
- **A blind coordinate click as the action model** — a desktop action is observation-grounded, policy-gated, verified, and recorded; an element-grounded reference is preferred, a coordinate is a fallback, and a vision-grounded coordinate is the final fallback, mapped from its recorded coordinate space to screen pixels before dispatch (§7, §8; `perception.capture-pipeline`, File 19 §6.5).
- **A silent coordinate-space mismatch** — a model-produced coordinate is mapped from its recorded coordinate space through the declared scale factors before dispatch; a coordinate in an unrecorded or unresolvable space is a typed error, never a blind dispatch (§8.3).
- **A private GUI sandbox abstraction, a private process spawner, or a private kill path** — all confined desktop execution runs through the one `Sandbox` contract and the `ManagedProcess`/`ProcessGroup` model; the surface extends the base contract only with its graphical-input and screen-observation capability surface (§13; `sandbox.explicit-rejections`, File 23 §20).
- **Presentational isolation presented as a security tier** — the background mode's window cloaking and virtual-desktop placement are presentation, not containment; the active-desktop and background modes have `None` security isolation, and untrusted automation runs at the `Virtualized` tier (§13; `sandbox.isolation-tiers`, File 23 §4.3).
- **A private action wire format, a private provider-adapter registry, or a private coordinate-normalizer registry baked into the canonical semantics** — the action format and the provider-specific coordinate handling are capability-declaration and implementation concerns behind the action and grounding capabilities; the model and provider selection are Files 16 and 17's (§8; `model.consequences-for-later-specs`, File 16 §16, `provider.consequences-for-later-specs` (File 17 §26)).
- **A private application-adapter registry or a parallel automation engine** — an application adapter is a registered extension over the generic perception-and-action substrate, riding the one capability registry and the proposal-first registration; generic accessibility is the default and vision the final recovery tier (§9; `capability.consequences-for-later-specs`, File 05 §20).
- **A private GUI task store, ownership field, or watchdog/monitoring subsystem** — a desktop task is a run with the canonical `control` field; takeover is run intervention and pause-resume; the needs-help condition is an elicitation handoff; cascading-damage protection is stuck/stagnation detection plus a state-driven risk budget; the surface owns no private task store, rate-limiter watchdog, or monitoring store (§11, §12; `run.consequences-for-later-specs`, File 04 §29, `world.explicit-rejections` (File 18 §16)).
- **Authority granted by captured foreign content** — text or values captured from a foreign application's screen or accessibility tree hold no capability or policy authority; all captured foreign content is `untrusted_source_data` (§11; `security.untrusted-content`, File 22 §12).
- **The agent interacting with Atlas's own windows through GUI Control** — this is a self-interaction loop; Atlas state is managed through Atlas capabilities, settings APIs, rails, and substrate projections, never by puppeting its own UI (§8.1, §19.2).
- **A per-tool `AlwaysAllow` lifting a destructive-target confirmation, or a destructive or sensitive-context action without the typed-confirmation gate** — the danger is per-target, so a destructive target, a sensitive-application context, or an out-of-focus target escalates to the `Denied`-floor typed-confirmation gate regardless of an `AlwaysAllow` on the underlying capability (§11; `policy.permission-floor-typed-confirmation`, File 06 §7).
- **Persisting an unredacted secret or sensitive capture, or performing biometric identification** — secret and personal captures are held in memory for the immediate operation and redacted before any persistence; a sensitive-application capture is not durably persisted absent user permission; biometric identification is forbidden absent an explicit authorized capability and consent (§11; `perception.capture-privacy`, File 19 §10, `secret.backend-boundary` (File 22 §4)).
- **Raw takeover capture or keylogging as the default hand-back mechanism** — takeover reconciles from current world state and fresh observations by default; raw manual input recording or detailed user-action reconstruction requires explicit consent, visible indication, policy gating, and sensitivity filtering (§12).
- **A GUI autonomy, participation, interaction-shape, persona, or mode field** — at any layer, in any form; GUI autonomy is capability permission tiers, leases, and approval posture plus user direction, progressive disclosure is which panels and view preset are open, the operating mode is a sandbox profile, and the `plan` capability is a tool, not a phase machine (§13, §16.2; `worksurface.no-autonomy-field`, File 25 §13). There is no planner-versus-executor model split, no participation level, and no `Drive`/`Supervise`/`Collaborate`/`Delegate` dial.
- **A fixed post-action delay as the readiness mechanism, or time-based behavior as a correctness condition** — readiness, document-change, and idle observation are event-first; the only permitted timers are the finite, configurable, killable wall-clock and cascading-damage safety guards (`sandbox.resource-limits`, File 23 §9.3 — decisive only without a completion signal, otherwise a last-resort backstop); a captured-state staleness bound is a flagged fallback only where a source emits no change event (§6.5, §8.5, §11.4; `perception.triggers`, File 19 §8, `sandbox.resource-limits` (File 23 §9.3)).
- **A view preset that silently changes backend policy** — applying a GUI layout preset changes presentation only and never silently changes model selection, context policy, execution entry, budget, sandbox profile, operating mode, or approval posture (§16.2; `worksurface.views-presets`, File 25 §7.2).
- **A parallel macro, capture, history, or action-log store** — a macro is a `Macro` artifact, captured state is an `Observation`, a captured series is a `ScreenshotSeries` artifact, and task and action history are version-graph and ledger projections; the surface introduces no parallel store (§4, §10; `version.explicit-rejections`, File 11 §23, `artifact.consequences-for-later-specs` (File 09 §22)).
- **Driving the browser's page or performing operating-system-level operations through a GUI-private path** — the GUI Control surface drives the desktop and foreign applications; a browser's page is the Web surface's (handed to the `BrowserPage` sensor and reached by reroute or borrow), any page-like GUI fallback is opaque desktop control only, and operating-system-level operations are the System Agent surface's (§18; `web.cross-surface`, File 28 §18.4).
- **A Windows-primary or single-platform framing** — the desktop platforms are first-class over replaceable per-platform mechanisms; a capability whose platform mechanism is absent reports unavailable rather than failing the surface (§14; `sandbox.cross-platform`, File 23 §15).
- **Naming a specific accessibility/automation engine, input mechanism, screen-capture mechanism, grounding model, optical-character-recognition engine, or virtual-desktop facility as the canonical semantics** — these are replaceable implementations behind the surface's sensors, processors, and capabilities; the canonical contract is the behavior, never the library (Source Resolution; `core.extension-integrity`, File 01 §7.10).

## 23. Consequences for Later Specs

Anchor: `gui.consequences-for-later-specs`

Later specs must follow these rules:

- The **System Agent** per-surface spec declares its own `SurfaceContract` to File 25's shape, the same way this file does for GUI Control; it operates at the operating-system level while the GUI Control surface puppets applications, and the two compose through borrow and reroute, not a shared private mechanism. The other per-surface specs (Coder, Web, Data Processor, Teacher, and System Agent) keep the GUI Control capability family out of their default loaded zones and reach it only by explicit borrow under the GUI Control approval posture and sandbox (§18).
- The **Automation and Triggers** spec owns the deep mechanics of the scheduled and event-triggered desktop tasks this file frames as `Trigger`-rail entries (§2.8): scheduling, eligibility, enablement, and non-interactive-execution safety for a desktop task, confined to the narrowest graphical-control sandbox profile (preferring the background or virtualized mode for unattended work), pinning the GUI Control surface and its policies at save time the way routing does, and never spawning an untracked or non-killable process or escalating privilege without the user; it introduces no parallel GUI execution path.
- The **Workflows, Templates, and Reuse** spec treats the GUI default workflows (§17.2), custom commands (§17.2), and recorded macros (§10) as reusable workflow and command definitions, and treats a successful desktop-control run as a promotable workflow; a recorded macro that warrants durable identity is already a `Macro` artifact version.
- The **Extension and Plugin System** and **MCP and External Integrations** specs may contribute GUI capabilities, application adapters, grounding-model backends, and per-platform accessibility, input, and capture mechanisms through the proposal-first registration and source-approval path; a plugin-contributed GUI capability or application adapter participates in the one registry, policy layer, sandbox, perception substrate, and ledger exactly as a built-in does, and its contributed policy defaults are narrowing-only.
- The **UI Shell, Layout, Presentation, and Interaction Models** and **UI Customization, Widgets, and Theming** specs render the GUI panels — the screen view with the element overlay, the element-tree inspector, the activity feed, the action log, the macro library, and the view presets — over the data and behavior contracts this file fixes; presentation may vary freely, the work model cannot. They must surface active desktop control, disruptive input, user takeover, and background-mode presentation-is-not-security status with immediate stop/takeover affordances. The accessibility/automation engine, the input mechanism, the screen renderer, the element-overlay geometry, and the grounding model are their implementation choices behind the panels and capabilities.
- The **Quality Control and Validation** spec registers GUI validators (post-action verification checks, macro-replay validation, and adapter-postcondition checks) producing `Validation`/`Critique`/`Observation` blocks and integrating through the completion-verification hook surface and the event and capability hooks, not a separate pipeline; it consumes the observe-act-verify contract (§8).
- The **Telemetry, Logging, and Observability** spec consumes the GUI events and the per-call attribution this file and File 10 emit; it renders the GUI task inspector from the version graph, ledger, and observation handles, never by re-capturing the desktop or re-dispatching an action for a historical view.
- The **Runtime Infrastructure and Lifecycle** spec orchestrates GUI Control surface, graphical-control sandbox, launched-application, and grounding-processor startup and reconstruction around the storage lifecycle File 20 owns, reaping orphaned GUI processes, sandboxes, and grounding-model subprocesses at restart rather than reconnecting, and rebuilding the live captures and the structured-state cache as projections; it reimplements no GUI execution, capture, or isolation.
- The **Evaluation and Benchmarking** spec verifies the GUI round-trips — capture-to-structured-observation-with-fingerprint, element-grounded action-to-verified-effect, the coordinate-space mapping, the observe-act-verify loop, the destructive-action, disruptive-input, and sensitive-context escalations, the user-takeover-and-resume, the self-interaction block, the macro-record-and-revalidating-playback path, and the adapter-first fallback chain — replaying over recorded observations and immutable references, not a live desktop, and verifying that no captured foreign content escalated authority, that no destructive target bypassed confirmation, that no Atlas-owned target was puppeted through GUI Control, and that no historical replay re-captured or re-dispatched against a live application (the GUI perception/action evals `codex_recommendations.md` §1980 names).
- The **Packaging, Platform, and Distribution** spec ships the built-in declarations for the canonical GUI capabilities, the GUI Control `SurfaceContract`, the GUI `Custom` event and observation kinds, and the default GUI settings as the `Builtin` source on each desktop platform, packages the per-platform accessibility, input, capture, virtual-desktop, and virtualization mechanisms and any guest agent behind their contracts, auto-downloads rather than bundles large local grounding models, and excludes the desktop-control capabilities from the mobile subset where the platform does not host them.
